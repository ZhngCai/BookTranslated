# 第 10 章　评估多智能体系统

本章涵盖：

- 理解我们真正在评估什么：多智能体轨迹——推理和动作的序列
- 构建跨模型、智能体和多智能体系统都适用的评估指标与评判器
- 实现一个与我们 picoagents 框架集成的实用评估库
- 为复杂多智能体任务规划有效的评估策略

## 10.1 引言

当你设计一个多智能体系统来应对任务时，例如"构建一个股票交易移动应用"，你的智能体会探索一系列动作——它做各种事情，然后可能宣布任务完成。但你如何真正验证或评估它的表现？只关注最终交付物——应用能用吗？——很有诱惑力，但这错过了展开的丰富问题解决过程：步骤或个体智能体之间的规划讨论、迭代的代码生成、调试回合，以及导致成功或失败的协调决策。

在本章中，我们将构建一个捕获这一完整图景的评估框架。我们不会把评估当作事后想法，而是让它成为 picoagents 库的核心组件——支持从简单模型调用到复杂自主编排的一切的系统化评估。

关键洞见是：无论你评估的是单个模型、一个智能体还是完整的多智能体工作流，你从根本上评估的是同一件事：**轨迹**（trajectory）——随时间展开的推理消息和动作序列。这种统一视角使我们能够在不同复杂度级别上应用一致的评估方法。

## 10.2 评估驱动的开发

在我与构建智能体或多智能体系统的团队合作的经验中，我看到的一个常见错误是评估在开发过程中被考虑得太晚。使用智能体的兴奋或炒作似乎常常分散了对仔细整体开发策略的探索——为了帮助解决这个问题，我经常推荐我所说的**评估驱动的开发**（evaluation-driven development）。

评估驱动的开发意味着在构建系统之前定义你将如何衡量成功。像测试驱动开发（TDD）——先写测试再写代码——你在实现智能体行为之前建立成功标准、指标和评估基础设施。

正如 TDD 测试澄清需求并指导实现，评估标准迫使你阐明"好"在你的领域意味着什么。如果你要衡量推理效率，你会从第一天起构建 Token 跟踪。如果你要比较工具调用序列，你会在框架中设计可观测性。评估约束成为设计要求。

> **轻松评估的力量**
>
> 正如 Eugene Yan 观察到的："我发现，一旦你设置了评估 + 实验框架，并让调整配置和提示词变得容易（一键运行 + 评估），团队就会喜欢运行实验并爬升这些数字，进步就会很快到来。"
>
> 这凸显了为什么尽早构建评估基础设施能带来回报——当实验没有摩擦时，团队自然会更快迭代并发现更好的解决方案。

### 10.2.1 评估规划框架

在构建 AI 智能体或多智能体系统的匆忙和兴奋中，我不幸看到许多团队直接跳入编写智能体代码或尝试框架。这通常是个错误。实际上，编写智能体应该晚得多——首先你需要非常清楚你将如何评估成功。

为了帮助指导这个过程，这里有一个简单的 5 步评估规划框架。在编写智能体代码之前，先完成这五个规划问题。本章其余部分提供回答每个问题所需的工具和技术。

| 步骤 | 规划问题 | 关键考虑 | 详见 |
| --- | --- | --- | --- |
| 1 | 定义成功标准 | 成功是什么样子？哪些维度最重要（准确性、速度、用户体验）？你将如何衡量改进？ | 基于参考 vs 无参考指标（10.5 节） |

## 10.3 我们评估什么：多智能体轨迹

每次运行智能体或多智能体系统时，你都会生成一条轨迹——为应对任务而采取的推理和行动的完整记录。这条轨迹包括：

- **消息**：用户、智能体和工具之间的对话流
- **动作**：工具调用、函数执行和外部交互
- **结果**：成功/失败状态、遇到的错误和最终结果
- **元数据**：计时、Token 使用和执行上下文

考虑这个简单示例：

```
任务："巴黎的天气怎么样？"
轨迹：
用户：巴黎的天气怎么样？
智能体：我需要获取当前天气数据。让我调用天气 API。
工具调用：get_weather(location="Paris")
工具结果：{"temp": 22, "conditions": "sunny"}
智能体：巴黎目前天气晴朗，温度 22°C。
```

这条轨迹讲述完整的故事——不仅是最终答案，还有智能体如何推理、使用了什么工具，以及方法是否有效。

现在考虑一个更复杂的多智能体场景：

```
任务："创建一个简单的计算器 Web 应用"
轨迹（简化）：
用户：创建一个简单的计算器 Web 应用
规划智能体：我将把它分解为前端和后端任务...
前端智能体：我将创建一个带基本操作的 HTML 界面...
后端智能体：我将实现计算逻辑...
[50+ 条迭代开发、测试、调试消息]
系统：任务成功完成。计算器应用已部署。
```

轨迹捕获了智能体之间的协调、迭代细化过程和涌现的解决方案——如果我们只评估最终交付物，这些信息就会丢失。

### 10.3.1 在代码中表示轨迹

在我们的 picoagents 库中，我们用简单的数据结构表示轨迹：

```python
from picoagents.types import (
    RunTrajectory,
    Task
)
class RunTrajectory:
    # What we're trying to solve
    task: Task
    # Complete conversation history
    messages: Sequence[Message]
    # Did we complete the task?
    success: bool
    # Error details if failed
    error: Optional[str]
    # Resource consumption metrics
    usage: Optional[Usage]
    # Additional execution context
    metadata: Dict[str, Any]
```

此结构无论你评估的是单个模型调用还是复杂的多智能体工作流都适用。消息捕获推理过程，而元数据提供执行上下文。

### 10.3.2 可观测性作为基础

> **可观测性使评估成为可能**
>
> 构建评估就绪的系统需要从第一天起考虑可观测性。当你的智能体在执行期间发出结构化事件（使用 OpenTelemetry 等标准）时，你可以重建完整轨迹进行评估，而无需专门为评估运行。这意味着每次生产运行都可能成为评估数据点。
>
> 我们的 picoagents 库设计上采取可观测性优先的方法：
>
> - **结构化消息日志**：每次交互都带时间戳、元数据和上下文被捕获
> - **用量跟踪**：Token 消耗、API 调用和执行时间被自动记录
> - **错误传播**：失败以完整上下文记录，而非静默失败
> - **执行轨迹**：完整轨迹可以回放和分析
>
> 这种对可观测性的前期投资在评估期间带来回报。当多智能体系统失败时，你可以准确追踪在哪里以及为什么——是推理错误、工具调用失败还是智能体协调问题？更重要的是，你可以通过从记录的事件重建轨迹，追溯性地评估任何过去的执行。

### 10.3.3 答案提取挑战

在评估真实智能体对话时，一个微妙但关键的挑战出现了：实际答案在哪里？

考虑一个使用工具的智能体：

```
智能体："让我计算：2+2"
工具："计算器结果：4"
智能体："计算完成。"
```

哪条消息包含答案？采用最后一条消息的朴素方法得到"计算完成"——完全错过了实际结果。

我们的评估系统通过答案提取策略解决这个问题：

```python
from picoagents.eval import ExactMatchJudge
# Use last non-empty message (default)
judge = ExactMatchJudge(
    answer_strategy="last_non_empty"
)
# Use only last assistant message
judge = ExactMatchJudge(
    answer_strategy="last_assistant"
)
# Concatenate all assistant messages
judge = ExactMatchJudge(
    answer_strategy="all_assistant"
)
```

这个看似微小的细节防止了评估失败，否则会让你的指标在生产中不可靠。

> **评判器需要从轨迹中获得什么**
>
> 不同的评估场景需要从轨迹中获得不同的信息。基于参考的评判器需要访问预期输出（来自任务定义）和实际输出（使用答案策略从智能体消息中提取）。评估响应质量的 LLM 评判器需要任务输入来理解请求了什么、智能体的响应来评估质量，有时评估多轮交互时还需要对话历史。
>
> 使用工具的智能体带来额外的复杂性——你可能需要检查的不仅是最终响应，还有调用了哪些工具以及使用了什么参数。我们的答案提取策略处理常见情况，但对于专门的评估需求，你可以创建直接检查 trajectory.messages 中消息序列的自定义评判器，提取你的评估标准所需的准确信息。

## 10.4 设计评估套件

为多智能体系统构建有效评估从根本上是一个创造性的设计问题。与传统的机器学习系统——BLEU、ROUGE 或 NDCG 等既定指标提供标准化衡量——不同，智能体式系统产生的结果抗拒简单的量化。解决软件工程任务的智能体轨迹，与生成数据可视化或进行市场研究的智能体轨迹看起来完全不同——然而三者都需要严格的评估。

这既是挑战也是机遇。挑战在于你不能简单地伸手去拿现成指标。机遇在于深思熟虑的评估设计成为竞争优势——开发与专家判断对齐的领域特定评估套件的团队将更快构建更好的系统。

### 10.4.1 为什么传统 ML 指标力不从心

传统 NLP 指标是为具有明确定义输出的结构化预测任务设计的。BLEU 衡量生成翻译与参考翻译之间的 n-gram 重叠。ROUGE 通过词重叠评分摘要质量。NDCG 对信息检索结果排序。这些指标在以下情况表现出色：输出格式可预测且结构化（文本序列、排序列表）、可以收集多个参考输出进行比较，以及成功可以通过表面相似性近似。

智能体式系统违反了全部三个假设。考虑智能体在典型执行期间产生什么：顺序各异但实现等效结果的工具调用序列、跨文本、代码、图像、音频和结构化数据的生成产物、对话质量与事实准确性同样重要的交互式对话、过程质量影响可靠性的多步推理链，以及外部状态变化如创建的文件、调用的 API 或修改的数据库。写软件的智能体可能通过 50 个推理步骤产出漂亮、测试良好的代码，或通过 200 个带大量回溯的步骤产出相同的功能。传统指标完全错过了这一点——它们无法区分优雅的解决方案与蛮力成功，也无法评估测试覆盖率或代码文档等中间产物的质量。

也许更根本的是，智能体式轨迹是非确定性和异构的。单次任务执行可能包括关于问题的自然语言推理、JSON 工具调用规范、Python 代码生成、终端命令输出、渲染的可视化、错误消息和调试步骤，以及多轮澄清对话。这种异构性抗拒简化为标量指标。你无法在代码、图像和对话的混合物上计算 BLEU 分数。

这就是大型语言模型作为评估者的力量变得明显的地方。现代多模态 LLM 可以处理智能体产生的确切数据格式——文本、代码、图像、结构化数据、工具调用——并使用首先实现智能体推理的相同能力推理它们的质量。如果 LLM 能写代码，它就能评估代码质量。如果它能生成可视化，它就能评估图表是否有效传达洞察。

传统软件系统执行确定性行为——下载文件、调用 API、返回结果。智能体的力量在于它们使我们能够构建应对需要推理和智能的任务的系统：如何架构应用、调试涌现的问题、从数据综合洞察。这些是人类以创造力和领域专长来处理的任务。作为系统开发者，我们的评估方法必须反映同样的智能和创造力。我们不能用简单的基于规则的指标评估智能行为，就像我们不能用简单的基于规则的逻辑构建智能系统一样。

### 10.4.2 将领域专长转化为评估方法

设计有效评估套件的关键是将领域专长转化为可衡量的标准。问自己：如果人类专家评估这个结果，他们会检查什么？

对于软件开发智能体，专家工程师会检查：

- **功能正确性**：代码是否解决了所述问题？
- **测试覆盖率**：边缘情况是否处理？测试是否实际验证行为？
- **代码质量**：实现是否可维护、可读、高效？
- **类型安全**：静态分析工具（mypy、pyright）是否报告问题？
- **文档**：函数是否有文档？是否有 README？
- **错误处理**：代码是否优雅失败并给出清晰消息？

每个专家判断都可以转化为评估方法：

```python
# Functional correctness: Run test suite
def evaluate_functional_correctness(code_trajectory):
    test_results = execute_pytest(
        code_trajectory.generated_code
    )
    return test_results.pass_rate
# Test coverage: Analyze coverage report
def evaluate_test_coverage(code_trajectory):
    coverage = run_coverage_analysis(
        code_trajectory.generated_code
    )
    return coverage.line_coverage_percent
# Type safety: Run static analysis
def evaluate_type_safety(code_trajectory):
    mypy_results = run_mypy(
        code_trajectory.generated_code
    )
    error_count = mypy_results.error_count
    total_lines = max(mypy_results.lines, 1)
    error_rate = error_count / total_lines
    return 1.0 - error_rate
# Code quality: LLM evaluation
def evaluate_code_quality(code_trajectory):
    return llm_judge.evaluate(
        code_trajectory.generated_code,
        criteria=[
            "Is the code readable with clear variable names?",
            "Are functions appropriately sized and focused?",
            "Is the implementation efficient?",
            "Does the code follow Python best practices?"
        ]
    )
```

注意方法的混合。一些专家判断（测试覆盖率、类型安全）可以干净地映射到确定性指标——在可用时应优先使用，因为它们快速、可复现，并提供精确信号。其他判断（代码可读性、架构合理性）需要受益于 LLM 评估的细致推理。

### 10.4.3 领域特定的评估示例

让我们与生成数据可视化的智能体对比。评估图表的专家数据科学家会检查：

- **数据准确性**：可视化是否正确表示底层数据？
- **视觉清晰度**：轴是否有标签？是否有描述性标题？
- **图表选择**：可视化类型是否适合数据？
- **可读性**：字体是否可读？颜色是否可区分？
- **统计诚实性**：刻度是否合适？是否避免了过度绘制？
- **上下文**：是否指定单位？日期/时间范围是否清晰？

评估方法看起来相当不同：

```python
# Data accuracy: Programmatic verification
def evaluate_data_accuracy(viz_trajectory):
    # Load ground truth data
    original_data = load_data(viz_trajectory.task.data_path)
    # Extract data points from visualization metadata
    # (agent may store plot data in trajectory metadata)
    viz_data = viz_trajectory.metadata.get('plot_data', None)
    if viz_data is None:
        return 0.0
    return compute_correlation(original_data, viz_data)
# Visual elements: Multimodal LLM evaluation
def evaluate_visual_quality(viz_trajectory):
    # Extract generated image from trajectory messages
    # (agents may produce MultiModalMessage with images)
    messages = viz_trajectory.messages
    image_messages = [
        msg for msg in messages
        if hasattr(msg, 'is_image') and msg.is_image()
    ]
    if not image_messages:
        return 0.0
    # Evaluate the generated visualization
    return multimodal_llm_judge.evaluate(
        messages=image_messages,
        criteria=[
            "Does the chart include a descriptive title?",
            "Are all axes clearly labeled with units?",
            "Is the text legible at normal viewing size?",
            "Are colors used effectively and accessible?",
            "Is the date range or temporal context clear?"
        ]
    )
# Statistical properties: Programmatic checks
def evaluate_statistical_honesty(viz_trajectory):
    checks = {
        "appropriate_axis_scaling":
            verify_axis_ranges(viz_trajectory),
        "no_severe_overplotting":
            check_point_density(viz_trajectory),
        "consistent_units":
            verify_unit_consistency(viz_trajectory)
    }
    return sum(checks.values()) / len(checks)
```

这里我们看到多模态评估的实际运作。RunTrajectory 包含一个 messages 字段，可以包含带图像、音频或其他媒体的 MultiModalMessage 实例。具有视觉能力的 LLM 评判器可以直接处理这些消息，评估生成的图表是否有可读的字体或适当的标题——这些任务用传统计算机视觉流水线将极其困难。这种能力自然地从智能体已有的工作方式延伸：如果智能体能生成和推理图像，同样的多模态模型就能评估这些图像。

> **实践中的多模态评估**
>
> 当使用具有视觉能力的模型（GPT-4o、Claude 3.5 Sonnet）作为评判器时，你可以直接从轨迹传递 MultiModalMessage 实例。评判器的 LLM 客户端处理多模态内容，就像在智能体执行期间一样。这种统一方法意味着评估使用与你的智能体系统相同的消息类型和模型能力。

### 10.4.4 何时使用数值指标 vs LLM 评判器

正如这些示例所示，有效的评估套件战略性地组合确定性指标与基于 LLM 的判断。决策框架：

**优先使用确定性指标**，当：

- 真实答案可用且比较定义明确
- 评估标准映射到可衡量的属性（测试覆盖率、错误率、响应时间）
- 一致性和可复现性至关重要
- 成本和延迟重要（评估数千个示例）
- 你需要跟踪随时间的细粒度变化

**优先使用 LLM 评判器**，当：

- 标准需要对质量的细致推理
- 存在多个有效解决方案且表面相似性具有误导性
- 人类判断涉及主观评估
- 输出格式非结构化或多模态
- 评估正确性需要领域专长

**两者都用**，当：

- 质量的不同方面需要不同的评估方法
- 你想用客观基线验证 LLM 判断
- 成本敏感的扩展需要用廉价指标过滤后再进行昂贵评估

例如，你可以在运行昂贵的代码质量和架构决策 LLM 评估之前，用快速单元测试（确定性）过滤代码生成结果。或者你可以使用确定性检查验证可视化有所需元素（标题、标签），然后使用多模态 LLM 评估这些元素的质量。

评估套件设计本身是一个迭代过程。从关于你领域中什么重要的假设开始，实现评估方法，然后验证你的指标实际上与下游成功相关。系统化方法：首先，咨询领域专家了解他们如何评估质量；其次，将专家标准转化为可衡量的评估；第三，测试你的指标是否与专家判断相关；第四，调整权重、添加维度并修复错位的激励；最后，监控针对你的指标优化是否提高真实表现。这种科学迭代防止常见陷阱，如优化实际上不衡量重要事物的指标，或创建不能反映真正改进的可被钻空子的评估标准。

设计领域特定的评估套件需要创造力，正是因为它抗拒公式化方法。每个应用领域都带来独特的成功标准、失败模式和质量维度。投资于深思熟虑评估设计的团队——汇集领域专长、技术衡量和对真实结果的验证——将构建更可靠的系统，并更快迭代走向真正有用的智能体能力。

关键洞见是评估不仅仅是要用更好的指标解决的技术问题——它是一个设计问题，需要理解质量在你的特定领域意味着什么，并创造性地将这种理解转化为衡量。带着这一基础，接下来的部分提供在我们的 picoagents 库中实现这些评估方法的技术基础设施，构建评判器、运行器和复合评估系统，可以评估从简单模型调用到复杂多智能体编排的一切。

## 10.5 如何评估：指标与评判器

一旦我们有了轨迹，如何给它评分？这需要两个组件：**指标**（衡量哪些维度）和**评判器**（如何给每个维度评分）。

### 10.5.1 无参考 vs 基于参考的指标

**基于参考的指标**将输出与已知正确答案比较：

对于有确定性答案的任务，你可以评估而无需昂贵的 LLM 调用：

```python
from picoagents.eval import ExactMatchJudge
from picoagents.types import Task
# Create task with expected output
task = Task(
    name="arithmetic",
    input="2+2",
    expected_output="4"
)
# Exact match judge for deterministic answers
exact_judge = ExactMatchJudge()
```

但如果智能体说"The answer is 4"而不是仅仅"4"呢？评估系统需要处理对话式响应的策略：

```python
from picoagents.eval import (
    ContainsJudge,
    FuzzyMatchJudge
)
# Finds "4" within longer responses
contains_judge = ContainsJudge()
# Handles "Four" vs "4" variations
fuzzy_judge = FuzzyMatchJudge()
```

**无参考指标**在没有真实答案的情况下评估质量：

- **有用性**：响应对用户有多大用处？
- **沟通清晰度**：智能体协调得有多好？
- **资源效率**：使用了多少 Token 或 API 调用？

许多多智能体任务需要无参考评估，因为"正确"解决方案可能差异很大（构建计算器应用有很多方式）。

**智能体特定指标**评估智能体达成解决方案所用的过程：

对于使用工具的智能体，你关心的往往不仅是最终答案，还有智能体是否选择了正确的工具以及顺序如何。智能体是在摘要之前先搜索的吗？它用计算器时参数正确吗？这些过程导向的指标对调试智能体行为特别重要——智能体可能碰巧通过错误的推理路径产生了正确的答案。你可以通过检查轨迹中的 ToolMessage 实例来实现工具评估，对照预期模式验证工具选择、参数正确性和执行顺序。虽然我们当前的评判器聚焦最终输出，但生产系统通常用工具调用准确性和推理轨迹验证的专门评判器扩展此模式。

### 10.5.2 LLM 作为评判器：实用方法

对于无参考评估，我们可以使用强大的语言模型作为评判器。这些 LLM 评判器可以评估传统指标遗漏的细致品质。

以下是我们创建和配置 LLM 评判器的方式：

```python
from picoagents.eval import LLMEvalJudge
from picoagents.llm import AzureOpenAIChatCompletionClient
# Create LLM judge with evaluation criteria
judge_client = AzureOpenAIChatCompletionClient(
    model="gpt-4.1-mini"
)
judge = LLMEvalJudge(
    client=judge_client,
    default_criteria=[
        "accuracy",
        "helpfulness",
        "efficiency"
    ]
)
```

评判器通过构建包含任务、预期输出（如有）和完整智能体对话的评估提示词来对轨迹评分。然后它使用 LLM 为每个标准提供分数（0-10）和推理。

```python
# Score a trajectory
score = await judge.score(
    trajectory,
    criteria=["accuracy", "helpfulness"]
)
# Access results
print(f"Overall: {score.overall}/10")
print(f"Accuracy: {score.dimensions['accuracy']}/10")
print(f"Reasoning: {score.reasoning['accuracy']}")
```

这种方法利用先进模型的推理能力提供跨多个维度的细致评估。

### 10.5.3 评分策略

将指标应用于轨迹时，我们有几种选择：

**单一答案评分**：整体评估完整轨迹

- 适合：整体任务评估
- 挑战：可能错过重要的过程细节

**两两比较**：与其独立评分每条轨迹，两两评估直接比较两个输出并识别哪个更好。这种方法在迭代开发期间特别有价值——每个智能体版本都可以系统性地与之前的基线比较，确保你在取得进展。点式评估问"这个响应有多好？"（需要绝对判断），而两两评估问更简单的问题"哪个响应更好？"这种相对判断通常更可靠，尤其是对于绝对分数显得任意的主观品质。权衡是你需要多次评估运行来建立相对排名。

```python
# Compare two agent configurations
scores_v1 = await runner.evaluate(agent_v1, tasks)
scores_v2 = await runner.evaluate(agent_v2, tasks)
avg_v1 = sum(s.overall for s in scores_v1) / len(scores_v1)
avg_v2 = sum(s.overall for s in scores_v2) / len(scores_v2)
improvement = ((avg_v2 - avg_v1) / avg_v1) * 100
print(f"Version 2: {improvement:+.1f}% vs baseline")
```

**维度评分**：独立评估多个方面

- 适合：详细反馈、识别具体弱点
- 挑战：实现和解释更复杂

### 10.6.1 设计任务套件

任务的选择决定你的评估将揭示什么洞察。我们的四个套件测试正交的能力：Simple-Reasoning 建立多智能体配置可能不提供价值的基线，Tool-Heavy 验证智能体是否能利用外部能力/工具，Planning 测试多步分解，Verification 评估批判是否改进输出。

考虑 Tool-Heavy 套件。这些任务需要任何模型训练都无法提供的实时信息——这一设计选择迫使系统要么成功使用工具，要么完全失败。以下是我们创建这样一个任务的方式：

```python
def create_tool_heavy_tasks() -> List[Task]:
    return [
        Task(
            name="Podcast Research",
            input="""Did Andrej Karpathy have a podcast interview with
            Dwarkesh Patel where he discussed Eureka Labs? If so, what
            did he say was the primary goal? Provide specific quotes.""",
            expected_output="""Yes, Andrej Karpathy discussed Eureka Labs.
            The primary goal is to personalize education using AI teaching
            assistants that allow students to ask questions and receive
            customized, interactive experiences..."""
        ),
        # Additional Tool-Heavy tasks...
    ]
```

预期输出不用于精确匹配，而是引导 LLM 评判器了解什么构成完整答案。此任务将立即区分配置：Direct-Model 会产生幻觉或承认无知，而支持工具的配置可以通过网络搜索找到这些事实。

### 10.6.2 创建评估目标

每个配置需要一个评估目标——一个无论内部结构如何都统一运行系统的适配器。最简单的是 Direct-Model，它完全绕过智能体框架：

```python
# Baseline: direct model calls
model_target = ModelEvalTarget(
    client=AzureOpenAIChatCompletionClient(model="gpt-4.1-mini"),
    system_message="You are a helpful, accurate assistant."
)
```

Single-Agent-Tools 包装一个带工具访问的智能体。关键设计决策是工具选择——我们提供 Think（显式推理）、Calculator（算术）、DateTime（时间查询）、GoogleSearch（当前信息）和 TaskStatus（工作流管理）：

```python
# Single agent with tools
agent_with_tools = Agent(
    name="assistant",
    instructions="""You are a knowledgeable assistant with access to tools.
    Use tools when they would improve accuracy. Think step-by-step for
    complex problems. For research tasks, use google_search to find
    current information.""",
    model_client=client,
    tools=[ThinkTool(), CalculatorTool(), DateTimeTool(),
           GoogleSearchTool(), TaskStatusTool()]
)
agent_target = AgentEvalTarget(agent_with_tools)
```

多智能体配置引入一个三智能体团队：规划者负责分解，求解者带工具负责执行，审查者负责质量保证。求解者获得与 Single-Agent-Tools 相同的工具，确保任何性能差异源于编排模式而非能力差距。RoundRobinOrchestrator 按固定顺序循环智能体，而 AIOrchestrator 让模型基于任务需求和状态动态选择下一个发言者。

### 10.6.3 配置评判器

鉴于我们采取 LLM 作为评判器的方法，评估质量完全取决于评判器校准。我们使用组合多个维度——准确性、完整性、有用性和清晰度——的复合评判器，LLM 提供精确匹配方法无法捕获的细致评分。

构建有效评估需要迭代和创造力。在开发此评估套件时，我遇到了与预期矛盾的初始结果：多智能体系统得分 6.82/10，而直接模型达到 7.94/10。检查评判器理由和轨迹跟踪揭示了几个在评估能产生有意义结果之前必须修复的关键问题。

**问题 1：冗长惩罚**

第一个问题出现在评判器推理中：

```json
{
  "overall": 6.0,
  "reasoning": {
    "clarity": "This is correct but verbose for a simple task"
  }
}
```

评判器将多智能体透明度惩罚为冗长。当规划者、求解者和审查者协作时，轨迹自然包含它们的完整推理过程。没有适当的引导，LLM 评判器将这种协作可见性解读为不必要的长度，而非有价值的透明度。解决方案需要明确纠正这种偏见的自定义指令：

```python
judge = LLMEvalJudge(
    client=judge_client,
    custom_instructions="""
    SCORING PHILOSOPHY:
    - If the answer is CORRECT and COMPLETE, score 8-10 regardless of length
    - DO NOT PENALIZE: Multi-agent collaborative process visibility
    - DO NOT PENALIZE: Showing reasoning steps or validation
    EVALUATION CRITERIA:
    1. Completeness: Multiple valid solutions = COMPLETE (9-10)
    2. Helpfulness: Correct + reasoning = HELPFUL (9-10)
    3. Clarity: Logically structured = CLEAR (9-10), not brevity
    """,
    default_criteria=["accuracy", "completeness", "helpfulness", "clarity"]
)
```

添加这些指令并重新运行评估后，多智能体分数从 6.82/10 提高到 9.30/10——一旦冗长偏见通过指令得到解决，其真实表现就显现出来。

**问题 2：维度归一化**

我观察到的另一个问题是，当使用 CompositeJudge 组合具有不同维度的评判器时，复合分数不符合预期。评判器 A 可能评分准确性和有用性，而评判器 B 评分清晰度。加权平均没有正确归一化——权重全局总和为 1.0 而非按维度。修复需要调整维度计算：

```python
# Normalize weights per dimension, not globally
for dim, contributions in dimension_contributions.items():
    total_weight_for_dim = sum(weight for _, weight in contributions)
    dimensions[dim] = sum(
        val * (weight / total_weight_for_dim)
        for val, weight in contributions
    )
```

这些问题说明了一个重要原则：**评估本身需要调试**。记录带评判器推理的完整轨迹，当结果看起来不对时检查数据，识别系统和评估框架中的偏见，然后迭代。没有这个过程，冗长偏见会导致对多智能体系统性能的错误结论。

### 10.6.4 运行评估

EvalRunner 协调所有配置和任务的执行，收集带完整执行轨迹的轨迹——消息、工具调用、Token 使用和计时：

```python
runner = EvalRunner(
    judge=composite_judge, parallel_tasks=True)
# Evaluate all configurations
for config_name, target in all_configurations:
    scores = await runner.evaluate(target, all_tasks)
    # Log complete trajectories for inspection
    save_results(config_name, scores)
```

每次评估产生丰富的评分数据：总分、维度细分、评判器推理和完整轨迹。这种粒度支持调试被评估的系统和评估本身——当分数看起来不对时，检查轨迹和评判器理由，识别问题在于智能体行为还是评估偏见。

结果揭示清晰的模式。Direct-Model 在 Tool-Heavy 任务上得 6.8 分，而 Multi-Agent-AI 得 9.2 分。在 Simple-Reasoning 任务上，Direct-Model 实际表现最好，9.7 分对比 Multi-Agent-AI 的 9.3 分。Token 效率显示多智能体协调的成本：Direct-Model 平均每个任务使用 355 Token，而 Multi-Agent-AI 使用 15,343 Token，增加了 43 倍。

Tool-Heavy 套件揭示最清晰的分化。Podcast Research 任务暴露了一个关键局限：Direct-Model 得分 3.2/10，因为它缺乏网络搜索能力，无法验证当前信息。所有其他带 GoogleSearchTool 的方法得分 9.0/10，展示工具访问如何改变研究密集型任务的表现。

有趣的是，Direct-Model 在 Simple-Reasoning 上获胜（9.7/10），击败所有多智能体方法。这表明 LLM 本身可以是简单推理任务的体面基线。这验证了一个重要原则：**不要过度工程**。当任务只需要直接的推理，无需工具协调或多步规划时，单次模型调用就足够了。多智能体开销（协调消息、推理可见性、多次 LLM 调用）没有提供任何好处，实际上引入了轻微的性能退化。

Planning 和 Verification 套件显示较少分化（所有配置得分 8.6-9.6/10），表明这些任务类型不强烈偏向任何特定架构。多智能体编排的价值很大程度上取决于任务特征。

**自定义评判器实现**：为你的领域实现一个超越通用准确性和有用性的专门评判器。例如，创建评估生成代码可读性、效率和可维护性的 CodeQualityJudge，或评估同理心、解决完整性和政策合规性的 CustomerSupportJudge。在扩展前在验证集上校准你的评判器。

**回归测试套件**：构建跟踪你的智能体随时间表现的回归测试系统。存储带元数据（模型版本、配置、时间戳）的评估结果，可视化趋势，并在表现低于阈值时自动告警。这支持自信迭代而不意外破坏能力。

**效率分析**：扩展评估框架，收集超越 Token 计数的详细效率指标——墙钟时间、工具调用计数、内存使用、API 成本。构建展示配置间效率-性能权衡的可视化。2 倍加速何时证明 0.5 分的分数下降是合理的？

## 10.8 相关研究与数据集

几个基准专门针对智能体和多智能体评估：

**GAIA**（Mialon et al. 2023）：466 个问题，测试推理、工具使用和多步问题解决。专注于对人类简单但对 AI 系统具有挑战性的任务，人类准确率 92%，而带插件的 GPT-4 为 15%。

**SWE-bench**（Jimenez et al. 2023）：来自 12 个流行 Python 仓库的 2,294 个问题的真实 GitHub Issue，测试软件工程能力。评估代码理解、bug 修复和多文件协调，Claude 2 仅解决 1.96%。

**GPQA**（Rein et al. 2023）：生物、物理和化学领域的研究生级问题，需要专门知识和复杂推理。包含 448 个"Google-proof"（谷歌搜索也无法直接解答）的问题，博士专家达到 65% 准确率，而熟练的非专家仅达到 34%。

**Humanity's Last Exam（HLE）**（Phan et al. 2025）：一个多模态基准，包含 2,500 个问题，跨数十个学科，处于人类知识前沿，设计为数学、人文和自然科学领域高级 AI 能力的全面测试。

这些基准共享我们以轨迹为中心的方法——它们评估的不仅是最终答案，还有通向解决方案的推理和工具使用过程。它们代表越来越具挑战性的试验台，当前 LLM 与人类专家表现相比存在显著差距，使其对衡量多智能体推理能力的真正进展有价值。

> **基准 ≠ 你的任务**
>
> 公开基准告诉我们相对表现（模型 A 在任务 X 上击败模型 B），而不是模型在你的任务上会表现如何。它们无法捕获你领域的独特成功标准、跨智能体栈的多个模型的组合，或你的具体数据特征和失败模式。
>
> 基准任务 ≠ 你的业务任务。这就是为什么创造性地投资领域特定评估设计至关重要——只有与你实际用例对齐的评估套件才能可靠地衡量更改是否提高真实表现。

### 10.8.1 污染挑战

AI 评估中日益增长的担忧是**基准污染**（benchmark contamination）——当训练数据无意中包含测试问题时，会夸大表面表现。这对可能使用网络搜索或检索工具的多智能体系统特别成问题，因为基准问题常以各种形式在网上流传。

缓解污染的一些策略：

- **使用多样化的评估方法**：不要只依赖公开基准
- **创建私有测试集**：开发特定于你用例的内部评估任务
- **监控可疑的高表现**：如果在既定基准上结果好得过分，调查潜在的数据泄漏
- **在新鲜的、未发表的问题上测试**：生成训练期间不可能见过的新任务

随着基准成为优化目标，它们衡量真正能力的能力会减弱。这使得开发健壮、多方面的评估方法变得更加重要，这些方法能随领域演进。

## 10.9 小结

有效的多智能体评估需要以轨迹的思维思考——任务执行期间展开的推理和动作的完整序列。这种统一视角支持跨模型、智能体和多智能体系统的一致评估方法。

关键原则：

- **采用评估驱动的开发**：在构建系统之前定义成功标准和评估基础设施
- **设计领域特定的评估**：使用确定性指标和 LLM 评判器将专家判断转化为可衡量的标准
- **迭代评估**：记录带评判器理由的完整轨迹，检查偏见，修复问题，重新评估
- **考虑多智能体特征**：没有适当引导，LLM 评判器可能将协作透明度惩罚为冗长
- **让指标匹配任务类型**：事实性任务使用确定性评估，主观评估使用 LLM 作为评判器
- **处理对话复杂性**：答案提取策略防止真实智能体交互中的评估失败
- **系统化规划**：遵循 5 步框架——定义成功标准、创建任务套件、选择指标、建立基线、规划迭代工作流

我们的综合评估揭示了多智能体系统何时提供价值与开销。多智能体配置在工具密集型研究任务上表现出色（9.2/10 对比直接模型 6.8/10），但在简单推理任务上增加不必要的开销，直接模型调用表现最好（9.7/10 对比多智能体 9.3/10）。Token 效率显示成本：多智能体系统使用比直接模型调用多 43 倍的 Token。这展示了为什么评估至关重要：它揭示哪种架构复杂性由任务需求证明合理，哪种是过度工程。

我们构建的评估系统为衡量和改进多智能体系统提供了实用基础。通过结合基于参考的效率与基于 LLM 的灵活性，并迭代智能体配置和评估方法，我们可以开发更有效的智能体架构，同时理解多智能体方法何时提供真正价值。

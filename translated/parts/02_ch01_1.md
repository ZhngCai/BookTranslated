# 第 1 章　理解多智能体系统

本章涵盖：

- **复杂性挑战**：理解单个 AI 模型何时变得力不从心，以及为什么需要智能体
- **智能体的定义**：核心能力（推理、行动、沟通、适应）与核心组件（模型、工具、记忆）
- **催生多智能体系统的复杂任务**：规划、多元专业能力、海量上下文和适应性解决方案
- **何时使用（以及何时不使用）多智能体方法**：多智能体系统并非总是正确的解决方案；要懂得何时使用它们

## 1.1 引言

如今的生成式人工智能（Generative AI，GenAI）模型已经展现出非凡的能力，能够在它们训练所用的海量数据中建模复杂的关系。例如，GPT-4、Claude、Gemini 等模型——也称为大型语言模型（Large Language Model，LLM）（Vaswani et al. 2017）——在文本处理任务上表现出色，例如：摘要段落、提取实体、生成代码等。凭借这些模型的能力，它们如今已被直接应用于各种行业的应用中以解决任务。例如，LLM 已被集成到生成营销文案、审查法律文件合规性、为聊天机器人和虚拟助手提供高级自然语言理解，以及协助研究人员进行科学发现的产品中。无论是个人用户还是企业，采用速度都在快速增长。一份近期报告指出，如今 75% 的知识工作者已经在工作中使用 AI（Microsoft AI Blog 2024），并且越来越多的初创公司正在构建利用这些模型解决现实问题的应用。

> **量化向 AI 智能体的转变**
>
> 人们普遍承认，对 AI 智能体的兴趣正在快速增长，但到底增长了多少？为了用具体数据回答这个问题，第 14 章演示了如何构建一个多智能体工作流，分析来自 Y Combinator——北美最大的初创公司孵化器之一——的初创公司数据。
>
> 我们将设计的工作流分析了 5,622 家 YCombinator 公司的描述。我们发现，构建 AI 智能体的初创公司从 2020 年的 6.1% 增长到 2025 年的 47.7%——短短五年间增长了 7.8 倍。这种快速增长标志着行业看到了机会所在：从 AI 辅助工具迈向能够处理复杂、多步骤任务的完全自主系统。
>
> 这一分析本身就体现了我们将在第 2 章探讨的多智能体工作流模式，完整实现在第 14 章中详细说明。如果你对方法感兴趣，随时可以跳到后面阅读！

> **定义：智能体、多智能体系统和工具**
>
> **智能体**：一种能够推理、使用工具行动、沟通和适应的 AI 系统
>
> **多智能体系统**：多个智能体协同工作，各自具备专门的能力
>
> **工具**：扩展智能体能力的外部能力，如 API、代码执行、网络搜索

表 1.1 中的任务 1 可以通过从模型训练数据或网络搜索引擎等现有系统中检索一般性知识来可靠地解决。这代表了模型可以完成的事情——无需规划、工具或适应的直接信息检索。

然而，任务 2 揭示了仅靠模型变得不足的地方。"英伟达今天的股价"代表着 LLM 在训练期间不太可能见过的信息；因此，它生成的结果很可能是错误的（幻觉）。任务 2 需要理解查询、规划（例如，将任务分解为获取当前股票数据、分析数据以回答问题等步骤）、行动（使用网络搜索或 API 等工具执行每个步骤）以及呈现最终结果。这正是我们需要智能体的地方——一个将模型的推理能力与使其能够代表我们行动的工具相结合的系统。当前的生成式 AI 应用通过构建包含 LLM 的预定义解决方案流水线来探索这种方法，LLM 驱动工具采取行动。

任务 3 代表的复杂度级别超出了即便是能干的单个智能体也无法有效处理的范围。它涉及多种类型的专业能力（界面设计、Android 开发、API 使用、集成测试等），并且需要一个迭代式解决方案：采取行动，由产生的结果决定走向解决方案的后续步骤（例如，检索合适的 SDK 文档、为应用中的每个模块编写多个版本、测试它们以识别错误、修复和集成，直到打造出一个可运行的应用）。这正是多个智能体变得必不可少的地方——每个智能体带来专门的能力，同时协作解决超出任何单一系统范围的任务。

在本书中，我们将专注于探索如何通过开发在多个智能体之间实现规划、行动和沟通元素的应用来应对这些复杂任务。反过来，这些应用有望催生全新且通用的数字界面、解决新类别的任务，或以减少人类劳作和付出的方式完成现有任务。

这种潜力超越了通用的任务自动化。当智能体理解用户上下文（当前活动、环境、近期交互）和偏好（明确定义的设置和行为模式）时，它们可以提供高度个性化的协助，处理诸如安排会议、起草邮件回复、预订航班、进行电商购物和报税等任务。

要释放这种潜力，我们需要理解基础构建模块：到底是什么让一个系统成为"智能体"？我们如何构建多个智能体有效协作的系统？让我们从审视这些核心概念开始。

> **单智能体 vs 多智能体：一条模糊的边界**
>
> 在实践中，"单个智能体"和"多智能体系统"之间的边界往往是模糊的。一个智能体使用的工具本身可能就是智能体（我们将在第 4 章 4.11 节探讨），或者在用户眼中表现为一个智能体的东西，其内部可能协调着多个协同工作的专门子智能体。
>
> 在本书中，我们展示显式的多智能体架构——智能体之间的协调是可见的、有意图的——因为这些模式最能清晰地体现设计原则。然而，我们探讨的编排模式、评估方法和伦理考量广泛适用于任何自主的智能体式系统，无论其架构呈现为"一个"智能体还是"多个"智能体。

## 1.2 生成式 AI 入门

生成式模型是深度神经网络的一个子集，擅长识别数据集中的复杂模式，从而使它们能够生成新的、相似的数据点。这些模型与判别式模型截然不同，后者专注于区分数据类型或对它们进行分类。生成式模型可以在各种模态的数据上进行训练。例如，在人类书面语言文本上训练的模型（如 GPT 系列）被称为大型语言模型（LLM）；在图像上训练的模型（如 DALL-E 系列）被称为图像生成模型（Image Generation Model，IGM）；而在两者上训练的模型（如 GPT4-V）通常被称为大型多模态模型（Large Multimodal Model，LMM）。本书将专注于生成文本输出的生成式模型，包括大型语言模型和大型多模态模型。

训练生成式模型的基本概念相对简单。以 LLM 为例，这些模型被训练来预测序列中的下一个词，或者填补文本中被掩蔽或隐藏的部分——即序列预测（sequence prediction）。通过将这一训练目标应用于足够大的数据集，模型学会了通过文本所描绘的世界的表示。反过来，模型可以利用这些表示生成连贯、相关且上下文恰当的文本。

为了应用这些模型解决任务，早期的工作专注于将多种任务框架化为序列预测问题。例如，为了对文本进行分类，先提供分类问题的描述，随后给出标签列表和一个提示词，询问："\<问题\> \<标签\> 所提供的标签中哪个是正确类别？"。类似地，为了摘要给定的段落，给出结构为"\<段落\> 上述段落的摘要是……"的提示词，引导模型生成该段落的摘要。事实证明，将任务框架化为序列预测问题，使模型能够利用训练期间获得的知识来完成其初始训练目标之外的广泛任务（例如，语言翻译、情感分析、问答、对话生成、命名实体识别、句法解析、代码合成、改写、语法纠正等）。这一背景对于理解这些模型应用于复杂任务时的能力和局限性十分重要。例如，这些模型展现的推理能力（如 2 个苹果 + 10 个苹果 = 12 个苹果）通常局限于训练数据中充分覆盖的场景，而无法固有地泛化到罕见或未见过的场景（如求解三进制下的线性方程）。

创建能够提高任务成功完成概率的序列的做法，被称为提示词工程（prompt engineering）。少样本提示（few-shot prompting）（Brown et al. 2020）——在序列中包含任务及其解决方案的示例，思维链提示（chain-of-thought prompting）（J. Wei et al. 2022）——包含分解为求解步骤的任务示例，以及 ReAct 提示（Yao et al. 2022）——将推理和行动结合在语言模型中，已成为领先的提示词工程方法。除了提示词工程之外，在特定任务的指令数据和显式收集的人类反馈数据上微调模型（Ouyang et al. 2022）已被证明可以增强模型对齐（alignment）——即旨在确保生成输出与人类意图、偏好和价值观一致的工作。

最后，虽然可以指示 LLM 生成解决任务的文本序列，但它们一次能处理的文本量是固定的，受到所谓的上下文窗口（context window）的约束。上下文窗口大小定义了模型在单个输入和输出序列中能够处理的最大 Token（词或词片段）数量。这一限制由模型的架构决定，特别是其计算和内存约束。理解上下文窗口对开发者至关重要，因为它影响输入数据的结构方式和任务的框架方式。截断、滑动窗口技术、摘要、分块和优化的提示词工程等策略，对于在这些约束内有效运行、在各种应用中最大化模型潜力同时平衡计算资源至关重要。

### 1.2.1 获取生成式 AI 模型的访问权限

像 GPT-4 或 Claude 这样的最先进模型，由于其计算需求和专有性质，主要通过基于云的 API 访问。包括 OpenAI、Anthropic、谷歌（Google）和微软 Azure 在内的模型提供商通过软件开发工具包（Software Development Kit，SDK）提供 API 级访问。典型的工作流程包括创建开发者账户、配置计费（大多数提供商提供按使用量计费的价格和免费层级），以及生成用于身份验证的 API 密钥。

在本书中，我们出于务实的原因统一采用 OpenAI API 规范：它已成为被多家提供商采用的事实标准。OpenAI SDK 原生支持 OpenAI 的服务和 Azure OpenAI——微软托管的 OpenAI 模型企业级部署，提供额外的安全、合规和区域可用性保证。这种标准化意味着为 OpenAI API 编写的代码只需极少改动即可在 Together AI、Anyscale 等提供商乃至本地模型部署上运行。

对于本地开发和隐私敏感的应用，vLLM（vLLM Team 2023）等工具支持自托管开源模型，同时保持 OpenAI API 兼容性。这种架构模式——不同提供商遵循通用的 API 规范——使我们构建的多智能体系统能够与底层模型提供商无关，无论是基于云的还是本地部署的。

## 1.3 为什么需要多个智能体？复杂任务的特征

虽然单个智能体可以有效地处理检索当前股价之类的任务，但即便是能干的智能体在面对高度复杂的挑战时也会遇到根本性的局限。考虑表 1.1 中的任务 3："构建一个移动应用，帮助用户查看股价、购买股票并报税。"尝试完成此任务的单个智能体需要理解多个领域的应用需求、设计用户界面和用户体验、编写 Android 开发代码、集成股票市场 API、实现报税功能，并处理测试、调试和部署。

图 1.3 展示了这一多领域任务的复杂性。

![图 1.3：一个复杂多领域任务的构成](images/p032_0.png)

*图 1.3：考虑以下复杂任务——"构建一个用于查看和购买股票、以及申报相应税费的应用"。为完成这样的任务，多智能体应用必须制定计划（例如，收集需求、设计界面、编写 Android 代码等），可选择地将计划中的步骤委托给具有专门相关能力的各种实体（智能体和人类），有效沟通并适应（从错误中恢复、探索新方法）以解决任务。*

即使能够访问强大的模型和全面的工具，单个智能体也面临若干挑战。所需的海量上下文很快就会超出实际限制——现有研究（Liu et al. 2024）表明，虽然 LLM 可以处理越来越长的文本，但它们倾向于关注文本开头和结尾的指令，而忽视中间的数据。更根本的是，这一任务需要多种类型的专业能力，很难在单个智能体的指令中有效编码。

促使采用多智能体方法的复杂任务通常表现出四个关键特征，如图 1.4 所示。虽然任何一个特征的出现都会增加任务的复杂性，但往往是这些特征的组合才为多智能体系统带来最大的机会。

![图 1.4：复杂任务的四个关键特征](images/p034_0.png)

*图 1.4：复杂任务表现出四个关键特征，使它们适合多智能体系统：规划（需要多个步骤和战略思维）、多元专业能力（需要不同领域的专门知识）、海量上下文（处理大量信息）和适应性解决方案（解决方案通过多次尝试涌现）。当任务组合多个特征时，其复杂性会越来越高，使其成为多智能体方法的理想候选。*

### 1.3.1 规划

复杂任务往往需要一个高层次的计划，其中包括将任务分解为必须成功完成的步骤。给定一些上下文，计划规定了一组应当执行的动作，以实现某个目标成功状态。这是机器人规划文献中一个众所周知且被广泛研究的属性，我们将在本书中借鉴该领域的概念。

### 1.3.2 多元专业能力

将复杂任务分解为多个步骤，往往会得到可以从特定专业能力中受益的步骤。例如，考虑应用开发任务，其目标是构建一个用于查看和购买股票并报税的移动应用。这一任务可以分解为分析应用需求、设计用户界面、实现所需功能、集成股票数据和报税所需的 API，以及测试和部署应用等步骤。反过来，这些任务映射为可以由专门智能体（例如，UX 智能体、Android 应用智能体等）承担的特定角色，每个智能体拥有专门的知识和技能。

专业能力的分离实现了关注点分离（separation of concerns）的方法，这是单智能体系统遵循通用指令集时难以实现的。从应用开发的角度看，创建具有明确指令的智能体提供了一种有用的抽象，可以将职责清晰地映射到特定实体，实现应用的领域驱动设计（domain-driven design）。

### 1.3.3 海量上下文

复杂任务往往需要处理海量的上下文才能解决。例如，在我们的应用开发任务中，智能体可能进行网络搜索查询并请求人类反馈以汇集需求，通过多个回合来组装正确的初始上下文。如此冗长的指令或上下文对单智能体系统构成重大挑战。现有研究（Liu et al. 2024）表明，虽然 LLM 可以处理越来越长的文本，但它们倾向于关注文本开头和结尾的指令，而忽视中间的数据。这一观点也受到认知科学理论的启发，例如认知负荷理论（cognitive load theory）（Sweller 1988），该理论认为人脑的工作记忆容量有限。当面对冗长或说明不足的指令时，这种容量会不堪重负，导致理解力和表现下降。

多智能体的视角可以通过选择性上下文供给（selective context provisioning）来帮助解决这一局限——即只将与任务相关的可用上下文部分（例如，迄今为止所执行操作的历史）提供给专注于该任务的智能体。通过结构化指令和管理上下文，最大限度地减少不必要的认知负荷，我们可以显著提高 AI 系统的任务表现。

### 1.3.4 适应性解决方案

复杂任务往往处于动态环境中，在采取某些行动之前，确切的解决方案是未知或不确定的。例如，特定的数据源可能在某一时刻不可用，需要探索其他数据源，或者每个行动可能产生意想不到的副作用等。例如，在应用开发任务中，对 API 的初始请求可能失败（例如，由于网络问题、参数格式错误或 API 的一般性变更），要求智能体根据反馈（例如，从 API 请求收到的错误消息，或寻求人类的明确帮助）以不同的参数重试请求来适应。在这些情况下，解决方案从适应中涌现——在智能体解决任务的过程中，围绕某个初始计划、行动和结果进行迭代推理。

这一属性也受到元认知（metacognition）研究洞见的启发，元认知研究认为，智能体对自己认知过程的觉察和调节可以显著影响问题解决过程。元认知技能——对今天的单智能体系统来说仍具挑战——使智能体能够实时反思、评估和调整其策略，从而在多智能体协作的涌现框架内产生更具适应性、可能更具创新性的解决方案。

鉴于这些适应性需求，编写确定性流水线（例如，特定的提示词、工具）变得更加困难，因此需要能够自我编排（具有一定自主性）的智能体来解决任务。

反思这些模式，可以为我们理解何时以及为何多智能体方法有益提供背景。当任务复杂、动态且需要多元专业能力时，多智能体方法可以提供有效管理这些任务所需的适应性和协作式问题解决能力。近期研究也强调了多智能体方法的益处。例如，（Du et al. 2023）发现"心智社会"（society of mind）方法（Minsky 1986）——一种提出人类智能源于多个简单智能体协同交互的理论——在多个智能体经过多轮对话辩论结果时，可以改善推理和事实准确性。类似地，（Liang et al. 2023）证明，使用具有独立角色的多个智能体（例如，执行任务的智能体和评判任务质量的智能体）可以提高生成结果的多样性和质量。

## 1.4 什么是智能体？

智能体的定义在 AI 文献中各不相同，从机器人学的早期概念到近期围绕 AI 模型驱动实体的想法。一个很好的起点是 Russell 和 Norvig 的经典著作（Russell and Norvig 2020），他们将智能体定义为任何通过传感器感知环境、并通过执行器作用于环境的实体，通过将感知映射到行动的智能体函数（agent function）运作。这一经典定义强调由逻辑推理驱动的感知-行动循环。

为了说明这种经典方法，考虑一台机器人吸尘器：它通过传感器感知环境（检测障碍物、灰尘量、电池状态），应用逻辑规则（如果检测到障碍物，转弯；如果检测到灰尘，加大吸力；如果电池电量低，返回充电座），并通过执行器行动（用于移动的电机、吸力机构、刷子旋转）。智能体函数遵循预定的逻辑：障碍物 → 避开，灰尘 → 清洁，低电量 → 充电。这创建了一个连续的感知-行动循环，每个传感器读数都会触发特定的程序化响应。

我们可以在此基础上构建，并将其扩展到生成式 AI 时代。虽然经典智能体通过预定义函数运作，生成式 AI 智能体保持同样的感知-行动循环，但增加了高级能力：由大型语言模型驱动的复杂推理、动态工具使用、自然语言沟通，以及基于结果的适应性行为。这些增强的能力使它们特别适合我们在本书中探讨的协作式问题解决。

在本书中，我们将智能体定义为**能够推理、行动、沟通和适应以解决问题的实体**。考虑我们的英伟达股价示例（表 1.1 中的任务 2）：一个有效的智能体必须理解信息请求、推理如何获取当前股票数据、使用合适的工具（网络搜索或金融 API）采取行动，并在初始方法失败时适应。这种适应可能包括尝试替代数据源或调整查询策略。

![图 1.5：智能体的核心组件](images/p040_0.png)

*图 1.5：智能体是一个软件实体，拥有核心组件——一个支持推理的生成式 AI 模型、使智能体能够行动的工具，以及使智能体能够回忆和复用信息的记忆。*

### 1.4.1 核心能力

智能体拥有四项基本能力，使其区别于基础模型或传统程序：

**推理（Reason）**：智能体可以通过对可用上下文应用规则或逻辑来合成新信息。这种推理可以是演绎、归纳或溯因式的，可以由生成式 AI 模型、自定义处理函数或两者的组合驱动。在我们的股价示例中，推理包括理解"今天的英伟达"需要当前市场数据，而不是来自训练数据的历史信息。

**行动（Act）**：智能体可以采取具体行动来影响环境或收集信息。这超越了生成文本响应——智能体可以执行代码、调用 API、搜索网络或与外部系统交互。对于股价任务，行动意味着实际调用金融数据 API 或执行网络搜索以检索当前定价信息。

**沟通（Communicate）**：智能体可以与用户、其他智能体和外部系统有效交换信息。这包括理解自然语言输入、组织恰当的响应，以及知道何时以及如何请求额外信息或澄清。

**适应（Adapt）**：智能体可以根据反馈、变化的条件或新信息修改其方法。如果初始 API 调用因速率限制而失败，有效的智能体可能会等待并重试、切换到替代数据源，或根据收到的错误消息调整其方法。

### 1.4.2 智能体如何工作

智能体通过图 1.6 所示的基本行动-感知循环运作。与生成单次响应的模型不同，智能体通过迭代循环工作——采取行动、感知结果，并根据结果适应，直到任务解决。多智能体系统建立在这一原理之上，多个智能体运行协调的行动-感知循环，以解决超出任何单个智能体能力的复杂任务。

![图 1.6：智能体的行动-感知循环](images/p043_0.png)

*图 1.6：智能体行动-感知循环：智能体通过迭代循环运作，在其中采取行动（例如调用 API）、感知结果（处理响应），并根据结果调整方法。成功时，智能体提供自然语言响应；出错时，它们可能以不同的参数重试，或告知用户局限性。*

这些能力由图 1.5 所示的三个核心组件协同工作实现：

#### 1.4.2.1 模型

支持决策和规划的推理引擎。这通常是一个大型语言模型（LLM）或大型多模态模型（LMM），能够理解上下文、生成计划并确定适当的行动。模型充当智能体的"大脑"，处理输入并决定下一步做什么。

为了让智能体成功完成任务，它们必须对任务状态进行推理，并确定要采取的适当行动。这一核心决策能力可以由生成式 AI 模型、预定义逻辑或显式的人类输入驱动。除了生成式 AI 模型之外，智能体还可以利用自定义逻辑（例如，基于某些启发式规则，在每次收到消息时调用 API 的逻辑），或显式的人类输入来驱动其行动和推理。智能地组合多种驱动因素的实现——使用生成式 AI 模型对任务状态进行推理，并请求即时（just-in-time）的人类输入提供反馈——可以显著提高智能体响应的质量和适应性。

#### 1.4.2.2 工具

工具（也称为技能或插件）是为执行特定任务而设计的逻辑的具体实现。它们是智能体对任务采取行动的主要方法。工具可以分为两类：通用工具和领域专用工具。

通用工具支持广泛的能力，例如代码执行器，它允许智能体完成任何可表达为代码的任务；或者 UI 界面驱动器，它允许智能体执行表述为一系列 UI 交互的任务。相比之下，领域专用工具旨在解决特定任务或一组相关任务（例如，使用特定参数调用天气 API）。为智能体提供工具访问权限，可以显著影响智能体能够处理的任务范围（多样性）和复杂性。

#### 1.4.2.3 记忆

为了让智能体有效执行任务并不断改进，它们需要记忆——回忆和复用过去交互信息的能力。这使智能体能够从经验中学习，并将教训应用于未来的任务。

**短期记忆**充当当前任务的工作记忆，跟踪近期行动、对话历史以及完成眼前目标所需的临时信息。在多智能体系统中，短期记忆通常包括共享上下文，以便智能体能够有效协调。

**长期记忆**存储积累的知识、成功的策略和学到的模式，这些在跨任务和会话之间持续存在。这使智能体能够随着时间建立专业能力，并将过去的经验应用于新情况。

除了这些时间维度上的区分，记忆系统还在控制权归属上有所不同。**应用管理的记忆**由开发者控制——信息由应用代码基于预定义策略自动存储和检索。**智能体管理的记忆**赋予智能体直接控制权——它们通过工具明确决定存储什么、何时检索信息，以及如何组织其知识库。在构建需要积极整理自身知识的智能体时，应用控制与智能体控制的记忆之间的这一区别非常重要。我们将在 4.8 节探讨这些记忆架构及其权衡。

这些组件在一个连续的循环中协同工作：模型对当前状态进行推理并确定要采取的行动，选择并使用合适的工具执行该行动，观察结果，用新信息更新记忆，并为下一步调整其方法。

> **对话式编程**
>
> 上述行动-感知循环引出一个实际问题：我们如何在代码中实现这种迭代的推理和行动？
>
> 一种强大的方法是对话式编程（conversational programming），其中智能体循环中的每一步——推理、行动和处理结果——都表示为对话中的消息。这与经过聊天微调的模型自然契合，这些模型的设计目的就是处理对话历史并生成上下文恰当的响应。
>
> 这种范式使智能体能够无缝融合自然语言交互与代码执行或 API 调用等具体行动，并构成了 AutoGen（Wu et al. 2023）等多智能体框架的基础——在这些框架中，智能体通过消息传递进行协调——这是我们将在后续章节详细探讨的模式。

### 1.4.3 智能体 vs 模型：清晰的区分

虽然智能体和模型都能处理自然语言并生成响应，但智能体在超越文本生成、与世界交互的能力方面有着根本的不同：

- 模型擅长基于其训练数据进行文本处理、分析和生成
- 智能体可以采取行动、使用工具、跨交互保持上下文，并根据结果调整其行为

我们的英伟达股价示例（表 1.1 中的任务 2）完美地说明了这一区别：模型可能会基于其训练数据生成一个听起来合理但可能错误的股价，而智能体会认识到需要当前信息，使用合适的工具获取实时数据，并提供准确、最新的响应。

这种超越文本生成、进入行动和适应的能力，正是智能体成为应对复杂现实世界任务的强大工具的原因——这些任务需要的不仅仅是信息合成。

## 1.5 什么是多智能体系统？

在智能体定义的基础上，我们将多智能体系统定义为：**涉及一组智能体的应用，每个智能体具有不同的能力和专门的目标，协同解决任务**。虽然这些智能体可以体现在物理机器人中，但本书聚焦于主要存在于数字世界的智能体。

如图 1.7 所示，多智能体系统可以通过两种截然不同的方法组织。

![图 1.7：多智能体编排的两种方法](images/p048_0.png)

*图 1.7：多智能体编排的两种方法：预定义工作流（左）与 AI 驱动的自主编排（右）。关键区别在于控制流是预先确定的，还是在运行时从 AI 驱动的决策中动态涌现。*

> **多智能体系统**
>
> 多智能体系统（或多智能体应用）是协同解决任务的智能体的集合。每个智能体保持特定的能力——推理、行动和沟通——并可以适应任务或环境的变化。多智能体系统的关键区别特征是其编排机制：决定智能体如何沟通、何时行动，以及它们在任务执行期间如何共享数据和控制流的模式。

> **编排**
>
> 在本书中，我们将反复使用"编排"（orchestration）一词，因此很有必要定义我们所指的含义。编排指使多个智能体能够有效协作实现共同目标的机制和模式。这涵盖两个主要方面——它们如何共享信息，以及谁控制执行流（它们行动的顺序）。
>
> 虽然学术文献和新兴实践有时将"协调"（coordination）和"编排"互换使用，但我们在全书中使用"编排"作为主要术语，以与行业标准及 AI/ML 框架中的常用用法保持一致。

如图 1.7 所示，多智能体系统可以通过两种截然不同的方法组织。**多智能体工作流**（左）使用预定义的控制流，智能体遵循既定的顺序和交接，创建可预测且可靠的过程。**自主多智能体系统**（右）使用 AI 驱动的编排，控制流在运行时动态确定，能够对复杂或不可预测的任务做出适应性响应。虽然两种方法都使用具有相同核心结构的智能体——模型、记忆和工具——但它们在编排决策的制定方式上有着根本的区别。

### 1.5.1 多智能体编排的两种方法

多智能体系统可以通过两种根本不同的方法组织，每种方法适合不同类型的问题：

**多智能体工作流（确定性编排）**：这些系统遵循预定义的协作模式，每个智能体都有明确指定的角色、职责和交接点。编排逻辑被显式编程，创建可预测且可重复的过程。例如，文档处理工作流可能有专门从事文本提取、分析和格式化的智能体，按预定顺序工作，每个阶段都有明确的输入和输出。

**自主多智能体编排（AI 驱动编排）**：这些系统使用 AI 模型驱动编排决策，允许智能体动态协商职责，并根据任务要求和中间结果调整其协作。编排从智能体交互中涌现，而不是预先编程的。这种方法对于最佳解决策略无法预先确定、必须通过探索和适应逐步形成的复杂任务特别有价值。

这两种方法之间的选择直接影响系统行为：工作流提供可预测性和可靠性，而自主系统提供适应性和创新性。我们将在第 2 章详细探讨每种方法中的具体模式，包括工作流的顺序和监督者模式，以及自主系统的群聊和交接模式。

> **一个适应性多智能体应用示例**
>
> 考虑这个场景：你需要创建一个应用，以最优价格预订前往特定目的地的航班。然而，你的目标航空公司 specialairlines.com 不提供 API——只有为人类用户设计的网页界面和移动应用。
>
> 这带来了几个超越简单查找和预订航班的挑战：
>
> **界面导航**：系统必须理解界面内容（HTML 元素、视觉布局），确定适当的动作（点击按钮、填写表单），并验证成功（检查确认消息）。每个动作都会改变界面状态，影响后续可能的动作。
>
> **动态适应**：系统必须通过迭代式问题解决来处理界面变化（按钮位置变动、表单字段更新）并从错误中恢复（预订失败、网络问题）。
>
> **多智能体编排**：成功需要专门智能体之间的协作——也许是负责界面交互的导航智能体、负责交易的支付智能体，以及负责验证的监控智能体——以及在需要协助时与人类用户沟通。
>
> 这一场景说明了一种解决方案无法预先确定、必须通过一系列适应性行动涌现的任务。它体现了需要跨多个智能体进行推理、行动、适应和沟通的复杂问题——超出当前单智能体系统能力的任务，是多智能体方法的理想候选。

## 1.6 为什么是现在？

多个因素凸显了多智能体生成式 AI 应用在今天的重要性，包括 AI 推理能力的进步、通过时间套利获得的经济机会、自我改进的系统、应对复杂任务的机会、对可靠自动化日益增长的需求、平台经济学，以及对伦理 AI 部署日益增长的需求。这些因素共同强调了多智能体系统在应对当代挑战中的重要意义。

### 1.6.1 生成式 AI 推理能力的进步

多智能体系统的大前提并不新鲜。这一主题已被广泛研究，既从理解人类如何协作解决任务的角度（集体智能、众包），也从人工智能体如何与自身和人类协作的角度（机器人规划、机器人导航、人机协作、群体智能等）。然而，人工智能体的发展一直受到限制，因为缺乏一个能够适应上下文、综合应对任务的计划并推动执行此类计划所需行动的推理引擎（或人工大脑）。生成式 AI 模型近期在展示出的推理能力上的进步——如 GPT-3.5 和 GPT-4——改变了这一现状，如今提供了一个关键组件，使创建真正自主多智能体系统的新实验和进展成为可能。

### 1.6.2 通过时间套利实现的经济价值

多智能体系统通过时间套利（time arbitrage）提供令人信服的经济优势。虽然智能体完成一项任务在绝对时间上可能比人类更长，但考虑到人类注意力的价值，经济学上有利于委托。例如，一项耗费你 30-100 美元时间（按你的时薪价值计算 1 小时）的任务，让智能体花 2-3 小时完成可能只需 1-2 美元。随着生成式 AI 推理成本持续下降，而人类时间变得更加宝贵，这一等式只会越来越有利。

### 1.6.3 自我改进系统的前景

与传统软件需要工程努力来改进不同，多智能体系统可以自动从底层 AI 模型的进步中受益。这创造了一个独特的机会：以最小的额外投入，构建价值随时间复利增长的系统。

> **注意**
>
> 在我的职业生涯中，我多次见到将能力委托给 AI 智能体的系统，其性能随着底层模型的改进而提升。一个很好的例子是我在 LIDA（Dibia 2023）上的工作——一个基于工作流的多智能体系统，用于从数据自动生成可视化。该系统初始版本使用 OpenAI 的 davinci 模型系列构建，在初始评估框架上的错误率为 20%。仅仅切换到几个月后发布的 GPT-3.5 turbo，错误率就全面从 20% 降至 3%。随着新的先进模型不断出现，我至今仍能看到这类系统级的改进。

### 1.6.4 应对隐性知识任务的机会

如今许多重复性问题难以自动化，或难以用可靠的软件工具支持。现有研究表明，一些自动化挑战源于这些任务需要隐性知识（tacit knowledge）——一种难以言说或编码、但更容易通过经验或实践传递的知识形式。然而，由编码了海量知识、并能与人类和其他智能体协作的 LLM 所赋能的智能体群体，为应对这些复杂任务提供了新的机会。这种方法可以帮助自动化以前被认为不可行的任务，从而减少人力投入和潜在的错误。

### 1.6.5 对可靠自动化日益增长的需求

企业和个人都在寻求能够自主执行复杂任务、同时保持高可靠性和安全性的 AI 解决方案。人类仍应留在监督回路中，确保自动化解决方案可靠、安全地带来成本和精力的节省。多智能体系统可以为复杂的现实世界自动化挑战提供所需的可靠性和适应性。

### 1.6.6 平台经济学与集成价值

多智能体系统实现了"超级应用"（everything app）经济学——通过集成而非专门的点状解决方案创造价值。这可以捕获用户偏好、跨领域学习并降低切换成本。同一个系统可以处理多样化的任务，无需用户进行专门配置或具备领域知识。平台经济学的收益包括：通过集成创造价值，作为平台节省时间并避免切换成本，以及能够捕获用户偏好、学习并随着时间推移变得更有价值。

### 1.6.7 伦理 AI 部署

随着 AI 部署的扩展和生成式 AI 模型应用于各种问题领域，对负责任、安全和以人为中心的多智能体框架的需求变得越来越关键。确保在 AI 开发和部署中满足伦理考量，有助于建立对这些系统的信任，并减少潜在的负面后果。

> **分布式智能体：跨越多个组织边界的智能体**
>
> 根据工程师的背景不同，"多智能体系统"一词可能唤起不同的心智模型。对一些人来说，重点是在单个应用/线程/进程内、具有相似权限结构而协作的软件实体。对另一些人来说，重点是分布式智能体互联网（internet of agents），其中智能体主要互不知晓（需要某种发现协议）、权限（安全与访问）明显不同，且通信必须在大规模下同时支持同步和异步模式。
>
> 在本书中，我们将主要聚焦第一种场景。虽然第二种很重要，但过早聚焦分布式智能体往往是过度设计——复杂性的增加——并且有标准方法可以帮助我们在需求出现时过渡到分布式设置。在 AutoGen 0.4 版本的重写/重新设计中，我们专门提供了可以是单进程或分布式的运行时（runtime）概念，允许开发者创建可以在任一模式下运行的智能体，而无需更改智能体逻辑本身。我们发现绝大多数用例都很好地由单进程/线程应用满足。
>
> 具体而言，在后面的章节（参见第 12 章）中，我们将讨论用于分布式智能体间通信的新兴协议、设计选择，以及如何将现有智能体适配到分布式环境中工作。

## 1.7 选择合适的 AI 智能体架构

构建 AI 应用需要从一系列架构谱系中选择合适的复杂度级别：用于文本生成的简单模型、用于行动的单智能体、用于结构化确定性协作的多智能体工作流，以及用于探索式问题解决的自主多智能体系统。虽然自主多智能体系统提供最复杂的能力，但它们引入了重大挑战，包括不可预测的结果、跨模型版本的可复现性问题、更高的出错概率，以及额外的成本和延迟。

### 1.7.1 决策框架

架构的选择遵循基于任务特征的逻辑递进。

从根本问题开始：**你的任务是否需要超越文本生成的行动？** 如果你的任务只涉及文本处理、分析或生成——例如回答训练数据中的问题、文档摘要或根据规格生成代码——那么直接调用 AI 模型生成响应就足够了。

对于需要行动的任务，下一个考虑是**你的解决方案方法是否广为人知、可以表达为工作流**。当你清楚了解所需步骤及其执行方式时，你是在单智能体和多智能体工作流之间做选择。

如果你的工作流受益于专门的专业能力——任务的不同部分需要不同的领域知识——那么多智能体工作流是合适的。当专门智能体之间的协作模式已被充分理解，且每个智能体的角色和交接遵循既定流程时，这种方法效果最好。例如，金融分析流水线需要独立的市场数据、风险评估和投资组合优化智能体按确定的顺序工作。然而，如果任务可以由一种专业能力有效处理，那么配备必要工具的单智能体更高效。

对于解决方案方法不明确的任务，你根据所需的探索程度在单智能体和自主多智能体系统之间做选择。如果任务涉及已知的动作序列，但需要相对简单的行动-感知循环——例如带结果验证的 API 调用——单智能体是合适的。然而，当解决方案通过探索和动态的智能体交互涌现、当智能体必须独立定义和改进、当智能体必须根据中间结果调整协作、或当性能通过从成功与失败中迭代学习而提升时，自主多智能体系统变得必要。例如，需求和实现方法通过实验逐步演进的应用开发。

**一个指导原则：选择能有效满足你需求的最简单架构。** 每个复杂度级别在提供更强能力和适应性的同时，都会引入额外的复杂性、开发时间和潜在故障点。如有疑问，从简单开始，随着你对任务真实需求的深入理解，再演进你的架构。

这些原则得到了 10.6 节综合评估结果的验证。当跨多种任务类型比较直接模型调用、带工具的单智能体和多智能体系统时，数据证实：直接模型调用在简单推理任务上表现出色（9.7/10 分，Token 效率比多智能体高 24 倍），而多智能体系统只有在任务需要工具协调或专门专业能力时才物有所值。例如，需要网络搜索的研究任务中，直接模型得分为 3.2/10，而支持工具的智能体得分为 9.0/10——展示了架构复杂性何时变得必要。

## 1.8 构建你的第一个多智能体系统

太棒了！如果你读到这里，你大概已经迫不及待要动手构建你的第一个智能体了。从第 4 章开始，我们将一起从零构建一个名为 picoagents 的多智能体库。

### 1.8.5 第 4 步：轮询编排

现在是激动人心的部分——让我们使用轮询编排（round-robin orchestration）让它们协作（一种简单的模式：智能体在共享对话中轮流处理任务，直到满足终止条件）：

```python
from picoagents.orchestration import RoundRobinOrchestrator
from picoagents.termination import MaxMessageTermination, TextMentionTermination
# 创建终止条件
termination = (MaxMessageTermination(max_messages=8) |
               TextMentionTermination(text="APPROVED"))
# 创建编排器
orchestrator = RoundRobinOrchestrator(
    agents=[poet, critic],
    termination=termination,
    max_iterations=4
)
```

现在，让我们用一个任务运行编排器：

```python
# 运行编排
async def run_orchestration():
    task = "Write a haiku about cherry blossoms in spring"
    stream = orchestrator.run_stream(task)
    async for message in stream:
        print(f"{message}")
asyncio.run(run_orchestration())
```

RoundRobinOrchestrator 管理一个轮流发言的循环，而终止条件确保对话恰当地结束——这里是达到最大消息数，或评论家以特定文本批准了俳句。

## 1.9 小结

总而言之，以下是本章的关键要点：

- **复杂性挑战**：生成式 AI 模型在许多任务上表现出色，但随着复杂性增加而面临局限。需要推理、规划和超越文本生成的行动的任务需要智能体——将模型与工具相结合、能够在世界中采取行动的系统。
- **智能体的定义与组件**：智能体是能够推理（使用逻辑合成信息）、行动（使用工具采取具体行动）、沟通（有效交换信息）和适应（根据反馈修改方法）的实体。这些能力由三个协同工作的核心组件实现：模型（推理引擎，通常是 LLM）、工具（支持行动）和记忆（短期记忆用于眼前任务，长期记忆用于积累的知识和经验）。
- **复杂任务的特征**：多智能体系统对表现出四个关键特征的任务最有益：需要规划（多步骤分解）、需要多元专业能力（专门的知识领域）、涉及海量上下文（大量信息），以及需要适应性解决方案（解决方案在动态环境中迭代涌现）。
- **决策框架**：当任务复杂、需要多元专业能力、涉及动态环境或受益于适应时，使用多智能体方法。对于简单、确定性的任务，专业能力多样性低或环境静态时，应避免使用。
- **当前的机遇**：多个因素使当下成为开发多智能体系统的有利时机：生成式 AI 推理能力的进步为自主智能体奠定了基础；时间套利带来的经济价值（智能体成本 1-2 美元 vs 人类时间 30-100 美元）；无需重新工程即可受益于 AI 模型进步的自我改进系统；应对以前无法自动化的隐性知识任务的机会；对可靠自动化日益增长的需求；实现"超级应用"集成价值的平台经济学；以及对伦理 AI 部署框架的需求。

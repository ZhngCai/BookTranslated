# 第 2 章　多智能体模式

本章涵盖：

- **多智能体编排模式的分类**：理解从显式工作流控制到自主涌现式编排的谱系
- **工作流模式**：顺序、条件、并行和监督者模式，具有开发者定义的执行路径和可预测的行为
- **自主模式**：群聊、交接和分层模式，智能体通过运行时推理和沟通确定编排
- **模式选择指南**：比较可靠性、自主性和复杂性之间的权衡，为你的任务选择正确的方法

作为一名软件工程师，你在职业生涯中很可能遇到过各种模式。无论是在计算机科学课程中学习单例（singleton）和观察者（observer）等设计模式，还是在准备面试时发现双指针和滑动窗口等算法模式，其底层原则始终一致：通过实验和实践，我们的领域识别出最有效的方法，并将这些洞见固化为可复用的解决方案。

模式为管理复杂性提供了结构，防止我们对已经充分理解的问题重复发明解决方案。多智能体系统也不例外。在第 1 章中，我们将智能体定义为能够推理、行动、沟通和适应以解决任务的实体，并探讨了使用多个智能体处理具有规划需求、多元专业能力需求和适应性解决方案的复杂任务的益处。本章探讨为有效协调多个智能体而涌现的编排模式。

多智能体编排的架构深刻影响系统行为。选择不当的模式可能导致无限循环、成本过高，或在现实条件下崩溃的脆弱解决方案。相反，某些模式会产生固有更可靠（但更受限）的系统，而另一些模式则支持可优雅适应复杂任务的可扩展系统。重要的是，智能体在处理任务，选择正确的任务管理模式——即何时暂停、委托给人类或重试——对于防止失控执行和确保智能体保持生产力至关重要。

## 2.1 多智能体编排模式的分类

如果你阅读多篇关于智能体应当如何编排的文章，会遇到各种术语，如"顺序模式""监督者模式""分层模式"和"群体模式"。虽然这些描述各不相同，但底层模式可以沿一个基本谱系分类：授予智能体确定其编排的自主性水平。

谱系的一端是工作流模式——开发者显式定义执行路径和控制流。另一端是自主模式——智能体通过运行时推理和沟通确定编排。理解这一谱系至关重要，因为每种方法在可预测性和灵活性之间提供了不同的权衡。

多智能体协调建立在数十年分布式系统研究的基础上。Apache Airflow、Temporal 和 Prefect 等传统工作流引擎，通过基于 DAG 的依赖管理和健壮的状态同步，仍然是实现工作流模式的绝佳基础。然而，AI 智能体引入了根本性差异：使用自然语言而非规则/启发式进行语义推理、基于中间结果适应的动态规划、需要新错误检测方法的概率性输出，以及基于 Token 的经济学——通信成本随对话长度而增长。这些差异在自主模式中最为明显，AI 驱动的协调实现了超越传统工作流系统的能力。

## 2.2 工作流模式（显式控制）

工作流模式提供开发者定义的执行路径，具有可预测的行为。一种常见的、新兴的实践是借鉴图论的概念，将多智能体编排建模为计算图，其中节点代表计算单元（单个函数、智能体，甚至智能体团队），边定义节点之间的控制流。

这种方法中的关键概念包括：

- **节点（Node）**：图中的计算单元（例如，一个智能体或函数）。节点通常有定义的输入，可以处理并生成输出数据结构。此外，节点可以维护自己的内部状态，读取和修改某些共享状态。它们通过输出和共享状态与系统其余部分交互。
- **边（Edge）**：节点之间的连接，定义两个节点之间的控制流或转移。对于定义从节点 A 到节点 B 的转移的边 E，其隐含行为是 A 的输出成为 B 的输入。边可以是条件性的——例如，从节点 A 到节点 B 的转移仅在满足某个条件时发生。该条件可以基于前一个节点的输出、某些共享状态、某些外部信号、任意逻辑、人类输入或它们的组合。

反过来，图方法带来了几个关键益处：执行路径在运行前的验证、智能体交互的可视化（便于推理系统行为），以及确定性的执行行为。

### 2.2.1 顺序工作流

顺序工作流是实现线性执行的编排模式，每个节点的输出馈入下一个节点（A -> B -> C），确保有序处理并具有可预测的执行时序。例如，图 2.2 所示的新闻摘要流水线：

![图 2.2：顺序工作流模式](images/p072_0.png)

*图 2.2：顺序工作流模式，展示从用户请求到主题选择、研究、分析再到报告生成的线性执行流。*

每个步骤必须在下一步开始前完成，确保信息的有序处理。顺序工作流非常适合具有自然顺序依赖的任务，一个阶段的输出成为下一阶段的基本输入。它们提供可预测的执行时序和清晰的错误隔离——如果一个阶段失败，你确切知道故障发生在哪里。在第 6 章中，你将使用 workflow.chain(step_a, step_b, step_c) 实现此模式，按顺序连接步骤。

### 2.2.2 条件工作流

条件工作流是使用基于逻辑的边来确定下一节点的编排模式，基于条件实现分支执行路径和动态路由。一个经典示例是图 2.3 所示的代码开发：

![图 2.3：条件工作流模式](images/p073_0.png)

*图 2.3：条件工作流模式，展示分支逻辑：代码测试可以要么通过（进入部署），要么失败（回到代码编写）。*

这种模式自然扩展到监督者式工作流——条件工作流的一种变体，中央控制节点评估请求，并根据任务特征将任务路由到专门智能体。考虑一个将咨询路由到相应部门的客户服务系统：

![图 2.4：监督者工作流模式](images/p074_0.png)

*图 2.4：监督者工作流模式，展示一个控制节点根据咨询类型将任务路由到专门智能体。*

监督者评估每个传入请求，并委托给合适的专门智能体，结果回流进行最终处理。在第 6 章中，条件路由使用带条件的 Edge 对象，基于验证结果实现分支：

```python
workflow.add_edge(
    "validate",
    "process",
    condition={
        "type": "output_based",
        "field": "is_valid",
        "value": True
    }
)
```

当每个节点本身包含一个工作流时，我们就得到了分层模式，可以构建多级支持台等复杂系统。主监督者委托给部门监督者，后者再管理其专门团队——创建多层编排以处理复杂的组织工作流。

### 2.2.3 并行工作流

并行工作流是使用有向无环图（Directed Acyclic Graph，DAG）实现独立任务并发执行的编排模式，具有拆分工作的扇出（fan-out）阶段和合并结果的扇入（fan-in）阶段。该模式有一个扇出阶段（拆分工作）和扇入阶段（合并结果）：

![图 2.5：并行工作流模式](images/p076_0.png)

*图 2.5：并行工作流模式，展示独立任务的并发执行及扇出和扇入阶段。*

并行执行非常适合可以无副作用并行化的工作，例如处理多个数据源或运行独立的分析。当单个任务耗时且可以同时运行时，此模式提供显著的性能收益。然而，它需要在扇入阶段仔细编排，确保所有并行分支在继续之前完成。第 6 章中的实现使用带自动扇入检测的 DAG 执行——当多条边以"always"条件指向同一步骤时，运行器会等待所有依赖完成。

工作流模式的主要优势是可靠性——你确切知道将会发生什么以及何时发生。然而，这种可预测性以牺牲灵活性为代价。工作流模式难以应对需要动态适应的任务，或最优动作序列无法预先确定的任务。

从实现的角度看，存在构建阶段（图被构造）和运行阶段（图被执行）的概念。有经验的读者可能会观察到，这些工作流模式与数据处理和软件开发中广泛使用的著名流水线模式在根本上相似。除了融入智能计算（例如节点中的 LLM 或嵌套工作流）之外，核心概念基本保持不变。这种相似性实际上是有利的——它使我们能够利用软件工程、扩展和测试中的现有思想来构建可靠的多智能体系统。

然而，这种方法依赖于几个假设：问题的解决方案是已知的，即正确的任务分解已被识别；必要的资源（如时间和开发者专业能力）可用于创建适当的动作序列；任务本身是静态和可预测的，无需实时调整或变更。在许多动态的现实世界场景中，这些假设往往不成立——任务参数可能变化，解决方案需要固定预定义流水线无法提供的灵活性和适应性。此外，许多团队可能缺乏为广泛任务制定特定解决方案所需的资源。

当这些假设不成立时——任务动态、解决方案未知或资源有限——自主模式提供了另一种方法，将控制权从开发者转移到智能体自身。

## 2.3 自主模式（涌现式控制）

自主模式基于任务状态和智能体推理实现运行时确定的执行。这里的一个关键思想是：控制流由 AI 模型驱动，因此在运行时动态确定。智能体不是遵循规定的路径，而是通过沟通和对当前任务上下文的共同理解进行编排。这些模式存在于一个控制谱系上，从结构化编排到完全涌现的行为。

> **智能体层层嵌套**
>
> 一条重要的设计原则同时适用于工作流和自主模式：任何"智能体"本身在内部都可能是一个多智能体系统。这些复合智能体向更广泛的系统呈现为单一实体，而其内部对话和编排保持私有。
>
> 例如，在基于计划的编排中呈现为单一"编码智能体"（Coder agent）的实体，其内部可能使用顺序工作流（研究→编码→测试步骤）。类似地，交接模式中的"研究团队"（Research Team）智能体可能在内部通过 AI 驱动的对话协调专家。标记为"法律审查"（Legal Review）的工作流节点，其内部可能是一个并行工作流，同时将文档分发给多个审查者。
>
> 这种分层方法提供了清晰的边界，并减少了整体系统中的通信噪声。它还允许你在不同的抽象层使用不同的编排模式——为每一层的特定协调需求选择正确的模式，而不是在所有地方强制使用单一模式。

### 2.3.1 基于计划的编排模式

基于计划的编排模式是一种自主模式，使用单一的编排器智能体通过显式的计划创建、动态任务分配和集中式进度监控来管理整个任务执行。这个智能体充当"项目经理"，创建计划、分配工作、审查进度，并在专门智能体之间进行编排。

控制流特征：

- **计划管理**：编排器维护带有分配和依赖关系的显式任务计划
- **可见性**：编排器看到所有上下文；其他智能体只接收相关信息
- **任务分配**：编排器基于当前计划进行显式的工作分配
- **状态管理**：集中在编排器中（计划、进度监控、结果评估）

![图 2.6：基于计划的编排模式](images/p079_0.png)

*图 2.6：基于计划的编排模式，展示单个编排器管理跨多个智能体的任务执行。*

考虑一个软件开发任务：编排器创建开发计划，将研究分配给智能体 A，监控输出，然后仅将智能体 A 研究中的相关上下文交给智能体 B 进行编码。这种选择性信息共享有助于防止上下文过载并保持专注。

编排模式擅长复杂任务分解和资源管理。它们可以在保持监督的同时高效地编排多样化的专家。然而，它们造成了单点故障，并可能在编排器的推理能力上成为瓶颈。

在第 7 章中，PlanBasedOrchestrator 使用 LLM 生成的计划和自动步骤评估实现此模式：

```python
from picoagents.orchestration import PlanBasedOrchestrator
orchestrator = PlanBasedOrchestrator(
    agents=[researcher, coder, reviewer],
    termination=MaxMessageTermination(20),
    model_client=model,
    max_step_retries=2
)
result = await orchestrator.run_stream(
    "Build a data analysis tool"
)
```

编排器自主创建执行计划（第 1 步：研究，第 2 步：编码，第 3 步：审查），在进行下一步之前评估每个步骤的成功，并根据失败分析用增强的指令重试失败的步骤。这种自动化的规划和恢复使该模式对瞬态故障具有韧性，同时保持监督。

> **用基于计划的编排应对复杂任务**
>
> 2023 年 11 月，一群来自 HuggingFace 和 Meta 的研究人员发表了一篇论文，介绍了 GAIA 基准（Mialon et al. 2023）。其核心目的是引入需要推理、多模态处理、网页浏览和通用工具使用能力等能力的任务——这些任务对人类来说概念上简单，但对最先进的 AI 而言具有挑战性。当时，我有幸与同事 Adam Fourney 合作，他领导了一个项目，目标是用 AutoGen 设计一个在 GAIA 上表现出色的多智能体系统。经过多次迭代并在排行榜上夺得第一名之后，我们得出了一个设计，并发表在题为"Magentic-One：使用 LLM 构建多智能体系统完成复杂任务"的论文中（Fourney et al. 2024）。Magentic-One 使用一种多智能体架构，一个领导智能体 Orchestrator 通过显式的任务台账和进度台账（Task and Progress Ledgers）指挥另外四个智能体解决任务，在多个具有挑战性的智能体式基准上取得了与最先进水平统计上可比的表现。类似地，Anthropic 的 Research 系统（Hadfield et al. 2025）采用编排器-工作者模式，领导智能体协调流程，同时委托给并行运行的专门子智能体，领导智能体根据查询复杂度动态生成 1-10 个以上的子智能体，相较单智能体方法实现了 90.2% 的性能提升。

虽然编排模式保持集中式控制，交接模式则在保持结构化编排的同时，将决策分散到各个智能体。

### 2.3.2 交接模式

交接模式是自主模式，使智能体能够以有限的局部知识运行，同时通过点对点委托实现协调行为。智能体基于对任务的理解和对其他可用智能体的了解，就何时以及向谁转移控制做出局部决策。

控制流特征：

- **可见性**：每个智能体只知道其他智能体的一个子集及其能力
- **轮流机制**：通过显式转移机制直接交接
- **决策制定**：基于任务需求和已知智能体的局部决策
- **状态管理**：在交接期间在智能体之间显式传递

![图 2.7：交接模式](images/p082_0.png)

*图 2.7：交接模式，展示智能体根据任务需求转移控制和上下文。*

一个客户服务场景说明了这一模式：客户服务智能体可以根据问题类型交接给技术专家或计费智能体。技术专家又可以交接给高级工程师，或将控制权返回给客户服务。每个智能体基于其对情况的局部评估做出交接决策，并传递相关上下文。

交接模式提供可扩展性和专门化，同时避免中心瓶颈。它们对于交接标准可以清晰建立的明确领域特别有效。从实现角度看，这种模式相对简单——智能体可以表示为工具；例如，智能体 A 将智能体 B 和 D 视为可用工具，交接即成为工具调用。然而，它们需要仔细设计，以防止智能体卡住或无效循环。

沿着自主性谱系继续前进，对话驱动模式甚至移除了结构化交接的约束，允许编排通过共享对话自然涌现。

### 2.3.3 对话驱动模式（群聊）

在对话驱动模式（也称为群聊模式）中，所有智能体参与共享对话，编排通过对话中的轮流发言涌现，而非显式计划或结构化交接。轮流发言是智能体依次轮流向共享对话贡献内容的机制。这种方法映照了人类团队协作——每个人都能看到讨论，并在适当时贡献。

> **为什么对话驱动模式天然有效**
>
> 大多数现代 AI 模型都为"聊天补全"（chat completions）而训练——通过阅读消息历史并生成恰当的响应，在对话中轮流发言。这使得 LLM 固有地非常适合对话驱动的协调，因为它们可以自然地参与多轮对话，并根据对话上下文确定适当的贡献。
>
> **实现简单性**：编排机制本质上是"所有智能体向同一个共享对话列表追加消息"——与复杂的工作流图相比，只需极少的编排逻辑。
>
> **自动改进**：随着上游 AI 模型能力增强，系统性能自动提升，无需更改代码即可获得"免费升级"。

*图 2.8：在对话驱动模式中，智能体主要通过向共享对话追加内容进行协作。*

控制流特征：

- **可见性**：广播式——所有智能体观察共享对话中的所有消息
- **轮流机制**：由选择机制（轮询、随机或 AI 驱动）确定
- **决策制定**：基于对话上下文选择下一个发言者，而非预定计划
- **状态管理**：隐含在对话历史中

#### 2.3.3.1 轮询对话模式

在轮询对话模式中，智能体按固定的重复顺序轮流发言，直到满足某个终止条件。对话以循环方式流动，每个智能体在将发言权传给下一个智能体之前贡献自己的输入。

![图 2.9：轮询对话模式](images/p085_0.png)

*图 2.9：在轮询对话模式中，智能体按固定顺序轮流发言。*

在第 7 章中，RoundRobinOrchestrator 通过按顺序循环智能体实现此模式：

```python
from picoagents.orchestration import RoundRobinOrchestrator
from picoagents.termination import MaxMessageTermination
orchestrator = RoundRobinOrchestrator(
    agents=[researcher, writer, critic],
    termination=MaxMessageTermination(12)  # 12 条消息后停止
)
async for message in orchestrator.run_stream("Research solar energy trends"):
    print(message)  # researcher -> writer -> critic -> researcher -> ...
```

#### 2.3.3.2 AI 驱动对话模式

在 AI 驱动对话模式中，LLM 或其他 AI 模型基于当前对话上下文选择下一个发言的智能体。这种选择可以基于任务状态、智能体专长或其他动态因素。轮次选择机制本身可以是另一个 LLM 提示词，评估对话历史并决定下一个该谁发言。

![图 2.10：AI 驱动对话模式](images/p087_0.png)

*图 2.10：在 AI 驱动对话模式中，LLM 基于上下文动态选择下一个智能体。*

例如，考虑一个研究任务：Research 智能体收集信息，Writer 撰写内容，Critic 提供反馈。在轮询选择中，每个智能体按预定顺序轮流。在 AI 驱动选择中，LLM 选择器基于当前对话状态确定下一个发言者："研究已完成，所以 Writer 应该起草内容"或"草稿需要改进，所以 Critic 应该提供反馈。"

在第 7 章中，AIOrchestrator 使用 LLM 智能地选择下一个发言者：

```python
from picoagents.orchestration import AIOrchestrator
orchestrator = AIOrchestrator(
    agents=[researcher, writer, critic],
    model_client=model,  # 用于智能体选择
    termination=MaxMessageTermination(12)
)
async for message in orchestrator.run_stream("Write article on AI trends"):
    print(message)
```

LLM 分析对话上下文和智能体能力，动态选择下一个发言者。例如，研究完成后，LLM 选择 writer 起草内容；草稿完成后，选择 critic 提供反馈。与固定轮流相比，这种自适应选择实现了更自然的协作。

对话驱动模式的优势在于其透明性和涌现式协作。所有智能体保持共享上下文，并可以自然地在他人的贡献之上构建。借助 AI 驱动的选择，复杂行为有机地涌现——例如，当代码执行结果出现在对话历史中后，Coder 智能体可能被再次选中，从而无需显式编程即可实现自然的重试循环、分支逻辑和就地探索。

> **与单智能体模式的联系**
>
> 对话驱动模式通过轮流发言和共享对话历史，天然实现了 ReAct（Yao et al. 2022）和 Reflexion（Shinn et al. 2023）等著名的单智能体研究模式。
>
> ReAct 创建了思考-行动-观察（Thought-Action-Observation）循环，其中推理轨迹指导行动计划。在回答复杂问题时，智能体在思考（"我需要搜索 X"）、行动（搜索维基百科）和观察结果以规划下一步之间交替。
>
> Reflexion 将失败转化为作为情景记忆存储的语言反馈。当任务失败时，智能体生成解释错误和纠正措施的反思——例如"我错误地假设锅在炉灶上。下次我应该先确认它的位置"——然后在后续尝试中应用这些教训。
>
> 在对话驱动模式中，这些行为自然涌现：专门智能体（Thinker、Actor、Observer）通过轮流发言实现思考-行动-观察循环，而对话历史中的过往错误实现了 Reflexion 式的学习。对话本身成为情景记忆，同时支持推理循环和从失败中学习。

然而，对话驱动模式面临显著的局限。Token 用量随对话长度线性增长，使其对长时间任务代价高昂。上下文窗口可能溢出，导致智能体丢失重要的早期上下文。正如 Cognition 的研究（Yan 2025）所强调的，基于同一对话工作的智能体仍可能因对彼此推理的不完全理解而做出"相互冲突的决策"，尽管可见性是共享的，仍可能导致零散的结果。

## 2.4 模式选择与比较

在探索了多智能体编排模式的完整谱系之后，我们现在可以从四个关键维度比较每种方法：**控制流**（执行如何在智能体之间移动）、**自主性**（系统能多灵活地探索开发者未显式编程的解决路径）、**控制**（开发者对系统行为拥有多少可预测的控制）、**复杂性**（所需的实现和运维复杂性）。

表 2.2 总结了各模式之间的权衡。注意控制和自主性如何反向变化：工作流以灵活性为代价提供可预测性，而对话驱动模式支持探索但行为确定性较低。

### 2.4.2 选择标准

与其问"哪种模式最好？"，不如问"我的任务需要什么？"不同的任务有根本不同的需求。步骤已知的数据流水线需要可预测性；开放式研究任务需要探索。让模式匹配任务的内在特征。

**任务特征**：

- 定义明确、可重复的流程 → 工作流模式（顺序、条件、并行）
- 动态、探索性任务 → 自主模式（对话驱动）
- 需要复杂规划 → 基于计划的编排
- 需要领域专业能力 → 交接模式

**系统需求**：

- 需要高可预测性 → 工作流模式
- 需要最大自主性 → AI 驱动对话
- 资源受限 → 交接模式（协调开销最小）
- 可扩展性顾虑 → 并行工作流或交接模式

**实现考虑**：

- 开发者资源可用 → 工作流模式
- 需要快速原型 → 对话驱动模式
- 生产可靠性至关重要 → 带显式任务管理的工作流模式
- 需要人类监督 → 任何模式 + 人类委托

### 2.4.3 混合方法

大多数生产系统受益于混合方法，基于任务分解组合多种模式：

- 对可预测、充分理解的组件使用工作流模式
- 在灵活性和适应必不可少的地方应用自主模式
- 在所有编排类型中一致地实现任务管理模式
- 设计分层组合，复杂智能体在内部使用不同模式

关键原则是模式与任务的对齐：让编排模式匹配每个任务的内在特征和系统的可靠性需求，而不是将所有编排强行套入单一模式类型。

## 2.5 任务管理模式

除编排模式之外，成功的多智能体系统还需要显式的任务管理策略，以确保富有成效的结果并防止失控执行。这些横切关注点同时适用于工作流和自主模式。

任务管理模式解决了超越编排分类法的关键运维问题。虽然工作流模式通常将一些任务管理逻辑嵌入其图结构中，但自主模式特别受益于显式的任务管理策略。

### 2.5.1 终止模式

有效的终止策略防止无限循环和过度的资源消耗：

- **基于预算的终止**：对时间、成本或迭代次数设置限制
- **语义终止**：使用 LLM 推理检测任务完成
- **外部信号**：支持人类干预或 API 触发的停止

例如，一项研究任务可能在 10 次迭代后终止，或者当 LLM 判定质量阈值已达到时终止，以先到者为准。

### 2.5.2 人类委托模式

复杂或敏感的任务往往需要人类监督。两种主要方法可实现有效的人类委托：

**基于 LLM 的委托**依赖智能体推理来确定升级需求。智能体评估风险、复杂性和置信度等因素，决定何时需要人类输入。例如："这条客户投诉提到了潜在的法律诉讼，可能影响我们的声誉——升级给人类审查。"

**基于规则的委托**使用代码中定义的显式触发器。这些提供基于硬阈值的确定性、可审计的升级：超过 10,000 美元的金融交易、涉及医疗或法律领域的请求，或连续三次任务完成失败。

## 2.6 小结

- **编排谱系**：多智能体模式存在于从显式控制（工作流模式）到涌现行为（自主模式）的谱系上。授予智能体的自主性水平从根本上决定了系统可预测性与灵活性的权衡。
- **工作流模式（显式控制）**：顺序工作流提供线性执行（A->B->C），条件工作流支持分支逻辑和监督者委托，并行工作流通过 DAG 支持并发执行。这些模式提供高可靠性和可预测性，但对动态情况的适应性有限。
- **自主模式（涌现式控制）**：基于计划的编排使用中央编排器进行动态规划，交接模式支持带局部决策的点对点委托，对话驱动模式允许通过共享对话进行编排。这些模式提供更大的灵活性，但需要更复杂的编排机制。
- **模式选择标准**：对需要高可预测性的定义明确、可重复的流程选择工作流模式。对需要灵活性的动态、探索性任务选择自主模式。考虑基于任务分解和系统需求组合多种模式的混合方法。
- **任务管理要点**：成功的多智能体系统需要显式的任务管理策略，包括终止模式（基于预算、语义或外部信号）、人类委托模式（基于 LLM 或基于规则）以及超越特定编排方法的错误处理机制。
- **实现指导**：让编排模式匹配任务特征，而不是将所有编排强行套入单一模式类型。使用分层组合，复杂智能体在内部实现不同模式，同时向更广泛的系统呈现统一接口。

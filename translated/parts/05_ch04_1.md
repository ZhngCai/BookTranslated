在进入实现细节之前，先看看我们最终要构建的开发者体验（代码清单 4.1）。别忘了将 "your_api_key" 替换为你的实际 OpenAI API 密钥。

*代码清单 4.1：完整的 picoagents Agent 示例*

```python
from picoagents import Agent, OpenAIChatCompletionClient
def get_weather(location: str) -> str:
    """Get current weather for a given location."""
    return f"The weather in {location} is sunny, 75°F"
# Create an agent - that's it!
agent = Agent(
    name="assistant",
    description="You are a helpful assistant.",
    instructions="You are helpful. Use tools when appropriate.",
    model_client=OpenAIChatCompletionClient(
        model="gpt-4.1-mini",
        api_key="your_api_key"
    ),
    tools=[get_weather]  # Functions become tools automatically!
)
# Use the agent
async for event in agent.run_stream("What's the weather in Paris?"):
    print(event)  # Stream events
```

[assistant] 16:55:45 | The weather in Paris is sunny, 75°F

## 4.1 设计原则

在逐步构建我们的智能体框架时，我们将做出关键的架构决策，这些决策决定你的智能体开发、调试和扩展的难易程度。这些不是抽象原则，而是解决你在构建智能体应用时会遇到的实际问题的实用选择。

**异步优先架构**：智能体任务涉及多个慢速操作：LLM API 调用（500ms-5s）、工具执行（时间不一）和 I/O 操作。没有异步，你的智能体在每次调用期间都会空闲，使多智能体系统慢得令人痛苦。一个简单的 3 智能体工作流同步执行可能需要 30 秒，但通过适当的并发只需 10 秒。我们在整个过程中采用 async/await，因为将异步改造成同步代码比反过来要困难得多。

**基于事件的流式传输**：智能体任务完成多个步骤可能需要 30 秒以上。没有流式传输，用户只能盯着空白屏幕，怀疑是否有任何进展。流式传输提供实时进度更新、支持响应式用户界面，并提供调试多步智能体行为所需的可观测性数据。当智能体卡在工具调用循环中时，流式事件会准确显示问题发生的位置。

**组件序列化**：你需要保存智能体配置、在团队成员之间共享，并可能为非技术用户构建可视化编辑器。当每个组件（智能体、工具、记忆）都能将自身序列化为 JSON 时，你可以对完整的智能体设置进行版本控制、构建配置 UI，并从保存的会话中恢复智能体配置和状态。

**优雅取消**：用户会启动长时间运行的智能体任务，然后需要取消它们——无论是由于提示词错误、无限循环，还是为了提供反馈。

**带核心行为的抽象基类**：当你想支持多个 LLM 提供商、不同的工具类型或各种记忆后端时，抽象接口可以防止供应商锁定，并支持使用 Mock 实现进行测试。BaseTool 接口让你从简单函数开始，之后无需更改智能体代码即可添加 REST API 工具、数据库工具或 MCP 工具等新兴标准。

## 4.2 智能体执行循环

任何智能体框架的核心都是**智能体执行循环**（agent execution loop）。理解这一循环至关重要，因为它决定了智能体如何思考、行动和学习。让我们从识别基础组件开始。

每次智能体交互都遵循相同的基本模式：

1. **准备上下文**：组合任务 + 指令 + 记忆 + 对话历史
2. **调用模型**：将上下文发送给 LLM 并获取响应
3. **处理响应**：处理文本响应或执行工具调用
4. **迭代**：如果调用了工具，将结果添加到上下文，并从第 2 步重复
5. **返回**：提供最终响应并更新记忆（如适用）

*代码清单 4.2：简化的智能体执行循环伪代码*

```python
# Simplified agent loop pseudocode
async def agent_execution_loop(task):
    context = prepare_context(task, instructions, memory, history)

    while not done:
        response = await model_client.create(context)

        if response.has_tool_calls:
            for tool_call in response.tool_calls:
                result = await execute_tool(tool_call)
                context.append(result)
        else:
            done = True
    update_memory(context) # optional
    return response
```

如代码清单 4.2 所示，智能体在一次"运行"（run）中采取多个步骤（模型调用 -> 工具调用 -> 模型调用），每个步骤可能花费任意长的时间。从这个角度看，智能体能够提供或流式输出进度更新非常重要，这在有人类等待响应的场景中尤其有益。流式传输还提供了调试智能体行为所需的可见性。

### 4.2.1 流式事件与实时更新

流式传输允许智能体在执行期间以事件形式产出进度更新，提供对正在发生的事情的实时可见性。这对于构建响应式 UI 和实时调试智能体行为至关重要。

### 4.2.2 BaseAgent：基础

让我们开始实现智能体架构。我们的智能体需要处理对话中不同类型的消息——系统指令（SystemMessage）、用户输入（UserMessage）、助手响应（AssistantMessage）和工具执行结果（ToolMessage）。我们将使用结构化的消息类型（用 Pydantic 构建以保证类型安全）来清晰表示这些通信。

现在定义基础智能体接口：

*代码清单 4.3：BaseAgent 类定义与初始化*

```python
class BaseAgent(ABC):
    """Abstract base class defining the core agent interface."""
    def __init__(
        self,
        name: str,
        instructions: str,
        model_client: 'BaseChatCompletionClient',
        tools: Optional[List] = None,
        memory: Optional['BaseMemory'] = None,
        context: Optional['AgentContext'] = None,
        middlewares: Optional[List] = None,
        max_iterations: int = 10
    ):
        self.name = name
        self.instructions = instructions
        self.model_client = model_client
        # Process optional components with defaults
        self.tools = self._process_tools(tools or [])
        self.memory = memory
        self.context = context or AgentContext()
        self.middleware_chain = MiddlewareChain(
            middleware or []
        )
        ...
```

BaseAgent 的初始化（代码清单 4.3 所示）建立了核心智能体组件：用于推理的模型客户端、用于行动的可选工具、用于学习的可选记忆，以及对上下文和中间件注入的支持。灵活的初始化支持从简单聊天机器人到复杂多工具系统的各种智能体。

智能体结构定义之后，我们需要指定执行契约。每个智能体必须实现两个定义任务处理方式的核心方法：

*代码清单 4.4：BaseAgent 的执行抽象方法*

```python
class BaseAgent(ABC):
    # ... initialization code from above ...
    @abstractmethod
    async def run(
        self,
        task: Union[str, UserMessage, List[Message]]
    ) -> 'AgentResponse':
        """Execute agent and return final response."""
        pass
    @abstractmethod
    def run_stream(
        self,
        task: Union[str, UserMessage, List[Message]]
    ) -> AsyncGenerator[Union[Message, 'AgentEvent'], None]:
        """Execute agent with streaming output."""
        pass
```

这些抽象方法（代码清单 4.4）强制每个智能体实现必须支持收集式（run）和流式（run_stream）两种执行模式。流式优先的设计确保我们能够构建响应式 UI，同时为不同的应用需求提供灵活性。

构造函数包含用于高级场景的 context 和 middleware 参数。大多数应用使用默认值，但显式注入支持特定用例：

- **上下文注入**：用对话历史预填充智能体
- **状态恢复**：从序列化的上下文重新加载智能体状态
- **编排**：在工作流中的智能体之间共享上下文
- **测试**：注入受控状态以实现可复现的测试

## 4.3 任务取消

智能体任务可能运行几分钟甚至几小时——研究主题、调用 API、处理数据。用户需要能在任务中途停止这些操作：他们意识到提示词写错了、智能体陷入循环，或者想在继续之前提供反馈。

我们通过 CancellationToken 实现任务取消——一种线程安全机制，通过异步操作传播停止信号。任务取消是中断并干净地终止正在运行的智能体操作的能力，停止 LLM 调用、工具执行和所有下游处理。智能体在执行期间的关键点检查此令牌：

*代码清单 4.5：使用取消令牌停止智能体执行*

```python
from picoagents import Agent, CancellationToken
# Create a cancellation token
token = CancellationToken()
# Pass it to the agent
async def run_with_cancellation():
    async for event in agent.run_stream(
        "Long running task",
        cancellation_token=token
    ):
        print(event)
# From another thread or async task - stop the agent
token.cancel()  # Stops execution immediately
```

当调用 cancel() 时（代码清单 4.5），令牌在智能体执行循环中传播——在流中停止 LLM 调用、阻止新的工具执行，并抛出 asyncio.CancelledError 以干净退出。智能体实现在每次模型调用前、Token 流式传输期间以及工具执行前检查 token.is_cancelled()。

同样的模式在整个框架中通用：智能体、编排器和工作流都接受 cancellation_token 参数。在第 8 章中，我们将把用户界面的"停止"按钮连接到取消令牌，让用户控制长时间运行的操作。

## 4.4 添加模型客户端

模型客户端是智能体与生成式 AI 模型之间的接口。这里设计良好的抽象可以支持多个 LLM 提供商，同时保持智能体代码干净。在本节中，我们将介绍一个通用的 BaseChatCompletionClient，它定义了两个关键方法——create 用于从 LLM 模型获取生成结果，create_stream 用于获取流式响应。

> **为什么叫 "BaseChatCompletionClient"？**
>
> 我们使用"ChatCompletion"一词，因为现代 LLM 是为具有交替角色（system、user、assistant）的对话交互而训练的。这种多轮对话格式——每条消息都有特定角色，模型以"assistant"角色生成响应——与旧的补全模型（只是继续文本）根本不同。"chat completion"术语反映了这种基于角色的对话训练范式，它实现了更结构化、更可控的交互。

*代码清单 4.6：BaseChatCompletionClient 抽象接口*

```python
from abc import ABC, abstractmethod
from typing import List, Optional, Dict, Any
class BaseChatCompletionClient(ABC):
    """Abstract interface for LLM providers."""

    @abstractmethod
    async def create(
        self,
        messages: List[Message],
        tools: Optional[List[Dict[str, Any]]] = None,
        **kwargs
    ) -> 'ChatCompletionResult':
        """Make a single LLM API call."""
        pass

    @abstractmethod
    async def create_stream(
        self,
        messages: List[Message],
        tools: Optional[List[Dict[str, Any]]] = None,
        **kwargs
    ) -> AsyncGenerator['ChatCompletionChunk', None]:
        """Make a streaming LLM API call."""
        pass
```

有了这个基类，我们就可以扩展它来支持特定的 LLM 实现。模式总是相同的：将我们的类型转换为提供商的格式，进行 API 调用，然后将响应转换回我们的统一格式。

下面是我们如何实现遵循三步转换模式的 OpenAI 客户端。首先，创建一个初始化方法，用所需模型和 API 密钥设置 OpenAI 客户端。

*代码清单 4.7：OpenAI 客户端初始化*

```python
class OpenAIChatCompletionClient(BaseChatCompletionClient):
    def __init__(
        self,
        model: str = "gpt-4.1-mini",
        api_key: Optional[str] = None
    ):
        self.model = model
        self.client = AsyncOpenAI(api_key=api_key)
```

初始化（代码清单 4.7）很直接——存储模型名称并创建 OpenAI 客户端。真正的工作发生在 create 方法中，它遵循我们的三步转换模式：

*代码清单 4.8：带转换模式的 OpenAI 客户端 create 方法*

```python
    async def create(
        self,
        messages: List[Message],
        tools: Optional[List[Dict]] = None
    ) -> ChatCompletionResult:
        # Step 1: Convert our types to provider's format
        api_messages = self._convert_messages_to_api_format(messages)
        # Step 2: Make the provider-specific API call
        response = await self.client.chat.completions.create(
            model=self.model,
            messages=api_messages,
            tools=tools
        )
        # Step 3: Convert response back to our unified format
        return ChatCompletionResult(
            message=AssistantMessage(
                content=response.choices[0].message.content
            ),
            usage=Usage(
                tokens_input=response.usage.prompt_tokens,
                tokens_output=response.usage.completion_tokens
            ),
            model=response.model
        )
```

请注意，同样的"转换输入 -> 调用 API -> 转换输出"模式可以应用于支持任何 LLM 提供商，同时保持我们的智能体代码不变。

### 4.4.1 智能体与模型的集成

现在看看智能体如何在其执行循环中使用模型客户端。智能体的工作是准备正确的上下文并处理响应：

*代码清单 4.9：智能体为模型客户端准备上下文*

```python
class Agent(BaseAgent):
    async def run_stream(
        self,
        task: Union[str, UserMessage, List[Message]]
    ) -> AsyncGenerator[Union[Message, AgentEvent], None]:
        # Prepare context with instructions and history
        llm_messages = [
            SystemMessage(content=self.instructions),
            *self.context.messages,
            *task_messages
        ]
```

上下文准备将智能体的系统指令、任何先前的对话历史和当前任务组合在一起。这为模型提供了恰当响应所需的全部信息。上下文就绪后，智能体调用模型并处理响应：

*代码清单 4.10：智能体调用模型客户端并处理响应*

```python
        # Call model client
        completion_result = await self.model_client.create(llm_messages)
        assistant_message = completion_result.message
        # Yield the response
        yield assistant_message
        # Update conversation context
        self.context.add_message(assistant_message)
```

关键洞见是：智能体只需准备对话上下文（指令 + 历史 + 当前任务）并将其传递给模型客户端。模型客户端处理所有提供商特定的细节，返回标准化的 ChatCompletionResult——无论你使用 OpenAI、Anthropic 还是任何其他提供商，其工作方式都相同。

## 4.5 启用结构化输出——可靠智能体的关键

我们的智能体目前产生人类可读但程序难以可靠解析的文本响应。要构建能够采取精确行动的智能体，我们需要可预测的、机器可读的数据。这正是结构化输出变得至关重要的地方。

结构化输出将模型约束为以特定格式生成响应，例如匹配预定义模式的 JSON 对象。与其希望正确解析"The weather in Paris is sunny"，我们获得可靠的结构化数据（如下所示），我们的代码/应用可以立即使用。

```json
{"location": "Paris", "condition": "sunny", "temperature": 75}
```

当智能体需要调用工具、在记忆中存储信息或与其他系统协调时，这种可靠性变得至关重要。让我们使用 Pydantic 模型实现结构化输出，以确保可预测的、机器可读的响应。

大多数现代 LLM 提供商都支持结构化输出。我们在 BaseChatCompletionClient 中的 create 方法实现可以包含一个可选的 output_format 参数（请参见 picoagents.llm._openai.py），它接受一个 Pydantic 模型。当提供时，客户端将确保模型的输出符合此模式。

首先，我们定义一个 Pydantic 模型来指定我们想要的结构：

*代码清单 4.11：用于结构化输出的 Pydantic 模型*

```python
from pydantic import BaseModel, Field
from typing import List
class UserProfile(BaseModel):
    id: int = Field(..., description="The user's unique identifier")
    name: str = Field(..., description="The user's full name")
    email: str = Field(..., description="The user's email address")
    age: int = Field(..., description="The user's age")
    skills: List[str] = Field(..., description="A list of the user's skills")
```

字段描述帮助模型理解要生成什么类型的数据。现在我们可以使用此模型来约束 LLM 的输出：

*代码清单 4.12：使用模型客户端的结构化输出*

```python
client = OpenAIChatCompletionClient(model="gpt-4.1-mini")
messages = [
    UserMessage(
        content="Create a profile for a software engineer named Alice \
                 who is 28 years old and skilled in Python, JavaScript, \
                 and machine learning.",
        source="user"
    )
]
# Call model with structured output constraint
result = await client.create(
    messages=messages,
    output_format=UserProfile  # This ensures structured output
)
```

output_format 参数告诉模型客户端将响应约束为匹配我们的 UserProfile 模式。结果作为正确类型的对象返回：

*代码清单 4.13：使用结构化输出结果*

```python
# The result.structured_output will be a UserProfile object
if result.structured_output:
    profile = cast(UserProfile, result.structured_output)
    print(f"Name: {profile.name}")
    print(f"Age: {profile.age}")
    print(f"Skills: {', '.join(profile.skills)}")
# Output:
# Name: Alice
# Age: 28
# Skills: Python, JavaScript, Machine Learning
```

请注意，result.structured_output 保证是有效的 UserProfile 对象，消除了容易出错的文本解析。在本书中，我们将依赖结构化输出的概念来可靠地构建智能体行为。

## 4.6 添加工具

结构化输出正常工作后，我们的智能体现在可以产生可靠的、可解析的数据，而不仅仅是文本。这一能力解锁了下一个层次：工具调用。当智能体需要查询天气、查询数据库或执行计算时，它可以生成我们的应用能够安全执行的结构化工具调用请求。

以下是结构化输出如何实现可靠的工具调用：

*代码清单 4.14：从结构化输出到工具调用*

```python
# Structured output enables reliable tool requests
class ToolCall(BaseModel):
    name: str
    arguments: Dict[str, Any]
# Agent produces this structure reliably
result = await model_client.create(
    messages=messages,
    tools=available_tools,
    # Tool schemas guide structured output
)
# Now we can safely execute the tool
if result.tool_calls:
    for tool_call in result.tool_calls:
        tool_result = await execute_tool(tool_call.name, tool_call.arguments)
```

没有结构化输出，我们就得解析"请调用 get_weather 函数并将 location 设为 Paris"——脆弱且容易出错。有了它，我们得到可以自信执行的可靠 JSON。

工具将智能体从文本生成器转变为行动实体。我们的工具系统利用刚刚构建的结构化输出基础，使 LLM 能够生成带有正确类型参数的精确函数调用。

### 4.6.1 LLM 中的函数调用（工具调用）

工具调用（也称为函数调用）是结构化输出的一种应用，LLM 生成与预定义工具模式匹配的精确格式的 JSON 请求。LLM 不是生成"请调用天气函数"这样的自由格式文本，而是产生带有正确类型参数的结构化函数调用——例如，当用户问"旧金山未来 4 天的天气怎么样？"时，生成 get_weather(location="San Francisco", date_range="next 4 days")。

这种结构化格式消除了解析歧义，确保工具收到正确类型的参数，使智能体能够可靠地与外部系统交互。没有结构化输出，智能体将需要脆弱的文本解析，稍许格式变化就可能失效。

工具调用遵循多步骤的请求-响应模式：

1. **定义工具**：向 LLM 提供函数模式（名称、描述、参数）
2. **工具调用**：LLM 使用模式生成使用特定工具的结构化请求
3. **工具执行**：应用执行函数并生成输出
4. **工具输出**：结果被发送回 LLM 以整合进响应

此模式利用结构化输出使 LLM 能够与外部系统交互，并访问其训练数据之外的数据，将它们从文本生成器转变为可靠的行动智能体。

在接下来的小节中，我们将实现一个 BaseTool 类，它持有函数模式的通用表示，最终将用于表示工具。

### 4.6.2 工具类别：通用 vs 任务特定

智能体的能力与其可访问的工具直接相关。工具分为两个基本类别：

**通用工具**提供适用于许多任务的广泛能力。示例包括可以执行任何程序化解决方案的代码解释器，或可以与应用和网站交互的用户界面驱动器。这些工具实现最大的灵活性，但引入不确定性和安全问题，需要仔细的沙箱化（详见第 5 章的安全考虑）。

**任务特定工具**为特定领域提供专注的能力——发送邮件、查询特定数据库或生成图像。这些工具约束智能体的行为，实现可预测性并帮助管理智能体的决策空间，但将智能体的能力限制在预定义函数内。

### 4.6.3 BaseTool 类

虽然你可以直接向智能体传递 Python 函数，但这种方法有局限性。当你需要调用 REST API、查询数据库或集成模型上下文协议（MCP）等新兴标准的工具时怎么办？你需要一个跨不同工具类型通用的接口。

BaseTool 抽象遵循我们之前讨论的抽象基类原则。它提供一个标准化契约，同时支持简单的基于函数的工具和复杂的外部集成：

*代码清单 4.15：BaseTool 抽象类和 ToolResult*

```python
class BaseTool(ABC):
    """Abstract base class for all tools."""
    def __init__(self, name: str, description: str):
        self.name = name
        self.description = description
    @property
    @abstractmethod
    def parameters(self) -> Dict[str, Any]:
        """JSON schema defining expected inputs."""
        pass
    @abstractmethod
    async def execute(self, parameters: Dict[str, Any]) -> ToolResult:
        """Execute the tool with given parameters."""
        pass
    def to_llm_format(self) -> Dict[str, Any]:
        """Convert to OpenAI (or any other) function calling format."""
       ...
```

此接口无需更改智能体代码即可实现可扩展性。你可以从简单函数开始，之后添加数据库工具、API 工具或连接外部服务的 MCP 工具。集成 MCP 工具与智能体的完整示例见 12.2.4 节。

### 4.6.4 FunctionTool：开发者体验

最常见的工具类型包装 Python 函数。与其为每个函数手动实现 BaseTool 接口，常见的做法是提供 FunctionTool 抽象来自动处理转换。这样，开发者只需编写带类型注解和文档字符串的普通 Python 函数：

```python
def get_weather(location: str, days: int = 1) -> str:
    """Get weather forecast for a location."""
    return f"Weather in {location}: sunny"
# This function automatically becomes a tool
agent = Agent(tools=[get_weather], ...)
```

反过来，FunctionTool 类自动处理转换：

1. **函数检查**：提取签名、参数名和类型注解
2. **模式生成**：将 Python 类型转换为 LLM 兼容的 JSON 模式
3. **执行包装器**：处理同步和异步函数，带错误处理
4. **结果格式化**：将函数输出转换为结构化的 ToolResult 对象

这种方法优先考虑开发者体验——你自然地编写函数，框架处理智能体集成。

### 4.6.5 智能体工具集成

BaseTool 接口定义好之后，让我们看看智能体在其执行循环中如何发现、处理和执行工具。智能体需要三个关键能力：将各种工具类型转换为标准格式、为 LLM 准备工具模式，以及安全地执行工具调用。

首先，智能体在初始化期间处理工具。由于开发者可以传入 BaseTool 实例或普通 Python 函数，我们需要将它们规范化：

*代码清单 4.16：将混合工具类型转换为标准格式*

```python
class Agent(BaseAgent):
    def _process_tools(
        self,
        tools: List[Union[BaseTool, Callable]]
    ) -> List[BaseTool]:
        """Convert mixed tool types to BaseTool instances."""
        processed = []
        for tool in tools:
            if isinstance(tool, BaseTool):
                processed.append(tool)
            elif callable(tool):
                # Wrap functions in FunctionTool automatically
                processed.append(FunctionTool(tool))
            else:
                raise ValueError(f"Invalid tool type: {type(tool)}")
        return processed
```

这种规范化（代码清单 4.16）在智能体初始化期间执行一次，确保所有工具遵循相同接口，无论开发者如何提供它们。

当智能体准备调用 LLM 时，它需要将工具模式转换为模型期望的函数调用格式：

*代码清单 4.17：为 LLM 准备工具模式*

```python
    def _get_tools_for_llm(self) -> List[Dict[str, Any]]:
        """Convert tools to LLM function calling format."""
        return [tool.to_llm_format() for tool in self.tools]
```

此方法（代码清单 4.17）生成 JSON 模式，告诉 LLM 有哪些函数可用、它们接受什么参数以及它们做什么。LLM 使用这些模式来决定何时调用工具，以及如何从用户的自然语言请求中提取参数。

最后，当 LLM 生成工具调用请求时，智能体必须安全地执行它并返回结果：

*代码清单 4.18：执行工具调用并处理结果*

```python
    async def _execute_tool_call(
        self,
        tool_call: ToolCallRequest
    ) -> ToolMessage:
        """Execute a tool call and return result message."""
        # Find the requested tool by name
        tool = self._find_tool(tool_call.tool_name)
        if tool is None:
            return ToolMessage(
                content=f"Tool '{tool_call.tool_name}' not found",
                tool_call_id=tool_call.call_id,
                success=False,
                error=f"Tool not found"
            )
        # Execute the tool with error handling
        try:
            result = await tool.execute(tool_call.parameters)
            content = (
                str(result.result) if result.success
                else f"Error: {result.error}"
            )
            return ToolMessage(
                content=content,
                tool_call_id=tool_call.call_id,
                tool_name=tool_call.tool_name,
                success=result.success,
                error=result.error
            )
        except Exception as e:
            # Handle unexpected errors gracefully
            return ToolMessage(
                content=f"Tool execution failed: {str(e)}",
                tool_call_id=tool_call.call_id,
                success=False,
                error=str(e)
            )
```

此执行方法（代码清单 4.18）处理几个重要情况：工具未找到错误、带结果的成功工具执行、优雅失败的工具执行，以及意外异常。返回的 ToolMessage 被添加到对话历史中，让 LLM 看到工具的结果并继续推理。

这三个方法就位后（代码清单 4.16、4.17、4.18），完整的工具集成工作流变得清晰。开发者直接将函数传给智能体（如代码清单 4.1 所示），智能体在初始化期间将其规范化，为 LLM 转换其模式，并在被调用时安全执行。LLM 基于可用模式自动决定调用哪些工具，从用户的自然语言请求中提取参数，而我们的框架通过优雅的错误处理处理执行。这一基础设施将简单的 Python 函数转变为可靠的智能体能力。

## 7.1 编排器循环

每个编排模式，无论智能体如何被选择或协调，都遵循相同的基本**编排器循环**（orchestrator loop）。无论你是实现简单的轮询方法调度智能体（智能体以轮询方式轮流，直到满足某个终止条件）、AI 驱动的选择（AI 模型决定下一个发言的智能体），还是专门的 AI 模型基于某个任务制定计划并指挥智能体，核心架构保持一致：

```
select the next agent                      # 选择下一个智能体
prepare context for the agent              # 为该智能体准备上下文
execute the agent with the prepared context # 用准备的上下文执行智能体
update shared state with the agent's response # 用智能体的响应更新共享状态
check termination conditions               # 检查终止条件
```

```python
# The core pattern that powers all orchestration
while not termination.is_met():
    next_agent = select_next_agent()        # Pattern-specific logic
    context = prepare_context_for_agent()   # Pattern-specific logic
    result = await next_agent.run(context)
    update_shared_state(result)
    check_termination(result)
```

这个核心循环提供了几个关键好处：

此循环在所有模式之间提供**一致性**（使其更易于理解和维护）、**可组合性**（允许你通过切换编排器实现来混合不同模式）、**可扩展性**（新模式只需实现模式特定方法，同时继承健壮的基础设施），以及**全面的可观测性**（通用埋点适用于所有模式类型）。

有了这种基础理解，让我们实现支撑所有协调模式的基础编排器类，然后构建具体实现，从轮询编排和灵活的终止条件开始。

### 7.1.1 构建 BaseOrchestrator

与第 4 章（4.2.2 节）的 BaseAgent 类类似，BaseOrchestrator 类（代码清单 7.5）处理流式传输、取消和状态管理的复杂性，同时让每个模式只专注于其特定的协调逻辑。

BaseOrchestrator 定义了所有编排模式必须遵循的契约。它初始化核心组件（智能体、终止条件和共享状态），并验证智能体名称唯一以防止协调冲突。

*代码清单 7.5：BaseOrchestrator 抽象类定义*

```python
from abc import ABC, abstractmethod
from typing import List, Optional, Sequence
from ..agents import BaseAgent
from ..messages import Message
from .termination import BaseTermination
class BaseOrchestrator(ABC):
    """Abstract base class for all orchestration patterns."""
    def __init__(
        self,
        agents: Sequence[BaseAgent],
        termination: BaseTermination,
        max_iterations: int = 50
    ):
        if not agents:
            raise ValueError(
                "At least one agent is required"
            )
        self.agents = list(agents)
        self.termination = termination
        self.max_iterations = max_iterations
        # Runtime state
        self.shared_messages: List[Message] = []
        self.iteration_count = 0
        # Validate agent names are unique
        names = [agent.name for agent in agents]
        if len(names) != len(set(names)):
            raise ValueError(
                "Agent names must be unique"
            )
```

构造函数建立每个编排器需要的三个核心组件：要协调的智能体列表、决定何时停止的终止条件，以及用于跟踪对话的共享状态管理。max_iterations 参数提供了一个安全后备，防止失控执行。

### 7.1.2 编排器运行循环

编排器的核心逻辑存在于两个方法中，它们遵循与我们用于智能体相同的模式。run_stream 方法提供消息和事件的实时流式传输，而 run 将一切收集到单个响应中，用于更简单的用例。

运行循环从设置执行上下文、规范化输入任务和准备流式输出开始：

*代码清单 7.6：编排器运行循环的设置与初始化*

```python
async def run_stream(
    self,
    task: Union[str, UserMessage, List[Message]],
    cancellation_token: Optional[CancellationToken] = None
) -> AsyncGenerator[
    Union[
        Message,
        OrchestrationEvent,
        OrchestrationResponse
    ],
    None
]:
    """Execute orchestration with streaming output."""
    self._reset_for_run()
    self.start_time = time.time()
    stop_message: Optional[StopMessage] = None
    streamed_messages: List[Message] = []
    try:
        yield OrchestrationStartEvent(...)
        # Normalize task to initial messages
        initial_messages = (
            self._normalize_task_to_messages(task)
        )
        self.shared_messages.extend(initial_messages)
        # Stream initial messages to caller
        for message in initial_messages:
            yield message
            streamed_messages.append(message)
        # Check termination on initial messages
        self.termination.check(initial_messages)
```

设置阶段处理几项关键职责。_reset_for_run() 调用清除先前执行的任何状态，确保每次编排全新开始。streamed_messages 列表跟踪我们已产出给调用方的所有消息——这对后续的终止检查变得重要。任务规范化处理三种输入格式：纯字符串（转换为 UserMessage）、UserMessage 对象（直接使用）或完整消息列表（用于继续对话）。我们在初始消息后立即检查终止，因为即使用户的输入也可能包含"DONE"或"TERMINATE"等停止关键词。

现在编排器进入其主协调循环。每次迭代选择一个智能体，用适当的上下文运行它，并处理结果。循环从选择下一个要执行的智能体开始：

*代码清单 7.7：智能体选择与上下文准备*

```python
        # Main orchestration loop
        while self.iteration_count < self.max_iterations:
            # Check for cancellation
            if (
                cancellation_token
                and cancellation_token.is_cancelled()
            ):
                raise asyncio.CancelledError()
            # 1. Select next agent (pattern-specific)
            next_agent = await self.select_next_agent()
            # 2. Prepare context (pattern-specific)
            context = await self.prepare_context_for_agent(
                next_agent
            )
```

select_next_agent() 和 prepare_context_for_agent() 方法是模式特定的——这是轮询与 AI 驱动或基于计划的编排的区别所在。轮询按顺序循环智能体，而 AI 驱动的编排使用 LLM 基于对话状态智能选择。

选择智能体并准备上下文后，编排器以流式支持执行智能体：

*代码清单 7.8：带类型守卫的流式智能体执行*

```python
            # 3. Execute agent with streaming
            agent_messages = []
            result: Optional[AgentResponse] = None
            async for item in next_agent.run_stream(
                context,cancellation_token):
                # Type guard for Message objects
                if (hasattr(item, "content")
                    and hasattr(item, "role")):
                    message_item = cast(Message, item)
                    agent_messages.append(message_item)
                    # Filter out UserMessages from streaming
                    if not isinstance(
                        message_item,
                        UserMessage
                    ):
                        yield message_item
                        streamed_messages.append(
                            message_item
                        )
```

流式执行使用类型守卫安全地处理不同的项目类型。我们过滤掉 UserMessages，因为这些只是我们发送给智能体的上下文，不是新内容。只有助手消息被流式传输给调用方，提供对智能体响应的干净实时可见性，而不回显提示词。

智能体执行完成后，编排器更新共享状态并检查对话是否应继续：

*代码清单 7.9：状态更新与终止检查*

```python
            # 4. Update shared state (pattern-specific)
            await self.update_shared_state(result)
            # 5. Check termination with delta messages
            new_streamed_messages = streamed_messages[
                self._last_termination_check_count:
            ]
            self._last_termination_check_count = len(
                streamed_messages
            )
            stop_message = self.termination.check(
                new_streamed_messages
            )
            if stop_message:
                break
            self.iteration_count += 1
```

状态管理阶段揭示了一个微妙但至关重要的模式：**基于增量的终止检查**。与其在每次迭代重复处理整个对话历史，我们用 _last_termination_check_count 跟踪位置，只将新消息传递给终止检查器。这比反复扫描数百条消息更高效，并允许终止条件聚焦于近期发展而非完整历史。模式特定的 update_shared_state() 方法正是支持不同编排策略的地方——轮询可能追加所有消息，而 AI 驱动的编排可能基于协调需求过滤或转换它们。

循环完成后（通过终止条件或最大迭代次数），编排器组装带有完整执行指标的最终响应：

*代码清单 7.10：编排完成与结果组装*

```python
        # Handle max iterations case
        if (
            self.iteration_count >= self.max_iterations
            and stop_message is None
        ):
            stop_message = StopMessage(
                content=(
                    f"Maximum iterations reached "
                    f"({self.max_iterations})"
                ),
                source="MaxIterations"
            )
        # Aggregate usage from all agent executions
        elapsed_time = int(
            (time.time() - self.start_time) * 1000
        )
        total_usage = Usage(duration_ms=elapsed_time)
        for agent_usage in agent_usage_stats:
            total_usage = total_usage + agent_usage

        yield OrchestrationResponse(
            messages=self.shared_messages,
            final_result=self._generate_final_result(),
            usage=total_usage,
            stop_message=stop_message,
            pattern_metadata=self._get_pattern_metadata()
        )
    except asyncio.CancelledError:
        # Handle cancellation gracefully
        raise
```

完成阶段确保我们总是提供有意义的停止消息，即使循环通过最大迭代而非显式终止条件退出。用量聚合特别重要——每次智能体执行跟踪自己的 API 成本和计时，我们将其相加，以准确了解编排的总成本。_generate_final_result() 辅助函数向后搜索消息，找到最后的助手响应，提供简洁的摘要，而不是强迫调用方扫描完整的消息历史。这种丰富、完整响应的模式使编排结果自成一体、易于使用。

此实现为所有编排模式提供了基础，同时处理几个复杂关注点：

**流式可观测性**：调试多智能体系统时，你需要实时看到发生的事情。哪个智能体在运行？正在交换什么消息？对话在哪里卡住了？流式接口提供了这种可见性，使构建响应式 UI 和调试复杂交互成为可能。

**优雅取消**：多智能体对话可能需要几分钟才能完成。用户不可避免地需要取消它们——无论是提供了错误的提示词，还是智能体进入了无生产力的循环。干净的取消防止失控的 API 成本，并确保系统保持响应。

**健壮的错误处理**：在多智能体系统中，一个智能体的失败不应使整个编排崩溃。错误处理确保异常被捕获和记录，同时保留失败点之前的对话状态。

**资源与性能跟踪**：了解编排花费多长时间以及消耗多少 API 调用，对成本管理和性能优化至关重要。自动指标采集提供这些数据，无需手动埋点。

每个编排模式继承这种健壮的基础设施，只需实现三个模式特定的抽象方法：select_next_agent() 选择下一个执行的智能体，prepare_context_for_agent() 组装对话上下文，update_shared_state() 在智能体执行后管理共享状态。这种干净的分离使模式能够专注于其独特的编排逻辑，同时受益于全面的流式传输、取消和错误处理能力。

## 7.2 构建终止条件

**终止条件**

回顾我们的编排器循环，你会注意到我们在每次迭代结束时进行终止检查——termination.check(new_messages)。这是多智能体系统最关键的方面之一：知道何时停止。

没有适当的终止条件，智能体对话可能无限运行。你可能见过聊天机器人陷入循环——多智能体系统也会出现同样的问题，只不过现在你每次循环迭代都要为多次 API 调用付费。你需要既可靠又灵活的终止条件。

### 7.2.1 BaseTermination 接口

要构建一个既能处理简单规则（"5 条消息后停止"）又能处理复杂组合（"10 条消息后停止，或有人说'DONE'，或 5 分钟后停止"）的终止系统，我们从一个公共基类开始：

```python
from abc import ABC, abstractmethod
from typing import List, Optional, Dict, Any, Sequence
from ..messages import Message
from ..types import StopMessage
class BaseTermination(ABC):
    """Abstract base class for all termination conditions."""

    def __init__(self) -> None:
        self._met = False
        self._reason = ""
        self._metadata: Dict[str, Any] = {}

    @abstractmethod
    def check(self, new_messages: Sequence[Message]) -> Optional[StopMessage]:
        """Check termination on delta messages."""
        pass

    def is_met(self) -> bool:
        return self._met

    def reset(self) -> None:
        self._met = False
        self._reason = ""
        self._metadata = {}

    def __or__(self, other: 'BaseTermination') -> 'CompositeTermination':
        return CompositeTermination([self, other], mode="any")
    def __and__(self, other: 'BaseTermination') -> 'CompositeTermination':
        return CompositeTermination([self, other], mode="all")
```

__or__ 和 __and__ 方法使 Python 的 | 和 & 操作符可用于组合条件。这让你可以编写直观的终止逻辑，如 MaxMessages(5) | TextMention("DONE")。

注意终止条件接收增量消息——仅自上次检查以来的新消息。这比每次重新处理整个对话更高效，并允许条件对近期发展做出反应，而不是反复扫描一切。

### 7.2.2 常见终止模式

两种最常见的终止模式是消息计数限制和基于文本的触发器。以下是它们在概念上的工作方式：

```python
# Conceptual: Message count termination
class MaxMessageTermination(BaseTermination):
    """Stop after N messages."""
    def check(self, new_messages):
        self.count += len(new_messages)
        if self.count >= self.max_messages:
            return StopMessage(f"Reached {self.count} messages")
        return None
# Conceptual: Text-based termination
class TextMentionTermination(BaseTermination):
    """Stop when specific text appears."""
    def check(self, new_messages):
        for message in new_messages:
            if self.search_text in message.content:
                return StopMessage(f"Found '{self.text}'")
        return None
```

两种条件都扩展 BaseTermination 并实现 check() 方法。关键区别：MaxMessageTermination 跟踪所有检查的累积计数，而 TextMentionTermination 扫描每条新消息中的触发短语。框架包含额外的终止类型，如 TokenUsageTermination（预算限制）、TimeoutTermination（时间限制）和 HandoffTermination（智能体发起的转移）。

### 7.2.3 可组合的终止逻辑

这是我们之前定义的 | 和 & 操作符变得有用的地方。你可以组合终止条件来处理复杂场景：

```python
# Terminate after 20 messages OR when someone says "DONE" OR after 5 minutes
termination = (
    MaxMessageTermination(20) |
    TextMentionTermination("DONE") |
    TimeoutTermination(300)
)
# Terminate only when BOTH conditions are met
complex_termination = (
    MaxMessageTermination(10) &
    TextMentionTermination("COMPLETE")
)
```

这种可组合性意味着你可以构建复杂的停止逻辑，而无需编写复杂的条件代码。每个条件保持简单和可测试，但它们的组合可以处理细致入微的需求。

## 7.3 实现轮询编排

基础就位后——编排器循环和灵活的终止系统——我们现在可以构建具体的协调模式。让我们从最简单的开始：**轮询编排**（round-robin orchestration）。

轮询协调就像一场结构化的会议，每个参与者按顺序获得发言机会。当你想让所有智能体均衡参与、对话流可预测时，此模式效果良好。

### 7.3.1 RoundRobinOrchestrator 实现

RoundRobinOrchestrator 实现三个抽象方法，创建一个简单但有效的轮流模式。首先，我们扩展基类并添加一个索引来跟踪下一个发言的智能体：


三个模式特定方法很直接：

```python
# Round-robin agent selection
async def select_next_agent(self) -> BaseAgent:
    """Cycle through agents in order."""
    agent = self.agents[self.current_agent_index]
    self.current_agent_index = (
        (self.current_agent_index + 1) % len(self.agents)
    )
    return agent
# Context preparation: share full history
async def prepare_context_for_agent(
    self, agent: BaseAgent
) -> str:
    """Format conversation history for next agent."""
    context = "Team progress so far:\n\n"
    for msg in self.shared_messages:
        context += f"{msg}\n"
    return context + "\nIt is now your turn."
# State management: append new messages
async def update_shared_state(
    self, result: AgentResponse
) -> None:
    """Add agent's new messages to shared history."""
    new_messages = result.messages[1:]  # Skip context echo
    self.shared_messages.extend(new_messages)
```

此实现非常简洁，因为它从 BaseOrchestrator 继承了所有复杂的基础设施。轮询模式只需指定：

1. **智能体选择**：按顺序循环智能体
2. **上下文准备**：共享完整对话历史
3. **状态管理**：将新消息追加到共享状态

> **提示**
>
> 你可以使用简单的 RoundRobinOrchestrator 实现许多简单用例，它通常需要最少的代码。非常适合大多数原型工作的第一个版本。

> **注意**
>
> 你会注意到这里的 prepare_context_for_agent() 方法将整个对话历史格式化为单个字符串。这是一种直接的方法，对许多场景都有效，但在实践中，你可能想实现更复杂的上下文管理策略来处理更长的对话或优化 Token 使用。有时，甚至为不同智能体选择多种格式——JSON、Markdown 或纯文本——都会影响响应的质量，因为这些可能影响底层模型的行为。
>
> 使用框架或库的缺点之一（尽管简单易用）是这类选择变得有些隐晦。当我们深入更复杂的实现时，请记住这一点——框架做出的决策可能并不总是完美契合你的特定用例，你可能需要自定义或扩展基类以满足你的需求。

我们刚刚实现的轮询编排器与前面代码清单 7.2 中介绍的是同一个。当然，你可以为更复杂的场景扩展它。例如，一个三智能体研究团队可能包括研究者、写作者和评论家，循环进行多轮细化：

```python
# Three-agent workflow with iterative improvement
termination = MaxMessageTermination(12) | TextMentionTermination("FINAL VERSION")
orchestrator = RoundRobinOrchestrator(
    agents=[researcher, writer, critic],
    termination=termination
)
```

你可以预期的关键行为模式：

- 研究者收集信息并提供事实洞察
- 写作者将研究综合为连贯内容
- 评论家提供反馈并提出改进建议
- 迭代细化持续到终止条件满足

### 7.3.2 可观测性与调试

我们之前示例中的流式接口提供全面的可观测性。除了基本的消息流，你还可以监控详细的编排事件以进行调试：

- **智能体选择事件**：选择了哪个智能体以及为什么
- **执行计时**：每个智能体响应需要多长时间
- **上下文大小**：每个智能体收到多少对话历史
- **终止触发器**：究竟是什么导致对话结束

这种可观测性对调试复杂的多智能体交互和优化系统性能至关重要。

## 7.4 AI 驱动的编排

轮询编排在你想要可预测的轮流时效果良好，但如果你需要更智能的协调呢？如果对话在写作者继续之前需要研究者的输入，或者评论家应该等到有实质性内容可审查时再发言，怎么办？

AI 驱动的编排通过使用 LLM 分析对话并决定下一个发言的智能体来解决这个问题。系统不是遵循固定顺序，而是适应实际的对话需求。

关键洞见是我们可以复用轮询编排的所有基础设施，只更改 select_next_agent() 方法。此伪代码展示了 LLM 如何分析对话上下文和智能体能力以做出智能选择决策：

*代码清单 7.12：使用 LLM 推理的 AI 驱动智能体选择*

```python
# Pseudocode for AI-driven agent selection
async def select_next_agent() -> BaseAgent:
    # 1. Gather agent capabilities
    capabilities = get_agent_capabilities_summary()

    # 2. Format recent conversation context
    conversation_context = format_conversation_for_selection()

    # 3. Create selection prompt
    prompt = f"""You are coordinating AI agents.
Available agents: {capabilities}
Recent conversation: {conversation_context}
Choose which agent should respond next
based on conversation needs."""
    # 4. Get structured LLM decision
    result = await llm_client.create(
        messages=[UserMessage(content=prompt)],
        output_format=AgentSelection
    )
    # 5. Return selected agent
    return find_agent_by_name(
        result.structured_output.selected_agent
    )
```

LLM 不是固定循环，而是分析对话上下文和智能体能力做出智能选择，实现响应实际对话需求的自适应协调。

轮询示例中的相同智能体可以与 AI 编排一起使用，但对话流动态适应：

```python
# Same agents as round-robin example
researcher = Agent(
    name="researcher",
    instructions="Research specialist...",
    ...
)
writer = Agent(
    name="writer",
    instructions="Content writer...",
    ...
)
termination = (
    MaxMessageTermination(6) |
    TextMentionTermination("TERMINATE")
)
# Switch to AI orchestration - intelligent selection
orchestrator = AIOrchestrator(
    agents=[researcher, writer],
    termination=termination,
    model_client=OpenAIChatCompletionClient(
        model="gpt-4.1-mini"
    )
)
# Adaptive flow based on LLM decisions:
# -> LLM selects researcher (need: information)
# -> LLM selects writer (research complete)
# -> Writer requests more data
# -> LLM selects researcher (need: clarification)
# -> LLM selects writer (info provided)
# -> "TERMINATE"
```

对话自然适应——如果写作者需要更多信息，LLM 将再次选择研究者，而不是强制固定的交替模式。

> **提示**
>
> 一旦你有了正确的智能体组件，AI 驱动的编排实现起来就很直接。LLM 处理协调决策，结构化输出确保带推理的可靠智能体选择。
>
> **权衡**：此模式为每次智能体选择增加 LLM 成本，因为对话历史和智能体能力包含在每个协调请求中。

## 7.5 基于计划的编排

轮询和 AI 驱动的编排都在逐时刻决定下一个行动的智能体。基于计划的编排采取不同的方法：它预先创建显式的执行计划，然后系统性地逐步执行，同时监控进度。

此模式在任务需要结构化分解时效果良好——将复杂目标分解为带特定智能体分配的清晰顺序步骤。可以把它想象成有一个项目经理：创建任务列表，将每个任务分配给合适的专家，验证完成情况，并在事情不如预期时处理重试。

### 7.5.1 LLM 生成的执行计划

编排器首先使用 LLM 分析任务和智能体能力，然后生成结构化的执行计划。与轮询（只是循环智能体）或 AI 驱动的编排（一次选择一个智能体）不同，基于计划的编排需要从 LLM 响应中可靠地提取多个结构化步骤。这正是结构化输出变得必不可少的地方。

我们使用 LLM 必须遵循的 Pydantic 模型定义计划结构：

*代码清单 7.13：执行计划的结构化模型*

```python
class PlanStep(BaseModel):
    """Single step in an execution plan."""
    task: str = Field(
        description="Clear, actionable task description"
    )
    agent_name: str = Field(
        description="Name of agent for this step"
    )
    reasoning: str = Field(
        description="Why this agent was chosen"
    )
class ExecutionPlan(BaseModel):
    """Complete execution plan."""
    steps: List[PlanStep] = Field(
        description="Ordered list of steps"
    )
```

定义了这些模型后，编排器可以向 LLM 请求结构化计划。关键部分是 output_format 参数，它将模型约束为返回有效的 ExecutionPlan 对象，而非自由格式文本：

*代码清单 7.14：带结构化输出的基于 LLM 的计划生成*

```python
async def create_plan(self, task: str) -> ExecutionPlan:
    """Create execution plan using LLM."""
    capabilities = self.get_agent_capabilities_summary()
    planning_prompt = f"""You are a helpful assistant
that breaks down tasks into executable steps.
Available agents and their capabilities:
{capabilities}
User task: {task}
Generate a concise execution plan. For each step:
- Assign to the agent best suited for that work
- Provide clear, actionable task description
- Explain briefly why that agent was chosen
Keep it focused. If only 2-3 steps needed, that's fine.
"""
    result = await self.model_client.create(
        messages=[UserMessage(content=planning_prompt)],
        output_format=ExecutionPlan  # Enforces structure
    )
    return result.structured_output  # Guaranteed ExecutionPlan
```

output_format=ExecutionPlan 参数至关重要——它将不可预测的 LLM 文本转换为可靠的数据结构。没有它，解析"首先，研究者应该收集事实，然后写作者创建内容"这样的自由格式响应将是脆弱且容易出错的。结构化输出确保每个计划都有清晰定义的步骤和智能体分配，编排器可以程序化地执行。

这种方法将模糊目标转化为具体的行动项。像"研究并撰写一份关于可再生能源的指南"这样的任务成为结构化计划：第 1 步（研究者：收集关键事实）、第 2 步（写作者：创建结构化内容）、第 3 步（审查者：验证准确性）。

### 7.5.2 步骤进度评估

与更简单的编排模式不同，基于计划的协调需要在继续之前验证每个步骤是否实际完成了目标。这种评估必须是程序化的——编排器不能只是希望步骤成功，它需要一个清晰的布尔决策来驱动重试逻辑。

同样，结构化输出至关重要。我们定义适当的评估应该是什么样子：

*代码清单 7.15：步骤进度评估的结构化模型*

```python
class StepProgressEvaluation(BaseModel):
    """Evaluation of step completion."""
    step_completed: bool = Field(
        description="Whether step was successful"
    )
    failure_reason: str = Field(
        description="Explanation if failed"
    )
    confidence_score: float = Field(
        description="Confidence (0.0 to 1.0)",
        ge=0.0,
        le=1.0
    )
    suggested_improvements: List[str] = Field(
        description="Suggestions for retry if failed"
    )
```

该模型确保每次评估都包含清晰的成败决策、推理和可操作的建议。每次智能体执行后，编排器使用结构化输出获得可靠的评估。评估过程要求 LLM 评估智能体的工作是否完成了步骤的目标：

```python
# Conceptual: Step evaluation with structured output
async def evaluate_step_progress(
    step: PlanStep,
    agent_result: AgentResponse
) -> StepProgressEvaluation:
    """Ask LLM: Did the agent complete this step successfully?"""
    # Build evaluation prompt with step context
    eval_prompt = f"""
    Expected: {step.task} (assigned to {step.agent_name})
    Agent produced: {agent_result.content}
    Was this step completed successfully?
    """
    # Get structured evaluation (not free-form text)
    evaluation = await llm.create(
        messages=[eval_prompt],
        output_format=StepProgressEvaluation
    )
    # Returns: {step_completed: bool, failure_reason: str,
    #          confidence: float, suggested_improvements: List[str]}
    return evaluation.structured_output
```

output_format 参数使程序化重试成为可能。没有结构化输出，LLM 可能返回"看起来不错"或"可能需要改进"这样的模糊评估——这些响应无法驱动重试逻辑。有了结构化输出，我们得到保证的布尔决策、显式的推理和可操作的建议，编排器可以用这些来增强下一次尝试。

### 7.5.3 智能重试逻辑

当步骤评估表明失败时，基于计划的编排器不会只是继续前进或完全停止。相反，它基于失败分析用增强的上下文重试该步骤。这种重试逻辑契合我们之前看到的相同 update_shared_state 模式，但现在带有评估和重试跟踪：

```python
# Conceptual: Retry logic in plan-based orchestration
async def update_shared_state(result: AgentResponse):
    """Handle step completion, evaluation, and retry."""
    # Evaluate what the agent just did
    evaluation = await evaluate_step_progress(
        current_step,
        result
    )
    if evaluation.step_completed:
        # Success - move forward
        move_to_next_step()
        reset_retry_count()
    else:
        # Failed - try again with enhanced context
        increment_retry_count()
        if retries_remaining():
            # Build enhanced instructions for next attempt
            retry_context = build_retry_context(
                evaluation.failure_reason,
                evaluation.suggested_improvements
            )
            store_retry_instructions(retry_context)
            # Next iteration will retry same step with context
        else:
            # Max retries exceeded - move on
            move_to_next_step()
            reset_retry_count()
```

关键洞见是重试指令在下一次尝试时成为智能体上下文的一部分。当 prepare_context_for_agent 再次为同一步骤运行时，它包含失败分析："上一次尝试因 X 失败。尝试改进 Y 和 Z。"这种有针对性的反馈相比盲目重试显著提高成功率。

> **何时使用基于计划的编排**
>
> 基于计划的编排最适合：
>
> - 具有清晰顺序阶段的多阶段流水线（研究 -> 写作 -> 审查）
> - 质量关键的任务，自动验证在继续之前捕获失败
> - 可恢复的失败，带反馈的重试显著提高成功率
>
> **关键使能因素**：结构化输出使此模式成为可能——没有计划和评估的可靠数据结构，程序化重试逻辑将无法工作。
>
> **成本考虑**：此模式每步需要 2 次以上 LLM 调用（规划 + 评估 + 执行）。当不需要显式规划时，对简单轮流使用轮询，对动态协调使用 AI 驱动。

## 7.6 练习

**自定义终止条件**：实现消息计数和文本提及之外的额外终止模式。例如，创建一个调用外部函数确定何时停止的 FunctionTermination，或跟踪累积 Token 使用并在预算超限时停止的 TokenBudgetTermination。

**交接编排**：扩展编排模式以支持直接的智能体间交接。与其让编排器总是选择下一个智能体，不如允许智能体基于对任务需求的评估显式地将控制权转移给特定同事。

**性能比较**：为编排运行实现全面的指标采集（执行时间、Token 使用、消息计数、智能体选择模式）。使用这些指标比较不同编排方法下的同一任务——对于各种用例，轮询、AI 驱动和基于计划的模式在成本和有效性上有何不同？

**上下文管理策略**：在 prepare_context_for_agent() 中实验不同的上下文准备方法。比较拼接文本与结构化格式（JSON、Markdown 表格）。测试将上下文限制为最近 N 条消息与完整历史。衡量这些选择如何影响智能体响应质量和 Token 成本。

## 7.7 小结

我们构建了一个完整的编排系统，协调多个智能体进行复杂的对话。此实现的关键洞见：

- **编排器循环**：所有编排模式共享相同的基础循环，在不同协调方法之间提供一致性和可组合性。
- **灵活的终止**：可组合的终止条件防止失控执行，同时允许适应不同用例和需求的复杂停止逻辑。
- **流式可观测性**：实时事件流提供对多智能体协调决策前所未有的可见性，支持有效的调试、监控和用户界面开发。
- **模式可扩展性**：抽象基类处理复杂的基础设施关注点，同时允许每个模式通过干净的扩展点只专注于其特定的协调逻辑。
- **生产考虑**：内置的取消、错误处理、资源跟踪和上下文管理支持，使系统适合真实世界的部署场景。

轮询编排器展示了这种架构如何用最少的代码构建复杂的协调模式。同样的基础支持上述高级模式，每个模式只需实现三个抽象方法的模式特定版本，同时继承我们构建的所有健壮基础设施。

# 第 5 章　构建计算机使用智能体

本章涵盖：

- 理解代码执行和 API 之外何时需要界面自动化
- 计算机使用智能体的剖析：动作生成、界面表示、执行
- 通过文本、图像和混合方法表示界面的策略
- 动作序列生成与将任务转化为界面动作
- 构建观察、推理并作用于 Web 和桌面界面的智能体

在第 4 章中，我们构建了可以使用 LLM 推理、通过工具行动并维护记忆的智能体。我们探索了函数工具如何让智能体执行代码、调用 API 和执行结构化任务。然而，许多现实场景需要一种不同的方法——能够理解用户界面并与之交互的智能体，类似于人类如何与应用交互以完成任务。这类智能体被称为**计算机使用智能体**（computer use agents）。

在本章中，我们将首先说明对计算机使用智能体的需求、支撑它们的核心思想，然后扩展第 4 章的 Agent 类，构建一个可以驱动 Web 浏览器完成任务的 ComputerUseAgent 类。我们将探索界面表示、动作序列生成和动作执行等组件。最后，我们将讨论计算机使用智能体领域的挑战与机遇。

## 5.1 当代码和 API 不够用时：计算机使用智能体的角色

![图 5.1：代码执行与界面交互两种行动方式](images/p199_0.png)

*图 5.1：智能体可以通过工具行动，方式要么是执行代码（或调用 API），要么是直接与应用交互。对于涉及复杂动态行为的任务，包括操纵界面，或没有 API 的任务（例如专有软件），计算机使用智能体可能很有价值。重要的是，许多用例可能受益于两种方法的组合。*

在第 4 章中，我们探索了如何构建可以访问生成式 AI 模型和工具（代码解释器、函数）的智能体，这些模型和工具交互以解决任务。我们概述了智能体可访问工具的质量如何显著影响它们能解决的任务，并概述了代码解释器或直接控制应用的能力等通用工具如何用于解决广泛的任务。

重要的是，虽然许多任务可以通过代码执行完成（例如，LLM 生成代码解决任务，或正确选择现有函数解决任务），但有些任务场景中代码执行方法力不从心（如图 5.1 所示）。

例如，一些任务具有复杂的动态行为，人类通过操纵界面相对容易完成，但以编程方式指定却很有挑战性。示例包括在 Photoshop 中打开北加州地图的图像，并仅在水域区域绘制多边形分区，或在具有复杂格式的电子表格应用中操纵数据。除单个任务外，计算机使用智能体支持更广泛的自动化模式：研究智能体导航多个网站以收集和比较信息（聚合定价数据、监控竞争对手、综合新闻）；后台智能体分拣邮件并创建相应的 GitHub Issue、更新 CRM 记录，或在互不相连的企业系统之间对账数据；软件测试智能体执行端到端测试场景、执行视觉回归测试，或探索 UI 路径寻找错误。在其他情况下，应用可能具有专为人类交互设计的功能，而没有相应的 API 可用。

这些任务通常需要对界面布局、视觉线索和上下文的深入理解，这些可能无法通过传统编程方法轻易获得。

> **提示**
>
> 虽然基础网页抓取可以获取静态内容的 HTML，但现代 Web 应用通常使用动态 JavaScript、AJAX 请求和反机器人措施（CAPTCHA、请求头检查）。模拟人类交互的计算机使用智能体——点击按钮、填写表单、处理动态内容——可以自动化仅靠代码无法完成的任务。这应始终遵守网站的服务条款。

在这些场景中，能够接受任务描述并直接与应用的用户界面交互以解决任务的智能体可能很有价值。计算机使用智能体通过直接与用户界面交互来自动化任务，处理仅靠代码执行难以完成的场景。事实上，如果你使用过 OpenAI 的 Operator（OpenAI 2025）、Anthropic 的 Computer Use（Anthropic 2024a）、TryCUA（TryCUA 2024）或 Manus（Manus AI 2025）等新兴工具，它们都遵循计算机使用智能体的通用原则。

我们将首先讨论计算机使用智能体的核心概念，包括计算机使用智能体的剖析、LLM 在生成动作序列中的作用，以及计算机使用智能体面临的挑战。然后，我们将从零实现一个计算机使用智能体，重点放在界面表示、动作序列规划和动作执行上。最后，我们将探索计算机使用智能体领域的挑战和机遇。

## 5.2 计算机使用智能体的剖析

计算机使用智能体，就像人类一样，必须执行一组步骤来完成任务。让我们从以下任务开始："查找并打印从西雅图到圣何塞的航班，出发时间在下午 5 点后，返程时间在上午 9 点前，本周三出发，周五早上返回。"处理此任务的智能体可能采取以下步骤，其中每个步骤都可以实现为界面上的一个动作或动作序列：

1. 导航到航班预订网站，如 flights.google.com。[navigate, browser]
2. 在出发地字段输入西雅图。[type, input]
3. 在到达地字段输入圣何塞。[type, input]
4. 选择所需的旅行日期。[click, dropdown]
5. 设置出发航班过滤器为下午 5 点后出发。[click, dropdown]
6. 设置返程航班过滤器为上午 9 点前到达。[click, dropdown]
7. 点击搜索按钮查找符合标准的航班。[click, button]
8. 打印结果 [click, print hotkey - Ctrl+P]

如果我们反思如何实现这一点，我们可以看到智能体必须：

1. 首先理解界面状态（例如，这是网页吗？当前页面是什么？有哪些字段可用于输入？哪些按钮可以点击？）。
2. 规划一系列动作以实现期望的结果或下一个期望的结果（例如，在地址栏输入 URL 并按 Enter）。
3. 在界面上执行这些动作（实际文本输入和 Enter 按钮的模拟）以完成任务。
4. 根据需要重复此过程以实现最终目标。

计算机使用智能体遵循**观察-思考-行动**（OBSERVE-THINK-ACT）执行模式。

具体来说，我们需要表示界面状态、生成动作序列和在界面上执行这些动作的机制。如图 5.2 所示，这些机制构成计算机使用智能体的核心组件。

### 5.2.1 动作序列生成

动作序列生成是生成式 AI 模型将高层任务转化为特定界面动作的过程。计算机使用智能体依赖这种能力将自然语言指令转换为用户界面上的可执行操作。在实践中，GPT-4+ 及其多模态变体等现成模型提供这种能力。例如，给定任务"佛罗里达州一种入侵蜗牛物种的植物学名称是什么？"，语言模型可能产生一个动作/目标对，如："动作：搜索'佛罗里达州入侵蜗牛物种的植物学名称'，目标：google.com 上的搜索按钮"。

然而，通用模型面临两个主要挑战：

- **界面表示格式**：模型的适用性取决于界面的表示方式。基于文本的表示（例如网页的 HTML）可以使用语言模型，而基于图像的表示（例如截图）需要能够同时处理文本和图像的多模态模型。
- **上下文理解**：预测下一个动作需要对当前界面状态的深入理解。这包括处理意外元素（例如弹窗）和根据指令准确定位 UI 目标。

为了应对这些挑战，近期学术界和工业界的研究探索了专门为 GUI 交互任务微调基础模型。这些专门模型不是在提示词引导的通用模型上止步，而是在大规模数据集上训练，这些数据集将界面状态与相应的动作序列配对。例如，UI-TARS（Yujia Lu et al. 2025）代表新一代专用的 GUI 智能体，通过几项关键创新实现了最先进的性能：(1) 在大规模 GUI 截图数据集上训练以增强感知，(2) 跨平台的统一动作建模，(3) 用于深思熟虑的多步决策的 System-2 推理，以及 (4) 使用反思性在线轨迹的迭代训练，使模型能够从自己的交互历史中学习。这种专门化方法相较通用模型展示了显著改进，在 OSWorld 上取得 24.6% 的成功率（超越 Claude Computer Use），在 AndroidWorld 上取得 46.6%（超过 GPT-4o 的 34.5%），表明领域特定的微调可能是推进计算机使用智能体能力的重要方向。

动作序列生成可以通过两种方式实现：

- **显式规划**：模型基于初始界面状态生成完整计划，然后执行。这种方法受益于结构化推理，但在动态界面中可能挣扎，早期步骤可能过时。例如，在静态网站上填写联系表单时，整个序列可以提前规划。
- **隐式规划**：模型迭代生成计划，在每一步考虑当前界面状态。这种方法更好地适应动态界面，但可能效率较低，需要更多试错。

显式规划与隐式规划之间的选择在很大程度上取决于界面的性质和任务需求。显式规划最适合静态、可预测的界面，如登录表单或联系表单，其中动作序列定义明确且在执行期间不太可能改变。这些场景受益于预先规划的效率和较少的模型调用。隐式规划在处理动态界面时表现优异，如航班预订系统、社交媒体信息流或搜索结果页面，其中界面状态在任务执行期间不可预测地变化。

### 5.2.2 智能体动作空间

计算机使用智能体的动作空间是指智能体在界面上可以采取的完成任务的行动集合。这个空间可以由智能体能够执行的交互类型定义，如点击按钮、输入文本、从下拉菜单中选择选项或提交表单。重要的是，必须定义此动作空间并将其提供给用于生成处理任务的动作序列的生成式模型。

## 5.3 界面表示

界面表示是将用户界面的当前状态呈现给 AI 模型以理解和生成动作的方法。计算机使用智能体需要这种表示来感知存在哪些元素、它们位于何处，以及可以执行哪些动作。表示格式的选择取决于被自动化的应用类型（Web、移动、桌面）和运行时可用的程序化访问。

存在三种主要方法：基于文本的（DOM/HTML 结构）、基于图像的（截图）和混合的（结合两者），每种方法在精度、计算成本和视觉理解之间提供不同的权衡。

Web 应用支持多种表示格式，因为它们既可以表示为基于文本的（HTML），也可以表示为基于图像的（界面截图）——两者都可以在运行时通过浏览器在客户端访问。移动应用可能有界面的基于文本的表示，但通常在运行时无法通过程序化 API 访问。例如，我们可能在训练时通过 XML 布局文件（或其他 UI 组件系统）访问 Android 应用的 UI 布局，但在运行时无法访问实际的 UI 元素。Ferret-UI（You et al. 2024）等近期工作探索了使用多模态 LLM 的接地式移动 UI 理解来应对这些挑战。类似地，桌面应用通常没有界面的基于文本的表示，捕获界面状态的唯一方式是通过截图或界面的视觉捕获。

### 5.3.1 基于文本的表示

这涉及将界面表示为结构化文本数据，如 HTML、XML、JSON 甚至原始文本。这种方法对语言模型处理高效，提供关于界面元素的精确信息，并且与具有清晰基于文本结构的界面配合良好。基于文本表示的常见方法包括解析网页的 DOM，或利用无障碍 API 通过平台特定 API 访问界面元素。

#### 5.3.1.1 DOM 解析

DOM 解析涉及从网页提取结构化数据。网页的 HTML 结构可以通过 HTTP 请求获取，或使用 Playwright 或 Selenium 等浏览器自动化工具直接访问页面的 DOM。生成式模型然后可以使用此结构化数据生成下一个动作：要交互的元素（通常通过生成一个可执行的 CSS 选择器来定位元素）和要对其执行的动作。

> **提示：DOM 过滤**
>
> 虽然整个 DOM 可以有效地表示网页状态，但由于几个原因，向模型提供整个 DOM 内容可能有问题。首先，DOM 可能相当大且包含无关信息（例如广告、隐藏元素），这可能使模型难以专注于界面的相关部分。其次，许多模型的 Token 容量有限，因此提供整个 DOM 可能超出模型的输入大小限制。为了解决这些问题，通常有益的做法是过滤 DOM，只包含与当前任务最相关的元素。这可能涉及基于属性、类或 DOM 中的位置选择特定元素，或使用启发式方法识别可能与任务相关的关键元素。
>
> 我们的 ComputerUseAgent 实现自动过滤 DOM 内容，专注于智能体可以有意义交互的交互元素，如按钮、链接、表单输入和其他可点击元素。

#### 5.3.1.2 无障碍 API：通过平台特定 API 访问界面元素

无障碍 API 提供了一种跨不同操作系统程序化访问和交互用户界面元素的方式。这些 API 旨在辅助辅助技术，但也可以被计算机使用智能体利用来与应用交互。

- **对于 Windows**：Microsoft UI Automation 是一个无障碍框架，使 Windows 应用能够提供和消费关于用户界面（UI）的程序化信息。它提供对桌面上大多数 UI 元素的程序化访问。UFO（Zhang et al. 2024）等近期研究展示了使用这些 API 进行 Windows 操作系统交互的有效 UI 专注智能体。
- **对于 macOS**：macOS Accessibility API 为 Apple 系统提供类似功能。它允许应用使用 AppleScript 或 Objective-C 与用户界面交互。

这些 API 可以提供界面的基于文本的表示，包括元素层级、属性和状态。虽然这种表示可以轻松馈入基于文本的模型，但它可能难以捕获复杂的视觉关系或动态内容。可能需要额外的处理或补充方法（如计算机视觉）来充分解释视觉线索和布局信息。

### 5.3.2 基于图像的表示

这涉及使用截图或视觉捕获将界面表示给模型。此方法可以捕获基于文本的结构中不存在的视觉信息，并且与缺乏可访问的基于文本表示的应用配合良好。然而，处理图像在计算上昂贵（相比文本更多 Token），需要具有图像处理能力的模型或某些中间图像处理步骤，通常意味着延迟增加，并可能丢失界面中存在的细粒度文本信息。

通常，由于处理图像的复杂性（没有 CSS 选择器的概念可用于获取截图中特定元素的引用），基于图像的表示可能包括两步过程：图像首先用标记注释（例如，元素周围的边界框和标签），然后再传递给模型以提高性能（Cheng et al. 2024）。这可以帮助模型专注于界面的特定元素，并降低图像表示的复杂性。OmniParser（Yadong Lu et al. 2024）和标记集提示（Set-of-Mark prompting）（Abuelsaad et al. 2024）等项目正在探索这种方法以提高任务性能。

### 5.3.3 混合（文本和图像）表示

结合文本和图像表示的混合方法也在兴起，提供两种格式的好处。例如，实现可能包含从 DOM 提取基于文本的信息并将其叠加在截图上的逻辑以提供视觉上下文，根据任务需求在文本和图像表示之间选择，或使用可以同时处理文本和图像的多模态模型。这种方法可以提供更全面的界面表示，捕获生成准确动作序列所需的结构信息和视觉上下文。

### 5.3.4 界面表示策略的比较

文本、图像和混合表示之间的选择涉及精度、成本和通用性之间的根本权衡。基于文本的表示提供高效的 Token 使用和通过 CSS 选择器的精确元素定位，但缺少人类与界面交互时所依赖的视觉上下文。基于图像的表示捕获完整的视觉信息，适用于任何界面类型，但消耗显著更多的 Token 且需要多模态模型。混合方法结合两种格式——我们的 ComputerUseAgent 实现通过 get_state() 中的 format 参数支持这一点，可以根据任务需求返回纯文本、纯视觉或混合表示。

## 5.4 动作执行器（界面自动化工具）

动作序列规划好之后，计算机使用智能体必须通过动作执行器在目标界面上执行这些动作。此组件负责将高层动作转化为低层界面交互、管理时序和同步，并处理错误情况和意外界面状态。例如，在 Web 应用中，动作执行器可以模拟鼠标点击、键盘输入或表单提交以与界面交互。在桌面应用中，它可以使用操作系统特定的自动化工具控制 UI 元素或模拟用户输入。动作执行器通常是界面表示组件的自动化工具；也就是说，用于推导界面状态的同一工具被用于在界面上执行动作。

动作执行的常用工具包括 Playwright 等浏览器自动化框架和 PyAutoGUI 等平台自动化库，后者支持跨 Windows、macOS 和 Linux 平台模拟与桌面应用的用户交互。

### 5.4.1 Playwright 概述

Playwright 是微软开发的开源自动化库，允许开发者程序化控制 Web 浏览器。它提供高层 API 与 Chromium、Firefox 和 WebKit 浏览器交互，使其适用于网页抓取、自动化测试和构建计算机使用智能体。

Playwright 的特性包括：

1. **跨浏览器支持**：Playwright 可以用单一 API 自动化 Chromium（包括 Chrome 和 Edge）、Firefox 和 WebKit（Safari）。
2. **全面的选择器和动作**：它提供定位和交互网页元素的机制，包括 CSS 选择器、XPath 和文本内容。它支持广泛的动作，如点击、输入、选择选项、捕获截图等。
3. **自动等待功能**：Playwright 在执行动作前自动等待元素就绪，减少对显式等待的需求，使脚本更可靠。
4. **网络拦截**：它允许监控和修改网络请求和响应，可用于测试不同场景或模拟 API 响应。
5. **移动模拟**：Playwright 可以模拟移动设备，支持响应式设计和移动特定功能的测试。

## 5.5 实现一个计算机使用智能体

既然我们理解了概念基础，让我们一步步构建 ComputerUseAgent。我们不是从零创建一个全新的智能体架构，而是做出一个关键的设计决策，利用我们在第 4 章构建的稳健基础。

我们的实现专注于使用 Playwright 的 Web 浏览器自动化，但我们开发的架构模式同样适用于桌面应用（使用 PyAutoGUI 或平台特定的无障碍 API）和移动界面（使用 Appium 或类似框架）。关键抽象是**界面客户端**——将浏览器客户端换成桌面自动化客户端，同样的智能体架构就可以处理不同的界面类型。

### 5.5.1 "智能体 + 工具"架构

我们不是从零构建自定义解决方案，而是扩展我们的基础 Agent 类来与界面交互。关键洞见是将界面动作——点击、输入、导航——视为智能体可以使用的工具。我们的基础智能体已经提供了执行循环、工具调用机制和上下文管理，用于界面自动化。

我们的 ComputerUseAgent 继承基础 Agent 类，并添加三个组件：用于浏览器自动化的界面客户端、表示界面动作的专门工具，以及捕获动作结果的增强观察能力。当任务到来时，智能体使用模型选择和执行工具，就像第 4 章中基础智能体使用函数一样。

*代码清单 5.2：ComputerUseAgent 类架构*

```python
class ComputerUseAgent(Agent):
    def __init__(
        self,
        interface_client,
        model_client,
        use_screenshots=True,
        max_actions=10,
        **kwargs
    ):
        # Create specialized web automation tools
        playwright_tools = create_playwright_tools(
            interface_client
        )
        # Inherit proven agent patterns
        # - tool calling, context management, streaming
        super().__init__(
            model_client=model_client,
            tools=playwright_tools,  # Our action space
            max_iterations=max_actions,
            **kwargs
        )
        # Manage browser interface internally
        self.interface_client = interface_client
        self.use_screenshots = use_screenshots
```

这种方法给我们带来关键好处：基础智能体的流式传输能力与我们的新工具配合工作，错误处理和取消机制扩展到浏览器自动化，上下文管理维护带工具结果的对话历史。

### 5.5.2 通过工具定义动作空间

我们的计算机使用智能体的功能以工具为中心。每个工具代表智能体可以在 Web 界面上采取的特定动作，从导航到 URL 到点击按钮和输入文本。这些工具定义了我们的智能体进行 Web 交互的动作空间。

*代码清单 5.3：创建 Playwright 工具套件*

```python
def create_playwright_tools(interface_client):
    """Create specialized tools for web interface interaction."""
    return [
        NavigateTool(interface_client),
        ClickTool(interface_client),
        TypeTool(interface_client),
        SelectTool(interface_client),
        PressTool(interface_client),
        HoverTool(interface_client),
        ScrollTool(interface_client),
        ObservePageTool(interface_client),
    ]
```

每个工具包装一个特定的 Playwright 操作。实现将每个工具定义为带适当参数模式的 BaseTool 子类。例如，NavigateTool 需要 URL 参数，ClickTool 需要 CSS 选择器，TypeTool 需要选择器和要输入的文本。这些工具定义了我们的智能体进行 Web 交互的动作空间。

### 5.5.3 关键的观察循环

这是计算机使用智能体与传统函数调用智能体的根本区别所在。当我们的天气工具返回"sunny, 75°F"时，那是完整的信息。但当我们的智能体点击一个按钮时，我们需要观察发生了什么。新页面加载了吗？表单出现了吗？错误消息显示了吗？

为了实现这一点，我们可以添加一个特定的 observe_page 工具，LLM 可以调用它来捕获当前页面状态的文本结构和视觉外观。

```python
FunctionTool(
    func=lambda: interface_client.get_state(),
    name="observe_page",
    description="Get current page state and content",
)
```

当 LLM 调用 observe_page 工具时，我们的实现拦截结果并用视觉上下文增强它。这种模式允许智能体接收组合结构化 DOM 数据和截图的多模态信息，以实现更丰富的推理。

*代码清单 5.4：拦截 observe_page 结果以添加视觉上下文*

```python
async def run_stream(self, task, cancellation_token=None, verbose=False):
    # Use base Agent's proven execution loop
    async for item in super().run_stream(
        task,
        cancellation_token,
        verbose):
        yield item
        # Intercept observe_page tool results to enhance with screenshots
        if isinstance(item, ToolMessage) and item.tool_name == "observe_page":
            if self.use_screenshots:
                # Capture current page screenshot
                state = await self.interface_client.get_state("hybrid")
                if state.screenshot:
                    # Add screenshot to agent's context for LLM reasoning
                    screenshot_msg = MultiModalMessage(
                        content="Page observation",
                        source=self.name,
                        role="user",
                        mime_type="image/png",
                        data=state.screenshot
                    )
                    self.context.add_message(screenshot_msg)
                    yield screenshot_msg  # Also stream for user feedback
```

这使我们的智能体能够处理文本和视觉信息。当 use_screenshots=True 时，智能体同时接收 DOM 结构和截图数据，使其能够理解仅靠文本难以表达的布局、视觉线索和界面状态。

### 5.5.4 界面状态表示

我们的界面客户端将原始网页数据转换为 LLM 可以有效处理的格式。它支持三种表示模式，每种都针对不同场景和计算约束进行了优化。

*代码清单 5.5：界面表示模式*

```python
async def get_state(self, mode="hybrid"):
    """Get current interface state in specified format."""
    if mode == "text":
        return InterfaceState(
            content=await self.page.content(),
            interactive_elements=await self._get_interactive_elements(),
            screenshot=None
        )
    elif mode == "visual":
        return InterfaceState(
            content="",
            interactive_elements=[],
            screenshot=await self.page.screenshot()
        )
    else:  # hybrid mode
        return InterfaceState(
            content=await self.page.content(),
            interactive_elements=await self._get_interactive_elements(),
            screenshot=await self.page.screenshot()
        )
```

三种模式决定捕获什么数据。使用 mode="text" 时，智能体接收 HTML 内容和带 CSS 选择器的交互元素列表，但没有截图。这对 Token 使用高效，但缺少视觉上下文。使用 mode="visual" 时，只捕获截图，需要多模态模型处理图像。mode="hybrid"（推荐）结合两种方法，提供用于通过 CSS 选择器精确元素定位的结构化数据，以及用于理解复杂布局和视觉关系的视觉上下文。我们的 DOM 过滤专注于智能体可以有意义交互的交互元素，在保持基本信息的同时减少 Token 使用。

### 5.5.5 增强的执行流程

所有组件就位后，让我们看看它们在完整任务执行中如何协同工作。核心执行循环与我们的基础智能体保持不变，但现在在 Web 界面动作空间上运行。

*代码清单 5.6：完整的 ComputerUseAgent 执行流程*

```python
import asyncio
from picoagents.agents import ComputerUseAgent
from picoagents.llm import OpenAIChatCompletionClient
from picoagents.agents import PlaywrightWebClient
async def main():
    # Create agent with multimodal reasoning capabilities
    computer_agent = ComputerUseAgent(
        interface_client=PlaywrightWebClient(headless=False),
        model_client=OpenAIChatCompletionClient(model="gpt-4.1-mini"),
        use_screenshots=True,  # Enable visual reasoning
        max_actions=10
    )

    try:
        # Task requires navigation, observation, and information extraction
        task = "What is the latest AI news on techcrunch.com?"

        async for event in computer_agent.run_stream(task):
            print(event)
    finally:
        await computer_agent.close()  # Clean up browser resources
if __name__ == "__main__":
    asyncio.run(main())
```

当你运行此代码时，智能体将打开浏览器窗口，导航到 TechCrunch，观察页面结构，提取相关标题，并返回最新 AI 新闻的摘要。

执行流程展示了我们的关键架构原则的实际运作。智能体接收任务，并使用其继承的工具调用能力将其分解为可操作的步骤。每次工具调用都可能改变界面状态，因此观察变得至关重要。增强的观察循环既提供精确动作所需的结构化数据，也提供智能推理所需的视觉上下文。

### 5.5.6 资源管理与错误处理

计算机使用智能体管理真实的浏览器进程和网络连接，因此适当的资源清理至关重要。我们的实现包含多层保护，防止资源泄漏并在出现问题时优雅降级。

*代码清单 5.7：健壮的资源管理*

```python
class ComputerUseAgent(Agent):
    async def close(self) -> None:
        """Ensure browser cleanup on agent shutdown."""
        if hasattr(self, 'is_initialized') and self.is_initialized:
            await self.interface_client.close()
            self.is_initialized = False

    async def run_stream(
        self,
        task,
        cancellation_token=None,
        verbose=False):
        # Initialize browser on first use
        if not self.is_initialized:
            await self.interface_client.initialize()
            self.is_initialized = True

        try:
            async for item in super().run_stream(
                task,
                cancellation_token,
                verbose):
                yield item
        except Exception as e:
            # Log error but don't crash on screenshot failures
            if "screenshot" not in str(e).lower():
                raise  # Re-raise non-screenshot errors
```

错误处理策略对截图捕获特别重要。虽然视觉上下文增强推理，但在不可用时不应破坏任务执行。我们的实现在截图捕获失败时优雅降级为纯文本模式，确保跨不同环境和网络条件的健壮运行。

## 5.6 计算机使用智能体的关键挑战

虽然计算机使用智能体为自动化复杂任务提供了强大的能力，但它们也面临几个重大挑战。本节探讨开发者和研究者必须解决的关键问题，以创建有效且可靠的计算机使用智能体。图 5.4 展示了这些挑战的相互关联性及其对开发和部署的影响。

![图 5.4：实现计算机使用智能体的关键挑战](images/p221_0.png)

*图 5.4：实现计算机使用智能体的关键挑战。该图展示了五大障碍：界面表示（平衡细节与效率）、上下文与记忆管理（保持任务相关性）、动作消歧（解决模糊目标）、安全与隐私（保护敏感数据）和延迟（平衡速度与准确性）。这些相互关联的挑战凸显了为现实应用开发有效可靠计算机使用智能体的复杂性。*

### 5.6.1 界面表示与接地

开发计算机使用智能体的主要挑战之一是找到为 AI 模型表示和接地界面状态的最佳方式。这对智能体有效理解和交互界面至关重要。

基于文本的表示，如 Web 界面的文档对象模型（Document Object Model，DOM），通常包含大量噪声或无关数据，这可能使 AI 模型困惑。这些表示也难以有效捕获视觉关系和空间布局。此外，JavaScript 生成的动态内容和频繁的界面更新对维护准确的表示构成挑战。

基于图像的表示虽然能更全面地捕获视觉信息，但也有自己的一系列挑战。处理图像比文本需要显著更多的计算资源，可能增加延迟并降低响应性。重要的文本细节，如确切的按钮标签或输入字段占位符，可能更难从图像中提取。此外，屏幕尺寸、分辨率和纵横比的变化可能使跨不同设备解读基于图像的表示变得复杂。

为了应对这些挑战，研究者正在探索创新方法，如结合文本和基于图像方法的混合表示，以利用两者的优势。标记集提示（Abuelsaad et al. 2024）等高级接地技术用锚点标记丰富表示，增强任务性能并减少歧义。此外，Ferret-UI（You et al. 2024）和 UI-TARS（Yujia Lu et al. 2025）等专门模型正专为界面理解而设计，UI-TARS 通过在大规模 GUI 截图数据集上训练并实现 System-2 推理进行深思熟虑的多步决策，展示了显著改进。

### 5.6.2 上下文与记忆

计算机使用智能体必须保持对用户上下文的全面理解，以提供相关且有用的协助。这涉及在多次交互和任务中学习和记住个体用户偏好、维护先前动作及其结果的记录、理解应用的当前状态，以及管理跨多个应用的任务所涉及的跨界面和环境的上下文。

应对这些挑战需要复杂的记忆管理和上下文建模技术。潜在的解决方案包括实现可以存储和检索相关过去经验的情景记忆系统、开发将丰富的上下文信息编码为紧凑表示的方法，以及创建捕获各种应用与任务之间关系的跨应用知识图谱。

### 5.6.3 动作消歧与可靠性

在许多场景中，计算机使用智能体可能遇到多个潜在有效的动作目标来完成一项任务。开发健壮的消歧逻辑对于确保智能体做出适当选择至关重要。这涉及在存在多个可能性时确定哪个动作或元素与当前任务最相关、开发处理模糊情况的策略，以及平衡自主性与用户输入的需求。

应对消歧挑战的新兴模式包括：训练专门模型基于上下文因素对选项进行排序和优先级划分；开发直观的方式让用户提供反馈并引导智能体的决策过程；以及实现让智能体评估自己决策信心并在不确定性高时寻求帮助的机制。UI-TARS 等近期工作展示了使用反思性在线轨迹的迭代训练如何帮助模型从自己的交互历史中学习，随时间改进决策。

### 5.6.4 安全与隐私

随着计算机使用智能体与各种应用交互并处理敏感用户数据，确保安全和隐私变得至关重要。这一领域的关键挑战包括：保护自动化任务期间访问的用户信息；跨多个应用安全管理访问凭据和权限；确保符合相关数据保护法规和应用特定的服务条款；以及向用户提供关于智能体可以访问哪些数据以及如何使用这些数据的清晰信息。

应对这些关切的潜在方法包括：对智能体处理的所有敏感数据实施健壮加密；开发让用户精确控制智能体可以访问哪些信息和能力的系统；以及创建智能体动作的详细日志以支持透明度和促进合规检查。

### 5.6.5 用户体验：延迟、响应性和成本

计算机使用智能体面临来自延迟和成本管理的重大用户体验挑战。复杂任务通常需要与 AI 模型多次交互，引入累积延迟和复合成本。保持流畅的用户体验需要处理智能体动作中的延迟、管理界面元素在处理期间变化或超时的情况，以及智能地决定何时请求用户反馈（例如，请求登录凭据或在相似选项之间消歧）以避免不必要的延迟或错误。

成本管理在生产部署中值得特别关注。与传统应用成本线性扩展不同，智能体的 Token 消耗可能螺旋上升，因为系统每个任务进行多次 LLM 调用、捕获和处理截图，并在会话之间维护对话上下文。生产团队应将成本视为基础设施，实施每个会话的 Token 预算，监控每任务成本指标，对常规操作使用较小模型，同时为复杂推理步骤保留较大模型。截图捕获代表显著的 Token 成本——考虑仅在必要时捕获，或对直接的工作流使用纯文本表示。

为了缓解延迟挑战，研究者和开发者正在探索几种策略。这些包括创建专门为界面理解和动作预测调优的更小、更快的模型，如为 GUI 交互优化的多模态模型。其他方法涉及实施预测和预取可能的下一个动作的技术、设计在后台继续处理的同时对智能体动作提供即时反馈的界面，以及在可能的情况下构建允许非阻塞操作和并行处理的智能体工作流。

### 5.6.6 可靠性与健壮性

确保跨多样化界面和场景的一致且准确的性能，仍然是计算机使用智能体的重大挑战。这包括适应界面变化、更新和意外元素（如弹窗或覆盖层）、实施健壮的错误处理和恢复机制以优雅管理意外状态或失败，以及跨各种浏览器、操作系统和设备类型保持统一行为。

应对这些挑战需要多方位的方法，包括开发可以随时间学习和适应界面变化的智能体、创建可以处理跨平台界面结构变化的灵活中间表示，以及设计可以在广泛场景和边缘情况中评估智能体性能的自动化测试系统。通过应对这些挑战，研究者和开发者可以努力创建更健壮、可靠和有效的计算机使用智能体，无缝地与广泛的应用和平台交互。

## 5.7 生产环境考虑

在生产环境中部署计算机使用智能体需要仔细关注资源管理、安全和性能。本节概述构建可靠、生产就绪系统的实际考虑。

### 5.7.1 资源管理

计算机使用智能体会产生消耗大量内存的浏览器进程，必须显式关闭——Python 垃圾回收不会自动终止它们。生产部署应实施超时机制以防止失控的智能体、监控每个会话的内存使用，并使用容器化来强制资源限制。对于并发会话，跟踪活跃智能体并强制执行清理策略以防止资源耗尽。

对于生产部署，启用无头模式（在 PlaywrightWebClient 中设置 headless=True）以减少资源开销，仅在决策需要时捕获截图，并对可预测的工作流使用显式规划以最小化 LLM 调用。

### 5.7.2 安全与合规

计算机使用智能体的安全考虑超越了典型的应用安全。这些智能体访问和交互潜在敏感的界面、处理用户凭据，并捕获可能包含私人信息的截图。近期研究揭示，商业 LLM 智能体已经容易受到简单但危险的攻击（Li et al. 2024），提示词注入攻击代表特别关键的威胁向量。提示词注入攻击（Wang et al. 2025）发生在嵌入网页 HTML 或渲染内容中的恶意指令操纵智能体行为时。

关键安全威胁包括：凭据暴露——处理身份验证令牌或 Cookie 的智能体可能被利用来跨连接系统冒充用户；供应链风险——第三方浏览器扩展或插件可能劫持活跃会话或窃取数据；检测挑战——EDR 和 DLP 等传统安全工具难以区分合法的人类行为和潜在恶意的智能体行为。

关键安全实践包括尊重 robots.txt 和网站服务条款。速率限制防止压垮目标服务器，并降低 IP 封禁或 CAPTCHA 挑战的风险。在隔离环境中沙箱化智能体限制了智能体被攻破或行为失常时的爆炸半径。数据隐私措施必须确保截图和 DOM 捕获被过滤，避免捕获和记录密码、信用卡或个人数据等敏感信息。

实现方法包括：存储前过滤捕获数据以移除敏感字段；实施跟踪访问了哪些界面的审计日志而不存储完整内容；使用具有最小必要权限的短期凭据；定期审查自动化行为是否符合目标网站政策。考虑对敏感动作要求用户确认、每个会话隔离浏览器实例，以及部署专为监控智能体安全威胁设计的浏览器检测与响应（BDR）工具。

## 5.8 小结

- **当代码和 API 不够用时**：当代码执行和 API 不足时，计算机使用智能体为涉及动态行为、没有 API 的专有软件和需要类人导航模式的复杂视觉界面的任务提供直接的界面交互。
- **三个核心组件使智能体功能成为可能**：计算机使用智能体由动作序列生成（LLM 将任务转化为界面动作）、界面表示（文本、视觉或混合方法）和动作执行（Playwright 等浏览器自动化工具实现计划动作）组成。
- **界面表示策略提供不同的权衡**：基于文本的方法（DOM 解析）提供精确的元素定位但缺少视觉上下文，基于图像的方法捕获视觉信息但需要昂贵的多模态处理，而混合方法结合两者以实现最佳性能。
- **动作序列的隐式与显式规划**：智能体通过隐式规划（迭代的逐步生成，适应动态界面）或显式规划（静态、可预测工作流的完整预先序列）生成动作序列。
- **生产部署需要健壮的错误处理**：成功的计算机使用智能体需要适当的资源管理、安全考虑（尊重 robots.txt 和服务条款）、性能优化（无头模式、截图管理），以及处理界面变化和网络故障的可靠性模式。

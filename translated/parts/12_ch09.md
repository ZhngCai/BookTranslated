# 第 9 章　那么多智能体框架呢？

本章涵盖：

- 区分有效多智能体框架与基础实现的十项核心能力
- 针对你的具体需求评估任何框架的实用评估标准和问题
- 权衡技术能力与组织约束的决策框架
- 结合自定义开发与框架采用的混合方法策略

如果你在阅读本书，你可能一直在纠结的一个紧迫问题就是：选择哪个框架来构建多智能体系统。这无疑是我收到的最常见问题之一，尤其是在 AutoGen（Microsoft Research 2023）的早期。在我写作本书时，市面上有数十个框架——坦率地说，太多了。

同时，我们在过去几章中实际上已经实现了（假设你跟着我走过了代码——我希望你做到了！）你从框架中能获得的几乎所有东西，从零构建。如果你觉得这个过程舒适且令人振奋，那太好了！如果你不觉得，或者你在合理地怀疑这是否就是全部，本章将帮助你驾驭这个决策。

我个人认为，直接比较框架是一场必输的游戏——它们不断变化。相反，我想总结我认为任何框架都应该擅长的核心能力，无论你自己实现还是采用现有解决方案，只要你打算基于它构建。

到本章结束时，你将有一个系统化的方法来评估多智能体框架，无论在这个快速变化的格局中出现或演进哪些具体工具，这种方法都将保持适用。

## 9.1 为什么还要考虑框架？

好吧，有几个理由考虑使用框架。

**经过验证的模式和最佳实践**：框架编码了你可能尚未遇到的问题的解决方案。它们可以代表数百小时的边缘情况调试、性能优化和生产部署加固。

**加速开发**：虽然从零构建提供对行为的底层控制，但框架可以显著缩短生产应用的上市时间。它们处理"管道"工作，让你专注于业务逻辑。

**生态与社区**：成熟的框架带有广泛的文档、社区支持和预构建的集成，复制这些需要相当的努力。

**维护与演进**：到目前为止，我看到的客户从框架中获得的最大好处是，框架团队处理关键维护工作，如新模型 API 的更新、安全补丁和性能改进——减轻你的长期维护负担。

**标准化、可互操作的组件**：我看到许多开发者不幸地严重低估了框架提供的标准化 API 的影响。框架提供无缝协同工作的可互操作组件（智能体、工具、记忆系统），减少集成挑战。即使在 picoagents 中，你可能已经注意到，仅仅继承相同的 BaseAgent 抽象，就意味着我们构建的 ComputerUseAgent 可以与任何多智能体编排方法配合，零代码更改。随着团队成长，这些标准化接口显著减少上手时间和集成错误。例如，当新的记忆提供商可用时，框架要么提供兼容的实现，要么你的团队可以构建一个具有清晰行为保证的实现，而自定义实现通常需要手忙脚乱地改造一切。

> **注意**
>
> 至少在 AutoGen 的案例中，框架最常用的部分之一是 ChatCompletionClient，它支持多个模型提供商。模型提供商非常频繁地更改其 API 和行为，如果没有框架抽象差异，跟上这些变化可能成为开发者的负担。

然而，框架也引入约束、学习曲线和潜在的供应商锁定。关键是理解你在权衡什么。

## 9.2 框架的十项核心能力

基于多年构建和评估多智能体系统的经验，以下是区分有效框架与基础实现的核心能力。在适当的地方，我们将回顾我们如何在最小的 picoagents 库中解决这些需求的示例，以及 Microsoft Agent Framework、Google ADK 和 Pydantic AI 等领先框架如何应对这些能力。

### 9.2.1 带分层抽象的直观开发者体验

设计良好的框架应该提供我所说的"低地板，高天花板"——常见用例的简单入口，以及处理专门需求的灵活性，而不会撞上框架限制。

**要寻找什么**：

- 自然表达核心概念（智能体、工具、编排）的高层 API
- 需要时的自定义行为的低层 API
- 渐进式披露——你只在需要时看到复杂性
- 从简单部件构建复杂系统的清晰组合模式
- 框架与你的语言的习惯用法和模式对齐

在 picoagents 中，我们遵循这些原则设计了干净的 API（4.1 节）：

```python
# High-level: simple agent creation
agent = Agent(
    name="assistant",
    model_client=client,
    instructions="You are helpful"
)
response = await agent.run("Write a story")
# Low-level: custom behavior through inheritance
class CustomAgent(BaseAgent):
    async def run_stream(self, task, context=None, cancellation_token=None):
        # Custom reasoning logic
```

我们还提供了编排（组合智能体的高层模式）和工作流（参见第 7 章实现编排模式、第 6 章实现工作流）的清晰抽象，让你将低层业务逻辑表达为计算图。

**要问的问题**：

- 我能在 20 行代码内实现基本的多智能体工作流吗？
- 当我需要自定义行为时，我能扩展框架而不用 fork 它吗？
- 抽象是否与团队现有知识熟悉？
- 框架是引导我走向良好实践，还是允许容易犯的错误？

### 9.2.2 带流式传输支持的异步优先架构

多智能体系统涉及固有的并发操作——多个智能体思考、工具执行、外部 API 响应。围绕同步操作设计的框架将产生瓶颈和糟糕的用户体验。

**要寻找什么**：

- 整个 API 的原生 async/await 支持
- 实时更新的流式接口
- 长时间运行任务的非阻塞操作
- 内置取消和超时处理
- 与现代 Web 框架集成友好

在 picoagents 中，我们实现了带事件流的异步优先架构（4.2 节、4.2.1 节）：

```python
# Async execution with streaming and cancellation
token = CancellationToken()
async for event in agent.run_stream("Write a story", cancellation_token=token):
    if isinstance(event, ModelCallEvent):
        print("🧠 Model thinking...")
    elif isinstance(event, AgentResponse):
        print(f"✅ Complete: {event.messages[-1].content}")
```

**要问的问题**：

- 我能在智能体工作时流式传输部分结果吗？
- 框架如何处理长时间运行的操作？
- 我能优雅地取消进行中的操作吗？
- 它与你现有的异步基础设施集成良好吗？

### 9.2.3 全面的可观测性与开发工具

复杂的多智能体交互难以有效调试、监控和开发。框架应提供对执行期间发生的事情的丰富可观测性，并结合复杂的开发工具以实现快速迭代和理解系统行为。

**要寻找什么**：

- 捕获智能体决策、工具使用和协调的事件流
- 跨智能体交互带关联 ID 的结构化日志
- Token 用量、延迟和成功率的指标
- 可视化多智能体工作流构建器和交互式调试环境
- 配置比较、性能分析和回放能力
- 与标准开发工具（IDE、调试器）集成
- 实时监控仪表盘和告警系统

在 picoagents 中，我们为可观测性实现了结构化事件流（4.2.1 节）：

```python
# Rich event streams with structured data
async for event in agent.run_stream(task):
    if isinstance(event, ModelCallEvent):
        print(f"Model: {len(event.input_messages)} msgs")
    elif isinstance(event, ToolCallEvent):
        print(f"Tool: {event.tool_name}({event.parameters})")
    elif isinstance(event, AgentResponse):
        total = (event.usage.tokens_input
                 + event.usage.tokens_output)
        print(f"Total: {total} tokens")
```

**要问的问题**：

- 我能理解智能体为何做出特定决策吗？
- 我如何跨复杂工作流跟踪资源使用？
- 出错时会发生什么——我能有效调试吗？
- 我如何快速测试智能体配置的更改？
- 我能可视化和理解复杂工作流吗？
- 有哪些性能优化工具？
- 框架如何与你现有的开发工作流集成？

**警告信号**：

- 测试需要完整的生产部署
- 有限的性能分析或性能分析工具

### 9.2.4 全面的状态管理与持久化

生产多智能体系统需要处理失败、动态扩展，并跨会话维护对话。这需要超越简单内存存储的复杂状态管理。

**要寻找什么**：

- 可序列化的智能体和对话状态
- 长时间运行进程的检查点能力
- 可插拔的持久化后端（文件、数据库、云存储）
- 框架更新的状态迁移工具
- 并发工作流之间的清晰状态隔离

在 picoagents 中，我们为状态管理实现了记忆和上下文系统（4.7 节）：

```python
# Persistent memory with different backends
memory = FileMemory(file_path="conversation.json")
agent = Agent(name="assistant", model_client=client, memory=memory)
# Context carries conversation state
context = AgentContext(messages=[...], shared_state={...})
response = await agent.run("Continue our discussion", context=context)
```

**要问的问题**：

- 我能暂停和恢复多智能体工作流吗？
- 框架如何处理崩溃或重启？
- 我能将状态持久化到我偏好的存储系统吗？
- 扩展事件期间进行中的操作会怎样？

**警告信号**：

- 并发访问期间的状态损坏风险

### 9.2.5 声明式配置与可复现性

随着多智能体系统变得复杂，管理配置变得关键。团队需要跨环境可靠地版本化、共享和部署智能体配置。

**要寻找什么**：

- 智能体规范作为代码或配置文件
- 版本控制友好的格式（JSON、YAML 等）
- 环境特定的配置管理
- 可复现的构建和部署
- 配置验证和模式支持

在 picoagents 中，我们实现了组件序列化：

```python
# Serialize complete agent configurations
agent = Agent(name="assistant", model_client=client, tools=[search_tool])
config = agent.to_config()  # JSON-serializable configuration
# Load from configuration
loaded_agent = Agent.from_config(config)
# Works across all components (orchestrators, workflows, etc.)
orchestrator = RoundRobinOrchestrator(agents=[agent1, agent2])
orchestrator_config = orchestrator.to_config()
```

**要问的问题**：

- 我能声明式定义智能体并对其进行版本控制吗？
- 我如何管理开发/预发布/生产之间的配置差异？
- 团队成员能轻松共享和修改智能体配置吗？
- 是否有防止无效配置的保障？

> **配置驱动设计的重要性**
>
> 我经常看到团队低估或忽视配置驱动设计的价值。这通常是个错误，特别是多智能体系统有许多活动部件、许多配置旋钮，设置自动化的消融测试以隔离不同配置的影响往往是关键。模型在变化、应用需求在变化等——没有简单地创建新配置并通过评估传递的能力，会显著拖慢许多团队。
>
> 此外，为组件提供可序列化的配置格式意味着你可以构建低代码或无代码工具，让非技术用户通过图库中存在的或可以使用可视化界面创建/完全指定的组件来构建复杂的多智能体系统。事实上，我在为多智能体系统构建低代码工具的所有工作都源于这一认识，并启发了 AutoGen、AutoGen Studio 和 Magentic-UI（Dibia et al. 2024；Mozannar et al. 2025）中使用的配置系统。

### 9.2.6 全面的防护栏与中间件基础设施

生产多智能体系统需要健壮的安全机制和拦截点来实现防护栏、合规检查和安全措施。框架应提供全面的中间件基础设施，使开发者能够在关键交互点注入自定义逻辑。

**要寻找什么**：

- 所有模型调用的前/后处理钩子，具有完整的请求/响应访问
- 工具执行前的函数调用拦截和验证能力
- 用于工作流控制和验证的智能体状态转移中间件
- 可链式组合的可配置防护栏流水线
- 内置的 PII 检测、脱敏和内容过滤能力
- 对模型和工具输入的恶意输入检测与净化
- 捕获所有安全相关交互的审计日志钩子
- 不阻塞系统性能的异步兼容中间件

在 picoagents 中，我们为防护栏实现了中间件：

```python
# Pass middleware list directly to Agent
agent = Agent(
    name="assistant",
    instructions="You are a helpful assistant",
    model_client=client,
    middlewares=[
        PIIRedactionMiddleware(patterns=["ssn", "email"]),
        RateLimitMiddleware(max_calls_per_minute=60),
        GuardrailMiddleware(
            blocked_content=["harmful_request"]
        )
    ]
)
```

**要问的问题**：

- 我能拦截和验证所有模型输入和输出吗？
- 我如何在不修改框架代码的情况下实现自定义防护栏？
- 我能在可配置流水线中链接多个防护栏吗？
- 框架支持不降低性能的异步防护栏吗？
- 我能在所有交互中实现实时 PII 检测和脱敏吗？
- 我如何在执行前验证函数参数的恶意内容？
- 是否有监控和控制智能体状态转移的钩子？
- 我能为我的特定领域需求实现自定义合规检查吗？

**警告信号**：

- 使防护栏不切实际的糟糕性能特征
- 随框架更新而损坏的中间件系统

> **注意**
>
> 防护栏基础设施对合规、安全和安全性至关重要的生产部署是关键。没有适当的中间件钩子，团队往往诉诸于修改框架代码或实现脆弱的变通方案，这些在更新期间会损坏。设计良好的防护栏系统应该高性能、可扩展，并跨框架版本可维护。

### 9.2.7 全面的模式支持与可扩展性

正如我们在第 2 章探索的，不同的任务需要不同的协调方法。一个好的框架应该支持完整的模式谱系，并允许自定义实现。

**要寻找什么**：

- 内置对工作流模式的支持（顺序、并行、条件）
- 自主模式（轮询、AI 驱动选择、交接）
- 任务管理模式（终止、人类委托、错误处理）
- 自定义协调逻辑的清晰扩展点
- 可为复杂场景组合的可组合模式

在 picoagents 中，我们实现了几个协调模式（第 6 章、第 7 章）：

```python
# Round-robin orchestration
orchestrator = RoundRobinOrchestrator(agents=[writer, editor])
# AI-driven agent selection
orchestrator = AIOrchestrator(agents=[researcher, writer], model_client=client)
# Workflow with custom steps
workflow = Workflow(steps=[
    PicoAgentStep("research", researcher_agent),
    TransformStep("format", lambda x: format_results(x))
])
# Flexible termination conditions
termination = MaxMessageTermination(10) | TextMentionTermination("APPROVED")
```

**要问的问题**：

- 框架支持我的用例所需的协调模式吗？
- 需要时我能实现自定义编排逻辑吗？
- 在同一应用中组合不同模式有多容易？
- 有高级模式实现的示例吗？

### 9.2.8 生产部署、安全与运维

从原型走向生产需要全面的安全措施、部署能力和运维支持。

**要寻找什么**：

- 智能体交互的输入验证和净化
- 带沙箱能力的安全工具执行
- 带水平扩展的容器友好部署
- 身份验证、授权和审计日志
- 负载均衡、故障转移和云平台集成
- 资源限制、速率限制和运维监控

在 picoagents 中，我们实现了基本的安全和可观测性功能：

```python
# Tool approval for security
@tool(approval_mode=ApprovalMode.ALWAYS)
def sensitive_operation(data: str) -> str:
    return process_sensitive_data(data)
# OpenTelemetry integration for monitoring
os.environ["PICOAGENTS_ENABLE_OTEL"] = "true"
agent = Agent(name="prod-agent", model_client=client)
```

**要问的问题**：

- 框架如何同时处理安全和部署？
- 存在哪些扩展和运维监控能力？
- 我能审计所有智能体行动并在生产中安全部署吗？
- 扩展期间如何管理密钥和处理失败？

### 9.2.9 评估与测试支持

与传统软件不同，多智能体系统由于其概率性本质和复杂决策过程，需要专门的评估方法。

**要寻找什么**：

- 内置轨迹评估（比较预期与实际智能体步骤）
- 单元测试（单次交互）和集成测试（复杂会话）的支持
- 带预定义指标的自动化评估框架
- 将真实会话捕获并转换为测试用例的工具
- 对最终输出和中间推理过程的评估

在 picoagents 中，我们实现了评估能力：

```python
# Define evaluation tasks and judge
tasks = [Task(name="haiku", input="Write a haiku",
    expected_output="5-7-5 syllable poem")]
judge = LLMEvalJudge(model_client=client, criteria=["creativity", "format"])
# Evaluate agents or orchestrators
runner = EvalRunner(judge=judge, parallel=True)
target = AgentEvalTarget(agent)
scores = await runner.evaluate(target, tasks)
print(f"Average score: {sum(s.overall for s in scores) / len(scores)}")
```

**要问的问题**：

- 我能轻松创建和运行智能体行为的自动化评估吗？
- 框架支持轨迹分析和工具使用评估吗？
- 我如何跨不同场景测试智能体性能？
- 有衡量智能体有效性的内置指标吗？

### 9.2.10 活跃的生态与长期可行性

框架采用是长期承诺。周围生态的健康状况往往决定框架是否保持可行并随你的需求演进。

**要寻找什么**：

- 带定期发布的活跃开发
- 响应式的社区和维护者参与
- 带示例的全面文档
- 第三方集成和扩展
- 清晰的路线图和治理结构

**要问的问题**：

- 框架的维护和开发有多活跃？
- 社区的规模和参与度如何？
- 有商业支持选项吗？
- 框架如何处理破坏性变更和升级？

## 9.3 框架评估与决策流程

使用基于十项核心能力的加权评分矩阵系统化评估框架。定义你的技术需求、组织约束和业务优先级，然后构建聚焦的原型测试真实世界场景。表 9.1 展示了一个比较不同框架选项的示例评估矩阵。

*表 9.1：框架评估矩阵*

| 能力 | 权重 | 框架 A | 框架 B | 自定义构建 |
| --- | --- | --- | --- | --- |
| 开发者体验 | 20% | 8/10 | 6/10 | 4/10 |
| 异步架构 | 15% | 9/10 | 7/10 | 8/10 |
| 可观测性与开发工具 | 10% | 7/10 | 5/10 | 3/10 |
| 状态管理 | 15% | 8/10 | 6/10 | 2/10 |
| 配置 | 5% | 6/10 | 8/10 | 7/10 |
| 防护栏与中间件 | 10% | 5/10 | 3/10 | 8/10 |
| 模式支持 | 10% | 7/10 | 8/10 | 10/10 |
| 生产与安全 | 10% | 8/10 | 6/10 | 3/10 |
| 评估支持 | 5% | 6/10 | 4/10 | 2/10 |

**在以下情况选择自定义开发**：

- 你的需求高度专门化，通用框架不太可能支持
- 你有经验丰富的工程师和足够的时间构建和维护基础设施
- 你需要对架构、性能或特定实现细节的完全控制
- 问题领域已被充分理解，需求稳定

**在以下情况选择框架采用**：

- 你想将工程精力聚焦于业务逻辑而非基础设施
- 你需要以有限的工程资源快速交付工作系统
- 你的需求与常见多智能体模式很好地对齐
- 你重视生态收益，如社区支持、文档和第三方集成

**在以下情况考虑混合方法**：

- 你想要快速原型能力，同时保持通往自定义优化的路径
- 系统的不同部分有不同的需求（一些自定义，一些标准）
- 在承诺完全自定义开发之前，你正在试验方法
- 你需要非关键组件的框架收益，同时保持对核心逻辑的控制

## 9.4 超越教学实现的生产能力

虽然 picoagents 有效地演示了核心多智能体概念，但生产框架解决了教学实现有意省略的企业需求。根本差距在于运维基础设施和深度生态集成，而非基本功能。

生产框架提供全面的工作流持久化和恢复系统，跨基础设施故障维护智能体状态，使长时间运行的进程在崩溃或重启后无缝恢复。实现这一点比我们在第 6 章实现的工作流 API 所覆盖的更复杂。它们提供企业部署能力，包括自动扩缩容、负载均衡和与云平台及组织身份验证系统集成的安全边界。

最关键的是，它们包含复杂的安全基础设施，带基于插件的防护栏系统，用于威胁检测、内容过滤和自动化合规检查，在所有智能体交互的中间件级别运行。这些框架还提供全面的可观测性平台，包括分布式追踪、性能分析和为团队协作与生产调试设计的交互式开发环境。

除基础设施外，生产框架擅长生态集成，复制这些需要大量的自定义开发。Microsoft Agent Framework 提供跨微软技术栈的无缝 Azure AI Foundry 集成，带原生身份验证、部署和监控。Google ADK 提供原生 Vertex AI Agent Engine 部署，带 Cloud Run 扩展和 VPC 安全控制。Pydantic AI 采取云无关的方法，提供与 Logfire、AgentOps、Arize 和 W&B Weave 等可观测性平台的广泛集成。

区别不在于功能数量——而在于当多智能体系统以企业规模运行并具有真实业务后果时，可靠性、安全性和可维护性所需的架构复杂度和生态集成。

## 9.5 小结

- **框架超越功能的价值**：框架的主要价值在于维护负担减轻（处理 API 变更、安全补丁）和防止团队扩展时集成复杂性的标准化组件接口，而非基本功能差异。
- **生产基础设施差距**：生产框架提供运维基础设施（工作流持久化、企业部署、安全防护栏、全面的可观测性）和深度生态集成——Azure 客户获得跨 Azure 技术栈的无缝 Microsoft Agent Framework 集成，Google 客户获得原生 ADK Vertex AI 部署，而云无关的框架提供广泛的第三方集成。
- **评估方法**：对照稳定能力（开发者体验、异步架构、状态管理等）评估框架，而非直接比较，因为框架演进迅速，但基本需求保持一致。
- **依赖上下文的选择**：框架选择很大程度上取决于团队能力、时间线约束和组织生态，而非抽象的技术优越性——没有普遍"最好"的框架。

多智能体框架格局将继续快速演进。通过专注于基本能力和系统化评估流程，而非具体工具比较，无论出现哪些新框架或现有框架如何演进，你都准备好做出好的决策。

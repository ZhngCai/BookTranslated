# 第 3 章　多智能体系统的用户体验原则

本章涵盖：

- 审视用户界面格局如何从命令行演进到多模态、多智能体系统
- 追溯软件工程实践从传统开发到自主多智能体系统的转变
- 在理解用户时区分终端用户和开发者画像
- 阐明多智能体应用的 UX 设计原则，包括能力发现、成本感知的行动委托、可中断性、可观测性和溯源

构建多智能体系统（或任何软件工具）的最终目标，是为用户解决特定问题。该系统可以作为组件被开发者利用（如软件开发者通过 SDK 或 API 等）来创建更大的系统，也可以被终端用户直接用于完成特定任务。无论目标用户是谁，开发具有最佳用户体验的系统都至关重要——系统要有效，即帮助用户以最小的摩擦或努力完成任务；并且令人愉悦，使其引人入胜、使用起来令人开心。为了实现这一点，我们必须理解用户及其行为、动机、态度和目标，然后设计满足这些需求的系统。

多智能体系统代表了从界面设计到**委托设计**（delegation design）的根本转变——一种 UX 范式，用户向自主系统提供开放式任务指令，而不是直接操纵特定的界面控件。传统应用提供直接操纵——点击"发送邮件"执行一个可预测的、程序员定义的例程。多智能体系统的运作方式不同，通过三个关键属性：**自主性**（AI 模型从庞大的动作空间中决定动作）、**后果**（基于 AI 推理的真实世界影响）和**持续时间**（跨系统的复杂、长时间运行的协调）。

用户不是控制特定动作，而是将开放式任务委托给可以执行任何可用能力组合的自主系统。一个可以访问邮件、日历和预订平台的旅行预订系统，基于 AI 对单条自然语言指令的解读，可能采取数百种不同的动作序列。

虽然 UX 原则适用于所有软件，但多智能体系统带来了独特的挑战，放大了这些原则的重要性。与以预定义行为响应用户输入的传统应用不同，多智能体系统包含自主智能体，它们可以基于 AI 决策采取具有现实后果的行动。当多个智能体协调时，单个 AI 决策可以在整个系统中级联，产生用户必须理解和控制的复合效应。这种从预定义例程到 AI 决定动作序列的转变，需要新的 UX 方法来传达智能体能力、行动成本、协调模式和干预点。

在本章中，我们将探讨多智能体系统的用户体验（UX），重点关注这种委托范式如何为终端用户和开发者创造新的需求和期望。我们将讨论这种从直接操纵到任务委托的根本转变如何创造独特的挑战和机遇。通过理解用户现在必须信任 AI 推理而非程序员逻辑，我们可以推导出帮助用户有效委托任务、同时保持适当控制和理解的设计原则。

> **终端用户看到的是多个智能体还是单个系统？**
>
> 终端用户通常将多智能体系统感知为单一实体，发出高层命令，由底层智能体协作执行。这种抽象提供了无缝体验，但建立信任需要对系统内部运作的可选可见性——尤其是对于具有重大后果的非平凡决策。可观测性原则（3.4 节）回应了这种透明度需求。

## 3.1 背景：界面与软件开发的演进

要理解多智能体系统独特的 UX 挑战，考察用户界面和软件开发实践如何演进会很有帮助。这一演进直接塑造了我们将在本章后面探讨的设计原则。

### 3.1.1 用户界面——从命令行到多模态、多智能体界面

用户界面的演进从基于文本的命令行发展到今天的智能多模态系统，每一次转变都在降低认知负荷的同时引入新的交互可能性。这一递进最终在多智能体界面达到顶峰——它可以解读自然语言、图像和语音输入，同时自主执行复杂动作。

传统界面要求用户学习特定命令（CLI）或视觉隐喻（GUI），将可访问性限制在具备专业知识的人群。沉浸式界面（AR/VR）引入了空间交互，但仍受预定义能力的约束。

以电子邮件作为这一演进的说明性示例。命令行邮件需要记忆语法（`mail -s "Subject" recipient@example.com`），GUI 客户端引入了带拖放组织的可视化撰写，而今天的智能界面支持自然语言请求："给团队发一封关于周一会议的邮件，并附上议程。"系统可以解读意图、定位相关文件并生成适当内容——但用户必须理解何时可以信任这些能力。

智能多模态、多智能体界面代表了最新的进展，提供几个关键能力：

- **自然输入处理**：跨多种语言的自由格式文本、语音、图像和视频
- **动态输出生成**：以文本、音频、视频或代码形式呈现的上下文恰当的响应
- **自主行动**：带工具的智能体可以代表用户执行多步骤任务
- **自适应交互**：系统根据用户上下文和偏好进行调整

然而，这种灵活性引入了新的挑战。与具有清晰定义的按钮和能力的 GUI 不同，智能界面可能处理范围庞大的任务，可靠性各不相同。这造成了**能力发现问题**——用户难以理解系统能有效做什么，以及它可能在哪些地方失败。

这一演进强调了朝着更自然、更自适应交互的持续驱动，同时凸显了对系统能力和局限性进行透明沟通的需求。

> **是什么让智能界面与众不同**
>
> 生成式 AI 引入了三项变革性能力，使现代界面区别于其前身：
>
> - **更易访问的界面**：智能多模态界面支持跨数百种语言的自然语言、语音、图像和视频交互，使系统能够触达更广泛的受众。这种包容性让用户以符合其偏好和能力的方式使用系统，降低了准入门槛。
> - **对模糊输入的支持**：生成式模型擅长解读模糊或容易出错的输入，处理不精确的命令和自然语言的细微差别，同时仍能提供连贯的响应。然而，这种灵活性引入了潜在误解或看似合理但错误的信息等风险，需要健壮的验证机制。
> - **动态内容生成**：生成式 AI 基于用户输入和任务需求动态创建和调整内容，实现更个性化、上下文更相关的交互。这减少了对大量预先设计的需求，在提供独特自适应用户体验的同时加速创新。

### 3.1.2 从 Software 1.0（规则）到 Software 3.0+（自主多智能体系统）

软件工程学科正在经历从显式的基于规则的编程到智能、自适应系统的转变（见图 3.1）。这一演进直接影响我们构建面向用户的应用的方式。

![图 3.1：从 Software 1.0 到 Software 3.0 的演进](images/p100_0.png)

*图 3.1：软件工程学科正从传统软件开发（Software 1.0）范式——开发者编写显式代码——演进到更动态、自适应和智能的系统（Software 3.0），其中自主智能体可以推理、沟通和行动以解决复杂任务。*

**Software 1.0** 涉及编写具有固定规则和逻辑的显式代码。例如，垃圾邮件过滤器使用预定义的关键词词典来分类邮件。

**Software 2.0** 引入了从数据中学习模式的机器学习系统。同样的垃圾邮件过滤器现在在大型数据集上训练以识别垃圾邮件模式，通过数据驱动的分类而非手工编码的规则提高准确率。

**Software 3.0+** 采用生成式模型和自主智能体，它们可以自适应地推理、沟通和行动。一个邮件系统现在可能包含这样的智能体：自动起草回复、检查日历可用性、提议会议时间，甚至安排约会——同时随着时间推移适应用户偏好和写作风格。

关键洞见是每种范式都不会完全取代前一种。邮件发送协议仍由 Software 1.0 逻辑高效处理，受益于模式识别的功能（垃圾邮件过滤）利用 Software 2.0 方法，而复杂、自适应的交互利用 Software 3.0+ 能力。开发者的挑战从编写显式代码转变为定义智能体能力并编排能够处理庞大任务阵列的智能系统。

## 3.2 多智能体的可靠性挑战

多智能体系统继承了单个 AI 模型的可靠性悖论，同时引入了可能放大不可预测性的新协调挑战。像 GPT-4 这样的模型可以从复杂的 JSON 模式中提取实体，编写复杂的 React 组件，却在"哪个数字更大，9.11 还是 9.9？"这样的简单比较上失败。当多个这样的模型通过智能体协调时，这些个体的不一致以意想不到的方式复合。

当智能体在复杂任务上协同工作时，即使单个智能体在隔离状态下表现良好，协调故障仍可能发生。智能体交互的动态特性使得预测哪些任务会成功、哪些会失败变得困难，造成基于用户不可见因素而变化的不可靠用户体验。

这创造了一个"锯齿状前沿"（jagged frontier）（Dell'Acqua et al. 2023）——一种 AI 能力高度不均衡的现象，一些看似困难的任务执行良好，而看似简单的任务却意外失败。锯齿状的本质意味着在同一个工作流中，一些任务可能落在 AI 擅长的前沿一侧，而其他看似难度相似的任务可能落在 AI 挣扎的一侧。在多智能体系统中，这种不可靠性不仅因个体模型限制而被放大，还因协调故障而被放大。看似复杂度相当的任务，其成败取决于智能体协调如何处理隐式假设和上下文共享。

**UX 影响**：对用户而言，这意味着多智能体系统可能在某些场景中表现出复杂的行为，而在其他看似相似的场景中灾难性地失败。与传统软件可预测的失败模式不同，智能体协调的动态特性使用户难以对系统能力和局限性建立准确的心智模型。

![图 3.2：可靠性悖论](images/p103_0.png)

*图 3.2：可靠性悖论：多智能体系统可以处理广泛的任务，但协调挑战在个体模型局限之外创造了额外的可靠性差异。UX 设计必须传达这种不确定性，同时通过透明度建立信任。*

## 3.3 多智能体用户画像与挑战

多智能体系统创造了单智能体或传统软件所不存在的独特用户体验挑战。从终端用户和开发者两个视角理解这些挑战，对于设计有效界面至关重要。这两种画像代表了两种截然不同的用户类型，对透明度和控制有着根本不同的需求。

### 3.3.1 终端用户画像：Jane——功能性透明度需求

考虑 Jane 预订一次涉及航班、酒店和租车的复杂商务旅行。在多智能体系统中，她的请求可能由专门智能体处理：

- **旅行智能体**：搜索航班和酒店
- **日历智能体**：检查日程冲突和偏好
- **报销智能体**：确保符合公司政策
- **预订智能体**：完成交易

**Jane 的核心需求**：

- **理解正在发生什么**：Jane 需要知道系统在做什么，而不需要技术协调细节（"旅行智能体找到 3 个航班，正在检查你的日历以发现冲突"）
- **理解为什么做出决策**：当智能体做出选择时，Jane 需要简单的解释（"基于你对早班出发的偏好选择了航班"）
- **简单的控制机制**：Jane 想要简单的方法来提供输入、纠正假设或改变方向，而不必重启工作流
- **渐进式披露**：Jane 更喜欢从基本信息开始，仅在需要时访问更多细节
- **通过清晰建立信任**：清晰沟通什么成功了、什么失败了以及为什么，可以建立 Jane 对委托任务的信心

Jane 代表需要**功能性透明度**的终端用户——理解结果并拥有简单控制，而不会被技术复杂性淹没。

### 3.3.2 开发者挑战：协调设计

Mike 正在构建旅行系统，面临多智能体特有的技术挑战：

- **协调模式选择**：他应该使用对话驱动模式（透明但可能混乱）还是交接模式（清晰但对用户不透明）？
- **错误归因**：当系统失败时，Mike 需要能够区分协调失败与单个智能体错误的调试工具。
- **心智模型设计**：Mike 必须以帮助用户理解系统的方式呈现智能体协调，而不让其被复杂性淹没。
- **性能分析与优化**：Mike 需要分析智能体动作的机制，以理解低效之处（例如冗余的昂贵步骤）、瓶颈和优化机会。

Mike 的主要挑战涉及确保智能体可预测、安全，并与 Jane 等终端用户的需求和行为紧密对齐。

这些画像说明了同一个多智能体系统必须服务根本不同的透明度和控制需求。Jane 需要关于结果的清晰、简单的沟通，而 Mike 需要对内部运作的详细技术洞察。

## 3.4 多智能体 UX 设计原则

前面概述的协调挑战和可靠性不可预测性需要特定的 UX 设计方法。以下原则通过针对终端用户（如 Jane）和开发者（如 Mike）量身定制的可操作策略，回应这些多智能体挑战。

![图 3.3：多智能体 UX 设计原则](images/p107_0.png)

*图 3.3：多智能体应用带来特定挑战，需要独特的设计考量以确保无缝有效的用户体验。这些包括为能力发现设计（理解智能体能做什么）、成本感知的行动委托（传达智能体行动的成本并允许委托机制）、可观测性（确保用户能观察智能体行动）和可中断性（允许用户干预智能体行动）。*

每个原则都为 Jane（需要功能性透明度的终端用户）和 Mike（需要架构透明度的开发者）提供策略，确保系统有效服务不同的透明度和控制需求。

在本节中，我们使用 PicoAgents WebUI——随 PicoAgents 框架附带的基于 Web 的界面——来说明这些原则。WebUI 展示了这些 UX 原则如何通过具体的界面模式在实践中实现。WebUI 的实现细节和源代码可在 PicoAgents 仓库（picoagents/src/picoagents/webui/）中获得，第 8 章提供了在一个最小智能体 Web 应用中从零实现这些原则的分步指南。

### 3.4.1 能力发现

**帮助用户理解智能体能做什么**

智能体拥有自主性，意味着它们可以执行许多不同的动作和协调模式。实际上，每个智能体都有特定的配置——系统提示词、可用工具和内部逻辑——使其在特定类型的任务上比其他任务更可靠。然而，用户并不知道这一点。这造成了能力发现问题：用户不知道哪些任务会顺利、哪些可能失败，当智能体在不合适的任务上表现不佳时，会导致挫败和不信任。

这一原则主张 UX 主动引导用户走向高可靠性任务示例，或根据用户上下文和系统能力建议相关的高可靠性任务。许多成功的工具通过提供示例任务作为用户可以选择的预设来回应这一点。

**实现策略**：

终端用户策略：

- **能力预设**：提供具体的任务示例，展示系统擅长的复杂度级别和任务类型（"预订含酒店的国内商务旅行"或"规划多城市会议行程"）。
- **引导式任务建议**：通过模板和建议，将用户引导至系统可靠能力范围内的任务。
- **渐进式披露**：从基本能力开始，随着用户熟悉系统的可靠性模式，逐步揭示高级功能。
- **成功概率指示器**：探索使用置信度指示器，帮助用户理解任务何时处于系统的舒适区（"对商务旅行可靠，复杂国际行程需审查"）。

开发者/高级用户策略：

- **多智能体架构透明度**：展示专门智能体如何协同工作、其协调模式和交接机制。
- **按协调模式的可靠性**：传达交接模式提供可预测的结果，而对话驱动模式支持灵活解决方案但结果多变。
- **工具与能力映射**：清晰记录每个智能体可以访问哪些工具，以及它们如何组合以处理不同任务类别。
- **能力边界**：清晰指示任务何时需要人类干预、单智能体或多智能体协调。

> **示例场景**
>
> 旅行预订系统提供能力预设，如"预订国内商务差旅""规划带团体价格的会议旅行"和"安排多城市销售拜访"。这些预设引导用户走向系统可靠处理的任务，而更复杂的请求如"规划带定制冒险活动的蜜月"被标记为需要旅行智能体咨询。界面清晰传达："我们的系统擅长商务旅行和标准度假预订。对于有特殊要求的复杂国际行程，请考虑使用我们的辅助预订选项。"

### 3.4.2 成本感知的行动委托

**传达智能体行动的成本，并允许委托机制**

多智能体系统的一个宝贵特性是能够将任务和行动委托给智能体，让用户把重复或复杂的任务交给系统。然而，行动具有不同级别的**后果**（consequence）——如果行动包含错误或不恰当，其潜在影响或危害。成本感知的行动委托是一种 UX 原则，用于传达行动后果，并提供用户控制机制来处理不同成本级别的行动。例如，摘要一封邮件成本低（错误时的后果最小），取消一个定期团队会议成本中等（损失时间、改变参与者计划），而将机密文档附加到邮件并发送给外部方成本高（潜在的数据泄露）。

构建能够推断或量化这些成本、将其传达给用户并提供如何处理此类行动设置的机制，非常重要。例如，用户应该能够指定如何处理中成本和高成本行动（例如，执行前请求批准、直接执行不询问，或永不执行）。

**实现策略**：

终端用户策略：

- **简单的成本沟通**：使用清晰、非技术性的语言解释行动影响（"这将取消你的团队会议并通知 5 个人"）。
- **三级批准系统**：低成本（自动执行）、中成本（执行后通知）、高成本（先请求许可）。
- **一键设置**：无需技术复杂性的整体委托偏好简单控制。
- **影响预览**：在执行前展示后果（"预订此航班将超出你每月旅行预算 200 美元"）。

开发者/高级用户策略：

- **详细的成本模型**：暴露成本估计算法、置信区间和考虑的因素。
- **自定义阈值配置**：允许对成本类别、智能体特定限制和条件规则进行细粒度控制。
- **委托模式控制**：基于协调复杂性配置不同的批准工作流。

> **示例场景**
>
> Jane 对旅行智能体说："预订我下周去伦敦会议的行程，并处理任何日程冲突。"系统搜索航班（低成本，自动执行），并识别出需要移动一个与旅行日期冲突的客户会议（中成本）。系统没有继续执行，而是向 Jane 展示："我找到了前往伦敦的可用航班[预览选项]。我还需要重新安排你周二与 ABC Corp 的客户会议，这需要通知 3 位与会者，并可能影响他们的日程。我应该继续重新安排会议吗？" Jane 可以批准特定行动，或为未来类似场景调整她的委托设置。

![图 3.5：picoagents 中的函数批准](images/p114_0.png)

*图 3.5：在 picoagents 中，函数可以配置为需要显式批准，WebUI 提供界面来批准函数执行请求。*

### 3.4.3 可观测性与溯源

**确保用户可以观察智能体做了什么（行动）以及为什么**

可观测性和溯源是确保用户可以观察智能体行动、追溯决策背后的推理，并理解影响结果的数据来源的 UX 原则。自主智能体可以探索非确定性的、仅在运行时才可知的轨迹。相同输入的每次运行都可能导致显著不同的轨迹。这使得终端用户观察这些轨迹变得重要，既可以建立智能体在做正确事情的信任，也可以更多了解其能力和局限，改进他们的任务表述方法。

**实现策略**：

终端用户策略：

- **实时活动流**：在智能体取得进展时展示实时更新，包括结构化计划、当前步骤和时间/成本估算（"旅行智能体找到 3 个航班，日历智能体正在检查日程冲突"）。
- **简单的进度叙述**：将复杂的智能体协调转化为用户友好的进度故事，解释发生了什么以及为什么。
- **结果归因**：当出现问题时，用用户语言和清晰因果关系解释（"航班预订失败，因为日历智能体检测到与你周二会议的冲突"）。
- **信任与置信度指示器**：以易懂语言展示数据来源和推理置信度（"基于你的旅行历史和当前日历可用性"）。

开发者/高级用户策略：

- **详细的协调可视化**：完整的智能体交接流、委托模式、共享上下文演进和决策树。
- **归因调试**：通过完整的错误追踪和性能分析，区分单个智能体行动与协调决策。
- **冲突解决日志**：对智能体分歧、推理过程和解决机制的完整可见性。
- **多智能体活动轨迹**：对话感知的日志，展示协调上下文、共享状态变化和跨智能体依赖，附带 Token 用量和性能指标。

> **示例场景**
>
> **好的做法**：Jane 请求"预订去伦敦的行程和酒店。"界面显示：旅行智能体找到航班，日历智能体检测到与 Jane 周二会议的冲突，报销智能体注意到酒店超出政策限额。Jane 看到协调流：日历智能体将会议详情传递给旅行智能体，后者调整日期，然后交给报销智能体批准。当智能体在酒店选择上意见分歧时，Jane 看到两个带推理的建议。
>
> **坏的做法**：Jane 的行程预订失败，显示"错误：预订不成功。"她无法分辨是旅行智能体找不到航班、日历智能体错误地屏蔽了日期，还是智能体之间存在协调失败。对哪个智能体贡献了什么、系统为何失败毫无可见性。

### 3.4.4 可中断性

**允许用户暂停、恢复或取消智能体行动**

可中断性是一种 UX 原则，确保用户可以在执行过程中的任何时刻中断、暂停、恢复或取消智能体行动。自主多智能体系统可以长时间运行、进行多次工具调用，并采取具有现实资源影响的行动。在某些情况下，特别是在人在回路（human-in-the-loop）的设置中，用户可能观察到昂贵或有问题的操作轨迹，需要暂停系统以提供反馈、纠正方向或完全取消。

这一原则主张设计这样的系统：用户可以随时中断智能体执行、暂停长时间运行的任务，并从中断处恢复而不丢失进度或系统状态。多智能体系统最适用于需要跨多个步骤规划、可能需要相当长时间才能完成的复杂任务。

**实现策略**：

终端用户策略：

- **简单的停止/启动控件**：清晰的暂停、恢复和取消按钮，无技术复杂性。
- **智能恢复**：恢复时，自动向用户同步暂停期间发生的事情。
- **温和的中断**：允许用户添加需求或纠正，而无需停止整个过程。
- **保存进度**：确保用户在需要中断任务时不丢失工作。

开发者/高级用户策略：

- **细粒度智能体控制**：中断单个智能体而不停止整个协调流。
- **协调状态管理**：跨中断维护共享上下文和智能体通信历史。
- **模式切换**：在任务中途改变协调模式（例如，从自主到受监督的交接模式）。
- **冲突解决干预**：智能体意见分歧时的手动解决工具，带有决策影响可见性。

> **示例场景**
>
> **好的做法**：在旅行规划期间，Jane 看到旅行和日历智能体在日期上意见分歧。她中断对话，提供她的实际可用时间，并观察智能体更新共享上下文。正在等待的报销智能体自动用纠正后的信息恢复。
>
> **坏的做法**：Jane 需要纠正日历智能体的假设，但只能停止整个工作流。当她重启时，智能体丢失了之前的协调上下文，必须从头开始。

![图 3.6：PicoAgents WebUI 的中断能力](images/p118_0.png)

*图 3.6：在 PicoAgents WebUI 中，用户可以使用左下角的"Stop"按钮在流中停止智能体执行。系统在会话中维护对话状态，允许用户暂停工作、审查进度，并在不丢失上下文的情况下稍后恢复。右侧的调试面板显示实时可观测的事件流，帮助用户在决定中断之前理解正在发生的事情。*

## 3.5 交互式与离线多智能体场景

多智能体应用中的任务场景可以归类为交互式或离线式，取决于任务的性质和预期的人类交互水平（如图 3.7 所示）。在**交互式场景**中，用户实时积极参与智能体，审查进度并按需提供输入。相比之下，**离线场景**涉及智能体自主工作以完成任务，无需用户逐轮的直接输入。每种方法都有其优点和缺点，选择取决于任务复杂性、用户偏好和期望的自主性水平等因素。

![图 3.7：交互式与离线多智能体场景](images/p120_0.png)

*图 3.7：多智能体应用可以根据所需的用户交互水平归类为交互式或离线式。交互式场景涉及实时用户参与，而离线场景涉及自主的智能体任务执行。*

例如，在旅行预订这样的交互式用例中，用户用自然语言表达偏好，观察智能体的进展，提供反馈（显式请求的或临时的），并验证任务状态。因此，相关界面必须允许用户定义任务、审查智能体的行动、假设或相关数据、提供输入、在出错时中断或干预，并确认智能体的行动。所有这些都必须相对快速地发生（低延迟）以防止用户挫败，利用一个传达智能体状态的交互式 UI（例如，智能体行动时间线的交互式视图、审查先前行动或显示当前活动）。

另一方面，离线任务可能涉及后台任务，如从非结构化邮件中提取结构化数据或将数据输入界面。例如，多智能体工作流可以从非结构化邮件中提取结构化数据，登录 CRM 系统并更新客户记录。在这种情况下，用户可能不参与任务执行，但可能会收到任务完成或任何需要其注意的异常的通知。在这种设置中，低延迟不那么关键；然而，可以实施自动审查和验证智能体行动及最终解决方案的工具，以改进整体解决方案。

## 3.6 小结

- **多智能体应用的 UX 设计代表了从传统界面设计**（用户点击执行可预测、程序员定义动作的按钮）**到委托设计**（用户向可以从庞大动作空间中选择的自主 AI 智能体发出自然语言指令）**的根本转变**。这种转变创造了新的 UX 挑战（Bansal et al. 2024），因为复杂度相当的任务可能因 AI 推理和智能体协调故障而不可预测地成功或失败。
- **UI 和软件演进经历了不同的阶段**——用户界面从命令行语法演进到图形隐喻，再到今天的智能多模态系统；而软件开发从显式的基于规则的编程（Software 1.0）转向机器学习（Software 2.0），再到自主多智能体系统（Software 3.0+）。这些平行演进创造了"能力发现问题"：用户难以理解这些强大但不可预测的系统能可靠完成什么。
- **两种截然不同的用户类型需要不同的设计方法**：终端用户（预订行程的商务旅客）需要对正在发生什么以及为什么的简单透明度，而构建这些系统的开发者需要对智能体协调模式、错误归因和性能优化的详细可见性，以确保可靠的用户体验。
- **四条核心 UX 设计原则回应多智能体委托挑战**：能力发现（引导用户走向可靠任务）、成本感知的行动委托（管理 AI 决策的现实后果）、可观测性与溯源（展示发生了什么以及为什么）、可中断性（允许对自主工作流进行优雅干预）。这些原则帮助用户有效委托复杂任务，同时保持适当的控制。
- **多智能体系统表现出可靠性的"锯齿状前沿"**——它们可以处理复杂的协调任务，如预订复杂的商务旅行，却因协调故障在看似更简单的请求上失败，需要新方法来传达不确定性并通过透明度建立用户信任。

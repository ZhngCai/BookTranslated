## 4.10 OpenTelemetry：行业标准的可观测性

我们探索的中间件模式——日志记录、指标采集、PII 脱敏、速率限制——解决了真实的生产问题。然而，为每个项目实现自定义中间件会产生开销，并使与现代监控工具的集成变得困难。OpenTelemetry 提供了一种标准化解决方案，适用于所有编程语言、框架和监控后端。

OpenTelemetry（OTEL）是一个由云原生计算基金会（Cloud Native Computing Foundation，CNCF）支持的开源可观测性框架。它定义了收集追踪（trace）、指标（metric）和日志的供应商中立标准——使你能够一次埋点，无需代码更改即可导出到任何后端（Jaeger、Datadog、Azure Monitor 等）。

对于 AI 系统，OpenTelemetry 提供 Gen-AI 语义约定（Gen-AI Semantic Conventions）——专为 AI 操作设计的标准化属性名和 Span 结构。这些约定定义了如何对 LLM 调用（模型名称、Token 用量）、工具执行（工具名称、成功/失败）和智能体工作流（带适当层级的多步操作）进行埋点。

当你遵循这些约定时，你的遥测数据立即变得可移植。无论你使用 PicoAgents、LangChain 还是 AutoGen，你的追踪都遵循相同的结构——更容易比较系统、共享工具和在平台之间迁移。这种标准化还支持关键的生产能力，如合规审计轨迹、跨团队成本跟踪和大规模性能监控。

### 4.10.1 构建 OTelMiddleware

让我们构建一个实现我们之前定义的 BaseMiddleware 接口的 OTelMiddleware 类。此中间件将遵循 Gen-AI 语义约定，确保我们的遥测符合标准。

首先，初始化创建遥测仪器：

```python
from opentelemetry import metrics, trace
class OTelMiddleware(BaseMiddleware):
    """OpenTelemetry middleware following Gen-AI conventions."""
    def __init__(self):
        self._tracer = trace.get_tracer("picoagents")
        self._meter = metrics.get_meter("picoagents")
        # Create metric instruments following Gen-AI semconv
        self._token_histogram = self._meter.create_histogram(
            name="gen_ai.client.token.usage",
            unit="{token}",
            description="Token usage per request"
        )
        self._duration_histogram = self._meter.create_histogram(
            name="gen_ai.client.operation.duration",
            unit="s",
            description="Operation duration"
        )
```

中间件获取用于创建 Span 的 tracer 和用于记录指标的 meter。它按照 Gen-AI 约定创建两个直方图仪器：一个用于 Token 消耗，一个用于操作时长。

当操作开始时，process_request() 创建带 Gen-AI 属性的 Span：

```python
async def process_request(self, context):
    """Start span before operation."""
    # Create span following Gen-AI naming conventions
    if context.operation == "model_call":
        span_name = f"chat {self._get_model_name(context)}"
    elif context.operation == "tool_call":
        span_name = f"tool {self._get_tool_name(context)}"
    span = self._tracer.start_span(span_name)
    # Add Gen-AI semantic convention attributes
    span.set_attribute("gen_ai.system", "picoagents")
    span.set_attribute("gen_ai.operation.name", context.operation)
    span.set_attribute("gen_ai.agent.name", context.agent_name)
    # Store span for completion in process_response
    context.metadata["_otel_span"] = span
    context.metadata["_otel_start"] = time.time()
    yield context
```

操作完成后，process_response() 记录指标并结束 Span：

```python
async def process_response(self, context, result):
    """Record metrics and end span."""
    span = context.metadata.get("_otel_span")
    # Record token usage metrics for model calls
    if hasattr(result, "usage"):
        self._token_histogram.record(
            result.usage.prompt_tokens,
            {"gen_ai.token.type": "input"}
        )
        self._token_histogram.record(
            result.usage.completion_tokens,
            {"gen_ai.token.type": "output"}
        )
        # Add usage as span attributes
        span.set_attribute("gen_ai.usage.input_tokens",
                          result.usage.prompt_tokens)
        span.set_attribute("gen_ai.usage.output_tokens",
                          result.usage.completion_tokens)
    # Record duration and end span
    duration = time.time() - context.metadata["_otel_start"]
    self._duration_histogram.record(duration)
    span.set_status(Status(StatusCode.OK))
    span.end()
    yield result
```

## 4.11 智能体即工具

我们已经构建了一个可以使用工具行动的单个智能体。这里工具的概念围绕一个离散的请求-响应操作（例如，函数调用、API 调用或数据库查询）。实际上，拥有能做更多事情的工具——即它们可以实现我们迄今讨论的智能体循环的某种版本——是有利的。从这个角度看，"智能体"和"工具"之间的界限变得模糊。

这支撑了一种新兴且强大的**智能体即工具**（agent as tool）模式：任何智能体都可以成为其他智能体的工具。关键的架构优势是每个智能体保持完全独立——自己的模型配置、工具集、记忆和中间件——同时成为更大系统中可复用的组件。

要实现 as_tool()，我们将智能体包装在暴露单个 task 参数的 BaseTool 接口中。此参数告诉调用方 LLM 向专门智能体发送什么。智能体的描述成为工具的说明，帮助协调方的 LLM 理解何时使用这个特定的专家。当协调方调用工具时，它传递一个任务字符串，该字符串被路由到被包装智能体的 run() 方法，智能体的最终响应成为工具的结果。

### 4.11.1 控制结果的信息量

智能体组合中的一个关键设计决策是：什么信息从专门智能体流回协调方。默认情况下，as_tool() 只返回专家的最终消息。虽然这提供了上下文隔离——防止协调方的上下文因专家的所有中间步骤而爆炸——但当最后一条消息只是"完成了！"或"谢谢！"而关键细节出现在早期消息中时，可能会丢失重要信息。

result_strategy 参数在上下文隔离与信息量之间取得平衡：

```python
# Default: last message only (maximum isolation, minimal context pollution)
weather_tool = weather_agent.as_tool()
# Last N messages: capture conclusion + key supporting details
analyst_tool = analyst_agent.as_tool(result_strategy="last:3")
# All messages: full transparency, but risks context explosion
debug_tool = debug_agent.as_tool(result_strategy="all")
# Custom: precise control over what information transfers
def extract_key_findings(messages):
    """Extract only messages containing data or conclusions."""
    return "\n".join(
        msg.content for msg in messages
        if any(keyword in msg.content.lower()
               for keyword in ["found", "result:", "conclusion"])
    )
research_tool = research_agent.as_tool(result_strategy=extract_key_findings)
```

随着智能体层级的加深，这种控制变得必不可少。一个管理五个专家、每个专家内部执行 10-20 次工具调用的协调方，如果每个中间步骤都向上冒泡，就会积累海量上下文。result_strategy 使每个组合层都能定义自己的上下文边界。

考虑构建一个研究系统：你的天气专家可能使用快速、便宜的模型（因为天气查询很直接），而你的数据分析专家使用昂贵的推理模型进行复杂计算。每个智能体可以由不同团队独立开发、测试和优化，然后无缝组合在一起。

*代码清单 4.31：带专门配置的智能体组合*

```python
# Each agent optimized for its specific domain
weather_agent = Agent(
    model="gpt-4.1-mini",     # Fast, cheap model for simple queries
    tools=[weather_api],
    memory=weather_cache
)
analysis_agent = Agent(
    model="o1-preview",      # Expensive reasoning model for complex analysis
    tools=[analyze_data, create_charts],

# Coordinator composes specialized agents

    model="gpt-4o",

```

执行时，协调方会自动将天气数据收集路由到天气专家（使用高效模型），将趋势分析路由到分析专家（使用推理模型）。执行流展示了清晰的委托：


## 4.12 上下文工程

> 如果说 LLM 是 CPU，那么上下文窗口就是内存。——Andrej Karpathy

智能体依赖大型语言模型（LLM）来处理指令并生成响应。然而，LLM 的上下文窗口是有限的——它们一次能关注的文本量有限。当智能体执行多步任务时，其上下文迅速增长，随着关键信息被挤出模型的注意力范围，性能有下降的风险。

提示词工程专注于精心设计给模型的单个输入，而上下文工程是主动管理多步智能体执行期间上下文如何积累和演进的实践。当智能体处理任务时，每个动作——工具调用、记忆检索、对话轮次——都会增加上下文。没有仔细的管理，这种增长会造成两个关键问题：

### 4.12.1 上下文腐化与上下文爆炸

**上下文腐化（Context Rot）**：随着 Token 数量增加，模型准确回忆信息的能力下降。研究表明，性能退化大约从 32K Token 开始，远早于宣传的极限。Transformer 架构的 n² 两两关系意味着每个 Token 都在消耗模型的注意力预算——一种收益递减的有限资源。

**上下文爆炸（Context Explosion）**：在智能体执行期间，上下文迅速增长。每次工具调用都会添加请求参数、执行结果和错误消息。记忆检索注入历史上下文。消息历史一轮一轮地积累。

考虑一次典型智能体运行期间发生的事情：

*表 4.2：智能体执行期间的上下文增长*

| 步骤 | 添加的上下文 | Token | 累计总数 |
| --- | --- | --- | --- |
| 初始 | 系统 + 记忆 + 任务 | 2,600 | 2,600 |
| 工具调用 | 助手 + 工具结果 | 3,150 | 5,750 |
| 5 次工具调用 | 多个结果 | 15,000 | 20,750 |

没有上下文管理，智能体会静默失败。一个在 5 步任务上完美工作的研究智能体，在 10 步工作流的第 8 步开始产生幻觉——不是因为模型退化了，而是因为 45K Token 的累积工具结果将关键指令挤出了注意力窗口。

### 4.12.2 本章中的上下文工程

如果你读到这里，你会认识到我们已经实现了某种形式的上下文工程。我们的 _prepare_llm_messages() 方法从系统指令、对话历史、记忆检索和当前任务组装上下文。我们的记忆实现探索了基于 RAG 的检索（应用管理）和通过 MemoryTool 的主动记忆管理（智能体自管理）——这些方法不仅添加上下文，而且刻意修剪它。

### 4.12.3 管理策略

现代智能体框架实现了多种上下文管理方法。这些策略应对上下文爆炸的不同方面，并可以在生产部署中组合使用。

**压缩（主动修剪）**：修剪旧消息以保持在 Token 预算内。在 PicoAgents 中，压缩是一等公民的智能体参数。CompactionStrategy 在工具循环内的每次 LLM 调用前运行，压缩后的列表替换后续迭代的工作列表：

```python
from picoagents.compaction import HeadTailCompaction
agent = Agent(
    name="researcher",
    instructions="You are a research assistant.",
    model_client=model_client,
    tools=[web_search, read_file],
    compaction=HeadTailCompaction(
        token_budget=50_000,
        head_ratio=0.2  # 20% head, 80% tail
    ),
)
```

HeadTailCompaction 保留头部（系统提示词和原始任务）和尾部（近期的工具调用和结果），在超预算时丢弃中间消息。头部保留智能体正在做什么；尾部保留它进行到哪里。一个关键约束：带工具调用的助手消息及其对应的工具结果形成原子组，绝不能拆分，否则 API 将拒绝请求。

挑战在于：过度激进的压缩会丢失关键细节，而保守的压缩无法回收足够的 Token。如果你的智能体重新读取已经处理过的文件，说明你的预算太紧了。

**主动记忆管理**：智能体主动管理什么被持久化。4.8 节的 MemoryTool 让智能体显式存储、组织和删除信息：

```python
# Agent curates its knowledge base
memory(
    command="create",
    path="/patterns/race_condition.md",
    file_text="Thread safety issues..."
)
# Later, prunes outdated information
memory(
    command="delete",
    path="/patterns/deprecated/old_approach.md"
)
```

这将记忆视为智能体主动管理的外部系统，防止无关历史上下文的积累。

**上下文隔离**：4.11 节的智能体即工具模式提供自然的隔离。专家智能体在自己的上下文气泡中运作，只返回浓缩的摘要：

```python
# Specialist operates in its own context bubble
analysis_agent = Agent(
    name="analyst",
    instructions="Analyze data thoroughly.",
    model_client=model_client,
    tools=[analyze_data, create_visualizations],
)
# Coordinator sees only condensed results
coordinator = Agent(
    name="coordinator",
    instructions="Coordinate the research.",
    model_client=model_client,
    tools=[analysis_agent.as_tool()],
)
# Specialist uses 30K tokens internally;
# coordinator sees only the 200-token summary
```

这防止了上下文爆炸——专家执行 20 次工具调用消耗 30K Token，但协调方的上下文只增长 200 Token 的摘要。

**工具结果过滤**：并非所有工具输出都需要完整表示。数据库查询可能返回 10K 行，但智能体只需要聚合统计：

```python
async def _execute_tool_call(
    self,
    tool_call: ToolCallRequest
) -> ToolMessage:
    result = await tool.execute(tool_call.parameters)
    # Filter large outputs before adding to context
    if self._is_large_result(result):
        content = self._summarize_result(result)
    else:
        content = str(result.result)
    return ToolMessage(content=content, ...)
```

### 4.12.4 实践中的策略

要从经验上理解这些策略的表现，考虑一个分析 AI/ML 公司的研究智能体。该智能体为三个候选公司搜索公司、收集详情、融资信息和增长指标，然后将发现综合成报告。这种多步工作流创造了显著的上下文增长。

实现三个版本——基线（无管理）、压缩（通过 HeadTailCompaction 进行头+尾修剪）和隔离（分层智能体）——揭示出可衡量的差异。基线智能体在其上下文窗口中积累全部 17 次模型调用和工具结果。压缩版本在每次迭代修剪消息，保留任务指令和近期工作。隔离版本将研究委托给专家智能体，协调方只看到最终摘要。

对 Token 消耗的影响：

- 基线：21,633 Token（无上下文管理）
- 压缩：7,276 Token（减少 66%）
- 隔离：5,892 Token（减少 73%）

![图 4.5：三种上下文管理策略的 Token 用量比较](images/p187_0.png)

*图 4.5：多步研究任务的三种上下文管理策略的 Token 用量比较。上下文隔离通过架构设计而非被动修剪防止上下文积累，实现了最大的减少。*

压缩通过消息修剪提供了可观的节省，但上下文仍随每次工具调用增长。隔离通过将专家工作包含在单独的上下文气泡中取得更好的结果——专家在内部消耗 Token，但协调方的上下文增长最小。

这阐明了一个关键原则：对于上下文控制，架构预防（隔离）优于被动管理（压缩）。

### 4.12.5 循环级钩子

4.9 节的中间件让我们对单个操作进行确定性控制：我们可以拦截每次模型调用或工具执行以记录、验证或阻止它。但有些行为需要在循环级别控制，而不是操作级别。考虑两个按操作中间件无法解决的问题：

**提前停止**：让一个智能体审查项目中的所有 30 个文件，它可能读了 6 个，写了一份自信的发现摘要，然后停止（也许还加上"如果你需要更多信息，请告诉我"）。智能体执行循环（4.2 节）在模型返回无工具调用时退出。对于已完成的任务，这是正确行为，但模型没有可靠的方法知道它是否真的完成了。

**缺少结构**：一个智能体没有先规划方法就直接开始执行工具调用。没有单个模型调用是问题所在，但整体执行缺乏规划步骤所能提供的纪律。

钩子将中间件相同的原则（通过代码而非提示词进行确定性行为修改）扩展到循环边界。中间件包装每个操作，而钩子有两个触发点：第一次 LLM 调用前（开始钩子）和循环尝试退出时（结束钩子）。两者都遵循相同的契约：返回一个字符串以作为用户消息注入，或返回 None 表示不动作。钩子内部发生什么由你决定：发布到 API、检查待办列表、调用评判模型，或简单地记录循环已开始。

PicoAgents 包含两个解决上述问题的内置钩子。PlanningHook（开始钩子）在智能体开始工作前注入规划指令：

```python
class PlanningHook(BaseStartHook):
    async def on_start(self, context: LoopContext):
        return (
            "Before starting, break this task into "
            "steps using the todo_write tool. "
            "Mark the first step as in_progress."
        )
```

LLMCompletionCheckHook（结束钩子）使用单独的 LLM 调用来判断任务是否实际完成，然后才允许循环退出：

```python
class LLMCompletionCheckHook(BaseEndHook):
    def __init__(self, model_client=None, max_restarts=2):
        self.model_client = model_client
        self.max_restarts = max_restarts
    async def on_end(self, context: LoopContext):
        if context.restart_count >= self.max_restarts:
            return None  # Safety valve: allow stop
        summary = self._build_conversation_summary(
            context.llm_messages
        )
        verdict = await self._judge_completion(
            context, summary
        )
        if verdict.startswith("COMPLETE"):
            return None
        return f"You are not done. {verdict}"
```

评判器基于智能体的实际工具调用和结果进行评估，而不是基于它的声称。max_restarts 参数防止无限循环。一个更简单的结束钩子可以完全跳过 LLM 调用，只检查待办列表中的所有项目是否都标记为完成。

在智能体上组合压缩和钩子：

```python
from picoagents.compaction import HeadTailCompaction
from picoagents._hooks import (
    PlanningHook, LLMCompletionCheckHook
)
agent = Agent(
    name="reviewer",
    instructions="Review all files in the project.",
    model_client=model_client,
    tools=[read_file, list_directory, grep_search],
    compaction=HeadTailCompaction(
        token_budget=50_000
    ),
    start_hooks=[PlanningHook()],
    end_hooks=[
        LLMCompletionCheckHook(max_restarts=3)
    ],
    max_iterations=50,
)
```

一个重要的相互作用：如果 Token 预算太紧，压缩会在每次迭代丢弃近期工作，而完成钩子会把智能体推回重新读取相同文件的循环。这种模式称为**颠簸**（thrashing）——智能体将其 Token 预算花在重新获取已经拥有的上下文上，而不是取得进展。颠簸比完全不压缩浪费更多 Token。首先合理确定预算（每步为智能体工作集的 2-3 倍），然后添加钩子。

>

上下文工程是关于主动管理信息如何流过智能体的上下文窗口。压缩保持 Token 用量有界，钩子防止提前停止，隔离包含专家工作，记忆跨会话持久化知识。对于长时间运行的任务，你需要全部这些。

## 4.13 加入人在回路

我们的智能体执行循环自主运作：智能体生成带工具调用的响应，工具自动执行，此循环持续到完成。虽然这种自主性实现了强大的自动化，但也会出现执行期间需要人类反馈的场景，这与设计时配置的中间件不同。

当智能体删除文件、执行系统命令、进行昂贵的 API 调用或修改数据库时，人类监督可以防止代价高昂的错误。这些批准点基于被调用的具体工具动态发生。

### 4.13.1 工具批准请求

工具可以标记为需要批准，使智能体停止执行并返回批准请求：

*代码清单 4.32：将工具标记为需要批准*

```python
from picoagents.tools import tool
@tool(approval_mode="always_require")
def delete_file(path: str) -> str:
    """Delete a file from the filesystem."""
    import os
    os.remove(path)
    return f"Deleted {path}"
@tool  # Regular tool - executes immediately
def read_file(path: str) -> str:
    """Read contents of a file."""
    with open(path, 'r') as f:
        return f.read()
```

当智能体遇到 approval_mode="always_require" 时，执行完全停止并返回批准请求。智能体不是暂停并持有资源——它退出，将所有状态存储在可序列化的 AgentContext 中。批准后，新的 agent.run() 调用恢复执行。这种无状态设计（详见第 8 章）使任何服务器都能处理恢复请求。

批准工作流涉及三个阶段：请求、用户决策和恢复。只需将装饰器添加到任何工具并将其传递给智能体——当该工具被调用时，智能体停止并返回批准请求：

*代码清单 4.33：完整的工具批准工作流*

```python
response = await agent.run("Delete /tmp/old_data.txt")
if response.needs_approval:
    for req in response.approval_requests:
        print(f"Tool: {req.tool_name}, Args: {req.parameters}")
        user_input = input("Approve? (yes/no): ")
        approval = req.create_response(
            approved=user_input.lower() == "yes"
        )
        response.context.add_approval_response(approval)
    # Resume with updated context
    response = await agent.run(context=response.context)
print(f"Result: {response.messages[-1].content}")
```

如果批准，工具执行且智能体继续。如果拒绝，智能体收到失败消息，可以寻求替代方案或报告任务无法完成。

### 4.13.2 无状态上下文与人类输入

除了工具批准之外，我们的无状态上下文设计支持执行期间的通用人类输入。智能体可以请求澄清、停止执行，并在输入到达时恢复——而无需持有服务器资源。

我们创建一个配置为在需要时请求澄清的智能体：

*代码清单 4.34：配置为请求澄清的智能体*

```python
agent = Agent(
    name="research_assistant",
    instructions="""
    You are a helpful research assistant. When you need more
    information, ask by returning a message starting with
    'CLARIFICATION NEEDED:' followed by your question.
    """,
    model_client=AzureOpenAIChatCompletionClient(
        model="gpt-4.1-mini"
    ),
    tools=[search_web, analyze_data]
)
```

智能体执行并检查是否需要澄清：

*代码清单 4.35：检测并处理澄清请求*

```python
response = await agent.run(
    "Research the impact of AI on employment"
)
if response.final_content.startswith("CLARIFICATION NEEDED:"):
    print(f"Agent: {response.final_content}")
    user_input = input("Your response: ")
    # New agent.run() with preserved context
    response = await agent.run(
        task=user_input,
        context=response.context
    )
print(f"Final result: {response.final_content}")
```

输出：

```
Agent: CLARIFICATION NEEDED: Which employment sector - technology,
manufacturing, services, or general overview?
Your response: Focus on technology sector
Final result: AI's impact on technology shows job displacement in
routine coding and creation in AI development, data science...
```

我们基于上下文的设计将人类输入视为工具结果：两者都是添加到上下文的消息。智能体指令指导何时请求输入，执行无缝恢复。这种无状态模式（详见第 8 章）实现了：

- **可扩展性**：任何服务器处理恢复请求；内存中无状态
- **资源效率**：等待输入时不持有连接
- **可靠性**：服务器崩溃不会丢失对话状态
- **负载均衡**：标准负载均衡器无需会话亲和即可工作

这种机制支持带用户反馈的多步工作流、对话式调试和渐进的解决方案细化。工具批准与指令驱动输入的结合，提供了全面的人在回路能力，无需复杂的会话管理即可扩展到生产 Web 部署。

## 4.14 小结

从零构建智能体框架揭示了决定智能体有效性和开发者体验的基础设计决策。本章建立了核心原则，并通过 picoagents 库演示了它们的实际实现。

- **基础设计原则**：异步优先架构支持跨多智能体系统的并发操作。基于事件的流式传输为响应式 UI 和调试可见性提供实时进度更新。组件序列化支持配置共享和状态恢复。优雅取消让用户控制长时间运行的操作。抽象基类支持无供应商锁定的可扩展性。
- **智能体执行循环**：准备上下文 -> 调用模型 -> 处理响应 -> 迭代的模式，从简单聊天机器人到复杂多工具系统保持一致。Agent(model, tools, memory) 后接 agent.run(task) 的接口提供了自然扩展的干净抽象。
- **结构化输出与工具调用**：使用 Pydantic 模型的结构化输出将智能体从文本生成器转变为可靠的行动者。这一基础支持值得信赖的工具调用，LLM 生成带正确类型参数的精确格式函数调用。FunctionTool 包装器自动将 Python 函数转换为工具，优先考虑开发者体验，同时保持类型安全。
- **记忆系统**：通过消息历史的短期记忆维护对话连贯性，而通过基于 RAG 的向量存储的长期记忆支持跨会话的持久学习。记忆系统可以是应用管理的（开发者通过 memory.add() 存储，应用代码通过检索策略注入）或智能体自管理的（智能体显式调用记忆工具来组织自己的知识）。选择归结为控制与便利：应用管理的记忆提供自动的上下文增强，而智能体自管理的记忆赋予智能体对存储什么以及如何组织的自主权。
- **控制与可观测性**：中间件提供对智能体操作的运行时控制。安全过滤在恶意输入到达模型之前阻止它们。速率限制防止滥用并控制成本。PII 脱敏保护日志中的敏感数据。日志记录捕获执行轨迹以供调试。遵循 Gen-AI 语义约定的 OpenTelemetry 集成提供行业标准的可观测性（Token 跟踪、性能监控和分布式追踪），可与任何 OTLP 兼容后端（Jaeger、Datadog、Azure Monitor、Arize Phoenix）一起工作——无需代码更改。
- **智能体组合**：智能体即工具模式支持从专门组件构建复杂的多智能体系统。每个专家保持独立配置（模型、工具、记忆、中间件），同时通过 as_tool() 接口成为可复用组件。这种组合模式支持灵活的架构——例如，天气专家对简单查询使用快速模型，而分析专家对复杂计算使用推理模型。

picoagents 框架证明，复杂的智能体能力源于可组合的、设计良好的抽象，而非单体实现。这些架构基础（特别是用于可靠性的结构化输出、用于控制的中间件和用于可观测性的 OpenTelemetry）提供了我们在后续章节探索计算机使用智能体、工作流和自主编排时所依托的根基。

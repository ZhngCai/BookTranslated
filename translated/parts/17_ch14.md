# 第 14 章　从非结构化数据中回答业务问题

本章涵盖：

- 使用结构化工作流将模糊的业务问题转化为可回答的问题
- 实施高性价比的预过滤，在保持准确性的同时降低 LLM 成本
- 构建带结构化输出、检查点和错误处理的生产级问答系统
- 独立测试和验证每个工作流组件以实现可靠组合
- 将这些模式应用于真实业务问题：趋势分析、客户洞察和战略研究

作为商业领袖和分析师，我们经常面对没有整洁数据集存在的问题。与本书核心主题相关的一个问题是"有多少初创公司在构建 AI 智能体？"或"初创公司正在构建什么样的 AI 智能体用例？"¹。还有其他类似的业务问题：客户真正抱怨什么，与他们声称想要的有什么不同？哪些研究论文代表真正的突破，哪些只是渐进式改进？哪些竞争对手在构建可防御的护城河，哪些在追逐炒作周期？

这些问题无法用 SQL 查询或 pandas 操作回答。它们需要语义理解、处理歧义和意图推理——正是结构化为多智能体工作流的 AI 模型的擅长之处。但将非结构化数据扔给 LLM 是不够的。生产系统需要工程纪律：成本优化、可靠性保证和可测试的组件。

本章演示如何使用多智能体工作流模式构建生产级问答系统。我们将处理一个具体的业务问题：分析数千个 YCombinator 公司描述来回答"哪些公司在构建真正的自主 AI 智能体？"我们开发的技术广泛适用于任何需要大规模语义推理的业务问题。

## 14.1 非结构化数据挑战

我们的业务问题看似直接：识别哪些 YCombinator 公司在构建 AI 智能体。但当你检查可用数据——主要是简短的公司描述——这变得复杂。考虑这些样本：

```python
descriptions = [
    "We use AI to improve customer service",
    "Our agents help you find competitive insurance rates",
    "Autonomous AI agents that manage your calendar",
    "Machine learning powered analytics platform",
    "AI-driven insights for better decision making"
]
```

这些公司中哪些实际构建 AI 智能体？第一个提到 AI，但可能只是用 ChatGPT 的 API，没有行动。第二个提到 agents，但它们可能是人类保险经纪人。只有第三个清晰描述了自主 AI 智能体。几个商业智能挑战变得清晰：

1. **一词多义**："Agent" 可能意味着 AI 智能体、保险代理或客户服务代表
2. **营销膨胀**：许多公司在没有实质实现的情况下声称"AI"——经典的商业智能挑战
3. **战略细微差别**：我们需要区分自主智能体与简单 API 集成以进行竞争分析
4. **规模**：在合理的时间和预算约束内分析数千家公司
5. **成本**：每次 LLM 调用都要花钱；朴素的方法对业务应用很快就会变得昂贵

## 14.2 将任务表达为工作流

我们将应用一个四阶段工作流，将业务问题转化为来自非结构化数据的可操作洞察。

作为第一步，我们需要将业务问题转化为某种多智能体模式。在这种情况下，我们将使用第 2 章介绍、第 6 章实现的工作流模式。这里的关键推理是：对于这样的问题，我们知道解决方案，可以将其分解为一组离散的、可测试的步骤。这与涌现行为模式形成对比，后者解决方案事先未知，智能体必须探索解空间。

在这种情况下，我们将使用一个简单的顺序四阶段流水线，每个阶段都有清晰的输入、输出，并可以独立测试：

- **第 1 步：数据加载**：加载并缓存 YCombinator 数据集。此步骤处理数据检索、缓存和基于 TTL 的失效，确保新鲜度而无需冗余 API 调用。
- **第 2 步：预过滤**：应用廉价的关键词过滤，在昂贵的 LLM 分析之前减少数据集大小。此步骤使用正则表达式模式识别同时提到"AI"和"agents"的候选者，确保高召回率同时最小化假阴性。
- **第 3 步：使用 LLM 的结构化分析**：对过滤后的候选者，应用结构化 LLM 分析来确定领域/子领域，以及它是否确实与 AI 或 AI 智能体相关等。此步骤使用精心设计的提示词和结构化输出模式，以最小化幻觉并确保一致结果。
- **第 4 步：洞察生成**：聚合结果、计算指标并生成可视化。此步骤将分析数据综合为业务决策的可操作洞察。

```python
# Our workflow stages (matching steps.py implementation)
workflow = Workflow(
    metadata=WorkflowMetadata(name="YC Agent Analysis")
).chain(
    load_data,        # Step 1: Load and cache company data
    filter_keywords,  # Step 2: Pre-filter with cheap/fast regex
    classify_agents,  # Step 3: Apply expensive LLM analysis
    analyze_trends    # Step 4: Generate insights and visualizations
)
```

此设计体现了关键原则：

- **关注点分离**：每个步骤有一个明确的职责
- **类型安全**：Pydantic 模型确保数据一致性，也确保一步的输出匹配下一步的输入
- **成本优化**：廉价操作在昂贵操作之前
- **容错**：检查点支持恢复
- **可测试性**：每个步骤可以独立验证

让我们实现每个阶段。

## 14.3 第 1 步：带智能缓存的数据加载

我们的第一步加载 YCombinator 数据集，但这揭示了一个直接的生产挑战。虽然简单的 pd.read_csv() 对原型有效，但生产系统需要健壮的数据管理：有效的缓存以避免冗余 API 调用、原子写入以防止损坏、基于 TTL 的失效以确保数据新鲜度。

首先，我们实现带 TTL 失效的缓存验证：

*代码清单 14.1：带 TTL 的缓存验证（steps.py: load_data）*

```python
async def load_data(
    config: WorkflowConfig,
    context: Context
) -> DataResult:
    """Load and cache company data with TTL invalidation."""
    cache_path = Path(config.data_dir) / "companies.json"
    cache_ttl = timedelta(days=7)
    # Check cache validity
    if cache_path.exists() and not config.force_refresh:
        cache_age = (datetime.now() -
                    datetime.fromtimestamp(
                        cache_path.stat().st_mtime))
        if cache_age < cache_ttl:
            print("📦 Loading from cache...")
            with open(cache_path) as f:
                companies = json.load(f)
            context.set('companies', companies)
            return DataResult(
                companies=len(companies),
                from_cache=True
            )
```

TTL 方法平衡了数据新鲜度与 API 成本。7 天 TTL 对缓慢变化的数据如公司列表效果良好。force_refresh 标志在需要立即更新时提供手动覆盖。

当缓存无效或缺失时，我们获取新数据：

*代码清单 14.2：新数据获取*

```python

    print("🌐 Fetching fresh data from API...")
    companies = await fetch_yc_companies()
```

此步骤仅在必要时处理昂贵的 API 调用。异步模式确保我们在数据检索期间不阻塞其他操作。

最后，我们实现原子写入以防止缓存损坏：

*代码清单 14.3：缓存安全的原子写入模式*

```python
    # Atomic write prevents corruption
    cache_path.parent.mkdir(parents=True, exist_ok=True)
    temp_path = cache_path.with_suffix('.tmp')
    with open(temp_path, 'w') as f:
        json.dump(companies, f, indent=2)
    temp_path.replace(cache_path)
    context.set('companies', companies)
    return DataResult(
        companies=len(companies),
        from_cache=False
    )
```

先写后重命名模式对生产可靠性至关重要。它保证读者看到旧的完整文件或新的完整文件，而绝不会在进程写入中途崩溃时看到部分状态。temp_path.replace(cache_path) 操作在大多数文件系统上是原子的，提供这种安全保证。

> **生产模式：健壮缓存**
>
> 此模式贯穿生产系统。无论是缓存 API 响应、数据库查询还是计算结果，原则保持不变：检查有效性、需要时获取、原子保存、通过上下文共享。

## 14.4 第 2 步：高性价比的预过滤

一旦我们有了数据，逻辑上下一步是使用 LLM 处理它来理解哪些公司在构建 AI 智能体。朴素的方法——将每家公司发送给 LLM——对数千家公司来说会很昂贵。相反，我们应用两阶段方法：廉价的关键词预过滤，然后仅对过滤后的候选者进行昂贵的 LLM 分析。

过滤策略使用正则表达式模式识别同时提到"AI"和"agents"的候选者。关键设计决策：

- **词边界（\bagents?\b）**防止将"page"匹配为"agents"
- **大小写不敏感**捕获"AI"、"ai"、"Ai"变体
- **宽泛的 AI 模式**包括"machine learning"、"llm"、"ai-power"以最大化召回率
- **交集要求（AI AND agents）**在保持召回率的同时提高精确率

*代码清单 14.4：过滤策略（伪代码模式）*

```python
# Define patterns (full regex in repo: steps.py)
AI_REGEX = compile(r'\bai\b|artificial intelligence|machine learning|...')
AGENT_REGEX = compile(r'\bagents?\b', ...)
def mentions_ai_agents(text):
    """Require BOTH AI and agent keywords."""
    return AI_REGEX.search(text) and AGENT_REGEX.search(text)
# Apply to dataframe
df["mentions_ai_agents"] = df.desc.apply(mentions_ai_agents)
agent_count = df.mentions_ai_agents.sum()
# Store filtered data in context for next workflow step
context.set('filtered_df', df)
return FilterResult(
    total=len(df),
    ai_companies=ai_count,
    agent_keywords=agent_count
)
```

> **完整实现**
>
> 完整的正则表达式模式和过滤逻辑：workflows/yc_analysis/steps.py - 参见 filter_keywords() 函数。

这种模式的有效性在于成本不对称：

- **正则表达式便宜**：在毫秒内处理数千个文档
- **LLM 昂贵**：处理数千个文档时，即使小的 Token 使用也很快累积²
- **策略**：使用高召回率的廉价过滤（不遗漏候选者），让昂贵的 LLM 处理精确率（移除假阳性）

这种过滤方法降低了 LLM 成本。在我们的 YC 分析中，关键词过滤将数据集从 5,622 家公司减少到 1,795 家（约 31.9%），只需对过滤后的子集进行 LLM 分析。

## 14.5 第 3 步：结构化 LLM 分析

现在我们对过滤后的候选者应用基于 LLM 的推理。关键思想是使用结构化输出（见 4.5 节）来最小化幻觉并确保一致结果。

首先，我们使用 Pydantic 定义输出模式：

*代码清单 14.5：分析的结构化输出模式*

```python
class AgentAnalysis(BaseModel):
    """Enforced structure for LLM responses."""
    is_about_ai: bool = Field(
        description="True if company is actually about AI/ML "
                   "technology (validates regex filter)"
    )
    domain: str = Field(
        description=(
            "Choose one: health, finance, legal, government, "
            "education, productivity, software, e_commerce, "
            "media, real_estate, transportation, other"
        )
    )
    subdomain: str = Field(
        description="Fine-grained category within the domain"
    )
    is_agent: bool = Field(
        description="True if company builds autonomous AI agents "
                   "acting on user's behalf"
    )
    ai_rationale: str = Field(
        description="Why is/isn't this about AI technology?"
    )
    agent_rationale: str = Field(
        description="Why is/isn't this an autonomous agent?"
    )
```

现在我们需要设计一个精确的分析提示词。下面显示的提示词经过多轮测试和细化的迭代演进：

**结构化分析提示词**

> 你是 AI 公司分析专家。
>
> 分两步分析公司描述：
>
> **第 1 步：AI 验证** 确定这家公司是否实际涉及 AI/ML 技术：
>
> - is_about_ai=true：真正涉及人工智能、机器学习、LLM、神经网络
> - is_about_ai=false：只是在其他上下文中提到"artificial"（调味、草坪等）
>
> **第 2 步：智能体分析（如果是 AI）** 如果公司确实是关于 AI 的，确定它是否构建自主智能体：
>
> - is_agent=true：AI 独立代表用户行动（安排会议、交易股票、编写和执行代码、调用 API）
> - is_agent=false：AI 只是生成输出或以其他最小方式使用
>
> 返回 JSON，包含：is_about_ai、domain、subdomain、is_agent、ai_rationale（为什么是/不是关于 AI）、agent_rationale（为什么是/不是智能体）。

此提示词中的关键设计决策：

1. **两阶段验证**：首先验证我们的正则过滤器，然后在真正的 AI 公司中分析智能体
2. **流水线验证**：is_about_ai 字段为我们衡量关键词过滤精确率提供结构
3. **分离的理由**：支持分别调试 AI 检测和智能体分析。基于现有研究，该研究显示要求 AI 模型生成解释可以减少幻觉并提高准确性（见 J. Wei et al. 2022）
4. **保守分析**：通过要求清晰的自主行为减少假阳性

此模式不仅结构化 LLM 响应——它编码了我们的业务逻辑。is_about_ai 字段验证关键词过滤器的精确率。分离的 ai_rationale 和 agent_rationale 字段支持调试，并通过思维链提示减少幻觉率。domain 字段的约束选择防止 LLM 发明新类别，否则会破坏我们的聚合步骤。

注意我们**没有**要求什么：置信度分数。早期迭代包含置信度字段，但我们发现 LLM 校准不佳——它们会给错误答案分配 0.9 的置信度。带解释的布尔决策比概率输出更可靠。

首先，我们处理检查点加载以支持恢复中断的分析：

现在我们实现带批量管理和成本跟踪的核心处理循环：

*代码清单 14.8：带结构化输出的批处理*

```python
    # Process companies in batches (rate limit management)
    batch_size = config.batch_size
    total_tokens = 0
    for batch_idx, batch_start in enumerate(
        range(0, len(df), batch_size)
    ):
        batch = df.iloc[batch_start:batch_start + batch_size]
        for _, company in batch.iterrows():
            if company['long_slug'] in processed:
                continue  # Skip already processed
            # Call LLM with structured output enforcement
            response = await client.create(
                messages=[
                    SystemMessage(content=system_prompt),
                    UserMessage(
                        content=f"Company: {company.name}\n"
                                f"{company.desc}"
                    )
                ],
                output_format=AgentAnalysis  # Enforces schema
            )
            # Track usage and cost
            processed[company['long_slug']] = {
                **company.to_dict(),
                **response.structured_output.model_dump(),
                'usage': {
                    'total_tokens': response.usage.total_tokens,
                    'cost_estimate': calculate_cost(response.usage)
                }
            }
            total_tokens += response.usage.total_tokens
```

output_format=AgentAnalysis 参数确保 LLM 返回匹配我们模式的有效 JSON。模型不能发明字段或返回非结构化文本。每个响应包含用于成本跟踪的用量数据。

最后，我们在每批后实现增量检查点：

*代码清单 14.9：增量检查点持久化*

```python
        save_checkpoint({'data': processed}, checkpoint_path)
        print(f"✓ Batch {batch_idx + 1}: "
              f"{len(processed)} companies, "
              f"${total_cost:.2f}")
```

每批后检查点（而非仅在结束时）提供容错。如果进程崩溃，你最多丢失一批工作。进度消息帮助实时监控成本累积，允许你在支出超出预算时停止。

> **为什么批量处理很重要**
>
> 大多数 API 有速率限制（例如，100 请求/分钟）。带延迟的批处理在保持吞吐量的同时防止触及这些限制。批量大小取决于你的 API 层级：
>
> - 免费层级：batch_size=5，顺序处理
> - 标准层级：batch_size=10，3 个并发批
> - 企业：batch_size=20，5+ 个并发批
>
> 批处理还支持在子集上测试。设置 batch_size=5 并仅处理 2 批，用 10 家公司测试而非数千家——对提示词迭代至关重要。每批检查点保存进度，因此你可以随时停止并稍后恢复而无需重新处理。

> **通过结构化输出实现零幻觉**
>
> response_format 参数对生产可靠性至关重要。它保证 LLM 返回匹配你 Pydantic 模式的有效 JSON。这消除了整类解析错误，并确保数千次分析的一致数据结构。

> **工程说明：这个提示词如何演进**
>
> 作为读者，你可能想知道我们如何推导出用于结构化分析的提示词的具体内容和焦点。答案很直接：这是一个迭代过程。我们通常从基本描述开始，手动审查几十个样本，然后更新提示词以解决失败案例，直到结果看起来令人满意。
>
> 为了获得更好的结果，你可以实现一个自动化的提示词优化循环——一个自动分析结果并使用 LLM 建议提示词改进的设置（见（Boateng et al. 2024; Zhou et al. 2022））。
>
> 记住：提示词不一定跨模型可移植。切换模型或部署时始终测试。

## 14.6 第 4 步：分析与洞察生成

最后一步聚合我们的结构化数据来回答业务问题。我们按领域对公司分组，识别哪些行业有最高的智能体采用率，计算成本指标以理解效率，并为利益相关者生成可视化。

首先，我们从分析数据中聚合领域分布：

*代码清单 14.10：领域分布聚合*

```python
async def analyze_trends(classify_result, context):
    """Generate insights from analyzed data."""
    analysis_results = context.get('analysis_results', {})
    agents = context.get('agents', [])
    # Domain distribution analysis
    domain_counts = {}
    for agent in agents:
        domain = agent.get('domain', 'unknown')
        domain_counts[domain] = domain_counts.get(domain, 0) + 1
    top_domains = sorted(
        domain_counts.items(),
        key=lambda x: x[1],
        reverse=True
    )[:10]
```

## 14.7 独立测试每个组件

对于 LLM 分析，我们使用 Mock 避免测试期间的 API 成本。我们创建返回带受控 Token 计数（100 输入、50 输出）的预定义 AgentAnalysis 响应的 AsyncMock 对象。这验证我们的处理逻辑正确处理结构化输出，而无需实际模型调用。该模式测试集成逻辑——代码是否正确提取 structured_output、跟踪用量并计算成本？

## 14.10 将这些模式应用于业务问题

四阶段模式——加载、过滤、分析、汇总——适用于传统分析力不从心的任何业务问题。当你在规模上需要 LLM 推理但成本重要时使用它。

**客户反馈分析**：过滤掉"谢谢"消息，分析情感和问题类型，跟踪随时间趋势。回答"客户真正抱怨什么？"并将 10,000 张支持工单转化为可操作的产品洞察。

**竞争情报**：按公司规模/行业过滤，分析商业模式和竞争定位，汇总市场趋势。回答"谁是我们真正的竞争对手？"通过处理数千个公司描述、新闻稿和产品公告。

**研究文献综述**：按发表渠道质量和相关性过滤，分析突破性 vs 渐进式工作，汇总新兴趋势。回答"我们的研发应该聚焦什么？"帮助团队保持最新而不淹没在论文中。

**合规监控**：按风险关键词过滤，分析违规类型，优先人类审查。回答"我们的合规风险在哪里？"同时降低监管风险并提高团队效率。

该模式有效，因为廉价过滤（我们的案例中约 68% 成本降低）后跟昂贵推理（高准确率）给你规模和质量两者。

## 14.11 局限性与未来优化

我们的分析展示了核心模式，但几个局限提示了生产系统中改进的领域：

**数据质量约束**：我们仅依赖 YCombinator 公司描述，其质量和完整性各不相同。一些描述营销色彩浓重，而另一些缺乏技术细节。未来的实现可以用公司网站的网络搜索结果补充，尽管这引入成本和延迟权衡。此外，我们的关键词过滤器可以通过更多迭代细化和测试改进。

**成本优化机会**：我们对所有分析使用 GPT-4.1-mini。通过模型选择策略可以实现额外成本降低——对更简单的情况使用更小的模型，仅在需要时使用更大的模型。

**规模考虑**：在非常大的规模（数百万文档），训练专门的较小模型变得具有成本效益。在公司分析任务上微调领域特定模型可以以显著更低的每请求成本和延迟提供相当的准确率。

**时间局限**：公司描述代表某一时点的快照。业务转向和产品演进未被捕获，可能错误分类自 YC 申请以来已转移焦点的公司。

这些局限不使模式失效——它们凸显了取决于你具体需求、规模和预算约束的工程决策。

## 14.12 小结

本章演示了如何使用多智能体工作流构建从非结构化数据回答业务问题的生产系统。你可以立即应用的关键要点：

- **对涉及非结构化文本的任何商业智能任务使用两阶段过滤模式**。在昂贵操作（LLM 调用）之前用廉价操作（正则、SQL、规则）过滤。
- **用 Pydantic 模式强制执行结构化输出**。绝不在生产中解析自由格式 LLM 文本。结构化输出消除幻觉，并确保数千条业务记录的一致数据结构。
- **为可恢复性对一切做检查点**。生产工作流会失败——来自速率限制、网络问题或崩溃。检查点让你无需重新处理即可恢复，节省时间和金钱。
- **集成前独立测试组件**。每个工作流步骤应能用 Mock 依赖隔离测试。这使调试更容易并提高系统可靠性。
- **用用量跟踪持续监控成本**。每次 LLM 调用应跟踪 Token、成本和时长。这支持预算控制并帮助识别优化机会。

我们构建的工作流回答真实的业务问题，并使用 1,695,384 Token 生成可操作洞察（从 5,622 家公司中分析 1,795 家）。按典型提供商费率，这代表约 56.39 美元的 API 成本³。无论是分析客户反馈、处理竞争情报还是从非结构化文本中提取战略洞察，这些模式都能扩展到生产工作负载，同时保持可靠性和成本效益。

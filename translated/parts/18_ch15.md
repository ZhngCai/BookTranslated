# 第 15 章　构建软件工程智能体

本章涵盖：

- 为软件工程智能体设计工具：文件操作、代码执行、记忆和元认知
- 设计通过规划、执行和验证引导智能体工作流的提示词
- 为长时间运行的任务配置压缩、钩子和上下文隔离
- 在真实代码审查任务上经验性地评估智能体表现

## 15.1 引言

在第 14 章中，我们构建了一个带预定义步骤的确定性工作流来从文档中提取洞察。当解决路径清晰时，这种方法效果良好。但当正确答案事先未知时——当任务需要探索、迭代和自适应问题解决时——会发生什么？

软件工程正是这类问题。编写代码意味着处理来自需求和现有代码库的上下文、规划任务分解、应用多样化专长（设计模式、测试、调试）、运行测试、修复 bug，并经常在得到可工作解决方案之前迭代多次。复杂性不能整齐地装入固定工作流。

与其脚本化每个可能的动作，我们将构建一个自主决定如何处理任务的软件工程智能体。在第 2 章的分类法中，这是一种自主模式：控制流由模型的推理驱动，而非预定义工作流。给智能体强大的工具、清晰的指令和跟踪进度的记忆，然后让它决定如何继续。这种**智能体 + 工具 + 记忆**模式是每个现代 AI 编码助手的基础——GitHub Copilot Agent Mode、Cursor、Anthropic 的 Claude Code、OpenAI Codex 和 Windsurf 都使用此设计的变体，建立在 4.1 节的执行循环和设计原则之上。

关键洞见：**智能体的能力上限取决于它拥有的工具和指导其使用的指令**。智能体能力从工具（哪些动作可能）、提示词（如何使用那些工具）和上下文工程（如何在长任务中维持表现）的相互作用中涌现。我们在第 4 章涵盖了各个构建块。本章将它们组合成一个可工作的软件工程智能体，并在真实代码库上评估它。

> **可运行的代码：软件工程智能体**
>
> - 智能体实现：examples/agents 中的 swe_agent/ 目录
> - 压缩基准：examples/contextengineering 中的 compaction.ipynb 笔记本——运行带缓存结果和图表的代码审查实验

## 15.2 为软件工程智能体设计工具

我们如何确定智能体需要什么工具？从一个思维实验开始：想象指导一个聪明但初级的开发者完成他们的第一个编码任务。你会告诉他们什么？

你会概述一个工作流：首先，理解需求。如果修改现有代码，阅读并理解当前实现。逐步进行更改。测试每次更改。调试失败。记录你的工作。

智能体与初级开发者在一个关键方面不同：底层 LLM 已经拥有强大的推理和编码技能。它可以编写高质量代码、调试错误并组合复杂解决方案。它缺乏的是与你的文件系统交互、执行命令或持久化状态的能力。你提供的工具给智能体这种操作能力。一旦配备 write_file 或 bash_execute 等工具，智能体就可以将其现有智能应用于实际实现。提示词（本章稍后讨论）指导使用哪些工具以及何时使用，而 LLM 的能力处理如何有效使用它们。

我们的软件工程智能体使用五类工具。PicoAgents 在 picoagents/tools/ 中提供所有这些的现成实现——我们鼓励查看源代码了解实现细节。这里，我们聚焦每个类别做什么以及为什么重要。

### 15.2.1 文件操作

在智能体编写代码之前，它需要理解现有代码库并做出有针对性的更改。文件操作工具通过四个互补函数提供这种能力。

```python
from picoagents.tools import create_coding_tools
tools = create_coding_tools(workspace=Path("./workspace"))
```

create_coding_tools 函数返回文件操作工具的集合：

- **read_file**：读取文件内容以理解现有代码
- **write_file**：创建新文件或编辑现有文件，带三种模式（完全重写、字符串替换或行插入）
- **list_directory**：递归探索项目结构以发现相关文件
- **grep_search**：跨多个文件搜索模式以定位特定代码

设计原则：

- **工作区隔离**：所有操作出于安全范围限定在工作区目录内
- **细粒度编辑**：str_replace 允许外科手术式更改，无需重写整个文件
- **搜索能力**：grep_search 支持在编辑前查找模式

为什么这些重要：

str_replace 模式至关重要。没有它，智能体必须：

1. 读取整个文件
2. 用更改重写整个文件
3. 冒着在未更改部分引入错误的风险

有了 str_replace：

```python
write_file(
    file_path="calculator.py",
    mode="str_replace",
    old_str=(
        "def add(a, b):\n"
        "    return a + b"
    ),
    new_str=(
        "def add(a, b):\n"
        '    """Add two numbers."""\n'
        "    return a + b"
    ),
)
```

这种外科手术式的精度减少错误并保留格式。

### 15.2.2 代码执行

写代码而不能运行它，就像烹饪而不能品尝。智能体需要执行工具来验证其工作并基于真实反馈迭代。两个执行工具提供这种能力：

```python
# Python REPL for immediate testing
python_repl(code="print(add(2, 3))")  # -> 5
# Bash execution for running tests, installing packages
bash_execute(command="python -m pytest tests/")
```

python_repl 工具直接执行 Python 代码片段并返回结果，用于快速测试和探索。bash_execute 工具运行 Shell 命令，用于运行测试套件、安装包或构建项目等任务。

**为什么执行工具必不可少**：

没有执行，智能体盲目运作：

- 编写无法验证的代码
- 建议无法运行的测试
- 无法调试失败

有了执行：

- **即时反馈循环**：编写 -> 测试 -> 修复
- **对结果的信心**：如果测试通过，代码有效
- **迭代细化**：失败的测试指导纠正

### 15.2.3 记忆系统

与处理代码文件的文件操作工具不同，MemoryTool（4.8 节介绍）为智能体自己的知识和跨对话的决策过程提供持久存储。

```python
from picoagents.tools import MemoryTool
memory = MemoryTool(base_path="./agent_memory")
```

MemoryTool 支持五个操作，镜像文件操作但专用于智能体的内部知识库：

- **view**：浏览记忆目录结构，查看智能体学到了什么
- **create**：创建新记忆文件以存储模式、决策或计划
- **search**：使用文本搜索跨所有记忆文件查找模式
- **append**：向日志文件添加条目以跟踪随时间决策
- **str_replace**：编辑现有记忆内容，如更新任务检查清单

记忆支持学习：

```
# First task: Build calculator
Agent creates: /memories/patterns/testing_pattern.md
"Always use pytest for Python projects. Include edge cases."
# Second task: Build another module
Agent searches memory -> finds testing pattern -> applies it
```

智能体建立了超越个体对话持续存在的机构知识。

### 15.2.4 元认知与协调工具

上述工具支持行动：读取文件、编写代码、执行命令。但有效的问题解决还需要反思和结构化进度跟踪。三个工具提供这种能力：

```python
from picoagents.tools import (
    ThinkTool, TodoWriteTool, TodoReadTool
)
```

ThinkTool 给智能体一个不采取行动的推理草稿本：

```python
think(thought="""
Analyzing the task:
1. Need to handle division by zero
2. Tests should cover edge cases
3. Can use the testing pattern from memory
""")
```

TodoWriteTool 和 TodoReadTool 提供结构化任务跟踪。智能体创建待办列表，工作时标记项目，并读取列表检查进度：

```python
todo_write(todos=[
    {"content": "Read all .py files",
     "status": "in_progress"},
    {"content": "Document quality issues",
     "status": "pending"},
    {"content": "Write summary report",
     "status": "pending"},
])
```

这些工具是元认知的。它们不修改代码或执行命令。它们给智能体在行动前规划的空间，并跟踪剩余什么。待办列表还与 4.12.5 节的循环级钩子集成：CompletionCheckHook 可以读取待办列表，验证智能体在允许循环退出之前实际完成了。

## 15.3 提示词的关键作用

工具提供能力，但提示词提供指导。考虑差异：

### 15.3.1 最小提示词（差的结果）

```python
agent = Agent(
    name="coder",
    instructions="You can write code. Use tools to help the user.",
    tools=[...],
)
```

结果：智能体不知道：

- 何时检查记忆
- 如何构建其工作流
- 如何确定任务完成
- 如何处理错误

### 15.3.2 详细提示词（好的结果）

结构良好的提示词引导智能体通过系统化工作流。以下是智能体设置和提示词的开头：

```python
agent = Agent(
    name="software_engineer",
    instructions="""
You are an expert software engineering agent.
## PHASE 1: MEMORY CHECK (ALWAYS DO THIS FIRST)
1. Use memory tool to view /memories directory
2. Check for relevant patterns and previous decisions
3. Apply any lessons from past tasks
## PHASE 2: PLANNING
1. Use think tool to analyze requirements
2. Use todo_write to create a structured task list
3. Mark the first task as in_progress
```

规划和记忆检查阶段确保智能体带着上下文开始。接下来是执行：

```python
## PHASE 3: EXECUTION
For each task in your todo list:
1. Use coding tools (read_file, write_file, bash_execute)
2. Test changes immediately
3. Use todo_write to mark completed, start next task
4. Log important decisions to /memories/decisions/
## PHASE 4: VERIFICATION
1. Run tests to verify implementation
2. Use todo_read to check all tasks are completed
3. Verify code quality (documentation, error handling)
## PHASE 5: COMPLETION
Before finishing, verify ALL todos are marked complete.
If blocked, explain what remains and why.
NEVER stop with in_progress or pending tasks.
""",
    tools=[...],
)
```

这种结构化方法将原始能力转化为系统化执行。每个阶段有清晰目标。待办列表提供钩子也可以检查的持久、机器可读的进度记录（见 4.12.5 节）。

### 15.3.3 提示词工程原则

几个模式使这些提示词有效。**显式工作流结构**将任务分解为编号阶段（记忆检查、规划、执行、验证、完成），防止智能体在动作之间随机跳跃。**记忆优先**确保智能体在全新开始前检查先前模式。**进度跟踪**告诉智能体如何记录进度——使用 todo_write 维护结构化列表，或记忆文件中的 Markdown 复选框。没有这一点，智能体没有系统化的方式知道剩余什么。

**完成标准**至关重要。智能体在 LLM 决定不再调用任何工具时停止（见 4.2 节）。如果"完成"模糊，智能体会过早停止。阐明完成意味着什么：所有计划步骤完成、测试通过、代码已记录。最后，**错误处理指导**防止智能体在第一次失败时放弃。指示它分析错误、尝试替代方案并将失败记录到记忆。

## 15.4 任务完成机制

智能体执行循环（4.2 节）在 LLM 返回不带工具调用的响应时退出。这将责任放在三件事上：你的提示词（定义清晰的完成标准）、你的工具（提供 LLM 可以评估的反馈），以及可选的钩子（外部验证完成）。

对于短任务，基于提示词的完成标准足够。告诉智能体"完成"意味着什么，它会在正确的时间停止。对于跨许多文件的长时间运行任务，智能体可能过早停止——它读了 30 个文件中的 6 个，写了一份自信的摘要。这是 4.12.5 节的提前停止问题。

健壮性的递进：

1. **仅提示词**：指令中的清晰标准（"在审查完所有文件之前不要停止"）。对简单任务有效。
2. **待办跟踪**：智能体使用 todo_write 维护检查清单。CompletionCheckHook 在允许退出前读取列表。确定性，无额外 LLM 调用。
3. **LLM 评判器**：LLMCompletionCheckHook 基于工具调用证据（而非智能体的声称）询问单独模型任务是否实际完成。对开放式任务最健壮。

三种方法在 PicoAgents 中都可用。钩子在 4.12.5 节介绍。在下一节，我们将看到它们在真实任务上的表现。

## 15.5 完整示例：代码审查智能体

为了看到工具、提示词和上下文工程如何协同工作，我们在一个真实仓库上运行代码审查智能体：handtracking 项目，一个跨多个目录（模型训练、实用程序、protobuf 模块）的 44 个 .py 文件的 Python 代码库。智能体的任务是探索每个目录、阅读每个文件，并产生质量问题和架构建议的摘要。

这是一个受益于上下文工程（4.12 节）的任务。44 个文件的仓库是可管理的，但真实代码库有数百或数千个文件。即使在这里，阅读每个文件也产生足够的 Token，上下文腐化在触及硬限制之前就降低了表现——智能体随着工具结果累积开始丢失对其指令和早期发现的跟踪。

### 15.5.1 智能体设置

```python
from picoagents import Agent, LLMCompletionCheckHook
from picoagents.compaction import HeadTailCompaction
from picoagents._hooks import PlanningHook
from picoagents.llm import AzureOpenAIChatCompletionClient
from picoagents.tools import create_coding_tools
client = AzureOpenAIChatCompletionClient(
    model="gpt-4.1-mini", ...
)
agent = Agent(
    name="code_reviewer",
    instructions="""You are a senior code reviewer.
    Explore every directory. Read every .py file.
    Produce a summary with quality issues and
    architecture recommendations.""",
    model_client=client,
    tools=create_coding_tools(workspace=repo_path),
    compaction=HeadTailCompaction(
        token_budget=15_000, head_ratio=0.2
    ),
    start_hooks=[PlanningHook()],
    end_hooks=[
        LLMCompletionCheckHook(max_restarts=5)
    ],
    max_iterations=50,
)
```

智能体使用 HeadTailCompaction 保持在 15K Token 预算内，PlanningHook 在开始前创建任务列表，LLMCompletionCheckHook 在允许退出前验证审查是否彻底。工具是只读的（read_file、list_directory），因为这是审查而非修改任务。

### 15.5.2 运行时发生什么

以下是智能体完成代码审查的浓缩轨迹。每个块是一次 LLM 调用，展示智能体选择的工具及其做出的关键决策：

```
调用 1（PlanningHook 注入规划指令）：
  → todo_write: [
      "Explore top-level directories",
      "Read all .py files in each directory",
      "Document quality issues",
      "Write architecture summary"
    ]
调用 2-4（探索）：
  → list_directory("/") → 找到 8 个子目录
  → list_directory("/utils") → 6 个 .py 文件
  → read_file("/utils/detector_utils.py")
调用 5-15（系统性文件读取）：
  → read_file（每次调用一个文件，依次处理
    /utils、/model、/protos 目录）
  → todo_write：标记"Explore top-level"完成
调用 16-20（更深的目录）：
  → list_directory("/model") → 4 个 .py 文件
  → read_file("/model/ssd_mobilenet.py")
  [此处压缩触发——上下文超过 15K，
   中间消息被修剪，头部+尾部保留]
  → read_file("/model/preprocessor.py")
```

在第 20 次调用，智能体返回不带工具调用的摘要。循环通常会退出，但 LLMCompletionCheckHook 拦截：

```
结束钩子触发：
  评判模型审查工具调用日志：
  "Agent read 12 of 44 files. Multiple directories
   unexplored. INCOMPLETE."
  → 注入："You are not done. Continue reviewing
    the remaining directories."
调用 21-35（恢复——读取剩余目录）：
  → read_file（继续处理 /protos、/training）
  [压缩再触发两次——锯齿模式]
  → todo_write：标记剩余项目完成
调用 36（最终摘要）：
  智能体产生带发现的架构审查。
  结束钩子再次触发 → 评判器："COMPLETE."
  → 循环退出。
```

轨迹揭示三个机制协同工作：PlanningHook 给智能体结构（调用 1），压缩保持上下文有界（调用 16-35），完成钩子防止提前停止（调用 20）。缺少其中任何一个，审查将不完整、无结构，或溢出上下文窗口。

该轨迹是一种配置。为了理解每个部分如何贡献，我们在五种配置下运行相同任务并比较。带图表和评判器推理的完整实验在配套笔记本（examples/contextengineering 中的 compaction.ipynb）。

*表 15.1：跨压缩策略的代码审查表现。质量是完整性和可操作性分数的 LLM 评判器平均。Isolation 总计包括协调方（39K）加子智能体 Token（51 次 LLM 调用共 79K）。*

| 配置 | 输入 Token | LLM 调用 | 读取文件 | 重复 | 质量 |
| --- | --- | --- | --- | --- | --- |
| NoCompaction | 915,591 | 50 | 16/44 | 27% | 6.0/10 |
| HeadTail 8k | 276,390 | 50 | 14/44 | 55% | 4.0/10 |
| HeadTail 8k（无钩子） | 144,136 | 32 | 17/44 | 15% | 5.5/10 |
| HeadTail 15k | 402,102 | 46 | 14/44 | 46% | 5.1/10 |
| Isolation | 118,824 | 66 | 48（子） | 0% | 4.5/10 |

### 15.5.3 数据说明什么

表 15.1 中三个发现突出：

**锯齿是健康的模式**。有了合适大小的预算，上下文增长直到超出预算，压缩修剪它，然后再次增长。单调增长（NoCompaction）意味着智能体无限期拖拽过时上下文。在预算处平坦的线（HeadTail 8k）意味着压缩几乎每次调用都触发，给智能体留下太少的工作记忆。

**过紧的预算导致颠簸，而非节省**。8k 配置有 55% 的重复文件读取。智能体读取一个文件，压缩将其从上下文丢弃，智能体因为没有见过它的记忆而再次读取同一文件。更紧的预算将 Token 重新分配到浪费的重复读取，而非节省它们。

**钩子和压缩相互作用**。比较带和不带完成钩子的 HeadTail 8k。没有它：32 次调用、15% 重复、5.5 质量。有它：50 次调用、55% 重复、4.0 质量。钩子正确识别了不完整的工作并将智能体推回去——但在 8k 预算下，智能体已经将其近期工作丢失给了压缩，因此它重复读取文件而非继续。有了更大的预算，钩子按预期工作，因为智能体保留了足够的上下文从中断处继续。

**实用规则**：将压缩预算定为每步智能体工作集的 2-3 倍。如果你的重复读取率超过 15%，预算太紧了。

## 15.6 实践考虑

**迭代限制**：基于任务复杂性设置 max_iterations。简单脚本：10-20。多文件项目：30-50。复杂审查或重构：50-100。太低导致过早终止。太高在颠簸的智能体上浪费计算。

**压缩预算**：对涉及许多文件的任务，使用 HeadTailCompaction。从 25-50K Token 的预算开始，基于重复读取率调整。对于短任务（10 次工具调用以下），不需要压缩。

**工作区隔离**：始终将文件工具范围限定在工作区目录。这防止智能体访问项目外的文件或修改系统文件：

```python
tools = create_coding_tools(workspace=Path("./project"))
```

**成本跟踪**：监控 response.usage 以理解 Token 消耗：

```python
u = response.usage
print(f"LLM calls: {u.llm_calls}")
print(f"Tokens: {u.tokens_input + u.tokens_output}")
```

## 15.7 关键洞察

1. **工具是前提，不是保证**。有 write_file 并不意味着智能体写出好代码。质量取决于 LLM 的训练、提示词的指导和执行工具的反馈。
2. **提示词编码专长**。提示词是你编码最佳实践、工作流模式和完成标准的地方。精心设计的提示词将通用 LLM 转化为专门的编码助手。
3. **记忆支持改进**。没有记忆，每个任务从零开始。有了记忆，模式累积且错误被记录。智能体随时间变得更有能力。
4. **完成需要外部验证**。基于提示词的标准对短任务有效。对于长时间运行的任务，钩子提供外部验证，智能体实际完成了，而非仅仅决定停止。
5. **上下文工程支持规模**。5 次迭代的任务无需压缩即可工作。跨 44 个文件的 50 次迭代代码审查不行。压缩、钩子和隔离（都在 4.12 节涵盖）是区分演示智能体与处理真实工作的智能体的东西。

## 15.8 小结

软件工程智能体的能力从工具、提示词、记忆和上下文工程的协同工作中涌现。工具定义哪些动作可能。提示词编码如何有效使用它们。记忆支持跨任务学习。上下文工程——压缩、钩子和隔离——在任务增长超出单个上下文窗口容量时维持表现。代码审查实验显示这些不是理论关切：没有正确的配置，44 个文件的审查退化为颠簸、提前停止或失控的 Token 成本。

## 15.9 练习

1. **添加代码审查工具**：实现一个运行静态分析（例如，pylint、flake8）的 lint_file 工具。更新智能体的提示词，在完成前包含代码质量检查。
2. **实现检查点**：修改记忆系统，在每个完成的子任务后保存进度。允许执行中断时从检查点恢复。
3. **多语言支持**：扩展智能体以处理 JavaScript 项目。需要什么新工具？提示词应如何改变？
4. **提示词消融研究**：从提示词中移除不同部分（记忆检查、规划、完成标准）。衡量对任务成功率的影响。
5. **压缩预算调优**：用不同的 token_budget 值（8K、15K、25K、50K）运行代码审查笔记本。比较重复读取率、文件覆盖率和质量分数。在什么预算下颠簸消失？

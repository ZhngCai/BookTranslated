# 第 12 章　分布式智能体协议

本章涵盖：

- 分布式智能体基础，以及它们如何扩展分布式计算概念
- 用于标准化工具和上下文集成的模型上下文协议（MCP）
- 用于跨组织智能体协作的智能体间协议（A2A）
- 安全考虑与选择正确协议的实用指导

到目前为止，我们讨论了构建智能体和多智能体系统，但有一个隐含假设：所有组件（例如，工具、多智能体系统内的智能体）在同一执行上下文中运行——同一台机器、同一网络内，或至少在同一组织边界内。这是学习智能体如何工作的合理起点，但一些现实应用通常需要更分布式的架构，其中智能体和工具在单独的执行上下文中运行——不同的机器、容器、区域或组织——通过网络通信，没有共享内存（图 12.1）。

![图 12.1：分布式智能体场景](images/p395_0.png)

*图 12.1：应对用户任务的智能体可能存在于单独的执行上下文中——不同的机器、容器、区域或组织——通过网络通信。*

想象你正在构建一个财务分析系统，其中你的数据检索智能体运行在你公司的安全云上，但它需要与来自你律师事务所基础设施的法律合规智能体以及来自第三方服务提供商的市场分析智能体协调。每个智能体运行在不同的机器上，可能在不同的地理区域，由不同的组织管理。这些智能体如何发现彼此？它们如何安全通信？当任务需要数小时才能完成而网络连接中途断开时会发生什么？如果智能体在执行期间需要请求用户确认怎么办？

这些挑战中有许多是经典的分布式计算问题：发现、通信、容错和协调。然而，智能体引入了现有分布式计算协议未设计处理的新特征：决策的自主性、可能运行数小时或数天同时保持交互的任务、在执行期间不可预测的点需要人类输入的工作流，以及由 AI 模型而非确定性规则驱动的适应性行为。

本章探讨近期协议如何应对这些挑战（MCP、A2A），它们如何与众所周知的分布式计算基础相关联，同时添加智能体特定的语义。我们将专注于理解这些协议为何重要、它们提供什么价值，以及何时在你的系统中使用它们。

## 12.1 分布式智能体的核心概念

设计组件在单独环境中运行的系统既带来优势也带来挑战。分布式智能体提供改进的**可扩展性**——你可以独立扩展特定能力，而非扩展整个系统。它们提供执行环境的**隔离**，强制执行安全和资源边界。它们支持**容错**，因为一个智能体的失败不一定使整个系统崩溃。它们让你利用跨不同基础设施的**异构资源**。权衡是相比在同一进程中运行的智能体，通信、协调和管理的复杂性增加。

### 12.1.1 分布式计算基础

分布式智能体的概念与分布式计算没有根本区别。核心问题——发现、通信、容错、协调——与 RPC、REST、gRPC 和消息队列所解决的挑战相同。

关键区别在于逻辑所在的位置。在传统分布式计算中，协调和决策驻留在基础设施层——Kubernetes 编排容器、服务网格管理流量、API 网关通过预定义规则路由请求。在分布式智能体系统中，这种逻辑移至应用层，由做出自主决策的 AI 模型驱动。基础设施关注点——通信协议、容错、安全、资源管理——停留在协议层。

具体的对照可以澄清什么是真正新的与什么是借鉴的：

**消息队列 -> 任务委托**：消息队列解耦生产者与消费者，实现异步任务处理。智能体任务委托建立在这种模式之上，但使用 AI 模型基于对任务状态的推理自适应地请求额外上下文或协助，而非预定义的工作流步骤。

**服务发现（Consul、etcd）-> 智能体发现**：传统服务发现帮助服务按名称或能力找到彼此。智能体发现添加更丰富的能力元数据——技能、领域专长、支持的交互模式——实现基于语义理解而非仅服务名称的智能路由。

**熔断器与重试 -> 容错**：分布式系统以退避方式重试失败请求。智能体任务通常跨越数小时或数天，因此它们需要会话可恢复性和持久任务状态——简单重试会丢失累积的工作。

**API 网关 -> 编排**：API 网关基于规则将请求路由到适当的后端服务。智能体编排器做同样的事，但使用 AI 驱动的推理自适应地分解复杂请求、路由到专家智能体并综合结果。

原语非常相似——发现、通信、容错、状态管理。变化的是语义：智能体以传统分布式系统通常不具备的方式自主、长时间运行、交互式和适应性强。除了执行预定义工作流，智能体还推理目标、从结果学习、与其他智能体协商，并基于上下文调整策略。这种由 AI 模型驱动的认知能力，将智能体协议与其分布式系统前身区分开来。

### 12.1.2 分布式智能体需求

在分布式环境中运行的智能体需要四项核心能力，这些能力源于智能体的独特特征：自主性、长时间运行执行、交互性和适应性行为。表 12.1 总结了这些需求。

*表 12.1：分布式智能体的核心能力*

| 能力 | 为什么智能体需要这个 |
| --- | --- |
| 流式传输与进度 | 智能体任务通常跨越数小时或数天，分析文档、编排工作流或处理数据集。用户需要实时可见性以实现可观测性、调试和信任。 |
| 可恢复性 | 3 小时智能体任务期间的网络故障不应丢失所有累积工作。会话必须经受断开和重连。 |
| 持久性 | 即使服务器重启，智能体结果也必须持久。客户端需要持久引用来检查状态或带外检索结果。 |
| 多轮交互 | 智能体经常需要执行中途的输入：高成本动作的用户确认、模糊请求的澄清，或推理步骤的 AI 协助。 |

以下部分探索为应对这些需求而出现的两个协议——MCP 和 A2A——以及它们如何实现这些能力。模型上下文协议（MCP）（Anthropic 2024c）专注于标准化工具和上下文集成。智能体间协议（A2A）（Linux Foundation 2025）解决跨组织智能体协作。

## 12.2 模型上下文协议（MCP）

当 Anthropic 在 2024 年 11 月引入 MCP 时（Anthropic 2024b），焦点很窄：给大型语言模型对上下文的标准化访问。名字本身——模型上下文协议——反映了这一范围。协议定义了 AI 应用（"客户端"）如何连接到暴露工具（可调用的函数）、资源（可读取的数据）和提示词（可复用模板）的外部系统（"服务器"）。

像 MCP 这样的标准化协议解决了困扰自定义实现的集成、分发、发现、安全和灵活性挑战。这就是为什么 MCP 随着基于智能体的系统激增而快速被采用。表 12.2 说明了 MCP 如何应对每个挑战。

*表 12.2：MCP 的价值主张*

| 挑战 | 没有 MCP | 有了 MCP |
| --- | --- | --- |
| 集成 | X 团队花数周集成 Z 团队的新工具 | X 团队第一天就支持任何 MCP 工具 |
| 分发 | 为 Cursor、Windsurf、VSCode、Claude Desktop 等分别编写扩展 | 编写一个处处可用的 MCP 服务器 |
| 发现 | 团队在 Slack 中问："有人有做 X 的工具吗？" | 团队发布和查找工具的中央注册表 |
| 安全 | 每个团队为 LLM 可访问的工具实现（或跳过）自己的认证 | 集中式身份验证和托管 MCP 服务器注册表 |
| 部署灵活性 | 工具与应用代码紧密耦合，需要相同的部署上下文 | 工具在单独上下文中远程运行——不同机器、区域或组织——同时对应用表现为本地 |

自推出以来，MCP 迅速演进，添加了不仅能为单个智能体提供上下文、还能支持更广泛的智能体间行为需求的能力。这些更新包括引入 MCP 请求征询（服务器可以在执行中途请求用户输入）、采样（服务器可以请求客户端的 LLM 进行补全）、可恢复流（会话经受网络断开）、进度通知（工具可以流式传输实时状态更新）和资源链接（工具可以返回超越工具调用的结果持久引用）。这些特性使 MCP 工具能够像完整智能体一样行为——运行数小时、流式传输更新、请求人类输入、将子任务委托给 LLM，并经受网络故障。

### 12.2.1 MCP 架构：服务器、客户端与宿主

MCP 定义了一个干净分离关注点的三层架构。底层是 **MCP 服务器**，暴露能力——工具（可调用的函数）、资源（可读取的数据）、提示词（可复用的 LLM 模板）以及潜在的自定义扩展。服务器可能暴露单个工具或数十个相关能力。例如，"TechCrunch 新闻服务器"可能暴露获取文章的工具、访问文章存档的资源和摘要新闻条目的提示词。

中间层是 **MCP 客户端**，处理与服务器的协议级通信。客户端与服务器保持 1:1 连接，管理消息交换、会话状态和错误处理的底层细节。客户端通常嵌入在更高层应用中，而非独立组件。

顶层是 **MCP 宿主**——面向用户的应用，如 Claude Desktop、Cursor 或 VSCode¹。宿主嵌入一个或多个 MCP 客户端连接到服务器，并基于用户需求和上下文对调用哪些工具做出智能决策。宿主编排整体工作流：接受用户请求、从连接的服务器发现可用工具、通常使用 LLM 确定调用哪些工具、通过客户端执行这些调用、处理交互式回调（如用户确认），并向用户呈现结果。

![图 12.2：MCP 的三层架构](images/p402_0.png)

*图 12.2：MCP 的三层架构：宿主（面向用户的应用）嵌入与暴露工具、资源和提示词的服务器通信的客户端。图中展示提供 Slack、Google Drive 和数据库等工具访问的示例 MCP 服务器。*

MCP 支持两种主要传输机制。**stdio 传输**将服务器作为客户端的子进程运行，通过标准输入和输出通信。这非常适合本地集成——IDE 扩展、桌面工具或服务器和客户端在同一台机器上运行的开发环境。**可流式 HTTP 传输**使用网络请求，更适合服务器远程运行、多个客户端需要连接到同一服务器，或你需要通过标准 HTTP 工具更容易调试和监控的分布式系统。

以下是使用 MCP SDK 的最小 MCP 服务器设置（也有 TypeScript 和其他语言版本）：

```python
# server.py
import os
from mcp.server.fastmcp import FastMCP
import requests
mcp = FastMCP(
    "TechCrunch News Server",
    host=os.environ.get("MCP_SERVER_HOST", "localhost"),
    port=int(os.environ.get("MCP_SERVER_PORT", 8011))
)
```

服务器暴露一个从 TechCrunch 获取新闻的工具：

```python
@mcp.tool(title="Fetch from TechCrunch")
def fetch_from_techcrunch(category: str = "latest") -> str:
    """Fetch the latest news from TechCrunch."""
    allowed = {"ai", "startup", "security", "venture", "latest"}
    cat = category.lower() if category.lower() in allowed else "latest"
    url = (f"https://techcrunch.com/tag/{cat}/"
           if cat != "latest"
           else "https://techcrunch.com/")
    try:
        response = requests.get(url)
        if response.ok:
            from bs4 import BeautifulSoup
            soup = BeautifulSoup(response.text, "html.parser")
            text = soup.get_text(separator=' ', strip=True)
            return text[:1000] + ("..." if len(text) > 1000 else "")
        return "Failed to fetch news."
    except Exception as e:
        return f"Error fetching news: {str(e)}"
```

最后，运行服务器：

```python
if __name__ == "__main__":
    mcp.run(transport="streamable-http")
```

此示例使用 FastMCP API，它处理协议样板代码。@mcp.tool() 装饰器将函数注册为任何客户端都可以发现和调用的 MCP 工具。运行此服务器使其在 http://localhost:8011/mcp 可用，准备好接受任何 MCP 兼容宿主应用的连接。

写完这个服务器后，它可以与 Claude Desktop、Cursor、Windsurf、VSCode 扩展或任何嵌入 MCP 客户端的自定义宿主应用一起工作——一次编写，处处使用。

### 12.2.2 MCP 核心概念

MCP 定义了几个原语，支持简单工具集成和复杂的智能体间通信。

**工具、资源和提示词**：服务器暴露三种类型的能力。**工具**是可以用参数调用的函数（如上面的 fetch_from_techcrunch 示例）。**资源**是可以读取的数据源，由 URI 标识——服务器可能暴露 news://techcrunch/ai 作为 AI 相关文章的资源。**提示词**是服务器提供的可复用 LLM 模板，用于标准化常见交互。

**进度通知**：工具可以在执行期间流式传输实时状态更新。服务器发送结构化进度元数据（完成百分比、当前步骤、状态消息），客户端显示给用户或记录用于调试。这使长时间运行的操作可观测而非不透明。

**会话管理与可恢复性**：MCP 中的 StreamableHTTP 传输支持使用会话 ID 和事件回放来经受网络故障。每条消息获得唯一事件 ID。当客户端断开后重连时，它提供最后收到的事件 ID，服务器从其事件存储（开发用内存，生产用数据库支撑）回放所有错过的事件。

**工具持久性的资源链接**：除了内联返回结果，MCP 工具还可以返回资源 URI。这很有价值，因为客户端可以选择轮询或订阅这些 URI 以获取更新。资源可以由持久存储（数据库、文件系统、云存储）支撑，确保结果经受服务器重启。这将任务执行与客户端连接解耦，实现异步工作流。

**请求征询（用户输入）**：服务器可以暂停工具执行以请求结构化用户输入。服务器发送带 JSON 模式的征询请求，指定预期的响应格式。客户端提示用户、验证响应并发送回去。关键是，客户端保留控制权——它可以验证、修改或拒绝征询请求。服务器基于输入恢复执行。这支持人在回路工作流，如付款确认或澄清请求。

**采样（AI 协助）**：服务器可以在工具执行期间请求客户端的 LLM 补全。当服务器发出采样请求时，客户端决定是否执行调用、使用哪个模型以及包含哪些上下文。采样是服务器发起但客户端中介的——一个深思熟虑的安全设计，使服务器不持有或使用模型 API 密钥。研究工具可能累积发现，并在继续前请求客户端的 LLM 生成摘要。这创造了双向 AI 交互：客户端使用 LLM 选择调用哪些工具，服务器使用相同的 LLM（通过客户端）增强其处理，而客户端仍然是 LLM 使用的守门人。

这些原语组合起来，将简单工具转变为能够长时间运行、交互式、适应性行为的自主智能体。

### 12.2.3 MCP 的智能体式能力

MCP 擅长上下文供给——给智能体工具、资源和提示词的访问。它也演进为通过实现之前识别的四项核心能力（表 12.1）来支持智能体间通信。表 12.3 展示了 MCP 特性如何实现每项能力。

*表 12.3：MCP 如何实现分布式智能体能力*

| 能力 | MCP 特性 | 工作方式 |
| --- | --- | --- |
| 流式传输与进度 | 通过 SSE/WebSocket 的进度通知 | 服务器在工具执行期间发送带完成百分比、当前步骤和状态消息的结构化进度更新 |
| 可恢复性 | 会话 ID + 事件回放 | 客户端用最后收到的事件 ID 重连；服务器从事件存储回放错过的事件 |
| 持久性 | 资源链接（持久 URI） | 工具返回由持久存储支撑的资源 URI；客户端轮询或订阅更新 |
| 多轮交互 | 请求征询（用户输入）+ 采样（LLM 调用） | 服务器暂停执行以请求用户输入或 AI 协助，然后基于响应恢复 |

有了这些能力，MCP 工具变得不仅仅是简单函数——它们像智能体一样行为。协调这些工具的宿主应用充当编排器智能体，对任务分解、路由和结果综合做出智能决策。

> **当工具成为智能体**
>
> MCP 工具已超越简单函数调用——它们可以流式传输进度、在执行中途请求用户输入、调用 LLM 进行推理，并在长时间运行的操作中维护状态。当 MCP 工具与有状态服务器、可恢复会话和采样/征询流组合时，它们可以像智能体一样行为。然而，智能体身份、治理和跨组织发现是独立的关注点。MCP 通过组合实现智能体式行为，但组织级治理（问责、SLA、可审计轨迹）仍然存在于协议之外。

![图 12.3：通过 MCP 客户端-服务器架构的智能体间通信](images/p408_0.png)

*图 12.3：通过 MCP 客户端-服务器架构的智能体间通信。带多个 MCP 客户端的宿主应用充当编排器智能体，与暴露作为专家智能体运行的工具的远程 MCP 服务器协调。每个服务器可以实现领域特定能力，而编排器管理用户交互、任务分解和跨分布式智能体网络的结果综合。*

这种能力组合支持强大的智能体间通信模式。如图 12.3 所示，宿主应用充当编排器智能体，与用户交互并将请求路由到作为 MCP 工具暴露的专家智能体。例如，作为 MCP 工具运行的旅行规划智能体和研究智能体成为能够数小时执行、交互式确认和适应性行为的自主组件。编排器处理任务分解、协调执行、管理并发智能体操作之间的状态、在整个交互中保留用户上下文、在智能体不可用时实现重试和回退逻辑，并将多个专家的结果综合为连贯响应。

### 12.2.4 实践中的 MCP 工具使用

MCP 工具设计为由 LLM 驱动，使其成为智能体集成的自然选择。要在我们的智能体中使用 MCP 工具，我们需要让它们与本地工具无缝协作，同时获得 MCP 提供的分布式收益——标准化、可发现性和跨应用兼容性。

回顾 4.6.3 节，我们构建了一个 BaseTool 抽象，为所有工具提供通用接口——无论是简单 Python 函数、REST API 调用还是外部集成。MCP 工具是需要在 MCP 协议语义与智能体工具接口之间桥接的外部集成。要做到这一点，我们需要解决两个重要设计需求：管理有状态的 MCP 会话，以及将 MCP 工具适配到我们智能体期望的 BaseTool 接口。

#### 12.2.4.1 有状态会话管理

与无状态函数调用不同，MCP 服务器需要持久的 ClientSession 对象进行通信。会话必须建立、维护并正确清理。MCPClientManager 类处理此生命周期：

```python
class MCPClientManager:
    """Manages connections to MCP servers."""
    def __init__(self):
        self._servers: Dict[str, MCPServerConfig] = {}
        self._sessions: Dict[str, ClientSession] = {}
        self._tools: Dict[str, List[MCPTool]] = {}
    async def connect(self, server_id: str) -> None:
        """Connect to server and discover tools."""
        config = self._servers[server_id]
        # Establish connection using appropriate transport
        read, write, context = await connect_to_server(config)
        # Create and initialize session
        session = ClientSession(read, write)
        await session.__aenter__()
        self._sessions[server_id] = session
        await session.initialize()
        # Discover available tools
        await self._discover_tools(server_id)
```

管理器维护服务器配置、活跃会话和已发现工具的注册表。连接到服务器时，它建立传输（本地服务器用 stdio，远程用 HTTP）、创建会话、初始化 MCP 协议握手，并通过调用 session.list_tools() 发现可用工具。这种关注点分离——配置、连接、发现——支持惰性连接模式，服务器被注册但直到需要才连接。

#### 12.2.4.2 将 MCP 桥接到 BaseTool

从智能体的角度看，MCP 工具必须与原生工具完全相同。MCPTool 类将 MCP 服务器工具包装为 BaseTool 实例：

```python
class MCPTool(BaseTool):
    """Wraps an MCP server tool as a PicoAgents tool."""
    def __init__(
        self,
        mcp_tool_name: str,
        mcp_tool_description: str,
        mcp_tool_schema: Dict[str, Any],
        client_manager: MCPClientManager,
        server_id: str
    ):
        # Namespace tool to avoid conflicts
        tool_name = f"mcp_{server_id}_{mcp_tool_name}"
        super().__init__(
            name=tool_name,
            description=mcp_tool_description
        )
        self.mcp_tool_name = mcp_tool_name
        self._parameters_schema = mcp_tool_schema
        self.client_manager = client_manager
        self.server_id = server_id
    @property
    def parameters(self) -> Dict[str, Any]:
        """Return MCP tool's parameter schema."""
        return self._parameters_schema
    async def execute(self, parameters: Dict[str, Any]) -> ToolResult:
        """Execute via MCP client."""
        session = await self.client_manager.get_session(self.server_id)
        result = await session.call_tool(
            self.mcp_tool_name,
            arguments=parameters
        )
        return ToolResult(
            success=not result.isError,
            result=self._extract_result_content(result),
            error=None if not result.isError else "Tool execution failed"
        )
```

桥接实现了三个关键映射。首先，它将 MCP 的 inputSchema（JSON Schema）映射到 BaseTool 的 parameters 属性，使模式可用于智能体的 LLM 函数调用。其次，它将 MCP 的 call_tool() 映射到 BaseTool 的 execute() 方法，在参数格式之间转换并处理异步会话调用。第三，它将 MCP 的 CallToolResult 转换为 ToolResult，从 MCP 的多部分响应格式中提取内容并标准化错误报告。

工具命名需要仔细考虑。多个 MCP 服务器可能暴露同名的工具（例如，文件系统服务器和云存储服务器都可能有"read_file"工具）。MCPTool 通过为工具添加 mcp_{server_id}_ 前缀来命名空间化工具以避免冲突，同时保留原始工具名以保持清晰。

由于 MCPTool 继承自 BaseTool，它自动获得 to_llm_format() 方法，将工具模式转换为 OpenAI 和 Azure OpenAI API 使用的函数调用格式。LLM 以其期望的标准格式接收工具定义，对工具源自外部 MCP 服务器毫不知情。

#### 12.2.4.3 实际示例：文件夹整理智能体

让我们通过一个分析目录并推荐更好组织的智能体来实践 MCP 集成。智能体连接到 MCP 文件系统服务器进行只读访问：

```python
from picoagents import Agent
from picoagents.tools import (
    StdioServerConfig,
    create_mcp_tools
)
# Configure MCP filesystem server
filesystem_config = StdioServerConfig(
    server_id="filesystem",
    command="npx",
    args=[
        "-y",
        "@modelcontextprotocol/server-filesystem",
        str(target_dir)
    ]
)
# Connect and discover tools
manager, mcp_tools = await create_mcp_tools([filesystem_config])
# Create agent with MCP tools
agent = Agent(
    name="organizer",
    model_client=model_client,
    tools=mcp_tools,  # MCP tools work like native tools
    instructions="""Analyze the directory structure
    and recommend a better organization based on
    file types, names, and patterns you observe."""
)
# Agent uses MCP tools transparently
result = await agent.run(
    f"Analyze {target_dir} and recommend folder organization"
)
# Cleanup
await manager.disconnect_all()
```

create_mcp_tools() 辅助函数通过一次调用处理服务器注册、连接和工具发现来简化设置。它返回管理器（用于生命周期控制）和已发现的工具（准备好供智能体使用）。智能体通过其 tools 参数接收 MCP 工具，就像原生 Python 函数一样——桥接层使它们不可区分。

当智能体的 LLM 决定调用 MCP 工具时，执行流与原生工具遵循相同路径。智能体调用 tool.execute(parameters)，触发 MCPTool 的 execute 方法，后者从管理器检索会话，调用 MCP 服务器的工具，将结果转换为 ToolResult 并返回给智能体。智能体处理结果并继续其推理循环，可能进行额外的工具调用或响应用户。

完成后总是调用 await manager.disconnect_all() 以正确关闭 MCP 会话并释放资源。对于自动清理，使用管理器的上下文管理器模式：

```python
async with manager.managed_connection("filesystem"):
    tools = manager.get_tools("filesystem")
    # Use tools...
# Automatically disconnected
```

## 12.3 智能体间协议（A2A）

谷歌于 2025 年 4 月引入智能体间协议（A2A），并于 2025 年 6 月在 Linux 基金会治理下发布（Linux Foundation 2025）。A2A 通过以任务为中心的架构处理分布式智能体通信：每次交互创建一个具有唯一标识符和生命周期状态（submitted、working、input-required、completed、failed）的 Task。任务成为持久的、可检查的工作单元，经受网络中断并提供清晰的问责——谁请求了什么、何时以及结果是什么。

A2A 将智能体视为可通过 HTTP 端点寻址的对话实体。位于知名 URI（/.well-known/agent-card.json）的智能体卡（Agent Card）预先声明能力、技能和身份验证需求，实现无需配置文件或注册表的自主发现。

通信使用基于消息的模式（user 和 agent 角色交换文本、文件或结构化数据），而非函数调用，对智能体需要澄清或额外授权时的中断状态有一等支持。

标准化智能体间协议解决了困扰自定义集成的跨组织协作、框架异构性、发现和不透明执行挑战。表 12.4 说明了 A2A 如何应对每个挑战。

*表 12.4：A2A 的价值主张*

| 挑战 | 没有 A2A | 有了 A2A |
| --- | --- | --- |
| 跨组织协作 | 为每个合作伙伴协商自定义 API 契约；集成复杂性随合作伙伴倍增 | 跨组织边界智能体发现和委托的标准接口 |
| 框架异构性 | 每个团队为其他每个团队的框架实现适配器（LangGraph、CrewAI、自定义） | 智能体暴露 A2A 服务器；编排器使用 A2A 客户端，无论内部框架如何 |
| 发现 | 手动合作伙伴协调："你的团队有做 X 的智能体吗？" | 知名 URI 上的机器可读智能体卡或可搜索注册表 |
| 不透明执行 | 暴露内部智能体细节（工具、记忆、推理）或失去协作能力 | 智能体保持黑盒；只有接口和能力可见 |
| 多轮工作流 | 每个集成自定义状态管理、会话处理、回调机制 | 协议级支持 input-required、auth-required 状态和上下文连续性 |

### 12.3.1 A2A 核心概念

A2A 定义一个简单的三方架构。**用户**——人类或自动化服务——发起请求。**A2A 客户端**（客户端智能体）代表用户行动，发现和调用远程智能体。**A2A 服务器**（远程智能体）通过实现协议的 HTTP 端点暴露能力。从客户端的角度看，服务器作为黑盒运行——其内部运作保持隐藏，保护知识产权和安全边界。

协议建立在经过验证的 Web 标准之上。通信使用 HTTP(S)，JSON-RPC 2.0 作为消息格式。方法名遵循 {category}/{action} 模式，如 message/send 或 tasks/get。实时更新使用 Server-Sent Events（SSE），一个基于 HTTP 服务器推送的 W3C 标准。身份验证和授权遵循标准 Web 实践——OAuth2、API 密钥、bearer 令牌——凭据通过 HTTP 头传递，而非嵌入协议消息。

![图 12.4：通过 A2A 联邦架构的智能体间通信](images/p417_0.png)

*图 12.4：通过 A2A 联邦架构的智能体间通信。宿主应用（编排器智能体）嵌入多个 A2A 客户端来发现和协调远程 A2A 服务器，每个实现专门的智能体能力。这种点对点模式支持跨组织协作，来自不同团队或公司的智能体可以在保持清晰边界和自主性的同时协同工作。*

如图 12.4 所示，A2A 支持一种联邦模型，一个智能体可以与多个远程智能体协调，每个可能由不同组织拥有。这与 MCP 以工具为中心的方法不同——这里，智能体是作为对等方协商和协作的自主实体。

A2A 围绕四个基本通信元素（表 12.5）：

*表 12.5：A2A 的核心通信元素*

| 元素 | 目的 | 关键特征 |
| --- | --- | --- |
| 智能体卡 | 发现与元数据 | /.well-known/agent-card.json 处的 JSON 文档；声明身份、端点 URL、能力、技能和身份验证需求 |
| 消息 | 通信轮次 | 带角色（"user" 或 "agent"）的单次交互；包含一个或多个部分（TextPart、FilePart、DataPart）用于模态无关的内容 |
| 任务 | 有状态工作单元 | 唯一 ID、定义的生命周期状态、支持多轮交互；达到终态后不可变 |
| 产物 | 具体输出 | 任务产生的有形结果（文档、图像、结构化数据）；可以增量流式传输 |

任务通过定义的生命周期状态推进（表 12.6）。活跃状态（submitted、working）表示正在进行的工作。中断状态（input-required、auth-required）暂停执行等待额外输入。终态（completed、failed、canceled、rejected）标记完成并变得不可变。一旦终态，任务不能重启——新请求创建新任务实例，复用相同的 contextId 以保持对话连续性。

*表 12.6：任务生命周期状态*

| 状态 | 类型 | 描述 |
| --- | --- | --- |
| submitted | 活跃 | 任务排队，等待执行 |
| working | 活跃 | 任务进行中 |
| input-required | 中断 | 暂停，智能体需要用户输入才能继续 |
| auth-required | 中断 | 暂停，需要辅助系统的额外凭据 |
| completed | 终态 | 成功完成 |
| failed | 终态 | 执行期间出错 |
| canceled | 终态 | 客户端或系统取消了任务 |
| rejected | 终态 | 智能体拒绝执行任务 |

**上下文（contextId）**是跨多个相关任务维护状态的机制。当智能体首次响应时，它生成一个上下文标识符。客户端的后续消息包含此 ID 以表明它们是同一对话的一部分。智能体使用上下文来维护对话历史、解析对先前产物的引用，并在任务边界之间提供连续性。这支持如下工作流：

```
任务 1："预订去赫尔辛基的航班" -> 已完成
任务 2："基于任务 1，预订酒店" -> 进行中
任务 3："基于任务 1，预订雪地摩托活动" -> 进行中
任务 4："基于任务 2，添加水疗预订" -> 已提交
```

所有四个任务共享一个 contextId，允许智能体理解依赖关系并推断早期任务的哪些产物与后续请求相关。

**发现与身份验证**：A2A 支持多种发现模式。对于公共智能体，客户端请求智能体域上的 /.well-known/agent-card.json。对于企业场景，策展的注册表提供可搜索目录。智能体卡可以支持分层披露——公共卡显示基本能力，而经过身份验证的扩展卡在身份验证后揭示敏感细节。身份验证在 HTTP 传输层遵循标准 Web 实践（OAuth2、API 密钥、bearer 令牌）。

**交互模式**：A2A 基于任务特征提供三种交互模式。请求/响应使用 message/send 和轮询用于简单任务。通过 message/stream 的流式传输（SSE）为实时更新维护持久连接。推送通知为非常长时间运行的任务（小时/天）提供 Webhook 回调，其中维护连接不切实际。

这些原语——任务生命周期状态、用于连续性的 contextId、SSE 流式传输和中断状态——使 A2A 能够支持之前识别的分布式智能体能力：通过 TaskStatusUpdateEvent 的流式进度、通过任务重新订阅和事件回放的可恢复性、通过持久任务和产物存储的持久性，以及通过 input-required 和 auth-required 状态的多轮交互。

## 12.4 安全考虑

MCP 和 A2A 都建立在标准 Web 安全实践之上，但将其适配到各自特定的用例。理解这些方法帮助你为安全需求选择和实现正确的协议。

**MCP：依赖传输的安全**

MCP 的安全模型因传输而异。对于 stdio 传输（本地子进程执行），服务器从环境（环境变量、凭据文件）检索凭据，因为客户端和服务器在同一安全边界内运行。对于 HTTP 传输，MCP 要求 OAuth 2.1 带强制 PKCE（Proof Key for Code Exchange，代码交换证明密钥）。PKCE 在这里至关重要，因为 MCP 宿主通常是无法安全存储客户端密钥的桌面应用（Claude Desktop、Cursor、VSCode）——PKCE 通过为每次身份验证请求生成动态代码验证器，使这些公共客户端能够安全使用 OAuth 流。MCP 还要求资源指示符（RFC 8707）用于令牌受众验证和动态客户端注册。MCP 明确禁止令牌传递——即服务器将客户端令牌转发给上游服务的反模式。这防止了混淆代理攻击，恶意服务器使用客户端的凭据访问非预期的资源。相反，MCP 服务器为每个后端服务获取单独的凭据，保持清晰的安全边界。

**A2A：统一的 HTTP 安全**

A2A 采取更简单的方法：一切都是 HTTP，所有安全遵循标准 Web 实践。智能体卡——位于 /.well-known/agent-card.json 的 JSON 文档——是中央安全声明机制。它使用 OpenAPI 兼容格式显式声明智能体支持哪些身份验证方案（OAuth2、API 密钥、bearer 令牌、基本认证），使安全需求与能力一起可发现。这种设计使客户端能从单个发现端点理解智能体能做什么以及如何与之认证。身份验证发生在 HTTP 传输层，而非 JSON-RPC 消息内。授权基于技能：OAuth 范围授予对特定能力的访问（例如 booking:read vs booking:write），智能体作为自主守门人强制执行额外检查（预算限制、批准、政策合规）。

**关键差异**

MCP 安全依赖传输，为工具集成优化——本地工具使用简单的环境凭据，远程工具使用企业 OAuth。A2A 安全是统一的，为联邦智能体协作优化——每次交互都是远程的，每个智能体可能不受信任，所有身份验证在 HTTP 层。两种方法都不是固有更好的；它们为不同的部署场景解决不同的问题。

> **实现细节**
>
> 本章提供安全模型的概念性概述。实现 MCP 或 A2A 系统时，请查阅官方规范了解详细需求：
>
> - **MCP 安全规范**：OAuth 2.1 流、受保护资源元数据（RFC9728）、动态客户端注册（RFC7591）、资源指示符（RFC8707）、会话管理和攻击缓解（混淆代理、令牌传递预防、PKCE）
> - **A2A 安全规范**：智能体卡安全声明、Webhook 身份验证、经认证的扩展卡、SSRF 预防和数据敏感性指南
>
> 两个协议都演进迅速。请在各自主项目站点查看最新规范，了解当前安全建议和最佳实践。

## 12.5 协议决策

MCP 和 A2A 服务于重叠的目标，但以不同方式处理。两个协议是互补的工具，各自针对特定用例优化。表 12.7 将核心能力映射到每个协议的处理方式。

*表 12.7：协议能力比较*

| 能力 | MCP 方法 | A2A 方法 |
| --- | --- | --- |
| 工具与资源访问 | 主要焦点。工具/资源/提示词通过服务器暴露。任何 MCP 宿主的通用连接器。 | 非核心焦点。智能体不透明——它们不向彼此暴露内部工具。 |
| 发现 | 宿主配置中的服务器注册。公共 MCP 服务器生态增长中。 | 知名 URI 上的智能体卡或策展注册表。机器可读的技能描述。 |
| 长时间运行操作 | 流式进度通知、通过事件回放的可恢复会话、持久状态的资源链接。 | 带定义状态的任务生命周期、SSE 流式传输、超长任务的推送通知。 |
| 交互式工作流 | 请求征询（用户输入）、采样（LLM 补全）。服务器请求，客户端满足。 | input-required 和 auth-required 任务状态。客户端发送后续消息恢复。 |
| 编排模式 | 编排器-专家：宿主智能体协调工具（可能是专家智能体）。 | 对等协调：客户端智能体发现并委托给作为自主实体的远程智能体。 |
| 跨组织互操作性 | 可能但非主要用例。同一 MCP 服务器跨宿主工作。 | 核心用例。联邦协作的标准化智能体间接口。 |
| 成熟度与生态 | 2024 年末推出，2025 年快速演进。主要平台强采用（Claude Desktop、Cursor、VSCode 等）。活跃开发。 | 2024 年推出，捐赠给 Linux 基金会。官方 SDK（Python、JS、Java、.NET）。新兴生态，主要聚焦 Google Cloud。 |

> **管理多个分布式智能体之间的上下文**
>
> A2A 和 MCP 等协议提供管理与单个远程智能体有状态交互的原语（使用 contextId 或会话）。但多智能体工作流需要管理在单一目标上协作的多个独立智能体之间的上下文和数据流。
>
> 考虑一个编排器将任务分解为步骤：数据检索智能体处理初始收集，分析智能体处理数据，综合智能体产生最终报告。每个在单独的执行上下文中运行。综合智能体如何知道早期智能体完成了什么？
>
> 编排器必须显式管理这种智能体间上下文。它收集早期步骤的输出，并将其作为后续步骤的输入提供。两种架构模式解决这个问题：
>
> **1. 编排器作为中央枢纽**
>
> 编排器充当有状态的中介：委托任务、收集结果，并将其综合为下一个智能体的输入。
>
> - 在 A2A 中：从已完成的任务收集产物，将其放入消息传递给新任务
> - 在 MCP 中：收集 ToolResult 数据，作为参数传递给下一个工具调用
>
> 最适合：大多数工作流——简单、健壮、易于调试的集中式工作流逻辑
>
> **2. 通过外部存储的共享状态**
>
> 对于大型数据载荷，智能体将结果写入共享存储（云存储、数据库）。编排器只在智能体之间传递引用。
>
> - 在 A2A 中：智能体返回指向存储输出的产物 URI
> - 在 MCP 中：工具返回指向持久数据的资源链接
>
> 最适合：性能和可扩展性重要的数据密集型流水线
>
> 在这些模式之间选择是一个关键的架构决策。这种对数据依赖的显式管理将孤立的智能体调用转化为协作的分布式工作流。

### 12.5.1 选择正确的协议

MCP 和 A2A 都支持智能体间通信，但在不同的抽象级别运行。MCP 提供对你组合成工作流的分布式组件的细粒度控制。A2A 让你将整个任务委托给在内部处理一切的自主智能体。

**在以下情况选择 MCP（组合式编排）**：

- **编排分布式细粒度能力**。当你的智能体需要组合来自不同来源的能力——你的数据库工具、合作伙伴的 API、第三方服务——MCP 让你在保持它们分布式的同时组合它们。每个能力在其最优环境中运行（数据库工具靠近数据、ML 模型在 GPU 上），而你的编排器从任何地方协调。
- **受控的信息流**。在 MCP 中，你的编排器位于用户和工具之间，控制信息流。你决定每个工具接收什么上下文——过滤敏感数据、注入用户偏好或在调用之间转换格式。
- **多平台工具**。编写一个跨 Claude Desktop、Cursor、VSCode 和自定义应用工作的 MCP 服务器。利用不断增长的现有 MCP 服务器生态。
- **调试和可观测性**。MCP 的细粒度特性使调试更容易——你看到每次工具调用、其输入、输出，并可以准确追踪工作流在哪里成功或失败。流式进度提供对长时间运行操作的实时可见性。

**在以下情况选择 A2A（委托式自主）**：

- **完整任务委托**。向自足的智能体发送高层请求（"预订去赫尔辛基的航班"），它们在内部处理所有复杂性。你看到任务状态（进行中、已完成）而非实现细节。
- **跨组织黑盒**。合作伙伴智能体暴露能力而不揭示实现。你律师事务所的合规智能体保持其法律数据库和推理私有——你只获得结果。
- **智能体市场**。通过智能体卡发现和使用完整的智能体解决方案，无需理解内部架构。提供商提供自主智能体，而不仅是工具。

**两者都用**，当：

许多系统在不同层受益于两个协议。你的编排器可能使用 MCP 组合其内部能力（访问数据库、调用 API、运行计算），同时使用 A2A 将专门任务委托给外部自主智能体（法律审查、医疗诊断、财务分析）。

**关键区别**：

MCP 给你对个体能力调用的可见性和控制。A2A 让你将整个任务委托给自主智能体。基于你的架构需要多少控制与自主来选择。

## 12.6 小结

- **分布式计算基础**：分布式智能体系统面临经典的分布式计算挑战——发现、通信、容错和状态管理。区分智能体的是它们的语义：决策的自主性、长时间运行执行（小时到天）、需要执行中途输入的交互式工作流，以及由 AI 模型而非确定性规则驱动的适应性行为。智能体协议将经过验证的分布式系统概念（RPC、消息队列、服务发现）适配到这些智能体特定的特征。
- **模型上下文协议（MCP）**：MCP 的出现是为了标准化工具和上下文集成，解决 AI 应用中自定义连接器的激增。协议从简单工具访问演进到通过流式进度、可恢复会话、资源链接的持久状态，以及通过请求征询和采样的多轮交互来支持完整的智能体间通信。MCP 擅长跨多应用的工具分发、编排器-专家架构，以及为长时间运行任务提供进度可见性。
- **智能体间协议（A2A）**：A2A 解决跨组织智能体协作，将智能体视为自主对话实体而非简单工具。协议使用智能体卡进行发现、任务生命周期状态进行有状态工作流、contextId 进行对话连续性、SSE 流式传输进行实时更新。A2A 为跨组织边界和异构智能体框架的联邦协作而设计。
- **安全模型**：MCP 使用依赖传输的安全——本地 stdio 传输用环境凭据，HTTP 传输用 OAuth 2.1。A2A 使用统一的基于 HTTP 的安全，在传输层遵循标准 Web 实践（OAuth2、API 密钥、bearer 令牌）。两种方法都适合其部署模型：MCP 用于具有不同信任边界的工具集成，A2A 用于统一远程访问的联邦智能体协作。
- **协议选择**：对跨多应用的可复用工具、编排器-专家架构和带标准化集成的工具生态选择 MCP。对跨组织协作、智能体市场和自主智能体之间的多轮有状态对话选择 A2A。许多系统以互补角色受益于两个协议——MCP 用于工具访问，A2A 用于智能体间协调。
- **架构指导**：架构分布式智能体系统时，专注于你要解决的问题而非协议本身。MCP 解决工具集成和编排，而 A2A 解决跨供应商发现和互操作性。协议格局将继续演进，但底层的分布式系统挑战保持不变。理解这些根本问题，使你能够在生态成熟时做出明智的架构决策。

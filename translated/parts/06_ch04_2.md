## 4.7 添加记忆

我们的智能体现在可以可靠地产生结构化输出并调用工具。但还缺少一块：持久化。当智能体调用天气工具并得知"巴黎今天晴天"时，这些信息在对话结束时消失了。记忆弥补了这一空白。

当智能体与用户和其他智能体交互时，它们需要保持对交互的记忆，以确保连贯且上下文相关的响应。从实现角度看，智能体可以通过两种方式维护记忆：通过消息历史的短期记忆，以及通过向量数据库的长期记忆。

当工具成功执行时，其结果可能需要流入短期和长期记忆系统。以下是工具结果如何连接到两种记忆类型：

*代码清单 4.19：从工具结果到持久化记忆*

```python
# Tool execution produces structured data
tool_result = await weather_tool.execute({"location": "Paris"})
# Result: {"location": "Paris", "condition": "sunny", "temperature": 22}
# SHORT-TERM: Immediately available in conversation history
context.add_message(ToolMessage(
    content=f"Weather in Paris: {tool_result}",
    source="weather_tool"
))
# LONG-TERM: Indexed for future retrieval across sessions
await memory.store({
    "content": f"Paris weather on {datetime.now().date()}: sunny, 22°C",
    "metadata": {"type": "weather", "location": "Paris", "date": datetime.now()}
})
# Later conversations can retrieve relevant past interactions
relevant_memories = await memory.retrieve("weather in Paris")
```

### 4.7.1 通过消息历史的短期记忆

短期记忆确保智能体了解近期上下文——刚刚发生的消息和动作的即时集合——使后续响应连贯且上下文相关。

![图 4.1：短期记忆](images/p146_0.png)

*图 4.1：短期记忆通过存储在内存列表或轻量数据库中的消息历史维护对话上下文，使智能体能够跟踪近期交互并提供连贯的响应。*

考虑这个交互：

1. 用户："埃菲尔铁塔有多高？"
2. 智能体："埃菲尔铁塔高 324 米。"
3. 用户："它是什么时候建成的？"

没有短期记忆，智能体无法解答第二个问题，因为它没有"它"指埃菲尔铁塔的上下文。在我们的智能体实现中，短期记忆实现为存储近期消息和工具结果的消息历史：

*代码清单 4.20：通过消息历史的短期记忆*

```python
# Agent maintains conversation context
class AgentContext:
    def __init__(self):
        self.messages: List[Message] = []
    def add_message(self, message: Message):
        self.messages.append(message)
        # Optionally truncate to keep recent context
        if len(self.messages) > 50:
            self.messages = self.messages[-50:]
# Usage in agent execution loop
self.context.add_message(
    UserMessage(content="What is the height of the Eiffel Tower?"))
self.context.add_message(
    AssistantMessage(content="The Eiffel Tower is 324 meters tall."))
self.context.add_message(
    UserMessage(content="When was it built?"))
# All messages become part of the prompt to the LLM
llm_messages = [SystemMessage(content=self.instructions), *self.context.messages]
```

短期记忆快速且立即可用，但它是短暂的——对话结束时，这些上下文就丢失了。长期记忆解决了持久化问题，使智能体能够跨会话学习和回忆信息。

### 4.7.2 通过检索增强生成（RAG）的长期记忆

长期记忆存储不是立即可用但可能对未来交互有用的信息。这包括领域知识、用户偏好、过去会话的情景记忆和一般世界知识。

![图 4.2：长期记忆](images/p148_0.png)

*图 4.2：长期记忆使用向量数据库通过 RAG（检索增强生成，Retrieval-Augmented Generation）存储和检索海量信息。数据被索引为嵌入，在运行时，智能体查询数据库以检索用于生成响应的相关上下文。*

挑战在于规模——长期记忆可能包含海量信息，远超 LLM 一次能处理的范围。解决方案是检索增强生成（RAG）：一种在推理前从数据源检索外部知识并动态添加到模型提示词中以增强的技术。这将模型的响应锚定在训练数据之外的领域特定或最新信息上。虽然向量数据库支持用于确定相关性的语义相似性搜索，但 RAG 来源可以包括任何外部数据：传统数据库、API、文件系统或知识图谱。

*代码清单 4.21：长期记忆的 RAG 流程*

```python
# 1. INDEXING: Convert information to vectors
encoder = SentenceTransformer('all-MiniLM-L6-v2')
text = "User prefers morning meetings and dislikes long emails"
vector = encoder.encode(text)
await vector_db.store(vector, text, metadata={"type": "user_preference"})
# 2. QUERY: Convert question to vector and retrieve
query = "When should I schedule the meeting?"
query_vector = encoder.encode(query)
similar_items = await vector_db.search(query_vector, top_k=3)
# 3. AUGMENTATION: Add retrieved context to prompt
context_items = [item.text for item in similar_items]
augmented_prompt = f"""
Relevant context: {context_items}
User question: {query}
Please provide a helpful response.
"""
```

RAG 配合向量数据库的关键优势：

- **可扩展性**：高效处理大量数据
- **相关性**：动态检索相关信息以实现准确响应
- **灵活性**：支持多种数据模态（文本、图像、音频）

### 4.7.3 记忆选择策略

在大多数关于 RAG 的论述中，会出现一个看似简单但实际复杂的问题：什么信息应该提交到长期记忆？一方面，索引一切会引入不相关信息带来的噪声；另一方面，索引太少又有遗漏关键上下文的风险。

三种主要方法应对这一挑战：

**人工策展**：人类通过捕获偏好的用户界面、交互式标记（"记住这个地址"）或开发者定义的重要信息类型规则，显式指定要记住什么。

**自动选择**：算法使用基于频率的启发式（经常被引用的信息）、重要性评分（与用户目标的相关性）或新颖性检测（独特信息）来识别值得存储的信息。

**混合方法**：结合人工和自动方法——自动系统建议要记住什么，人类为关键决策提供最终批准。

### 4.7.4 BaseMemory 接口

我们可以用智能体的上下文（消息历史）实现短期记忆，用 RAG（向量数据库）实现长期记忆。为了在我们的库中实现这一点，我们首先定义一个抽象不同记忆实现的 BaseMemory 接口。下面的实现复用于 AutoGen 库。

*代码清单 4.22：BaseMemory 抽象接口*

```python
from abc import ABC, abstractmethod
from typing import List, Optional, Dict, Any
class BaseMemory(ABC):
    """Abstract interface for agent memory systems."""

    @abstractmethod
    async def add(
        self,
        content: str, metadata: Optional[Dict[str, Any]] = None
        ) -> None:
        """Store new content in memory."""
        pass

    @abstractmethod
    async def query(self, query: str, limit: int = 10) -> List[str]:
        """Retrieve relevant memories based on query."""
        pass

    @abstractmethod
    async def get_context(self, max_items: int = 10) -> List[str]:
        """Get recent/relevant context for LLM prompt."""
        pass
```

这里的 BaseMemory 接口为 3 个关键操作提供抽象：第一，add() 存储新信息；第二，query() 基于查询检索相关记忆；第三，get_context() 获取用于提示词增强的近期或相关上下文。反过来，这意味着我们设计的任何智能体都可以利用 get_context() 返回用于增强提示词的数据结构。

这一设计中值得反思的一些重要决策包括：

**上下文 vs 记忆**：AgentContext 管理当前会话状态（消息、临时数据），而 BaseMemory 提供跨会话的持久存储（用户偏好、学到的事实、长期知识）。

**应用管理的存储**：开发者调用 memory.add() 存储信息——成功的结果、用户偏好、对话摘要。框架然后通过 get_context() 将此存储的记忆注入智能体的提示词，这可能使用简单的近期过滤或语义相似性搜索等复杂检索策略。智能体接收此上下文，但不控制存储或检索什么。

**检索增强的上下文**：在准备提示词时，智能体调用 memory.get_context()，它执行复杂的检索逻辑，从简单的近期过滤到语义相似性搜索。

**通向 RAG 实现的路径**：query() 方法为检索增强生成提供了基础。应用可以在此接口背后实现向量数据库、语义搜索或知识图谱，同时保持智能体代码不变。

AgentContext 在智能体执行期间管理当前会话状态，包括对话消息、请求元数据（user_id、session_id）和用于编排的共享状态。与提供跨会话持久存储的 Memory 不同，AgentContext 是瞬态的，通常在主要交互之间重置。AgentContext 实现为可序列化的 Pydantic 模型，支持无状态的智能体执行——任何服务器都可以处理恢复请求，而无需在内存中维护会话状态——这是可扩展 Web 部署的关键设计。瞬态会话状态（AgentContext）与持久知识（BaseMemory）之间的这种分离，既实现了响应式的对话流，也实现了跨会话的持久学习。

### 4.7.5 智能体记忆集成

以下是智能体在执行期间如何使用记忆：

```python
async def _prepare_llm_messages(
    self,
    task_messages: List[Message]
    ) -> List[Message]:
    """Prepare context with memory integration."""
    system_content = self.instructions

    # Memory provides relevant context through get_context()
    if self.memory:
        context = await self.memory.get_context(max_items=5)
        if context:
            system_content += f"\n\nRelevant context:\n{'\n'.join(context)}"

    return [
        SystemMessage(content=system_content),
        *self.message_history,
        *task_messages
    ]
```

BaseMemory 接口可以扩展以支持不同的存储和检索策略。这种架构将检索策略与智能体执行分离，实现复杂的记忆系统，同时保持智能体接口干净一致。

对于开发和测试，我们从一个简单的内存实现开始。ListMemory 类将记忆存储在列表中，并自动管理容量：

*代码清单 4.23：ListMemory 初始化与存储*

```python
class ListMemory(BaseMemory):
    """Simple in-memory list-based memory storage."""
    def __init__(self, max_memories: int = 1000):
        self.memories: List[MemoryContent] = []
        self.max_memories = max_memories
    async def add(
        self,
        content: MemoryContent
    ) -> None:
        """Add new memory, removing oldest if at capacity."""
        self.memories.append(content)
        # Remove oldest memories if over capacity
        if len(self.memories) > self.max_memories:
            self.memories = self.memories[-self.max_memories:]
```

add() 方法（代码清单 4.23）接受包含内容和可选元数据的 MemoryContent 对象，在达到容量时自动淘汰最旧的记忆。这种 FIFO 方法确保记忆系统保持在资源限制内。

对于检索，query() 方法执行简单的文本匹配来查找相关记忆：

*代码清单 4.24：ListMemory query 实现*

```python
    async def query(
        self,
        query: str,
        limit: int = 10
    ) -> MemoryQueryResult:
        """Simple text-based search in memory contents."""
        query_lower = query.lower()
        matching_memories = []
        for memory in reversed(self.memories):  # Search newest first
            if query_lower in memory.content.lower():
                matching_memories.append(memory.content)
                if len(matching_memories) >= max_results:
                    break
        return matching_memories
```

搜索（代码清单 4.24）按逆序遍历记忆（最新的优先），并执行不区分大小写的子串匹配。虽然简单，但这种方法对小型记忆集效果良好，并为测试提供可预测的行为。

最后，get_context() 方法为提示词增强提供近期记忆：

*代码清单 4.25：ListMemory 上下文检索*

```python
    async def get_context(self, max_items: int = 10) -> List[str]:
        """Get most recent memories for context."""
        recent_memories = (
            self.memories[-max_items:] if self.memories else []
        )
        return [memory.content for memory in recent_memories]
```

这个简单实现（代码清单 4.25）返回最近的记忆，但更复杂的实现可以利用不同的存储后端：

- **基于向量的语义记忆**：使用嵌入和向量相似性搜索查找上下文相关的记忆
- **基于图的知识记忆**：将事实存储为实体和关系，实现复杂的知识检索
- **混合记忆系统**：组合多种策略（近期性 + 语义相似性 + 显式知识）

## 4.8 智能体自管理的记忆

我们刚刚探索的 BaseMemory 接口提供应用管理的存储——开发者调用 memory.add() 存储信息，应用代码通过检索策略将相关上下文注入提示词。但如果智能体需要直接控制自己的记忆呢？考虑一个发现关键 bug 模式的代码审查器。它应该主动存储该模式、在知识库中组织它，并在未来的审查中检索它。

这就是智能体自管理的记忆：智能体通过工具显式地读取、写入和组织自己的持久知识，而不是被动接收应用提供的内容。这种方法遵循 Anthropic 上下文管理工作所记录的模式，其中智能体使用基于文件的操作跨会话积极策展其知识库。

### 4.8.1 记忆即工具

我们可以通过创建一个包装文件操作的工具来实现智能体自管理的记忆。MemoryTool 扩展 BaseTool，为智能体提供基于文件的记忆系统，让它们可以按需创建目录、存储文档和检索信息。与应用代码自动查询的 BaseMemory 不同，MemoryTool 要求智能体显式调用它——智能体决定何时检查记忆、存储什么以及如何组织信息：

*代码清单 4.26：创建带记忆工具的智能体*

```python
from picoagents.tools import MemoryTool
# Create memory tool with file-based backend
memory_tool = MemoryTool(base_path="./agent_memory")
# Agent explicitly uses memory through tool calls
agent = Agent(
    name="code_reviewer",
    model_client=model,
    tools=[memory_tool],
    instructions="""You are a code reviewer.
ALWAYS check memory first:
  memory(command="view", path="/memories")
Store important patterns:
  memory(command="create",
         path="/memories/bugs/pattern_name.md",
         file_text="...")"""
)
```

智能体现在将记忆视为一个可以查询和更新的外部系统，就像调用数据库或 API 一样。框架处理工具执行，但智能体控制存储什么以及何时存储。

### 4.8.2 跨会话学习

智能体自管理的记忆实现了跨对话持续的学习。让我们看看代码审查器如何从一个会话学习，并在下一个会话中应用这些知识。

在第一个会话中，智能体遇到一个竞态条件 bug：

*代码清单 4.27：会话 1：智能体发现并存储一个 bug 模式*

```python
code_with_bug = '''
self.results = []
for future in futures:
    self.results.append(future.result())  # RACE!
'''
response = await agent.run(
    f"Review this code:\n```python\n{code_with_bug}\n```"
)
```

当智能体分析此代码时，它识别出竞态条件并采取行动记住它。智能体使用 memory(command="view", path="/memories") 检查其记忆，然后创建一个描述该模式的新条目：

```python
memory(
    command="create",
    path="/memories/bugs/race_condition.md",
    file_text="Thread safety: shared state mutations \
        in concurrent code can cause race conditions...")
```

现在，在一个全新的对话会话中，我们重置智能体的上下文并呈现类似的代码：

*代码清单 4.28：会话 2：智能体将学到的模式应用于新代码*

```python
agent.context = AgentContext()  # Reset context - new session
similar_code = '''
async def fetch_all(self):
    for coro in asyncio.as_completed(tasks):
        self.responses.append(result)  # RACE!
'''
response = await agent.run(
    f"Review this code:\n```python\n{similar_code}\n```"
)
```

会话之间，智能体的对话上下文完全重置，但其记忆持续存在。当智能体在新会话中用 memory(command="view", ..) 检查记忆时，它检索到之前存储的 race_condition.md 文件，并立即识别出新代码中的相同模式。尽管从未见过这个特定的 fetch_all 函数，智能体应用其学到的竞态条件知识来识别 bug。

### 4.8.3 记忆操作

MemoryTool 提供六个镜像文件系统命令的操作。这些使智能体能够构建和维护结构化的知识库：

```python
# View directory or file
memory(command="view", path="/memories")
memory(command="view", path="/memories/bugs/race.md")
# Create new file
memory(command="create",
       path="/memories/patterns/singleton.md",
       file_text="Singleton pattern notes...")
# Edit existing file
memory(command="str_replace",
       path="/memories/bugs/race.md",
       old_str="shared state",
       new_str="shared mutable state")
# Insert at specific line
memory(command="insert",
       path="/memories/notes.md",
       insert_line=3,
       insert_text="New observation\n")
# Delete file or directory
memory(command="delete", path="/memories/old_notes.md")
# Rename or move
memory(command="rename",
       path="/memories/temp.md",
       new_path="/memories/archive/temp.md")
```

这些操作让智能体完全控制其知识组织。智能体可以为不同的 bug 类型创建目录，将过时的模式移到归档区，或在学习新变体时更新模式。

### 4.8.4 安全考虑

由于智能体可以执行文件操作，MemoryTool 包含路径验证以防止安全问题：

```python
class MemoryBackend:
    def _validate_path(self, path: str) -> Path:
        """Prevent directory traversal attacks."""
        # Resolve to absolute path
        full_path = (self.base_path / path).resolve()
        # Ensure path stays within base directory
        try:
            full_path.relative_to(self.base_path)
        except ValueError:
            raise ValueError(
                "Access denied: path outside memory"
            )
        return full_path
```

此验证阻止了试图访问指定记忆目录之外文件的 ../../../etc/passwd 之类的尝试。所有记忆操作都保持在基础路径内沙箱化。

### 4.8.5 在记忆方法之间选择

应用管理记忆与智能体自管理记忆之间的选择归结为控制与便利。框架管理的记忆（BaseMemory）给你便利——开发者通过 memory.add() 存储信息，应用代码使用语义相似性或近期过滤等策略自动检索和注入相关上下文。智能体自管理的记忆（MemoryTool）给智能体控制权——它们通过显式工具调用决定存储什么、何时检索以及如何组织其知识库。

当你想要自动的上下文增强、而不给智能体存储决策权时，使用应用管理的记忆。当智能体需要积极策展和组织自己的知识时，使用智能体自管理的记忆。两种方法可以共存——智能体可能将应用管理的记忆用于对话历史，同时使用智能体自管理的记忆来组织学到的模式。

## 4.9 为控制与可观测性添加智能体中间件

能力越大，责任越大。现在我们有了一个可以使用模型生成文本、或使用工具采取行动（可能产生意外副作用）的智能体，拥有确保安全受控使用的机制非常重要。这就是中间件概念的用武之地。中间件拦截流经智能体的单个操作（模型调用和工具执行）。当智能体准备调用 LLM 或执行工具时，这些操作首先经过中间件链。链中的每个中间件都有机会检查即将发生的事情，可能修改输入，并决定是继续还是完全阻止该操作。

![图 4.3：智能体中间件](images/p162_0.png)

*图 4.3：智能体中间件在执行前后拦截操作。没有中间件（上），请求直接从用户流向智能体再到响应。有中间件（下），拦截器可以在流水线的每个阶段验证输入、阻止恶意请求、脱敏敏感数据或记录结果。*

### 4.9.1 中间件在实践中如何工作

当你在初始化期间向智能体传递中间件时，智能体将其核心操作包装在这些拦截器中。执行期间发生的事情如下：

1. **模型调用拦截**：在调用 self.model_client.create() 之前，智能体将请求路由通过中间件
2. **工具调用拦截**：在执行 tool.execute() 之前，智能体将请求路由通过中间件
3. **链执行**：每个中间件可以检查操作、修改输入/输出，或终止链

中间件接收关于正在发生的事情的完整上下文：操作类型（"model_call" 或 "tool_call"）、智能体名称、当前上下文和正在处理的数据。最重要的是，每个中间件获得将要调用的实际函数，使其对是否继续以及如何继续拥有完全控制权。

### 4.9.2 BaseMiddleware 接口

为了标准化中间件的工作方式，我们定义一个所有中间件必须实现的通用接口。中间件提供三个在操作不同阶段执行的方法：

```python
from abc import ABC, abstractmethod
from collections.abc import AsyncGenerator
from typing import Any, Union
class BaseMiddleware(ABC):
    """Abstract base class for middleware."""
    @abstractmethod
    async def process_request(
        self, context: MiddlewareContext
    ) -> AsyncGenerator[
        Union[MiddlewareContext, AgentEvent], None
    ]:
        """Process before the operation executes."""
        yield context  # Must yield context to proceed
    @abstractmethod
    async def process_response(
        self, context: MiddlewareContext, result: Any
    ) -> AsyncGenerator[Union[Any, AgentEvent], None]:
        """Process after completion."""
        yield result
    @abstractmethod
    async def process_error(
        self, context: MiddlewareContext, error: Exception
    ) -> AsyncGenerator[Union[Any, AgentEvent], None]:
        """Handle errors from the operation."""
        raise error
```

每个方法都是一个异步生成器，产出其结果而不是返回它。这种设计让中间件在处理期间可以通过在产出最终上下文或结果之前产出多个值来发出事件（日志、指标、批准请求）。

process_request() 在任何模型调用或工具执行之前运行。通过抛出异常来阻止可疑请求；通过在产出上下文之前产出 AgentEvent 对象来发出可观测性事件。

process_response() 在成功操作后运行，你可以在其中过滤输出或记录计时。process_error() 通过重试逻辑或回退响应处理失败。

下面是一个安全中间件的具体示例。我们从定义检测恶意输入的模式开始：

*代码清单 4.29：安全中间件初始化*

```python
class SecurityMiddleware(BaseMiddleware):
    """Blocks malicious input before it reaches the model."""
    def __init__(self):
        self.malicious_patterns = [
            r"ignore.*previous.*instructions",
            r"system.*prompt.*injection",
            r"\\x[0-9a-f]{2}",  # Hex encoding attempts
            r"<script.*?>.*?</script>",  # Script injection
        ]
```

这些模式（代码清单 4.29）检测常见的攻击向量，如提示词注入尝试、十六进制编码技巧和脚本注入。现在我们实现请求拦截：

*代码清单 4.30：安全中间件请求处理*

```python
    async def process_request(self, context):
        """Block malicious requests."""
        if context.operation == "model_call":
            for message in context.data:
                if hasattr(message, "content"):
                    for pattern in self.malicious_patterns:
                        if re.search(
                            pattern,
                            message.content,
                            re.IGNORECASE
                        ):
                            raise ValueError(
                                "Blocked malicious input"
                            )
        yield context
```

当中间件（代码清单 4.30）检测到危险模式时，它立即抛出异常。恶意输入永远不会到达模型，不会进行昂贵的 API 调用，问题内容也不会进入你的遥测日志。这道安全屏障在威胁到达系统之前阻止它们，为你的智能体应用创建第一道防线。

### 4.9.3 智能体如何使用中间件

在内部，智能体将其核心操作路由通过中间件链。具体来说，我们在 Agent 类实现中包装模型调用和工具执行：

```python
# Model call routed through middleware chain
async for item in self.middleware_chain.execute_stream(
    operation="model_call",
    agent_name=self.name,
    agent_context=self.context,
    data=llm_messages,
    func=lambda msgs: self.model_client.create(
        msgs, tools=tools
    ),
):
    if isinstance(item, ChatCompletionResult):
        completion_result = item
    else:
        yield item  # Forward middleware events
# Tool execution routed through middleware chain
async for item in self.middleware_chain.execute_stream(
    operation="tool_call",
    ...
):
    # Same pattern: collect result, forward events
```

execute_stream() 方法将每个中间件作为异步生成器流水线按顺序处理。每个中间件可以产出事件（日志、批准请求），然后产出最终上下文或结果。这种流式设计支持分布式追踪、内容过滤和性能监控，而不会使核心智能体实现变得杂乱。

### 4.9.4 真实世界的中间件应用

让我们探索一些你可能在生产应用中实现的实用中间件。

**日志记录与可观测性**：在生产中，你需要对智能体在做什么有可见性。日志中间件可以捕获每次模型调用的输入、输出和计时数据。这在调试智能体为何做出某些决定或衡量系统性能时至关重要。

```python
class LoggingMiddleware(BaseMiddleware):
    """Log all agent operations."""
    async def process_request(self, context):
        context.metadata["start_time"] = time.time()
        print(f"[{context.agent_name}] "
              f"Starting {context.operation}")
        yield context
    async def process_response(self, context, result):
        elapsed = time.time() - context.metadata["start_time"]
        print(f"[{context.agent_name}] "
              f"{context.operation} done in {elapsed:.2f}s")
        yield result
    async def process_error(self, context, error):
        print(f"[{context.agent_name}] "
              f"{context.operation} failed: {error}")
        raise error
```

以下是我们如何将此中间件传递给智能体：

```python
from picoagents import Agent, LoggingMiddleware
from picoagents.llm import OpenAIChatCompletionClient
# Create agent with logging middleware
agent = Agent(
    name="assistant",
    description="A helpful assistant for answering questions",
    model_client=OpenAIChatCompletionClient(model="gpt-4.1-mini"),
    instructions="You are a helpful assistant.",
    middlewares=[LoggingMiddleware()]  # Uses default logger
)
# Execute task - middleware automatically logs operations
response = await agent.run("What's 2+2?")
print(f"Response: {response.messages[-1].content}")
```

执行时，中间件捕获所有带时间戳的操作：

```
[assistant] Starting model_call
[assistant] Completed model_call in 0.82s
Response: 2 + 2 = 4.
```

**安全与内容过滤**：在处理用户生成内容或敏感领域的应用中，你需要防护栏。安全中间件可以在输出到达用户之前，扫描模型输出中的个人身份信息（PII）、不当内容或政策违规。此中间件可以完全阻止有问题的响应，或通过移除敏感信息来净化它们。

作为示例，我们可以实现一个从模型输出中检测并脱敏 PII 的中间件。我们可以定义一个简单的基于正则表达式的 PII 检测器，并在中间件中使用它：

```python
from picoagents import Agent, PIIRedactionMiddleware
from picoagents.llm import OpenAIChatCompletionClient
# Create agent with PII protection
agent = Agent(
    name="customer_service",
    description="Customer service agent with PII protection",
    model_client=OpenAIChatCompletionClient(model="gpt-4.1-mini"),
    instructions="Process customer information.",
    middlewares=[PIIRedactionMiddleware()]
)
# Process message containing sensitive data
response = await agent.run(
    "Customer John Doe called from 555-123-4567 about "
    "order confirmation sent to john@example.com"
)
print(f"Response: {response.messages[-1].content}")
```

中间件自动检测并保护敏感信息：

```
Input: Customer John Doe called from 555-123-4567
       about order confirmation sent to john@example.com
Response: Customer John Doe called from the redacted phone number
          regarding an order confirmation sent to the redacted
          email address. How would you like me to assist with
          this information?
```

**速率限制与成本控制**：LLM API 调用可能很昂贵，一些用户可能滥用你的系统。速率限制中间件跟踪每个用户或会话的使用情况，并可以阻止超出定义配额的请求。这对于暴露在互联网上的应用尤为重要，你需要控制运营成本。

```python
from picoagents import Agent, RateLimitMiddleware
from picoagents.llm import OpenAIChatCompletionClient
from datetime import datetime
# Create agent with aggressive rate limiting for demo
agent = Agent(
    name="limited_assistant",
    description="Rate-limited assistant for cost control demo",
    model_client=OpenAIChatCompletionClient(model="gpt-4.1-mini"),
    instructions="You are a helpful assistant.",
    middlewares=[
        RateLimitMiddleware(max_calls_per_minute=3)  # Only 3 calls/min
    ]
)
# Make multiple rapid requests with timestamps
for i in range(5):
    timestamp = datetime.now().strftime("%H:%M:%S.%f")[:-3]
    try:
        response = await agent.run(f"Question {i+1}: What is {i}+{i}?")
        print(f"[{timestamp}] Request {i+1}: \
            Success - {response.messages[-1].content[:40]}...")
    except Exception as e:
        print(f"[{timestamp}] Request {i+1}: Rate limited - {e}")
```

时间戳清晰地展示了速率限制的实际效果。注意请求 4 如何花费近一分钟（59.58s），因为中间件强制执行了每分钟 3 次调用的限制：

```
[20:02:05.317] Request 1: Success - 0 + 0 = 0...
[20:02:05.682] Request 2: Success - 1 + 1 = 2...
[20:02:06.156] Request 3: Success - 2 + 2 = 4...
[20:02:06.517] Request 4: Success (59.58s) - 3 + 3 = 6...  # Rate limited!
[20:03:06.101] Request 5: Success - 4 + 4 = 8...
```

**审计与合规**：在受监管的行业中，你需要记录 AI 系统的每个决策。审计中间件可以捕获智能体操作的完整轨迹——收到什么输入、做出什么决定、生成什么输出——并以合规就绪的格式存储。这创建了不可变的审计轨迹，可以由合规工具分析或导出到 OpenTelemetry 等可观测性平台。

## 8.1 为什么智能体应用与众不同

在构建之前，让我们回顾一下为什么智能体应用可能需要与传统 Web 应用不同的架构。

当你使用 picoagents WebUI 或 ChatGPT 或 Claude 的 Web 界面等工具时，响应你的查询（例如"巴黎的天气怎么样？"）你可能会看到文本逐词出现——分块地。传统 Web 应用不是这样工作的——它们显示加载旋转器，然后显示完整结果。智能体应用则不同，它们通常涉及生成长文本，穿插着可能需要一段时间的工具调用。这需要一种不同的用户体验方法。

任务运行几分钟或几小时，而不是几秒。用户不能盯着旋转器等待智能体研究主题、调用多个工具并综合结果。他们需要看到进度：模型生成的文本/代码/图像/音频、正在运行的工具，以及返回的结果。

智能体协调需要可见性。当多个智能体一起工作时（见第 2 章），用户需要看到它们的对话和交接。哪个智能体在发言？它们贡献了什么？它们如何协调？

一些智能体需要任务中途的输入。智能体在继续之前可能需要澄清或批准。UI 必须在任务运行期间处理双向通信。

## 8.2 智能体 Web 应用的两个组成部分

每个智能体 Web 应用——无论技术选择如何——都有两个协同工作的主要组成部分：**后端**（处理所有智能体执行和 API 逻辑）和**前端**（提供用户界面）。

![智能体应用的两个部分](images/p292_0.png)

*智能体应用由两部分组成：处理智能体执行的后端 API，以及允许用户提供查询并查看结果的前端 UI。*

### 8.2.1 后端组件：智能体执行与 API

后端涵盖在服务器上运行的一切：智能体逻辑、API 端点和通信协议。它由两个集成的部分组成：

#### 8.2.1.1 智能体执行逻辑

这部分包含你的 AI 逻辑，使用我们在前面章节开发的相同智能体模式：

```python
# From Chapter 4 - the core agent logic
weather_agent = Agent(
    name="weather_assistant",
    instructions="Help users check weather",
    model_client=OpenAIChatCompletionClient(
        model="gpt-4.1-mini"),
    tools=[get_weather]
)
async for event in weather_agent.run_stream(
    "What's the weather in Paris?"
):
    print(event)
```

**关键特征**：此逻辑纯粹专注于智能体实现，独立于它如何暴露给用户。相同的智能体代码可以从多个界面运行——命令行、Web、移动应用或 Slack 机器人。虽然我们在本书中使用 PicoAgents，但你可以在这里使用任何智能体框架：AutoGen、LangChain 或自定义代码。

#### 8.2.1.2 API 与通信组件

要通过 Web 界面运行智能体，我们需要一种接受用户输入（例如"What's the weather?"）并在智能体工作时流式返回更新的方式。此 API 组件通过在 Web 服务器（智能体运行的地方）与用户界面之间实现通信协议来实现这一点。协议的选择对提供使智能体交互感觉响应灵敏的流式、实时更新至关重要：

```python
# Example: FastAPI with SSE streaming
@app.post("/chat/stream")
async def chat_stream(request: ChatRequest):
    # Bridge: Convert agent events to HTTP stream
    async def event_generator():
        async for event in weather_agent.run_stream(request.message):
            yield f"data: {event.model_dump_json()}\n\n"
    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

> **技术栈推荐**
>
> 智能体应用使用 FastAPI。其异步原生设计能很好地处理流式模式——没有线程复杂性，通过 Pydantic 自动进行请求/响应序列化，以及内置的 API 文档。FastAPI 是生产就绪的，拥有成熟的 ASGI 生态：开发时用 Uvicorn 部署，生产时用 Gunicorn + Uvicorn 工作者，并与 nginx、Docker 和云平台集成。我用 Flask（对流式传输来说过于同步）、Express（样板代码更多）和 Django（对大多数智能体 API 来说大材小用）构建过智能体应用。FastAPI 更适合智能体所需的异步流式模式。
>
> 流式传输坚持使用 Server-Sent Events。SSE 使用简单的 HTTP 连接提供从服务器到客户端的单向流式传输——正是你需要的进度更新、Token 流式传输和工具执行可见性。WebSocket 增加了你很少需要的双向复杂性，而 HTTP 轮询对实时更新效率低下。FastAPI + SSE 的组合以最小的基础设施复杂性为你提供响应式智能体 UI 所需的一切。

### 8.2.2 前端组件：用户界面

前端渲染智能体响应并捕获用户输入。它消费后端 API，并向用户呈现连贯的体验：

```javascript
// Example: Vanilla JS consuming SSE
const response = await fetch('/chat/stream', {
    method: 'POST',
    body: JSON.stringify({ message: userInput })
});
const reader = response.body.getReader();
while (true) {
    const { done, value } = await reader.read();
    if (done) break;
    // Parse and render events
    displayAgentResponse(value);
}
```

**关键特征**：前端知道如何渲染事件和捕获用户输入，但不需要理解智能体内部——它只消费后端 API。

### 8.2.3 为什么这种分离很重要

这两个组件是独立可替换的。表 8.1 总结了每个组件如何独立替换：

*表 8.1：智能体应用中的组件独立性允许你更换后端框架或前端技术，而不影响系统的另一部分。*

| 组件 | 你的选择 | 独立性 |
| --- | --- | --- |
| 后端 | 智能体框架：PicoAgents、AutoGen、LangChain；API：FastAPI+SSE、Express+WebSocket、Flask+轮询 | 更换框架或协议而不改变前端 |
| 前端 | React、Vue、Streamlit、原生 JS | 更换而不改变后端逻辑 |

这意味着你可以：

- 从原生 JS 开始，稍后升级到 React（相同后端）
- 从 FastAPI 切换到 Express（相同前端）
- 在 Web、移动和 CLI 中使用相同的智能体（不同的前端实现）

### 8.2.4 构建智能体 UI 的两种方法

你可以通过两种方式构建这些组件：

**Python 原生框架**如 Streamlit 和 Chainlit 让你仅使用 Python 定义后端和前端。编写智能体逻辑，添加一些框架特定的装饰器，你就有了一个可工作的 Web UI。非常适合快速原型和内部工具。

**从零构建**给你完全的控制。你实现自己的 API 端点并选择前端技术——原生 JavaScript、React、Vue 或任何其他框架。这种方法需要更多代码，但能实现生产应用必不可少的自定义用户体验。

选择取决于你的约束：开发速度 vs 定制需求、团队专长，以及你是在构建内部工具还是面向客户的产品。

## 8.3 Python 原生框架

Python 原生框架完全消除了前端开发。你用 Python 编写智能体逻辑和 UI，框架处理 HTTP 端点、流式传输和浏览器渲染。

两个框架主导这一领域，各自针对不同的用例进行了优化。**Streamlit** 提供广泛的数据可视化组件，特别适合分析仪表盘和数据驱动的智能体界面。相比之下，**Chainlit** 专注于对话式 AI 应用，提供带原生流式支持的内置聊天界面，非常适合聊天机器人风格的智能体。

```python
# Streamlit - agent interface in ~10 lines
import streamlit as st
from picoagents import Agent
st.title("News Analysis Agent")
if prompt := st.chat_input("Enter news topic"):
    with st.chat_message("assistant"):
        response = agent.run(prompt)
        st.write(response)
# Chainlit - conversational interface
import chainlit as cl
from picoagents import RoundRobinOrchestrator
@cl.on_message
async def handle_message(message: cl.Message):
    async for event in orchestrator.stream_events(message.content):
        await cl.Message(content=event.message, author=event.agent).send()
```

**优点**：无需前端专长（仅 Python）、快速原型（几分钟得到可工作的 UI）、内置流式传输和聊天组件、低维护（框架处理更新）。

**局限**：定制受限（框架范式限制设计）、复杂交互的性能问题、不太适合需要精良 UX 的面向客户应用。

**使用时机**：构建内部工具、创建演示或原型、团队缺乏前端开发者、简单交互模式满足需求。

表 8.2 比较 Python 框架与从零构建之间的权衡：

*表 8.2：Python 框架支持快速原型但定制有限，而从零构建以开发时间和前端专长需求为代价提供完全控制。*

| 因素 | Python 框架 | 从零构建 |
| --- | --- | --- |
| 开发速度 | 几分钟得到原型 | 数天到数周 |
| 定制 | 受框架限制 | 完全控制 |
| 前端专长 | 无需（仅 Python） | 必需 |
| 最适合 | 内部工具、演示 | 生产应用、自定义 UX |

团队通常从 Python 框架开始进行快速验证，然后随着需求演进将高价值应用迁移到自定义解决方案。

> **框架选择**
>
> 对于生产应用，考虑从零构建。Streamlit 等 Python 框架对原型和内部工具效果良好，但当你需要自定义流式模式、复杂状态管理或特定 UX 流程时，往往会超出它们的限制。本章的模式展示如何构建你确切需要的东西，不受框架约束。

## 8.4 从零构建完整的智能体 Web 应用

在以下小节中，我们将用约 200 行代码构建一个最小但完整的智能体 Web 应用。构建时，我们将在实用的地方实现 3.4 节的 UX 原则——具体是可观测性（实时显示智能体动作）和能力发现（引导用户走向可靠任务）。你可以在 PicoAgents 仓库的 examples/app/ 中找到完整的工作示例。

### 8.4.1 项目结构

```
examples/app/
├── backend/
│   └── app.py
└── frontend/
    └── index.html
```

智能体逻辑定义在 backend/app.py 中——就是我们一直在使用的同一个天气智能体。你可以先创建这个文件夹结构和每个文件的空版本。

### 8.4.2 后端实现

要实现后端服务器，我们将使用 FastAPI 库创建带多个 Web 端点的 Web 应用后端。Web 端点的目标是通过 Web 协议暴露你的智能体，使我们的 Web 界面等其他实体可以调用该端点。

首先我们导入 FastAPI 并定义我们的智能体：

```python
# backend/app.py
from fastapi import FastAPI
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
app = FastAPI(title="Minimal Agent Web App")
def get_weather(location: str) -> str:
    """Get weather for a location."""
    return f"Weather in {location}: Sunny, 72°F"
# Create our agent
weather_agent = Agent(
    name="weather_assistant",
    description="A weather assistant",
    model_client=OpenAIChatCompletionClient(model="gpt-4.1-mini"),
    instructions="Help users check weather using the get_weather tool",
    tools=[get_weather],
)
```

接下来，我们定义一个可以接收请求（例如，巴黎的天气怎么样）、将其传递给我们的智能体，然后返回响应流的 Web 端点。

```python
class ChatRequest(BaseModel):
    message: str
async def stream_agent_events(message: str):
    """Stream agent execution as Server-Sent Events."""
    async for event in weather_agent.run_stream(
        message,
        stream_tokens=True):
        # Format as SSE: "data: " prefix + JSON + double newline
        yield f"data: {event.model_dump_json()}\n\n"
@app.post("/chat/stream")
async def chat_stream(request: ChatRequest):
    """Handle chat requests with streaming responses."""
    return StreamingResponse(
        stream_agent_events(request.message),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
        },
    )
```

在上面的代码片段中，首先，我们设置 FastAPI 创建一个接受 HTTP 请求的 Web 服务器。这里的关键函数是 @app.post("/chat/stream") 路由定义，它处理智能体与外部调用方（例如 Web 界面）之间的实际连接。当用户发送消息时，此函数将其传递给 weather_agent.run_stream()，将每个智能体事件转换为 Server-Sent Events 格式（SSE 协议），并实时流式传输回浏览器。@app.post("/chat/stream") 装饰器创建用户连接以与智能体聊天的 HTTP 端点。

SSE 格式优雅简单——每个事件格式化为 data: \<json\>\n\n，这是浏览器原生理解的标准协议，无需特殊库。我们设置 stream_tokens=True 使智能体在 Token 生成时逐个发出，创建你在 ChatGPT 中看到的熟悉的"打字"效果。

```bash

export OPENAI_API_KEY=your-key-here
# In one terminal

# In another terminal
```

### 8.4.3 前端实现

现在我们有了后端 API，可以继续创建一个让用户与此端点交互的 Web 界面。我们将其分解为两个逻辑部分：首先建立连接并接收流，然后解析和渲染事件。

```javascript
// frontend/index.html (connection setup)
async function sendMessage() {
    const message = inputEl.value.trim();
    // Add user message to UI
    addMessage(message, 'user');
    // Create empty assistant message for streaming
    currentMessage = addMessage('', 'assistant');
    // Fetch with POST to /chat/stream
    const response = await fetch('http://localhost:8000/chat/stream', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ message }),
    });
    // Read SSE stream
    const reader = response.body.getReader();
    const decoder = new TextDecoder();
    let buffer = '';
```

第一部分处理用户交互并建立流式连接。当用户输入消息时，我们立即在聊天界面中显示它，并为智能体的响应创建空占位符。关键洞见是预先创建助手消息——这给了我们一个在 Token 流入时更新的对象，创造那种特有的"打字"效果。然后我们向我们的后端端点发出 POST 请求，而不是等待完整响应，我们获得一个 reader 让我们在数据到达时处理。buffer 变量将帮助我们处理部分数据——网络数据包并不总是与完整事件对齐。

```javascript
    // frontend/index.html (event processing)
    while (true) {
        const { done, value } = await reader.read();
        if (done) break;
        // Decode chunk
        buffer += decoder.decode(value, { stream: true });
        // Process complete SSE messages (separated by \n\n)
        const lines = buffer.split('\n\n');
        buffer = lines.pop(); // Keep incomplete message
        for (const line of lines) {
            if (line.startsWith('data: ')) {
                const event = JSON.parse(line.slice(6));
                // Handle different event types
                if (event.content && event.role === 'assistant') {
                    // Streaming token - append to current message
                    currentMessage.textContent += event.content;
                } else if (event.event_type === 'tool_call_started') {
                    // Show tool execution
                    addMessage(`🔧 Calling ${event.tool_name}...`, 'thinking');
                }
            }
        }
    }
}
```

上面的第二部分处理实际的流式数据处理。我们从服务器读取到达的数据块，将字节解码为文本，并添加到缓冲区。SSE 协议将事件定义为以 data: 开头并以双换行符（\n\n）结尾的行，因此我们按该模式分割。微妙之处在这里：我们从分割数组中弹出最后一个元素并保留在缓冲区中。为什么？因为网络数据包可能只携带半个事件——分割会将其拆成碎片。通过将不完整的部分保留在缓冲区中，我们确保它与下一个块组合形成完整事件。

一旦我们有了完整事件，就解析 JSON 并相应更新 UI。当我们收到助手的内容时，将其直接追加到我们之前创建的消息——这创造了文本逐 Token 平滑出现的效果。当我们看到工具调用开始时，添加视觉指示器，让用户理解智能体正在采取行动——实现 3.4.3 节的可观测性原则。前端不需要理解智能体推理或工具执行逻辑——它只需要知道如何渲染不同的事件类型。这种分离意味着你的后端智能体可以变得任意复杂——使用多个工具、调用其他智能体或实现复杂推理——而无需更改前端。前端只消费事件并适当渲染，保持智能体逻辑与用户界面之间的干净分离。

### 8.4.4 添加能力发现

为了实现能力发现原则（3.4.1 节），我们添加预设提示词，引导用户走向智能体处理良好的任务。这在用户首次遇到界面、不知道该问什么时特别重要。

首先，创建带示例提示词的容器：

```html
<div class="preset-prompts" id="presets">
    <p>Try these examples:</p>
```

然后添加点击时填充输入字段的按钮：

```html
    <button class="preset-btn"
            onclick="usePreset('What is the weather like in Paris?')">
        What is the weather like in Paris?
    </button>
    <button class="preset-btn"
            onclick="usePreset('Tell me about the weather in Tokyo')">
        Tell me about the weather in Tokyo
    </button>
    <button class="preset-btn"
            onclick="usePreset('How is the weather today?')">
        How is the weather today?
    </button>
</div>
```

预设在第一封消息后消失，一旦用户理解智能体的能力，界面保持干净。这种简单的模式——在空状态显示 2-3 个示例提示词——帮助用户发现智能体能做什么，而不会被文档淹没。

### 8.4.5 添加可中断性

智能体任务可能运行几分钟或几小时，消耗 API 资源和成本。可中断性原则（3.4.4 节）要求让用户在需要时中止执行。虽然 SSE 只从服务器向客户端发送数据，我们可以通过检测客户端何时关闭 HTTP 连接来实现取消。

该模式有三个部分：(1) UI 中的停止按钮，(2) 前端在点击时关闭 HTTP 连接，(3) 后端检测到关闭的连接并停止智能体。浏览器提供内置的 AbortController API 用于取消 HTTP 请求——当你调用 abort() 时，连接立即关闭。这实现了任务取消（4.3 节），让用户控制长时间运行的操作。

**前端**：创建 AbortController，将其 signal 传递给 fetch()，并在用户点击停止时调用 abort()：

```javascript
// Create abort controller when starting request
abortController = new AbortController();
fetch('/chat/stream', {
    method: 'POST',
    body: JSON.stringify({ message }),
    signal: abortController.signal  // Enable cancellation
});
// Toggle Send button to Stop while streaming
if (loading) {
    sendBtn.textContent = 'Stop';
    sendBtn.onclick = () => abortController.abort();
}
```

**后端**：当客户端关闭连接时，Python 的异步运行时抛出 GeneratorExit。我们捕获此异常并使用 PicoAgents 的 CancellationToken 停止智能体：

```python
from picoagents import CancellationToken
async def stream_agent_events(
    message: str,
    cancellation_token: CancellationToken
):
    try:
        async for event in weather_agent.run_stream(
            message,
            stream_tokens=True,
            cancellation_token=cancellation_token  # Pass to agent
        ):
            yield f"data: {event.model_dump_json()}\n\n"
    except (GeneratorExit, asyncio.CancelledError):
        # HTTP connection closed - stop agent execution
        cancellation_token.cancel()
        raise
```

CancellationToken 通过智能体流水线传播，立即停止 LLM 调用和工具执行。

## 8.5 从原生 JavaScript 到 React

最小应用使用原生 JavaScript——非常适合学习 SSE 流式传输和理解核心模式。但当状态管理变得复杂时，原生 JavaScript 变得具有挑战性。想象在数十个组件中跟踪对话历史、多个智能体会话、打字指示器、错误状态和工具执行状态。原生 JS 需要手动状态同步——忘记更新一个变量就会导致 bug。

生产级智能体 UI 需要你在 ChatGPT 或 Claude 中看到的能力：带复制按钮的语法高亮代码块、平滑的流式动画、工具调用的条件渲染，以及跨设备的响应式布局。最小应用有约 50 行 JavaScript 用于基本聊天。带多智能体编排、会话管理和丰富工具显示的生产 UI 将有 500 多行原生 JS——难以维护。

现代框架解决这些问题。存在几个优秀选项：**React** 提供最大的生态和广泛的文档，**Vue** 提供更平缓的学习曲线和优秀的文档，**Svelte** 编译为高度优化的原生 JavaScript，**Angular** 为企业应用提供全面的框架。所有这些框架都提供适合智能体 UI 的基于组件的架构、声明式渲染和状态管理解决方案。

> **智能体 UI 使用 React**
>
> 我推荐智能体 UI 使用 React。是的，Vue 更容易学习，Svelte 性能更好，但 React 的生态主导地位对智能体应用更重要。你会找到更多用于语法高亮、Markdown 渲染和实时流式传输的库。更重要的是，当你调试复杂的智能体状态或需要扩展 UI 时，LLM 和 AI 编码助手对 React 代码的表现显著更好——它们在训练期间见过的 React 示例多得多。这种实际优势胜过理论上的框架优点。

PicoAgents WebUI 使用 React，因为它处理多种实体类型（智能体、编排器、工作流）、复杂的会话管理、丰富的工具执行可视化和编排模式显示。

好消息是：**后端保持不变！** API 组件（FastAPI + SSE）不关心前端是原生 JS 还是 React。一旦你用原生 JS 理解了模式，升级到 React 只是让 UI 代码更容易管理。

## 8.6 WebSocket 与 Server-Sent Events：选择你的流式传输策略

智能体应用需要前端和后端之间的实时通信。存在两种主要方法：**WebSocket**（双向、持久连接）和 **Server-Sent Events**（基于 HTTP 的单向流式传输）。

这两种协议之间的选择常常被误解。决定用户体验的是应用设计，而不是协议本身。设计良好的 SSE 应用对用户来说可以感觉和 WebSocket 一样响应灵敏，同时扩展起来要容易得多。

根本的权衡不在于协议——而在于你在哪里管理复杂性：在应用代码中还是在基础设施中。两种方法都可以支持用户任务中途提供反馈的交互式智能体，但它们处理这种反馈的方式不同，这决定了你在哪里付出复杂性成本以及你的应用如何扩展。

**WebSocket** 保持持久连接，状态在整个对话期间存在于内存中。用户反馈发生在同一连接上（同步），提供简单的应用逻辑，但需要带会话亲和的复杂基础设施。

**SSE + 上下文管理**流式传输进度，然后保存对话上下文，并在交互之间关闭连接。用户反馈通过同一端点以不同的请求类型发生（异步），需要应用级上下文管理，但支持简单、无状态的基础设施。

关键洞见是：**用户不关心底层协议**。他们关心及时获得响应和看到进度。无状态 SSE 应用可以提供与 WebSocket 完全相同的用户体验。考虑这个时间线：

```
# User starts a task at 9:00 AM
POST /chat/stream {"message": "Analyze our deployment and fix any issues"}
# Agent investigates, calls tools, streams progress
# Agent needs approval for sensitive operation, saves context, closes stream
# User reviews at 2:30 PM (5+ hours later)
POST /chat/stream {"approved": true, "session_id": "abc123"}
# Agent loads context, continues exactly where it left off
# User sees immediate response as if agent "remembered" everything
```

对用户来说，这感觉与持久 WebSocket 连接完全相同。智能体"记住"了整个对话，无缝地继续推理，并提供预期的响应。但在幕后，5 个多小时的等待期间没有消耗任何资源。

**WebSocket 实现**保持连接打开，智能体状态在内存中：

```python
@app.websocket("/ws")
async def agent_websocket(websocket: WebSocket):
    await websocket.accept()
    conversation_state = []  # Lives in memory
    while True:
        user_input = await websocket.receive_json()
        # Process and respond immediately
        async for event in agent.run_stream(
            user_input,
            context=conversation_state):
            await websocket.send_json(event.model_dump())
```

这种方法对实时协作功能、游戏场景，或当你有不可序列化的状态（如已加载的 ML 模型）时效果良好。然而，它需要会话亲和——每个用户必须保持在同一个服务器实例上，如果服务器宕机，所有连接都会断开。

**SSE + 上下文管理**通过无状态的请求-响应循环处理相同的交互：

```python
@app.post("/chat/stream")
async def chat_stream(request: ChatRequest, session_id: str):
    # Load conversation context
    context = await session_manager.get_or_create(session_id)

    if request.message:
        context.add_message(UserMessage(content=request.message))
    elif request.approved is not None:
        # Handle approval response through same endpoint
        context.add_approval_response(approved=request.approved)
    async def event_generator():
        async for event in agent.run_stream(context.messages):
            yield f"data: {event.model_dump_json()}\n\n"
        # Save updated context when stream ends
        await session_manager.save(session_id, context)
    return StreamingResponse(event_generator(), media_type="text/event-stream")
```

这种无状态设计支持 WebSocket 无法高效支持的工作流：审批工作流（智能体等待用户审查数小时/数天）、后台处理（用户离线时智能体继续工作）、多设备连续性（对话在设备之间无缝移动）和成本敏感操作（智能体在昂贵的 LLM 调用之间休眠）。

表 8.5 总结 WebSocket 与带上下文管理的 SSE 之间的关键区别：

*表 8.5：WebSocket 提供真正的双向实时通信，但需要会话亲和并消耗持久内存，而带上下文管理的 SSE 以无状态基础设施实现相同的用户体验，水平扩展并支持延迟数小时或数天的异步工作流。*

| 因素 | WebSocket | SSE + 上下文管理 |
| --- | --- | --- |
| 用户体验 | 实时双向 | 感觉实时，实际异步 |
| 基础设施 | 需要会话亲和 | 标准负载均衡 |
| 资源使用 | 持久内存消耗 | 仅处理期间使用资源 |
| 异步工作流 | 有限（连接超时） | 完全支持（小时/天级延迟） |
| 可扩展性 | 垂直（更大的服务器） | 水平（更多服务器） |

大多数应用在需要扩展之前，可以在单服务器部署上运行数月，但当你确实需要扩展时，架构选择就很重要了。基于 SSE 的应用可以在标准负载均衡器后添加服务器实例，无需特殊配置——任何服务器都可以处理任何请求，因为上下文按交互获取/保存。基于 WebSocket 的应用需要会话亲和配置以确保用户保持在同一个服务器实例上，为交互能力增加基础设施复杂性。

> **实用建议**
>
> 大多数智能体应用从 SSE + 上下文管理开始。无状态设计支持 WebSocket 根本无法高效支持的异步工作流，同时提供相同的响应式用户体验。你的应用将水平扩展、随处部署，并支持审批延迟和后台处理等高级工作流。
>
> 只有当你对活动执行期间的实时双向通信有特定需求（如协作编辑）或需要维护不可序列化的状态时，才选择 WebSocket。

> **云部署策略**
>
> 从托管平台上的容器化部署开始——具体是 Google Cloud Run、AWS ECS 或 Azure Container Instances。这些服务处理扩展、健康检查和部署，同时抽象基础设施复杂性。使用 SSE 流式传输（我推荐的方式），标准负载均衡器和 CDN 集成无需额外配置即可工作。
>
> Serverless 函数看似有吸引力，但对智能体应用效果不佳。大多数智能体任务运行时间超过 15 分钟的函数限制，冷启动会破坏用户期望的响应感。GPU 实例只有在你运行本地 LLM 推理时才重要，但在达到大规模之前，OpenAI 等 API 服务对大多数应用更具成本效益。

## 8.7 部署与扩展考虑

大多数智能体应用从简单开始，并根据实际使用情况逐步扩展。

### 8.7.1 从简单开始：单服务器部署

大多数智能体应用从单服务器部署开始——这完全没问题。你可以用单台服务器以良好性能服务数百个并发用户。容器编排和高级扩展模式的复杂性只在你成长时才变得必要。

从使用 Docker 和 docker-compose 的基本容器化开始。这提供跨环境的一致性和简化的部署：

```dockerfile
# Multi-stage Dockerfile for agent application
FROM node:18-alpine AS frontend-build
WORKDIR /app/frontend
COPY frontend/package*.json ./
RUN npm install
COPY frontend/ .
RUN npm run build
FROM python:3.11-slim AS backend
WORKDIR /app
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY backend/ .
COPY --from=frontend-build /app/frontend/dist ./static
EXPOSE 8000
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

对于初始部署，带 docker-compose 的单服务器设置能有效处理中等负载：

```yaml
# docker-compose.yml for simple deployment
version: '3.8'
services:
  agent-app:
    build: .
    ports:
      - "80:8000"
    environment:
      - OPENAI_API_KEY=${OPENAI_API_KEY}
      - DATABASE_URL=${DATABASE_URL}
    volumes:
      - agent_data:/app/data
    restart: unless-stopped
  redis:
    image: redis:alpine
    volumes:
      - redis_data:/data
    restart: unless-stopped
volumes:
  agent_data:
  redis_data:
```

只有当你有了需要复杂性的具体证据时才添加——监控显示连接限制、响应时间退化或当前设置无法处理的功能需求。

### 8.7.2 何时扩展到单服务器之外

当你看到具体症状时，你会知道是时候扩展了：响应时间退化、连接限制被触及，或服务器在并发智能体执行中挣扎。不要过早优化——有证据时再扩展。

你的流式协议选择（8.6 节涵盖）从根本上决定你的扩展路径。基于 SSE 的应用可以在标准负载均衡器后添加服务器实例，无需特殊配置。基于 WebSocket 的应用需要会话亲和配置以确保用户保持在同一个服务器实例上。

对于大多数智能体应用，AWS ECS、Azure Container Instances 或 Google Cloud Run 等云容器编排平台处理扩展、健康检查和部署，同时抽象基础设施复杂性。使用 SSE 流式传输，标准负载均衡器和 CDN 无需额外配置即可工作。

## 8.8 练习

既然你理解了智能体 Web 应用的工作原理，尝试这些练习来加深理解。每个都基于我们之前创建的最小应用。

**练习 1：用事件可见性增强 UI**

最小应用显示基本消息和工具调用，但智能体生成许多其他事件类型。修改前端以显示额外事件，如思考步骤、工具结果和完成状态。添加一个"清除对话"按钮重置聊天界面。考虑如何视觉上区分不同的事件类型——也许使用不同的颜色、图标或可展开的详细部分。

**练习 2：添加多个工具并观察协调**

用简单天气函数之外的额外工具扩展你的智能体。例如，添加计算器工具、网络搜索工具或文件读取工具。测试需要按顺序使用多个工具的查询（"巴黎的天气怎么样，72°F 换算成摄氏度是多少？"）。观察 UI 如何显示智能体在不同工具调用之间的协调。此练习揭示工具可用性如何影响智能体行为，以及为什么清晰的工具执行可见性对用户很重要。

**练习 3：使用 AgentContext 实现对话历史**

当前的最小应用独立处理每个请求——智能体不记得之前的消息。PicoAgents 提供 AgentContext 用于管理对话历史，但我们的最小示例尚未使用它。修改后端，为每个会话创建和维护 AgentContext 对象，存储在内存中（使用以会话 ID 为键的字典）。处理请求时，将新消息和现有上下文都传递给 agent.run_stream(task=message, context=session_context)。智能体将自动用对话历史更新 context.messages。你需要：(1) 生成会话 ID（可以使用从前端发送的 UUID），(2) 为每个会话检索或创建上下文，(3) 将更新的上下文传递给后续请求。此练习演示 PicoAgents 如何将智能体逻辑（无状态）与对话状态（通过上下文管理）分离，遵循 PicoAgents WebUI 中使用的相同模式（参见 _sessions.py 作为参考）。

**练习 4：用工具批准添加成本感知的委托**

使用 4.13 节的工具批准机制实现 3.4.2 节的成本感知行动委托原则。添加一个具有后果的工具（如 send_email 或 delete_file），并使用 @tool(approval_mode="always_require") 装饰器配置它执行前需要批准。当智能体尝试使用此工具时，暂停执行并在 UI 中显示一个批准对话框，展示工具名称和参数。用户可以批准或拒绝，智能体相应恢复。这需要：(1) 将工具标记为需要批准（4.13 节展示了模式），(2) 在前端流中检测 ToolApprovalRequest 事件，(3) 显示带批准/拒绝按钮的批准 UI，(4) 通过新请求发送批准响应以继续执行。此练习演示第 4 章的人在回路模式如何与 Web UI 集成，让用户控制具有后果的行动。

**练习 5：生产考虑**

在部署你的智能体 Web 应用之前，解决三个关键生产问题：(1) **身份验证**——为你的 FastAPI 端点添加 API 密钥验证或 OAuth 以控制访问，(2) **可观测性**——遵循 4.10 节的模式集成 OpenTelemetry，跨部署跟踪智能体操作、API 成本和性能，(3) **速率限制**——使用 FastAPI 中间件（如 slowapi）限制每个用户的请求并防止滥用，因为智能体应用可能进行许多昂贵的 LLM 调用。这些不是智能体特有的挑战——它们是适用于任何生产 API 的标准 Web 应用关注点。

## 8.9 小结

- **实时流式通信是智能体应用必需的**，因为它们长时间运行、多步骤的本质。基于你的具体用例需求，选择 WebSocket 进行双向交互式工作流，或 Server-Sent Events 进行单向进度监控。
- **第 3 章的三条 UX 原则直接转化为实现**：可观测性（实时流式传输智能体事件）、能力发现（引导用户走向可靠任务的预设提示词）和可中断性（通过 AbortController + CancellationToken 取消）。这些模式使智能体 UI 在 AI 不可预测性的情况下仍可预测和可控。
- **SSE 的单向数据流不阻止取消**：通过在客户端关闭 HTTP 连接时捕获 GeneratorExit，我们通过 CancellationToken 在智能体流水线中传播取消，停止 LLM 调用和工具执行。此模式为长时间运行的任务节省资源，无需 WebSocket 的复杂性。
- **后端架构需要智能体库与流式基础设施之间的集成**。FastAPI 为 WebSocket 和 SSE 实现都提供异步支持，SSE 提供更简单的部署和水平扩展。
- **前端开发需要处理流式智能体数据和复杂状态管理的特定模式**。React 的组件架构和状态管理适合构建可视化多智能体协调模式的响应式界面。
- **框架选择取决于用例和约束**。Streamlit 擅长快速原型和数据驱动的内部工具，Chainlit 提供带内置流式传输的优化对话界面，而自定义 React 解决方案为生产应用提供最大控制。
- **流式传输选择决定部署复杂性**。SSE 支持带标准负载均衡的无状态部署，而 WebSocket 需要会话亲和和更复杂的基础设施。大多数应用最初使用单服务器 SSE 部署效果良好，只有证据显示需要时才扩展——连接限制、响应时间问题或实时双向交互需求。
- 构建有效的智能体应用需要理解实时多智能体协调的独特挑战，并为你的具体需求选择正确的工具。本章涵盖的模式和架构为创建响应式、可扩展的智能体体验提供了基础，让你的多智能体系统为用户带来活力。

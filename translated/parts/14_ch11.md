# 第 11 章　优化多智能体系统

本章涵盖：

- 优化什么、何时优化，以及如何确定优化工作的优先级
- 生产多智能体系统的十个常见失败模式及应对每个模式的具体策略
- 两级优化框架：智能体系统参数 vs 模型级参数
- 使用评估驱动的迭代系统化改进多智能体系统表现

## 11.1 引言

到这里，你应该已经熟悉智能体（第 4 章）、常见的多智能体模式（第 2 章）以及如何评估表现（第 10 章）。下一个合乎逻辑的步骤：我们如何系统化地改进表现？

当我思考优化时，我想起小时候和父亲一起修理内燃机的经历。我们修理自己的车（标致 505 和 504）以及连接到发电机用于发电的柴油发动机。我们遵循一个简单的两阶段过程：首先，让发动机运转起来作为基线；其次，迭代地观察信号（发动机声音、转速表现）并调整参数（火花塞清洁度、燃油混合比、点火正时）以实现最佳性能。

对于智能体，我们遵循同样的过程。我们有要测量的信号（第 10 章的评估指标）。我们有要调整的参数（指令、工具、编排模式）。问题是：哪些参数以最少的努力带来最多的改进？本章通过建立优化优先级框架并检查十个常见失败模式来回答这个问题——它们准确告诉你需要修复什么。这些说明大多适用于自主多智能体编排模式，错误经常源于这些系统的灵活性和自主性。

优化循环很直接：测量（运行评估）、分析（识别失败）、修改（调整参数）、验证（重新运行评估），然后重复。

![图 11.1：多智能体系统的优化循环](images/p371_0.png)

*图 11.1：多智能体系统的优化循环，展示迭代周期：测量（运行评估）→ 分析（识别失败）→ 修改（调整参数）→ 验证（重新运行评估）→ 重复。*

挑战不在于循环本身——而在于知道调整哪些参数能产生最大影响。

## 11.2 优化什么、何时优化、如何优化

多智能体系统有两个优化层级，每个需要不同的专长并提供不同的投资回报：

**模型级参数（最低层级）**：

这包括 LLM 权重、架构、超参数和训练数据。虽然重要，但优化模型级参数通常需要深入的 ML 专长和大量计算资源——通常超出应用级优化的范围。

**智能体系统参数（应用层级）**：

- **指令**：系统提示词、行为指南、任务特定方向
- **工具**：提供哪些能力（搜索、计算、文件操作）
- **记忆**：跨交互保留和检索什么上下文
- **模型选择**：GPT-4 vs GPT-3.5 vs 微调变体
- **编排模式**：工作流 vs 自主（见第 2 章）
- **终止条件**：何时停止（最大轮数、Token 限制、任务完成信号）
- **人类委托**：哪些动作需要批准（基于风险的政策）

**优化问题**：给定评估的测量结果，我们应该调整哪些参数以及如何调整？

**优化优先级——从影响最大的地方开始**：

1. **从智能体系统参数开始**：这是你用最少的努力获得最大杠杆的地方。采取由评估数据指导的迭代方法——批判性地检查失败，并得出与这些参数的相关性。

指令和工具对智能体行为有最直接的影响。当评估揭示失败时，首先检查：指令足够具体吗？智能体有正确的工具吗？在考虑模型更改或编排复杂性之前，这些简单的修复往往就能产生显著收益。

模型选择很重要——前沿模型（GPT-5、Claude 4.5）的指令遵循能力远强于较小模型。然而，当推理模型试图承担超出其设计范围的职责（例如编排器的角色）时，有时会降低多智能体系统的表现。

一旦个体智能体工作得相当好，就实验编排模式和终止条件。使用评估指标跨模式比较表现。在第 10 章（10.6.5 节）中，我们展示了对于简单推理任务，Direct-Model（9.7/10）击败了 Multi-Agent-AI（9.3/10）——多智能体开销在该特定用例中没有提供任何好处。改进终止条件（使用带对齐指令的 TaskStatusTool）显著减少了 Token 使用并提高了可靠性。

2. **最后优化模型级参数**：模型训练资源密集且需要专门专长。只有在特定条件证明合理时才追求：(1) 需要显著降低成本/延迟（小模型便宜 20-30 倍），(2) 隐私/合规原因排除第三方模型，或 (3) 智能体系统优化已达到收益递减。

典型轨迹：优化智能体系统参数直到表现趋于平稳（前沿模型通常 95%+），然后考虑在收集的执行数据上微调较小模型。我们将在 11.3.2 节涵盖何时微调合理以及实际工作流。

## 11.3 自主多智能体系统为何在生产环境中失败

在本节中，我们探讨自主多智能体系统在生产环境中失败的 10 个常见原因，以及应对每个失败模式的具体策略。在构建 AutoGen 框架并支持生产部署两年后，我观察到多智能体系统以一致、可预测的方式失败。理解这些失败模式能准确告诉你该优化什么。把它当作诊断和修复多智能体系统的检查清单。

### 11.3.1 你的智能体缺乏详细指令

**问题**：智能体由 LLM 驱动，LLM 需要仔细的提示词。模糊或不完整的指令导致不可预测的行为和糟糕的表现。

"帮助研究任务"这样的模糊指令几乎没告诉智能体如何运作。有效的指令类似于全面的职位描述，涵盖行为指南、工具选择、约束、输出格式和错误处理。我们在第 4 章（第 4 章）涵盖了指令设计——优化的关键是基于评估失败迭代地扩展指令。当智能体在特定测试用例上失败时，添加应对这些失败模式的指导。

**优化策略**：使用你的评估结果系统化地扩展指令。当智能体在特定测试用例上失败时，添加应对这些失败模式的指导。将指令视为随着你对任务的理解而演进的活文档。优秀的智能体提示词可以有数页长！

### 11.3.2 停止使用小模型（未经优化）

**问题**：模型大小之间的能力差距显著。较小的模型在指令遵循上表现急剧下降，并难以胜任多智能体协调所需的复杂推理。这创造了一个困境：前沿模型（GPT-5、Claude 4.5）提供强大表现，但成本是小模型的 20-30 倍。对于大批量生产部署，这种差异是实质性的。

**现实**：较小模型开箱即用无法匹配前沿表现。你的 Llama-7B 或 Qwen3B 模型需要大量优化或微调才能接近 GPT-4/Claude 级别的表现。但"用更大的模型"在成本约束下并不总是实际——前沿模型在大规模下比小模型贵 20-30 倍。

**解决方案**：优化轨迹通常遵循此路径：

1. 从前沿模型开始建立基线表现并理解任务需求
2. 用前沿模型优化智能体系统参数（指令、工具、编排）
3. 仅在智能体系统优化达到平稳后考虑模型级优化：
   - **路由**：将简单查询导向小模型，复杂查询导向大模型（能以 15% 的成本达到 90% 的表现）
   - **蒸馏**：在前沿模型输出上训练小模型以转移能力
   - **级联**：先尝试小模型，仅失败时升级到大模型

> **何时微调实际合理？**
>
> 优化智能体系统参数后，分析剩余的失败。两种场景证明模型级优化合理：
>
> **场景 1：参数无法修复的残余失败**。问：系统为什么仍然失败？常见原因：
>
> - **分布外问题**：你的领域涉及训练数据中罕见的知识（例如，不常见材料的化学性质、小众监管框架）
> - **反直觉的业务逻辑**：正确行为违反常见模式（例如，在你的呼叫中心，有时提前挂断客户是正确的结局）
> - **长尾边缘情况**：出现在你的业务中但很少出现在一般文本中的解决方案
>
> 这些失败表明模型缺乏领域特定的推理模式——正是微调所解决的。
>
> **场景 2：完整表现下的效率优化**。即使在 100% 准确率下，微调也可能因成本、延迟或隐私而合理。关键洞见：你的业务领域是有边界的。前沿模型携带强推理能力（需要的）加上广泛的世界知识（你的任务不需要的）。SFT 和 RL 微调帮助较小模型为你的特定领域保留推理能力，同时将容量从不使用的通用知识中重新分配。这就是为什么在你的任务上微调的 7B 模型有时可以匹配 70B 通用模型。
>
> **实际工作流**：

![图 11.2：模型优化决策框架](images/p377_0.png)

*图 11.2：模型优化决策框架。大多数团队在智能体系统调优达到 95%+ 准确率后即"完成！"。微调仅在残余领域特定失败或效率需求（成本、延迟、隐私）下合理。*

1. 在带预期输出的数据集中定义任务
2. 构建评估来量化表现（见第 10 章）
3. 迭代调优智能体系统参数——检查轨迹，问"为什么失败？"，调整提示词、工具、终止条件
4. 达到平稳期（前沿模型通常 95%+）
5. 分析残余失败——如果属于上述场景 1 或 2，继续进行微调
6. 从你优化后的系统收集执行轨迹来创建训练数据

学术工作支持这种方法。Luo et al.（Luo et al. 2025）通过自动收集执行轨迹，演示了在智能体内使用 RL 训练 LLM。然而，这仍然特定于任务（不能为所有智能体训练一次），并需要定义显式的奖励函数。

这些模型级技术需要 ML 基础设施和专长——它们是在穷尽智能体系统改进后追求的进阶优化。

### 11.3.3 你的智能体指令与你的 LLM 不匹配

**问题**：开发者常常低估模型差异。系统消息在同一模型的不同版本之间不可移植，更不用说跨不同提供商。简单更换模型却期望相似行为，是一个常见且代价高昂的错误。

考虑这条在 GPT-4 上效果良好的指令：

```python
instructions = """Analyze the data and provide insights.
Think step-by-step about patterns, then formulate
3-5 key recommendations."""
```

这在 GPT-4 强大的推理能力下可能完美运作。但在较小模型上，模糊的"逐步思考"和"提供洞察"可能产生不一致的结果。

**解决方案**：将指令视为模型特定的资产：

```python
# Model-specific instruction registry
INSTRUCTIONS = {
    "gpt-4": """Analyze the data and provide insights.
        Think step-by-step about patterns, then formulate
        3-5 key recommendations.""",
    "gpt-3.5-turbo": """Follow these exact steps:
        1. List all data points in the dataset
        2. Identify the 3 highest and 3 lowest values
        3. Check for patterns (increasing, decreasing, cyclical)
        4. For each pattern found, write one specific recommendation
        Format each recommendation as:
        - Pattern: [what you observed]
        - Recommendation: [specific action]""",
}
def create_agent(model: str):
    return Agent(
        name="analyst",
        instructions=INSTRUCTIONS[model],
        model=model
    )
```

**优化策略**：

- 为不同模型家族维护单独的指令集
- 提示词与模型选择一起进行版本控制
- 切换模型时运行 A/B 测试，而不仅在新任务上
- 使用你的评估框架验证指令更改保持表现

第 10 章的评估基础设施在这里变得关键：你可以系统化地测试模型更改是否影响你在特定任务上的表现。

### 11.3.4 你的智能体缺乏好的工具

**问题**：工具定义智能体的动作空间。智能体可靠性直接受工具质量限制。一个常见错误是构建许多通用工具，而非更少但优秀的领域特定工具，或者干脆不投资为生产用途设计工具。

**解决方案**：投资经过实战检验的工具目录。PicoAgents 提供三类内置工具，你可以用作自己生产工具的模板：

**核心工具**（通用实用程序，无外部依赖）：

- **ThinkTool** - 在复杂任务期间支持结构化推理（基于 Anthropic 的研究，显示 54% 的表现提升）
- **TaskStatusTool** - 强制带理由显式评估任务完成
- **CalculatorTool** - 安全的数学表达式求值
- **DateTimeTool** - 当前时间、解析和格式化操作
- **JSONParserTool** - JSON 解析和路径提取
- **RegexTool** - 模式匹配和文本操作

**研究工具**（信息检索）：

- **GoogleSearchTool / WebSearchTool** - 带安全域名过滤的网络搜索
- **WebFetchTool** - 从 URL 获取和提取内容（HTML、文本或 Markdown）
- **ArxivSearchTool** - 学术论文搜索
- **YouTubeCaptionTool** - 从 YouTube 视频提取字幕

**编码工具**（文件操作和代码执行）：

- **ReadFileTool / WriteFileTool** - 带工作区隔离的文件 I/O
- **ListDirectoryTool** - 目录浏览
- **GrepSearchTool** - 跨文件模式搜索
- **BashExecuteTool** - 带超时的安全命令执行
- **PythonREPLTool** - 隔离的 Python 代码执行

你可以在本书的 GitHub 仓库中探索完整实现，并查看 examples/agents/、examples/workflows/ 和 examples/orchestration/ 中的使用示例。我们在第 4 章（4.6.3 节）涵盖了工具设计和实现模式。

**生产工具的关键原则**：

1. **可靠性优于广度**：10 个优秀工具胜过 50 个平庸工具（随着工具空间增长并填满上下文，智能体会感到困惑）
2. **清晰的错误处理**：工具绝不应使智能体崩溃——返回结构化错误
3. **显式约束**：记录速率限制、数据新鲜度、失败模式
4. **重试逻辑**：为瞬态失败实现退避策略
5. **验证**：在返回给智能体之前检查工具输出

将工具开发聚焦于领域特定的业务操作，而非通用实用程序。生产智能体需要针对你特定工作流量身定制的可靠工具。

### 11.3.5 你的智能体不知道何时停止

**问题**：终止条件控制成本和可靠性。糟糕的终止逻辑导致消耗 Token 的失控进程，或放弃可解决任务的过早退出。

考虑这个常见反模式：

```python
# Ineffective: Agent never told to produce this pattern
termination = TextMentionTermination(
    text="TASK_COMPLETE"  # But agent instructions never mention this!
)
agent = Agent(
    name="research_agent",
    instructions="Research the topic and provide findings."
    # No instruction to say "TASK_COMPLETE"
)
workflow = SequentialWorkflow(
    agents=[agent],
    termination=termination
)
# This will run until hitting max_rounds or timeout!
```

**解决方案**：将终止条件与智能体能力对齐。我们在第 7 章（7.2 节）涵盖了 MaxMessageTermination、TokenUsageTermination、TimeoutTermination 和 CompositeTermination 等终止模式。更好的是，使用 TaskStatusTool 让智能体显式发出完成信号：

```python
agent = Agent(
    name="research_agent",
    instructions="""Research the topic and provide findings.
    When finished, call the task_status tool with:
    - status='complete' if all requirements met
    - status='incomplete' if you hit limitations
    - rationale explaining your assessment""",
    tools=[search_tool, task_status_tool]
)
```

**优化策略**：使用评估数据校准终止条件。跟踪如下指标：

- 成功任务完成所需的平均轮数
- 测试用例间的 Token 使用分布
- 失败模式（超时 vs 最大轮数 vs 任务完成）

开发期间设置保守限制，然后根据生产数据收紧。记住：以部分结果提前终止，胜于在发散的轨迹上浪费资源。

### 11.3.6 你使用了错误的多智能体模式

**问题**：多智能体系统存在于从显式工作流控制到自主涌现行为的谱系上（见第 2 章）。模式选择深刻影响成本、可靠性和系统行为。错误的选择浪费资源或无法提供多智能体收益。

**关键优化洞见**：更自主的模式并非固有更好——它们以可预测性换取灵活性。问题是哪种权衡匹配你的任务特征。

**第 10 章的经验证据**：

我们的综合评估（10.6.5 节）跨不同任务类型比较了 Direct-Model、Single-Agent-Tools、Multi-Agent-RoundRobin 和 Multi-Agent-AI。结果揭示清晰模式：

- **Simple-Reasoning 任务**：Direct-Model 获胜（9.7/10）vs Multi-Agent-AI（9.3/10）。多智能体开销没有提供任何好处。
- **Tool-Heavy 任务**：多智能体方法表现出色（9.2/10）vs Direct-Model（6.8/10）。工具协调证明了复杂性的合理。
- **Token 效率**：Direct-Model 使用 1 倍 Token，Multi-Agent-AI 使用 43 倍 Token。成本差异是实质性的。

**优化原则**：从可能有效的最简单模式开始。仅在评估展示明确好处时添加复杂性。设计良好的单智能体通常胜过设计糟糕的多智能体系统。

**模式选择指南**：

表 11.1 将任务特征映射到适当的模式。我们在第 2 章（第 2 章）深入涵盖了这些模式。

*表 11.1：基于任务特征的模式选择指南*

| 任务特征 | 模式 | 权衡 |
| --- | --- | --- |
| 固定、已知步骤 | 顺序工作流 | 可预测的成本、易调试、低灵活性 |
| 条件路由 | 条件/监督者 | 显式分支、有界执行 |
| 独立子任务 | 并行工作流 | 最大吞吐量、清晰的扇入/扇出 |
| 未知分解 | 基于计划的编排 | 动态规划、每步增加开销 |
| 不确定的解决路径 | AI 驱动编排 | 涌现式协作、无界成本 |

**优化策略**：

1. **用工作流做原型**：从顺序/条件模式开始
2. **用评估测量**：运行测试套件，跟踪成功率和 Token 使用
3. **识别瓶颈**：固定路径在哪里失败？
4. **选择性添加自主性**：转换特定瓶颈部分，而非整个系统
5. **验证改进**：确保复杂性换来可衡量的收益

**常见反模式**：

不要对线性任务使用 AI 驱动编排：

```python
# Anti-pattern: 3-5x cost for no benefit
expensive = AIOrchestrator(
    agents=[fetch_agent, transform_agent, save_agent]
)
# Better: Deterministic, fast, cheap
efficient = SequentialWorkflow(
    agents=[fetch_agent, transform_agent, save_agent]
)
```

生产系统通常使用混合方法：顶层协调用基于计划的编排，可预测的子任务用工作流。微软的 Magentic-One（Fourney et al. 2024）和 Anthropic 的研究系统（Hadfield et al. 2025）都展示了这种任务感知的模式切换。

### 11.3.7 你的智能体没有在学习（记忆）

**问题**：在野外看到的大多数智能体示例是无状态的——它们不保留之前交互的知识，也不随时间改进。每次对话都从零开始，重复同样的错误。

**解决方案**：实现支持学习的记忆系统。在第 4 章（4.7 节），我们涵盖了两种记忆管理方法：应用管理（开发者调用 memory.add() 存储，框架通过 get_context() 注入）和智能体自管理（4.8 节）（智能体使用记忆工具主动组织自己的知识）。两种方法都使用向量数据库进行语义搜索，并支持各种后端（ChromaDB、Qdrant、Pinecone）。

**优化考虑**：记忆增加延迟（检索）和成本（嵌入、存储）。使用评估来确定：

- 记忆对任务成功率的提升是否足以证明开销合理？
- 多少记忆会产生收益递减？
- 哪些任务从记忆中获益最多？

并非每个智能体都需要记忆。对于独立任务，无状态智能体更简单、更快。

### 11.3.8 你的智能体缺乏元认知

**问题**：长时间运行的复杂任务受益于自我反思——规划、审查进度，并识别当前方法不奏效的能力。没有元认知，智能体无法放弃受损的轨迹或在卡住时重置。

**解决方案**：通过反思循环实现元认知能力。我们在第 2 章（第 2 章）涵盖了基于计划的模式，并在第 7 章（7.5 节）实现了它。PlanBasedOrchestrator 提供内置元认知：创建初始计划（7.5.1 节）、执行步骤、每步后评估进度（7.5.2 节），并在进度不足时重新规划（7.5.3 节）。微软的 Magentic-One（Fourney et al. 2024）展示了类似的自我监控，通过其"台账"系统实现了高达 31% 的表现提升。

**优化权衡**：元认知为反思增加 LLM 调用，但可以防止在失败的轨迹上浪费计算。使用评估来衡量反思开销是否由提高的成功率证明合理。

### 11.3.9 你没有为任务建立评估

**问题**：没有评估框架，你无法理解当前表现或配置更改如何影响结果。这使优化成为猜谜游戏。

我们在第 10 章全面涵盖了评估。与优化的联系是直接的：**你无法优化你无法衡量的东西**。

**最小可行评估**：

```python
from picoagents.eval import (
    EvalRunner, ExactMatchJudge, AgentEvalTarget)
from picoagents.types import Task
# 1. Define tasks with clear expected outputs
tasks = [
    Task(
        name="weather_tool",
        input="What's the weather in Paris?",
        expected_output="Use weather API tool",
        category="tool_usage"
    ),
    Task(
        name="summarization",
        input="Summarize this article: ...",
        expected_output="concise summary",
        category="summarization"
    )
]
# 2. Create judge and runner
judge = ExactMatchJudge()
runner = EvalRunner(judge=judge)
# 3. Evaluate each configuration
scores_v1 = await runner.evaluate(
    AgentEvalTarget(agent_v1), tasks)
scores_v2 = await runner.evaluate(
    AgentEvalTarget(agent_v2), tasks)
```

### 11.3.10 你的智能体不知道何时委托给人类

**问题**：对智能体来说，所有动作看起来都平等。没有适当的风险评估，获取天气数据和转账具有相同的分量。这造成了严重的可靠性和安全关切。

**解决方案**：实现成本感知的行动委托，这是我们在 3.4.2 节涵盖的 UX 原则。行动具有不同级别的后果——如果行动包含错误或不恰当，其潜在影响。优化挑战是实现成本评估和批准机制。

**PicoAgents 实现**：

工具支持 ApprovalMode 来控制执行：

```python
from picoagents.tools import tool, ApprovalMode
from picoagents.agents import Agent
# Low-risk tool: executes immediately
@tool
def search_web(query: str) -> str:
    """Search the web for information."""
    return f"Search results for: {query}"
# High-risk tool: requires approval
@tool(approval_mode="always_require")
def send_email(to: str, subject: str, body: str) -> str:
    """Send an email to a recipient."""
    return f"Email sent to {to}"
@tool(approval_mode="always_require")
def delete_database_record(table: str, record_id: int) -> str:
    """Delete a record from the database."""
    return f"Deleted record {record_id} from {table}"
# Agent with mixed-risk tools
agent = Agent(
    name="assistant",
    model_client=model,
    tools=[search_web, send_email, delete_database_record]
)
# When agent calls high-risk tool, execution pauses
response = await agent.run(
    "Research competitors and email report to boss@company.com"
)
if response.needs_approval:
    # Agent found information and wants to send email
    # User can review and approve/reject
    approval_requests = response.approval_requests
    for request in approval_requests:
        print(f"Tool: {request.tool_name}")
        print(f"Parameters: {request.parameters}")
        # User decides: approve or reject
```

**成本分类框架**：

*表 11.2：工具风险级别与批准需求*

| 风险级别 | 特征 | 示例 | 批准模式 |
| --- | --- | --- | --- |
| 低 | 只读，无副作用 | 搜索、计算、读取文件 | NEVER（自动执行） |
| 高 | 不可逆或代价高昂 | 发送邮件、删除数据、付款 | ALWAYS（需要批准） |

**优化考虑**：人在回路增加延迟，但防止灾难性失败。权衡取决于你的领域：

- **研究助手**：大多数动作低风险，优化速度
- **客户服务**：偶尔高风险（退款），仅对这类动作要求批准
- **金融交易**：每个动作都高风险，需要批准

第 3 章的成本感知委托原则在这里成为优化关注点：平衡安全（防止灾难性动作）与速度（最小化批准摩擦）。使用评估来衡量批准政策是过于严格（>95% 批准率表明过度谨慎的标记）还是过于宽松（在测试用例中遗漏实际风险）。

### 11.3.11 附加：你可能根本不需要多智能体系统

**问题**：多智能体架构增加复杂性。多个自主协作的智能体增加了错误和可靠性问题的表面积。

在实现任何多智能体系统之前，诚实地评估你的任务是否需要这种复杂性。

**决策检查清单**：

在以下情况使用多智能体系统（详细讨论见 1.3 节）：

1. **可分解性（规划）**：任务可以分解为通向目标的明确步骤
2. **多元视角（多元专业能力）**：步骤映射到不同领域或专长领域
3. **海量上下文**：个体步骤涉及处理大量信息
4. **适应性需求（适应性解决方案）**：在采取并评估行动之前解决方案未知

**单智能体足够时**：

```python
# Don't need multi-agent for simple tasks
simple_task = "Translate this text to French"
result = await translation_agent.run(simple_task)
# Don't need multi-agent for linear, single-domain tasks
linear_task = "Summarize this 10-page document"
result = await summary_agent.run(linear_task)
```

**多智能体增加价值时**：

```python
# Complex, multi-domain research task
complex_task = """Analyze market trends for electric vehicles
in European markets, considering regulatory changes,
consumer sentiment, and competitive landscape"""
# Benefits from specialized agents:
# - Research agent: Gather data from multiple sources
# - Analysis agent: Process quantitative market data
# - Regulatory agent: Track policy changes
# - Synthesis agent: Combine insights into coherent report
result = await orchestrator.run(
    task=complex_task,
    agents=[research_agent, analysis_agent,
            regulatory_agent, synthesis_agent]
)
```

**优化原则**：从可能有效的最简单架构开始。仅在评估展示明确好处时添加复杂性。单个设计良好的智能体通常胜过设计糟糕的多智能体系统。

### 11.3.12 总结：失败模式即优化机会

这十个失败模式不仅是需要避免的问题——它们是优化机会。每个都代表一个维度的测量和系统化改进可以增强你的系统：

1. 详细指令 -> 基于失败分析迭代扩展
2. 模型能力 -> 战略性模型选择与优化（下一节）
3. 指令-模型匹配 -> 模型特定的提示词工程
4. 工具质量 -> 策展的、可靠的工具目录
5. 终止条件 -> 数据驱动的阈值校准
6. 模式选择 -> 经验性的模式比较
7. 记忆与学习 -> 战略性记忆实现
8. 元认知 -> 反思循环设计
9. 评估基础设施 -> 所有优化的基础
10. 人类委托 -> 基于风险的批准策略

第 10 章的评估框架支持跨所有这些维度的系统化改进。

## 11.4 小结

优化多智能体系统需要迭代的纪律：通过评估衡量表现、识别失败点、调整参数，并验证改进。关键是知道将优化工作聚焦在哪里能产生最大影响。

- **两级优化框架**：多智能体系统有智能体系统参数（指令、工具、记忆、模型选择、编排模式、终止条件、人类委托）和模型级参数（权重、架构、训练数据）。智能体系统优化以最少的努力提供最大的杠杆。模型级优化（微调、RL 训练）需要 ML 专长和大量资源——仅在智能体系统优化达到收益递减或特定条件证明合理时（成本降低、隐私需求）追求。
- **优化优先级**：从智能体系统参数开始。指令和工具对行为有最直接的影响。模型选择很重要（前沿模型有更好的指令遵循），但推理模型可能降低多智能体协调中的表现。编排模式选择至关重要——我们第 10 章的评估显示 Direct-Model（9.7/10）在简单任务上胜过 Multi-Agent-AI（9.3/10），Token 成本低 43 倍。仅在评估展示明确好处时添加复杂性。
- **十个生产失败模式**：多智能体系统以可预测的方式失败。每个失败模式代表一个优化机会：指令不足（基于评估失败迭代扩展）、模型能力不足（战略性选择）、指令-模型不匹配（维护模型特定提示词）、工具质量差（策展经过实战检验的目录）、终止不明确（将条件与智能体能力对齐）、编排模式错误（通过评估进行经验比较）、缺少记忆（在有益处的地方战略性实现）、缺乏元认知（基于计划的反思循环）、没有评估基础设施（基础需求）和人类委托不明确（基于风险的批准政策）。
- **评估基础**：你无法优化你无法衡量的东西。第 10 章的评估基础设施支持所有优化活动——它识别失败模式、验证改进，并支持系统化迭代。没有评估，优化成为猜谜。

优化是一种持续的纪律，而非一次性活动。从可能有效的最简单架构开始，严格衡量表现，并在评估展示明确好处时逐步添加复杂性。设计良好的单智能体通常胜过设计糟糕的多智能体系统。
